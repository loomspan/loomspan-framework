# Explicit failure handling and diagnostics — review 1

## Code Review Findings

### [P2] Apply the classification traversal bound to the original failure

- **Location:** `src/main/java/ai/loomspan/internal/core/TraceFailureMetadata.java:25`.
- **Evidence:** The candidate normalized the failure into `effective`, then passed that result to `SkillFailurePolicy.recoverable`, which normalizes again. The policy intentionally traverses at most 64 transparent wrappers. A 65–128 wrapper chain ending in `RecoverableSkillException` therefore received a second traversal allowance during recording, although the single policy call used for disposition classified the original chain as terminal. Type and exact message still came from the first normalized object.
- **Trigger:** Record a designated exception inside 65 `ExecutionException` wrappers. The focused regression failed with expected `TERMINAL`, actual `RECOVERABLE`, at depth 65. A separate source-launch reproduction with 100 wrappers printed `POLICY_RECOVERABLE=false` and `RECORDED_METADATA={classification=RECOVERABLE, exceptionType=java.util.concurrent.ExecutionException, message=context}`.
- **Impact:** Canonical diagnostics and observer/Console consumers report correction permission inconsistent with the shared policy. With null wrapper messages, the producer also emits `RECOVERABLE` plus a null `exceptionMessage`, which its strict current Go consumer rejects. The triggering depth is unusual, but bounded malformed/deep wrapper handling is explicitly in scope.
- **Recommendation:** Classify the original failure through the existing policy once per classification decision; retain the first normalized object for effective type/message.
