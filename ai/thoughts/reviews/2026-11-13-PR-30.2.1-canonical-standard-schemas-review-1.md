### [P2] Preserve BOM-aware decoding of file-backed skill documents — resolved

- **Location:** `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:402`.
- **Evidence:** The candidate replaced SnakeYAML's InputStream decoding with
  `new String(bytes, UTF_8)`. The previous loader uses `YamlUnicodeReader`, which
  recognizes UTF-8/16/32 byte order marks. A local probe loaded a UTF-16 document
  through the original byte ingress, while the candidate path rejected embedded
  NUL characters after the forced UTF-8 conversion.
- **Trigger:** A BOM-marked UTF-16 or UTF-32 skill resource accepted by the existing
  file loader.
- **Impact:** An unrelated file-encoding regression prevents skill registration.
- **Fix:** Added an internal InputStream decoding entry point using the same
  SnakeYAML Unicode reader, and routed the catalog's existing managed stream to
  it. The caller retains stream ownership. Exact decimal construction and config
  separation still occur through the same decoder.

### [P2] Add the required catalog ingress diagnostic regressions — resolved

- **Location:** `src/test/java/ai/loomspan/internal/skill/YamlSkillCatalogTests.java:245`.
- **Evidence:** The candidate had lower-level decoder tests but no added catalog
  regression for non-string keys, numeric/string key collisions or nonfinite
  values. The dedicated testing plan requires source/path assertions through the
  catalog, independently of decoder tests, even when execution is blocked.
- **Trigger:** Catalog translation of structured decoder failures changes, or
  quoted JSON field names are interpreted differently during registration.
- **Impact:** The changed authoring diagnostic boundary and positive registration
  controls lacked their explicitly required integration regression tests.
- **Fix:** Added source/path cases for numeric collisions, boolean schema keys,
  nested TypeSafe keys and nonfinite bounds/data, plus a successful quoted-key and
  quoted-nonfinite-string registration control. Their execution remains blocked
  by the authorized downstream compile boundary; they are not counted as passes.

### [P3] Keep executor config independent of BigDecimal exponent limits — resolved

- **Location:** `src/main/java/ai/loomspan/internal/serialization/YamlValues.java:29`.
- **Evidence:** The lossless first parse constructed every float as BigDecimal
  before removing config. `config: {huge: 1e9999999999}` is accepted as Infinity
  by the preserved ordinary constructor, but the candidate failed with exponent
  overflow before its separate config decode. Extremely negative exponents have
  the analogous issue despite the ordinary decoder accepting zero.
- **Trigger:** An executor config numeric literal outside BigDecimal's exponent
  range; the scope explicitly preserves ordinary configuration numeric behavior.
- **Impact:** This narrow configuration input becomes unusable solely because
  unrelated JSON-bound fields adopted a new numeric representation.
- **Fix:** Retain an unrepresentable decimal's original literal in a private
  ingress marker until config separation and JSON compatibility checking. Config
  keeps its original ordinary decoder result. JSON-bound values fail with source,
  pointer and original literal; they are never rounded or accepted as a fallback.
