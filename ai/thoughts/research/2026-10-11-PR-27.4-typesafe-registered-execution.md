## Detailed findings

### Registration, public kinds and captured declarations

`src/main/java/ai/loomspan/api/SkillKind.java:6` already contains `YAML, JAVA,
REST, TYPESAFE`. `CapabilityKind` maps its internal `TYPESAFE_SKILL` identity to
that public enum. `SkillGenerationManager.java:241` publishes the kind in
candidate validation metadata and `:527` constructs TypeSafe capability metadata.
`SkillGeneration.java:66` permits native definitions alongside YAML and REST
definitions and freezes its exact-name maps. Capability ownership is checked by
object identity against the captured generation, rather than name alone.

`YamlSkillCatalog.java:342` rejects native leaves using chat connections;
`:355` rejects chat YAML using the TypeSafe driver. Its strict native presence
check at `:461` prohibits chat/planning/output fields even when supplied with
null or false values. `YamlSkillDefinition.java:95` derives native output schema
from its captured `TypeSafeDeclaration` rather than an authored answer validator.
The declaration resolves detached per-call request values. Its fixed descriptive
schema is separate from dynamic invocation criteria.

### Direct and child execution share existing boundaries

`DefaultSkillTemplate.java:152` prepares root input through ordinary validation
and normalization; `:270` passes the captured capability, normalized input and
session into `CapabilityExecutionRouter`. Its `validate` API performs input/access
prechecks, not provider execution. `ExecutionCoordinator.java:101` obtains native
definitions from the current generation. It opens the mission frame, checks
access, then at `:154` dispatches native work before creating a chat interaction,
visible tools or planning/synthesis engine.

`MissionWorkExecutor.java:126` delegates evaluation to its existing tracked work
path. `TypeSafeExecutor.java:35` uses the binding's captured generation, native
connection and mission lifecycle. Request resolution/validation precedes
`reserveProviderAttempt`; retries send the same serialized request. Both sends
and response processing check interruption and lifecycle openness. Response usage
and evidence pass through existing state/usage owners. It extracts only readable
object-valued `answers`, serializes that complete object, and installs no schema
validation, chat synthesis or repair.

`DefaultCapabilityInvoker.java:89` accounts a nested tool call before execution.
Its binding path checks owning mission and accepted producer identity, assembles
detached input, then calls `SkillInputValidator.validateExact` with bound paths
before dispatch. Unbound fields retain ordinary normalization. The same current
session and generation flow into nested execution; there is no criteria/result
cache keyed by skill name.

### One effective schema map, two binding contracts

`SkillGenerationManager.java:301` resolves effective schemas before validating
parent output bindings. `resolveOutputSchema` at `:442` recursively inherits
forwarding schemas, detects forwarding cycles, and serializes each native
definition's generated schema through the same vocabulary serializer used for
ordinary output metadata. The resulting schema feeds tool metadata, the public
catalog and the registered inspection catalog.

`validateOutputBindings` at `:308` selects source/destination schema nodes and
checks compatibility. `selectBindingSchema` performs exact source lookup while
destination properties use existing case-insensitive matching; open/unknown
branches remain runtime obligations. `checkBindingCompatibility` at `:379`
preserves type checks, nullable-to-nonnullable rejection, enum intersection,
integer-to-number widening and nested object/array checks. It does not require
source enum inclusion or prove dynamic output values statically.

Child binding declarations are validated separately at `:294` through
`ChildInputBindingDeclarations.validate`, with receiver contracts, path and graph
rules. They do not call the producer-output compatibility comparator. Runtime
receiver-input validation remains authoritative. Binding pointer syntax remains
object-field-only; native request substitution's array traversal is separate.

`SkillGenerationManagerTest.java:43` already tests schema equality across tool,
public and registered catalogs, original YAML and opaque source label, overlap
acceptance, disjoint enum/singleton-type/number-to-integer rejection, and dynamic
Choice registration without fixed enum proof. Generic tests following `:96`
cover path/count/nullability/open-schema and integer widening behavior.

`DeclaredOutputBindingsPlanningIntegrationTest.java:23` already exercises native
selected value acceptance, overlap with actual enum rejection, missing probability
lookup, and differently cased source keys failing exact lookup. Those fixtures
use fixed Choice criteria; the generated schema does not validate native answers
before a consumer selects them.

### Existing forwarding owns completion

selected children and excluded parent output/linter declarations.

`DesignatedChildResultIntegrationTest.java:59` already includes `native` and

completion of later accepted REST work, one native call, absence of final synthesis

work. `TypeSafeSkillIntegrationTest.java:710` executes the published mixed-batch
leaf directly and as a fully bound forwarding child, asserting identical named
answers, inherited schema, forwarding event and three total HTTP requests.

## Contract classification and architecture documentation

- **Application API:** `SkillKind`, `SkillDescriptor`, `SkillTemplate`, catalog and
  reload types are in `ai.loomspan.api`; the architecture test allowlist and README
  establish deliberate support. The enum already includes TYPESAFE, README `:161`
  documents it, and the descriptor remains unchanged. `DefaultSkillCatalogTest`
  currently constructs YAML/JAVA/REST entries in its eager snapshot test.
- **Supported SPI:** `RestSkillHandler` remains the sole SPI; no native provider
  SPI or typed facade is introduced by existing native implementation.
- **Configuration and manifest contracts:** TypeSafe driver/model compatibility,
  strict native manifest grammar, source labels, binding syntax and forwarding
  rules are author-facing behavior owned by registration/runtime source and docs.
- **Persisted or serialized contracts:** Application-adapter REST/SSE, consumed
  NDJSON and MCP DTOs cross Java-to-Go-to-TypeScript boundaries. Existing consumers
  and executable fixture corpora are protected as one current release contract;
  TypeSafe source additions are already coordinated. Console exact-version marker
  policy remains unchanged; no new schema migration/legacy reader is present.
- **Ephemeral diagnostic formats:** Native trace records, derived journal and
  UI/MCP evidence retain current-run diagnostic fidelity and explicit capture
  limits. Existing `ExecutionJournalProjector` redaction remains the documented
  narrow journal/observer exception, separate from canonical traces/results.
- **Internal or accidentally exposed implementation:** Generation/coordinator,
  native declaration/client/executor, capability kinds and registered catalog
  records are implementation detail. Architecture allowlist entries `:64–66`
  classify technically public native classes without making them supported SPI.
  Spring wiring/constructors/beans do not independently create extension contracts.

The ticket expressly authorizes atomic current-consumer kind/source changes
without shims or dual formats. Existing production support reuses mission work,
binding checks, captured generations and text/location renderers. No new binding,
mission, forwarding or observation subsystem is evidenced or needed to describe
the existing path. No dead-code conclusion is established by this investigation.
