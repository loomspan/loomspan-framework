## Summary

The PR 28.1 foundation is present: `SkillExecutor`, `SkillExecutorInvocation`, separate reference-only executor registrations, shared Java discovery/invocation, and `ImmutableContainers`. Executor annotation configuration references are stored as authored strings; YAML executor declarations and namespace executor configuration are absent.

`YamlSkillCatalog` currently parses YAML into a tree, performs raw form and field checks, binds `YamlSkillManifest`, validates typed content and constructs `YamlSkillDefinition`. REST restrictions occur in raw and typed catalog checks; concurrency applicability occurs in raw, typed and definition checks. Definitions retain a copied mutable manifest behind defensive accessors, using Jackson tree conversion for copying. REST is identified from manifest field presence/value; a constructor enforces the relationship between REST and absent model execution configuration.

Startup uses strict Spring Boot `@ConfigurationProperties`; publication parses approved YAML sections and flattens their framework-owned settings into a fresh Binder. The pinned Spring YAML loader loses null/empty-container distinctions and flattens nested paths before Loomspan binding. The accepted ticket explicitly includes correcting such ingress. The existing publication parser does not receive a target namespace; the manager has that namespace when it invokes parsing. Namespace-generation ownership and path/reference binding belong to PR 28.3.

## Detailed findings

### Manifest processing and declaration presence

- `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:41` is the startup and supplied-document parser. `checkedConfigured` and `checkedSupplied` share `loadDefinition`; validation issues retain source, skill and field path. Supplied documents retain exact source labels and bytes through `YamlSkillSource`.
- At line 419, `readManifest` reads a Jackson tree and requires an object root, name, valid local identity and description. It rejects obsolete `mapping`, then calls raw TypeSafe, REST, concurrency, output binding/forwarding and allowed-child checks. `treeToValue` subsequently binds `YamlSkillManifest`; `UnrecognizedPropertyException` becomes an ordinary `unknown field` authoring error with a derived path.
- `YamlSkillManifest.java:29` has an internal `Field` enum and `EnumSet` of declared fields. Relevant setters add presence even when supplied null. Lists/maps often normalize null to empty, so the presence set is distinct from bound values. `restoreDeclaredFields` restores the exact set after copying. There are REST and TypeSafe fields, but no executor or config fields.
- `YamlSkillCatalog.java:60` defines REST-forbidden fields. `validateRawRest` at line 519 requires boolean true and rejects forbidden field presence through `root.has`. `loadDefinition` at line 334 again selects REST and repeats restrictions using the manifest presence set. REST leaves share the ordinary input-schema validator, have no model settings and receive empty evidence/children.
- `validateRawTypeSafe` at line 475 rejects declared REST, prompt, thinking/planning/concurrency/children/linter/output fields and compiles the native declaration. `YamlSkillManifest.setTypesafe` also compiles it. Typed TypeSafe processing at line 349 requires input schema/model, rejects attachment schema nodes, and requires a TypeSafe driver. Ordinary model YAML requires a model and rejects a TypeSafe driver.
- `validateRawConcurrency` at line 686 checks both explicit `planning_mode: true` applicability and boolean type. `validateConcurrency` at line 705 repeats applicability/null checks after binding. Model schema, linter, output and binding checks remain separate applicable-field validation.
- `YamlSkillCatalog.java:843` owns input-schema validation; it supports object/array/scalars plus attachment input nodes. Explicit absent input schema retains the generic input contract. Configuration domain data is not routed through this schema machinery today.
- `YamlSkillCatalog.java:759` uses `SkillIdentity.resolve` for authored references and supplies source/field diagnostics. `prepareReferences` at line 765 canonicalizes allowed children, forwarding and binding producers. `SkillIdentity.java:6` normalizes namespace case only, preserves local-name case, validates ASCII identifiers and length, and resolves local references against their owner without foreign fallback.

### Immutable definitions and copying

- `YamlSkillDefinition.java:15` owns resource, copied manifest, model execution configuration, evidence, source, child constraints and canonical identity. It exposes defensive manifest/schema/linter copies, compiled bindings and typed helper accessors.
- Its constructor at line 37 copies the manifest first. It requires exactly the current relationship between REST form and missing execution configuration and independently rejects inapplicable/null concurrency. These are concrete existing repetitions of the ticket's named rules.
- `typesafe()` at line 184 reads declaration presence; `rest()` at line 191 delegates to the declared REST boolean. There is no explicit declaration-form field. `requireExecutionConfiguration` throws for any definition without model execution settings.
- `copyManifest` at line 236 converts through a Jackson ObjectNode, detaches the authored TypeSafe tree separately, shares the immutable compiled TypeSafe declaration, and restores the original presence set. `copyValue` uses Jackson conversion for other typed schema objects. Executor-owned config does not exist in this copying path yet.
- `src/main/java/ai/loomspan/internal/util/ImmutableContainers.java:10` is PR 28.1's shared copier. `copyMap` recursively copies map keys/values and lists into insertion-ordered unmodifiable containers, retaining nulls and non-container leaves by value/identity. It does not serialize, classify content, freeze arbitrary objects or read resource bytes.
- `SkillExecutorInvocation.java:12` uses that copier for all three maps: `input`, `skillConfig`, and `executorConfig`. It also requires `skillName` and `executorConfigGenerationId`. This public record's copying semantics already cover nested nulls, containers and resource leaves in `SkillExecutorTest`.

### Real startup ingestion and Spring integration

- `LoomspanProperties.java:27` is `@ConfigurationProperties(prefix = "loomspan", ignoreUnknownFields = false)`. It is enabled by `LoomspanAutoConfiguration.java:68`, alongside execution-trace integration settings. Current fields include session, execution trace, shutdown, skills, observability, connections and models; there is no executor configuration field.
- `LoomspanProperties.afterPropertiesSet` validates connections and models. Their schemas are framework-owned. Connection reference interpretation in publication is specific to connection configuration, rather than a generic operation on arbitrary data.
- Auto-configuration is registered through `src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`. There is currently no custom PropertySourceLoader registration or startup executor data processor in main resources.
- `LoomspanAutoConfigurationTests.java:93` initializes `ApplicationContextRunner` using Spring's `YamlPropertySourceLoader` over `application-test.yml`. `LoomspanPropertiesTest` additionally tests ordinary scalar property binding and strict unknown settings. These establish current integration patterns, but do not exercise an executor subtree.
- The pinned versions in `pom.xml:54` are Spring Boot 4.1.0 and Spring AI 2.0.0, with Java release 21. Matching dependency sources are locally available under `C:/Users/mgiacomi/.m2/repository`.
- Inspected `spring-boot-4.1.0-sources.jar`, `org/springframework/boot/env/YamlPropertySourceLoader.java`: loading delegates to package-private `OriginTrackedYamlLoader`, then publishes immutable origin-tracked flattened maps.
- In that same jar, `OriginTrackedYamlLoader.constructObject` replaces an empty sequence with tracked `""`; scalar null also becomes tracked `""` through `getValue`. Its `load` invokes `getFlattenedMap(map, true, "")`. These changes occur before `LoomspanProperties` is bound.
- Inspected `spring-beans-7.0.8-sources.jar`, `org/springframework/beans/factory/config/YamlProcessor.java`: `buildFlattenedMap` recursively joins map keys with dots, indexes collections and substitutes an empty value for empty maps/collections. A literal dotted key and the corresponding nested path therefore cannot be distinguished from the flat representation alone.
- Inspected Spring Boot's `StandardConfigDataLocationResolver`: its constructor discovers `PropertySourceLoader` implementations with `SpringFactoriesLoader`; explicit file resolution selects a matching extension loader, and directory resolution enumerates loader extensions and deduplicates references. Spring Boot's `META-INF/spring.factories` registers the standard Properties and YAML loaders. This is executable dependency-source evidence about the actual ingress extension mechanism, not a claim that a custom Loomspan implementation already exists.
- Consequently, a manually populated map on properties would not establish the startup fidelity required by the ticket; the current documented ingress has already transformed those values. No downstream reconstruction of their original distinctions exists in the checkout.

### Publication parsing and namespace context

- `ExecutionConfiguration.java:6` is an allowlisted public record containing authored YAML with a one-million-character size cap. It is a transport boundary; the record does not parse or reinterpret contents.
- `ExecutionConfigurationParser.java:23` uses a duplicate-detecting YAMLMapper to decode untyped maps/lists. Only top-level `loomspan` is accepted. The section allowlist at line 29 contains connections, models, session and execution-trace.
- `parse` validates framework section keys, translates explicit connection credential-reference fields, flattens permitted settings and binds a new `LoomspanProperties` through `MapConfigurationPropertySource`. `scalar` stringifies non-container scalar values for these existing framework-owned settings. Current parsing has no executor-config handling.
- `Parsed` currently contains only properties and trace-persistence policy. Parsing receives Environment/credential-values and a reference-resolution flag, but not namespace identity. `optionalObject` treats null like omission for existing optional framework sections; that existing helper does not establish the new executor section's rules.
- `SkillGenerationManager.java:160` already holds normalized target namespace in `PreparationView`. Both `prepare` and `validate` call the parser before constructing the candidate catalog. Prepare first parses without resolving connection credentials, checks the complete declarations against captured foreign metadata, then parses again with credentials and builds independent runtime resources.
- Each parse binds fresh properties and defaults; it receives no prior-generation/startup properties to merge. This is the current basis for complete replacement behavior. Validation creates structured `<configuration>` issues from parsing failures.
- `SkillGenerationManager.initializeStartup` at line 99 creates Private default plus namespaces assigned fixed callable Java methods, all with startup settings. The current namespace enumeration does not include executor-only registrations; PR 28.3 owns that change.
- `SkillGeneration.java:20` owns immutable callable and definition maps, catalogs and runtime. Its kind check at line 71 distinguishes REST, TypeSafe and ordinary YAML. There is no executor config owner yet.
- `ExecutionRuntime.java:31` manually copies framework session, connections, models and skills settings into provider-runtime properties. No generic executor config is stored there. The accepted design expressly reserves authoritative executor configuration to the generation owner rather than a separately mutable provider-runtime copy.
- `SkillDependencyValidator.java:42` overlays candidate and captured foreign metadata; `checkAdmission` uses selected snapshot generations. Its graph checks still concern callable-child dependencies. It currently checks REST handler cardinality at line 102. `SkillGenerationManager.prepareCatalog` at line 229 constructs REST invokers and model-backed descriptors. Remaining REST runtime/API removal and executor execution integration are PR 28.3 scope.
