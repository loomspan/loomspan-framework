## Summary

Startup currently has three ingress paths. `ExecutorYamlPropertySourceLoader` reads YAML into ordinary objects and replaces one entire `loomspan.executor-config` section with an opaque `Raw` value. Spring selects the effective document/property source, and a configuration-properties converter binds that winning section. Connections retain Boot's ordinary flattened property binding and placeholder resolution. Configured skill files load later through `YamlSkillCatalog.checkedConfigured`, independently of both setting paths.

`SkillGenerationManager.initializeStartup` consumes the already-bound `LoomspanProperties`, checks the configured catalog, builds private default and Java-owned namespace generations, and captures provider/executor/skill state. No startup-local variable lookup/cache joins these ingress paths today. Publication now has candidate-local authored parsing and one memoized pass after PR 35.3. That facility is separate from startup and keeps the source/path metadata, marker keys, terminal strings and original skill declaration bytes needed by the ticket.

Existing executable tests establish executor-section replacement through profile/import precedence, preservation of ordinary Spring properties, nulls, aliases and scalar kinds, and actual startup executor delivery. The agreed field-level connection inheritance is described in the earlier handoff's temporary experiment. A committed focused test for that exact connection/profile case was not found in the scanned startup tests. The implementation and testing steps therefore need their own current proof of the complete ticket scenario.

## Current startup flow

### YAML property loading and effective executor selection

`src/main/resources/META-INF/spring.factories` registers `ai.loomspan.internal.autoconfigure.ExecutorYamlPropertySourceLoader` as a Boot `PropertySourceLoader`. It supports `yml`/`yaml` and returns `Ordered.HIGHEST_PRECEDENCE` (`ExecutorYamlPropertySourceLoader.java:17–23`). There is no repository environment postprocessor registration.

The loader opens the resource once with `YamlValues.documents`, retaining each map document. It follows Boot's treatment of empty documents for association. It then invokes Boot's `YamlPropertySourceLoader.load(name, resource)` and requires its emitted document count to match (`:24–35`). The delegated property sources carry normal Boot document names, profile/import activation properties and origin values. This code runs for individual documents before Boot selects active profile sources.

For every document containing `loomspan.executor-config`, the loader removes only that section's flattened keys, retains all other delegated values, and adds `loomspan.executor-config -> new Raw(originalSection)` in an immutable `OriginTrackedMapPropertySource` (`:37–49`). The raw value can represent invalid shapes. The comment at `:21` and converter at `ExecutorConfigurationBinding.java:18–19` deliberately leave structural validation until an effective source is bound.

`ExecutorConfigurationBinding` is fixed integration machinery imported by `LoomspanAutoConfiguration` and by the focused binding test. Its static `@ConfigurationPropertiesBinding` converter turns the opaque `Raw` into `ExecutorConfiguration.from(source.value())` (`ExecutorConfigurationBinding.java:10–19`). The converter has no Environment or lookup collaborator. An opaque whole-section value makes the winning source replace the lower executor section rather than merging namespace entries.

The loader's initial `YamlValues.documents` materializes the YAML graph into ordinary maps before delegation. `YamlValues.settings` disables non-scalar keys for that path and rejects duplicate keys (`YamlValues.java:28–47`). That is distinct from the authored facility, whose Compose path accepts authored non-scalar keys. The loader has no source/path occurrence table or retained Node graph today.

### Typed connections and ordinary Spring values

`LoomspanProperties` is `@Validated`, `@ConfigurationProperties(prefix = "loomspan", ignoreUnknownFields = false)`, and `InitializingBean` (`LoomspanProperties.java:26–28`). Its connection map is a regular nested Java configuration-properties object (`:49–50,97–106,464`). Provider settings are bound through ordinary Boot binding. Its `afterPropertiesSet()` immediately calls `validateAuthored(path -> true, path -> false)` and validates all effective connections/models (`:126–137`).

Connection checks include required driver, applicable option blocks, API-key/Vertex authentication modes, request timeout, header driver/name/value and provider retry constraints (`:137–280`). Normal nested conversion supplies `AiDriver`, `Duration`, booleans and numeric properties. Gemini accepts JSON contents at `gemini.credentials-json`, and the adapter parses service-account contents via `ServiceAccountCredentials.fromStream` (`SpringAiProviderIntegration.java:153–161,455–466`). The retired credential URI path was removed in PR 35.2.

No special connection transport or startup literal wrapper is present in the YAML loader or configuration binding class. Boot's property binder supplies a `PropertySourcesPlaceholdersResolver`. Read-only `javap -p -c` inspection of the exact locally installed Boot `4.2.0-RC2` classes confirms that `ConfigurationPropertiesBinder.getBinder()` installs that resolver, and its `resolvePlaceholders(Object)` processes `String` inputs before conversion. The exact installed `Binder` exposes constructors accepting an explicit `PlaceholdersResolver`, while the regular configuration-properties binder obtains its resolver from current property sources.

This differs from the published path. `ExecutionConfigurationParser` builds a flat `MapConfigurationPropertySource` and a plain `new Binder(...)`, then restores exact headers separately (`ExecutionConfigurationParser.java:67–94,135–150`). That binder construction does not install Boot's Environment placeholder resolver. Its normal conversion remains active, and its `BindException` message is replaced with a field name plus a fixed reason (`:155`). The parser is strict published-schema ingestion, including target namespace and restricted top-level sections. Startup properties include additional supported sections such as skills, shutdown, observability and complete execution tracing, so it is not the startup parser.

The ticket/handoff explicitly authorizes changing startup connection placeholder meaning. Values outside connections, executor data and executor-backed skill `config` retain their normal binding. Examples include `loomspan.models.*.provider-model`, skill locations, `loomspan.session`, and observability authentication properties.

### Configured skill discovery and definition capture

`LoomspanAutoConfiguration.skillGenerationManager` receives fully bound `LoomspanProperties`, a normal Environment and codecs. It takes a fixed skill-loading properties snapshot and supplies a catalog factory to the generation manager (`LoomspanAutoConfiguration.java:155–172`). The snapshot copies skill locations, connection driver identities and model catalog entries. Runtime creation consumes full effective properties through `ExecutionRuntime` and `NamedAiConnectionRegistry`.

`SkillGenerationManager.initializeStartup` runs once, both through `SmartInitializingSingleton` and from `LoomspanAiAutoConfiguration.namedAiConnectionRegistry` (`SkillGenerationManager.java:87–111`, `LoomspanAiAutoConfiguration.java:29–32`). It initializes fixed Java dependencies, obtains a catalog, and calls `checkedConfigured(true)`. It checks the default namespace with the bound executor configuration, then creates additional Java capability/executor namespaces with their namespace's selected settings. All startup namespaces have private visibility. It installs the fully built group after all preparation succeeds. Partial failure closes built generations (`SkillGenerationManager.java:90–119`). Provider runtime construction happens during `prepareCatalog` (`:246–280`).

`YamlSkillCatalog.checkedConfigured` resets the catalog, discovers resources from effective `loomspan.skills.locations`, sorts them by resource description, and loads each file (`YamlSkillCatalog.java:133–151,279–307`). Each resource is read to bytes exactly once per load, wrapped in `YamlSkillSource`, then parsed (`:310–328`). Resource descriptions are registered as diagnostic source labels. Ordinary and executor-backed skill form checks remain in the catalog. The configured path has no variable source and no resolved configuration override.

PR 35.3 added `checkedSupplied(..., trees)` for candidate use. A call-scoped `candidateTrees` map is installed and cleared in `finally` (`YamlSkillCatalog.java:154–161`). `readManifest` chooses the config override by diagnostic source, then uses `SkillDocumentValues.decode(originalText, source, mapper, resolvedConfig, configPresent)` (`:399–408`). Original declaration numbers and source bytes remain authoritative, while only executor config is replaced (`SkillDocumentValues.java:69–79`). This prevents marker keys inside config from entering JSON-bound declaration conversion. The configured-resource path does not currently supply such trees.

`SkillGenerationManager.prepareCatalog` captures the checked definitions and selected namespace executor settings in the generation (`:246–280`). The existing owner/consumer/skill invocation maps are already fed by captured definitions and namespaces. PR 35.4 does not require a new executor invocation argument or public resolver.

## Existing authored and resolution facilities

`AuthoredYamlVariables.execution(String|InputStream, source)` and `.skill(...)` use SnakeYAML Engine Compose with authored key support (`AuthoredYamlVariables.java:53–67`). They currently compose one document. The internal `Document` retains a Node root and source label. `Location` contains source and path, and `Occurrence` adds the exact name (`:28–30,70–85`). There is no line/column field in that diagnostic contract.

Execution selection covers descendants of each connection and each executor namespace, while skill selection covers `config` for executor-backed files. It does not select the top-level connection names or namespace names (`:87–104`). Keys, values and sequence items inside the selected boundary participate. Exact one-key `$var` maps reserve the marker shape, and names must be string, nonblank and unpadded (`:107–129,225–252`). Dotted and bracket-quoted paths plus `{key#i}`/`{value#i}` positions retain authored provenance.

`Document.discover`, `.staged` and `.substitute` validate selected markers. Substitution checks missing/blank results and converts callback failures to a fixed `lookup-failed` reason (`:147–172`). Every replacement is returned as one string. A supplied YAML-looking string is not reparsed. `AuthoredMap` retains variable-authored key locations, and materialization detects effective-key collisions before insertion (`:32–36,175–192`). The materializer preserves shared identity for marker-free aliases, while the bounded graph check rejects cycles and limits logical expansion (`:159–162,194–218,280 onward`). The shared bound is 1,000,000 logical values (`YamlValues.java:13,91–96`).

`PreparedCandidateVariables` owns one execution document and the supplied skill documents for a detached publication. It discovers across all selected sections, checks exact explicit-map usage and memoizes `Function<String,String>` results by distinct name before substituting execution then skills (`PreparedCandidateVariables.java:20–39,67–89`). It is package-private in `internal.skill`. Its staged unknowns/selector logic preserve decidable checks before resolution. `SkillGenerationManager.prepare` independently stages and resolves the candidate, then validates and captures the effective data (`SkillGenerationManager.java:159–174`). Startup does not instantiate this candidate.

## Open questions for implementation planning

1. Which internal representation carries each YAML document's selected authored nodes through Boot source selection, including connection field inheritance, while preserving inactive-document behavior and exact marker key/value locations? The existing loader retains only a materialized executor section, and the shared authored parser currently exposes a single-document entry point.
2. Where does startup coordination obtain the effective selected subtrees before connection validation and establish the one lookup cache shared with configured skills? The current raw converter runs during properties binding, while configured skill files load during generation startup. Other configuration properties must keep native Boot processing, including test contexts that bind `LoomspanProperties` without full Loomspan runtime.
3. How are higher-priority flattened sources, programmatic `MapPropertySource`, command-line values and system environment names reconciled with retained YAML nodes? Existing ordinary connection binding supplies those semantics. The ticket requires normal Environment lookup for variable values and field-level inheritance, so source selection and variable lookup are distinct operations to verify.
4. How does the configured catalog receive resolved config with original bytes/source metadata and existing lossless declaration behavior? The supplied-candidate override path exists, while configured-resource loading currently has no resolved tree collaborator.
5. Which final document records the artifact/revision, shared fixture, exact final test results and downstream ownership? The future handoff already contains the right coordination material, and the final committed revision is available only after completion.

These are implementation and testing choices within the agreed outcome. Current evidence identifies no product decision requiring developer assistance.
