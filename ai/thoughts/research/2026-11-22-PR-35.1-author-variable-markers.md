## Summary

Current shared YAML ingress is `YamlValues`, using SnakeYAML Engine's `Load` API with a Core schema. It immediately constructs Java scalars, maps and lists. There is no `$var` discovery or substitution implementation in checked-out Java production source. Configuration entry points subsequently enforce textual map keys or convert subtrees to Jackson nodes and typed Spring properties.

Executor configuration already has a distinct raw YAML boundary. Published execution configuration reads it before scalar flattening, startup transports it separately from Boot flattening, and skill documents separate the actual top-level `config` subtree from JSON-bound manifest data. These paths currently preserve literal executor strings and ordinary YAML scalar kinds. Existing logical alias expansion and recursion checks run before downstream traversal.

The ticket establishes a new shared marker grammar and authored path convention. The broader handoff records the same scope and syntax, while companion tickets own lookup-source selection, candidate-wide name accounting, provider schema changes and startup precedence. Go code in this repository belongs to Loomspan Console. Independent Cloud discovery is an external consumer identified by the handoff, and its implementation is outside PR 35.1.

## Detailed findings

### Raw YAML construction and resource controls

`src/main/java/ai/loomspan/internal/serialization/YamlValues.java:17` constructs SnakeYAML settings and custom scalar constructors. Explicit timestamps become strings. Ordinary configuration floats use the loader's ordinary numeric kinds, including nonfinite doubles. The skill-document variant uses `BigDecimal` for finite decimals and retains a private representation when an exponent cannot be represented by `BigDecimal`, allowing a later JSON-bound diagnostic to identify the location.

`YamlValues.java:43` rejects duplicate keys, sets the loader's collection-alias allowance to `Integer.MAX_VALUE` and code-point allowance to `Integer.MAX_VALUE`. These settings are accompanied by a separate logical expansion limit of 1,000,000 values at line 11. `read`, the stream overload, `readSkillDocument` and `documents` all call the graph check before returning constructed values (lines 51–59).

The check at `YamlValues.java:66` walks both mapping keys and values plus sequence elements. It uses identity-based tracking. An ancestor marked in progress produces a recursive-container failure. A completed shared container contributes its previously computed logical size each time it occurs, so repeated aliases are counted without exponentially traversing their graphs. The bound at line 87 rejects logical expansion above 1,000,000. Existing tests cover ordinary scalar kinds, recursive containers, duplicate mappings, preserved aliases and oversized logical expansion.

The current Java `Map` representation is the result of YAML construction. It has no filename or authored mapping-entry metadata. Collection keys can exist at this stage, whereas later consumers impose textual keys. The current `Load`-based abstraction exposes no composed-node or authored-occurrence API.

### Published execution configuration

`src/main/java/ai/loomspan/internal/skill/ExecutionConfigurationParser.java:49` reads authored YAML through `YamlValues.read`. Its `object` helper checks that all keys are nonblank strings and copies each map into a `LinkedHashMap`. The parser allows only known root and configuration section names. The `ExecutorConfiguration` subtree is extracted before provider flattening and passed through `requireTarget(targetNamespace)`.

The parser's existing credential mechanism is field-specific. `api-key-ref`, `header-refs`, `gemini.credentials-ref` and `gemini.credentials-json-ref` resolve through either `Environment.getProperty` or a supplied map. `resolveReferences=false` returns an unresolved string sentinel. Supplied-map use tracks reference names and rejects unused entries. The subsequent flat property source goes through Spring `Binder`, `LoomspanProperties.afterPropertiesSet` and session validation. Existing reference exceptions are constructed from field paths and reasons.

This is current entry-point behavior. PR 35.1's outcome assigns its replacement integration to PR 35.3, with provider literal/schema changes in PR 35.2. No existing use of the proposed `$var` contract was found.

### Startup YAML and executor configuration

`src/main/java/ai/loomspan/internal/autoconfigure/ExecutorYamlPropertySourceLoader.java:23` reads each document through `YamlValues.documents`, delegates ordinary properties to Boot's `YamlPropertySourceLoader`, and associates resulting document property sources in authored order. It replaces flattened `loomspan.executor-config` properties with an opaque `Raw` wrapper for the entire section. Other properties retain Boot behavior. The loader reports an association mismatch if the raw and delegated document counts differ.

`src/main/java/ai/loomspan/internal/autoconfigure/ExecutorConfigurationBinding.java:14` registers the fixed converter from `Raw` to `ExecutorConfiguration`. Its current wrapper contains only the constructed value. It carries no authored filename/path object and no per-field connection node representation.

`src/main/java/ai/loomspan/internal/skill/ExecutorConfiguration.java:16` requires a map of namespaces, normalizes namespace identifiers, rejects normalized duplicates, requires each namespace root to be a map, and enforces textual data keys. `requireTarget` at line 35 rejects every foreign namespace, including an empty one. `ImmutableContainers.copyMap` copies and freezes map/list graphs with identity memoization, preserving scalar leaves and shared container identity.

### Skill documents and the actual top-level config boundary

`src/main/java/ai/loomspan/internal/serialization/SkillDocumentValues.java:44` decodes the document through the exact-decimal skill reader. If the actual root map contains `config`, it reads that subtree again through ordinary `YamlValues.read` and removes it from JSON admission. It validates JSON compatibility of the remainder, creates a Jackson tree and restores a placeholder reflecting the config root's map/non-map shape. `Decoded` carries the real executor configuration separately.

The separation is tied to the actual top-level `config` key. A field named `config` within an input or output schema remains JSON-bound data. `SkillDocumentValuesTest` verifies exact decimals in those nested schemas, ordinary executor numeric kinds, timestamp behavior, malformed byte decoding, BOM-aware ingress and YAML resource controls.

`src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:388` reads this result before binding a manifest. `validateDeclarationForm` at line 480 selects executor form by the presence of `executor`, validates its textual reference and requires config to be a map. It prohibits config on model-backed forms. The catalog validates required identity and description fields and declaration applicability, removes transport placeholders, binds the remaining manifest, then copies actual config entries into a textual-keyed map at lines 432–438. Config markers used as keys would reach that textual-key check in current behavior. Other skill fields, schemas and transforms follow their existing distinct validation paths.

### Locations and diagnostics

`SkillDocumentValues.InvalidDocumentException` carries source, path and reason, with JSON Pointer paths produced by its JSON compatibility walk. The catalog converts that exception into skill authoring diagnostics. Generic malformed YAML is caught separately as `YamlEngineException` and reported at the manifest field. Execution configuration's diagnostics use dot-shaped property paths built during flattening.

The PR 35.1 convention is newly specified by the ticket. It combines identifier dot paths, JSON-quoted brackets for other string keys, sequence indices and authored entry indices for mapping keys and unresolved paired values. The existing paths above are evidence of current diagnostic boundaries, not an implementation of that new convention. The YAML value abstraction currently has no occurrence record that combines a filename with such a path.

### Tests and fixture conventions

Focused existing tests include `YamlValuesTest`, `SkillDocumentValuesTest`, `ExecutorConfigurationTests`, `ExecutionConfigurationParserTest`, `ExecutorDeclarationTests` and `ai.loomspan.autoconfigure.ExecutorConfigurationStartupTests`. `ExecutorConfigurationTests#aliasedConfigurationDoesNotExpandIntoAnExponentialContainerTree` checks shared immutable aliases. Its oversized expansion test and `SkillDocumentValuesTest#retainsDuplicateCycleAliasExpansionAndTimestampRules` protect the current logical resource limit.

`src/test/resources/skills/valid` and `invalid` contain authored YAML examples consumed through production decoders by focused tests such as `SchemaDeclarationFixturesTest`. A separate root-level `loomspan-console-fixtures` corpus demonstrates reusable JSON/NDJSON and semantic expected files consumed by Java and Go, with path resolution supporting repository-relative and sibling fixture roots. That corpus concerns Console diagnostics and does not currently contain application-variable fixtures.

The Maven project targets Java 21 and uses Surefire 3.5.2. The named public-surface architecture test is `src/test/java/ai/loomspan/architecture/LoomspanPublicSurfaceArchitectureTest.java`. Research did not run tests or establish local Maven dependency readiness.

## Open questions for implementation planning

1. The ticket defines observable grammar and paths, while the concrete internal authored-node representation and callable method shapes are unspecified. Current ingress constructs maps immediately. Planning must choose how the shared facility retains ordered mapping entries and preserves existing scalar construction and resource checks before downstream consumers.
2. Reusable fixture directory and expected-file schema have no existing variable-specific convention. Planning must define a language-neutral schema for names and all source/path occurrences, keeping the four-name worked pair distinct from the additional `header.name` case.
3. Identifier path grammar and occurrence ordering need an explicit local definition consistent with the acceptance examples. Non-string, non-marker keys can occur in raw YAML before owning validators enforce their domain restrictions, and their diagnostic addressing needs a defined internal convention.

These are ordinary implementation choices within the ticket. No developer decision is required by the current research findings.
