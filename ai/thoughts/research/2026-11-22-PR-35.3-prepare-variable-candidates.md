# Research — PR 35.3 prepared candidate variables

## Research question

Map the current staged validation, provider parsing, executor and skill configuration ingestion, generation capture and publication paths for the PR 35.3 ticket. Identify the existing shared marker facility, API contracts, executable fixtures and documentation that establish the starting behavior. This is full-profile pipeline Step 1 against the clean PR 35.2 commit `6768783`.

## Summary

`SkillReloader` already has separate Environment and copied explicit-map preparation overloads, including labeled preparation. `DefaultSkillReloader` captures a target base and external metadata before expensive work. `SkillGenerationManager.prepare` currently checks authored skill documents with an unresolved provider configuration, resolves provider references in a second configuration parse, then builds the generation using the earlier checked definitions. Map usage accounting and value lookup currently belong to `ExecutionConfigurationParser` and cover the three provider reference fields.

`AuthoredYamlVariables`, introduced by PR 35.1, independently retains YAML nodes and authored source paths, discovers markers in selected connection/executor/skill-config subtrees, and substitutes exact terminal strings with collision checks. It currently has no runtime preparation caller. Executor owner configuration, consumer configuration and skill configuration already have independent captured paths through generation ownership, admission binding and the v1 invocation. Publication performs state and freshness checks without parsing or value lookup.

The shared worked corpus establishes four names and six occurrences, including the sequence occurrence. It currently exercises discovery/substitution, and its provider field and skill declaration differ from accepted runtime syntax. Planning must account for that when using the fixture through actual preparation. No developer decision is identified by this research.

## Detailed findings

### Application boundary and source selection

- `src/main/java/ai/loomspan/api/SkillReloader.java:11` declares two staged validation overloads and six preparation overloads. The supported map signatures accept `Map<String, String>` named `credentialValues`. Labeled methods accept `publicationVersion` before documents and explicit visibility. There is no public variable resolver, SPI or invocation resolver argument.
- `src/main/java/ai/loomspan/internal/skill/DefaultSkillReloader.java:51` routes every no-map preparation to `prepareInternal` with a null map, representing Environment mode. Explicit-map overloads at lines 59–76 first require a non-null map and copy it into a `LinkedHashMap`. The map's keys and values are not normalized here.
- `DefaultSkillReloader.prepareInternal` at line 79 normalizes the target namespace, requires configuration/visibility/documents and copies the document collection. It captures a `PreparationView`, calls the manager, wraps runtime preparation failures in `SkillReloadException`, checks lifecycle again and closes a candidate rejected during that check.
- `ExecutionConfiguration` is a supported record carrying a required authored YAML string limited to 1,000,000 characters (`src/main/java/ai/loomspan/api/ExecutionConfiguration.java:6`). Its current class comment still calls this reference-only configuration despite the literal provider support added by PR 35.2.
- `SkillDocument` carries `sourceName` and authored YAML (`src/main/java/ai/loomspan/api/SkillDocument.java:4`). Catalog ingress owns source-label, duplicate-label and null-document validation.

### Current two-pass preparation and staged validation

- `src/main/java/ai/loomspan/internal/skill/SkillGenerationManager.java:148` captures the target's current ID or absence plus a copied coherent map of active namespaces under `generationMonitor`. Preparation then runs outside that monitor.
- `prepare` at line 162 first calls `ExecutionConfigurationParser.parse(..., environment, false)`, creates a fresh `YamlSkillCatalog` with those properties, parses the supplied documents and checks dependencies/configuration selections. It requires that checked set to be valid. It then reparses execution YAML using either Environment resolution or the explicit map and passes the original checked set plus the second parse's properties to `prepareCatalog`.
- `validate` at line 175 performs only the unresolved parse and checked-document/dependency path, returning `SkillValidationResult`. It never invokes the runtime factory. A thrown configuration error becomes a structured issue with source `<configuration>` and path `configuration`.
- `check` at line 190 delegates to `SkillDependencyValidator` with fixed Java capabilities, target-assigned executor registrations, external generation metadata and the target namespace's executor settings.
- `prepareCatalog` at line 237 builds capability metadata and definition maps from the checked definitions, allocates a new process-local ID and only then invokes the runtime factory. The resulting generation captures target executor settings and the label. A failure after runtime creation closes that runtime.
- Startup follows `initializeStartup` at line 90, using `checkedConfigured` and the already bound startup properties. This separate startup path is assigned to PR 35.4 by the tickets and handoff.

### Provider schema, conversion and current reference accounting

- `src/main/java/ai/loomspan/internal/skill/ExecutionConfigurationParser.java:22` permits only `loomspan.connections`, `models`, `session`, `execution-trace` and `executor-config` beneath the root. Nested allowlists cover connection options, model fields, quotas, retry policy and trace persistence.
- The parser reads ordinary YAML with `YamlValues.read`. Connection field allowlists currently accept literal `api-key`, `headers`, Gemini `credentials-json`, and the separate `api-key-ref`, `header-refs`, `credentials-json-ref` forms. Literal/reference counterparts are exclusive.
- `reference` at line 160 accepts a scalar property name. Unresolved mode returns the fixed string `unresolved-reference`. Resolved mode calls either `environment.getProperty(key)` or `supplied.get(key)` directly for each occurrence, checks null/blank, records the key in a local `used` set and returns the value. It does not share a candidate cache across occurrences or document sections.
- At line 127, the explicit map's keys must all occur in that local provider-reference `used` set. The exception says `credentialValues contains an unused reference`. Executor settings and skill config do not contribute to that set.
- Connections and models are flattened into `MapConfigurationPropertySource` and bound by a new standalone `Binder`, without an Environment placeholder resolver. Authored direct values and resolved reference values therefore use this same isolated binding path. Header maps are carried separately and assigned after binding so exact header names and null values reach validation.
- `LoomspanProperties.afterPropertiesSet` at line 125 validates connections and models. Required driver/API key, Gemini exclusive authentication modes/project/location, driver-applicable options, header token names, null header values, exact whole-millisecond request timeouts and retry constraints are owned here. The parser additionally checks positive session depth and nonnegative quotas.
- URI credential settings and loading were removed in PR 35.2. The parser accepts Gemini JSON contents, and adapter credential construction remains under `SpringAiProviderIntegration`. Tenant identity policy is assigned to Cloud in the handoff.

### Authored markers and source locations

- `src/main/java/ai/loomspan/internal/serialization/AuthoredYamlVariables.java:42` exposes internal execution and skill factories for strings and BOM-aware streams. Its reusable `Document` owns a SnakeYAML composed node tree and selected boundaries.
- Execution selection at line 68 traverses each immediate value below actual root `loomspan.connections` and `loomspan.executor-config`. Selector keys themselves lie outside traversal. Skill selection at line 63 requires the actual root to contain `executor` and the actual top-level `config` to be a mapping.
- `discover` at line 92 walks selected descendants in mapping order, keys before values, and sequence order. A marker is exactly one case-sensitive string `$var` key. The name must be a YAML string, nonblank and unpadded under the shared Java whitespace set. Ordinary multi-key maps containing `$var` continue traversal.
- `substitute` at line 117 validates all authored markers before lookup and materializes independent output containers. Returned values are exact nonblank strings and are terminal leaves. They are neither parsed as YAML nor scanned for placeholder syntax. Other nodes use shared Core-schema construction.
- The facility currently invokes the provided callback at every occurrence. Its API does not contain a shared distinct-name cache or explicit-map accounting. `discover()` supplies the names and locations needed by a candidate owner to establish those semantics.
- Key equality is checked before insertion at lines 142–155. A collision reports both original authored locations in order. Dotted/quoted key paths, zero-based list paths, and `{key#i}`/`{value#i}` locations are authored-coordinate conventions, preserved after substitution.
- `InvalidVariablesException` contains fixed reasons and authored locations. Callback exceptions become `lookup-failed`, missing returns become `missing-value`, and blank strings become `blank-value`; callback causes and supplied strings do not appear in these messages.
- Alias recursion and logical expansion are checked before discovery/materialization. Shared settings preserve the 1,000,000-node bound. `YamlValues` separately supports lossless JSON-bound numeric ingress for skill declarations. The marker facility uses ordinary YAML numeric construction throughout materialization.

### Skill configuration ingestion and fidelity

- `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:154` sets the target namespace before checking supplied documents. Each valid source label becomes a `ByteArrayResource` and `YamlSkillSource` holding the original bytes. Collection errors remain tied to source labels.

- `src/main/java/ai/loomspan/internal/serialization/SkillDocumentValues.java:42` decodes the document with lossless numeric settings for the JSON-bound portion. It separately rereads actual config with ordinary YAML settings, removes config from the JSON compatibility traversal and returns it independently. This preserves current Java numeric kinds in executor data while retaining exact decimals for schemas and other declaration fields.
- `YamlSkillCatalog.validateDeclarationForm` at line 480 permits config only on executor leaves and requires the config root to be a map. Executor references must remain textual and are qualified against the skill-owning namespace. Model/prompt/planning fields are forbidden on executor leaves by presence. Description and valid local skill name remain required.
- `YamlSkillDefinition.config()` returns the manifest's captured config (`src/main/java/ai/loomspan/internal/skill/YamlSkillDefinition.java:23`). `YamlSkillSource` continues to carry authored bytes for metadata and diagnostics. Runtime variable substitution must account for both the ordinary runtime map and retained original document provenance.

## Open questions for planning

1. What representation will staged validation use for unresolved markers while retaining decidable literal constraints, declarations, target checks and dependency checks? Current provider staging uses a fixed textual sentinel and binds/validates immediately. Whole-node markers may supply typed driver/mode fields or effective configuration keys, so the planning step must map precisely which checks can run before those values exist.
2. How will the resolved executor-config tree reach ordinary catalog config while preserving lossless numeric handling outside config and original authored bytes for diagnostics? Current `SkillDocumentValues` deliberately decodes those portions differently, and the marker facility currently materializes ordinary numeric kinds for the whole tree.
3. Which candidate owner will share distinct-name resolution and explicit-map accounting across execution plus all supplied skill documents before provider construction? Existing mechanisms expose the required names/locations, but provider parsing currently owns the value source and used set.
4. How will the worked corpus become a valid production candidate while retaining its four names, occurrence ordering and shared expected JSON? Its current discovery-only fields and declaration shape need to be accounted for in the implementation/test plan.

These are ordinary implementation planning tasks within the requested outcome. There is no unresolved external product choice or required developer question.
