## Summary

representation. YAML definitions expose canonical schemas, but reflected Java
registration still generates JSON trees, serializes them and resolves them into
`SkillInputSchemaNode`. Several downstream consumers still refer to the removed

the complete runtime and tests cannot currently execute through the normal build.

The ticket's retained Java corrections map directly to two existing classes:
`LoomspanMethodInputSchemaGenerator` and `SkillMethodBeanPostProcessor` (BPP).
Generation uses the schema mapper, binding uses the application mapper, and
parameter types are independently constructed without the concrete bean context.
Resource metadata rewriting happens after bean traversal. Container materialization
retains Resource leaves, followed by whole-container Jackson conversion. Existing
cleanup is already present on success and failure.

The ticket explicitly owns generation/effective binding and demonstrated binding
corrections. NetworkNT runtime adaptation, ordinary validation, callback ingress,
attachment handling, binding projection, output/planning integration and live
acceptance have separate downstream owners. These boundaries are material to the
verification record and do not remove this ticket's owned acceptance obligations.

## Detailed findings

### Discovery, contract selection and publication

- BPP obtains `AopUtils.getTargetClass(bean)` and uses Spring MethodIntrospector,
  merged annotations and BridgeMethodResolver to discover canonical declarations
  (`SkillMethodBeanPostProcessor.java:161`). Interface declarations are selected
  through `resolveContractMethod` (`:270`), preserving interface parameter metadata
  and rejecting incompatible multiple interface contracts or mixed Java roles.
- `registerSkillMethod` validates parameter optionality, builds the input schema,
  creates an invoker, resolves its input contract and only then inserts metadata
  into `capabilitiesByName` (`:217–240`). A generation failure therefore precedes
  publication of that capability. Registration is per method; there is no
  all-bean transaction in this method.
- `registerExecutor` (`:199`) requires one non-varargs `SkillExecutorInvocation`
  parameter. It registers an implementation reference, policy, config path and
  invocation lambda; it never calls the Java schema generator on that invocation
  record. Executors and callable skills have separate indexes and collision checks.
- `completeDiscovery` additionally verifies runtime proxy invocability and
  JSR-250 enforcement before discovery is finalized (`:66`). Canonical method and
  selected contract method remain distinct in JavaSkillInvoker calls.

### Current generated trees and resolved Java types

- `LoomspanMethodInputSchemaGenerator.generate` (`:30`) creates a Draft 2020-12
  object root with properties in method parameter order, all parameter names in
  `required`, and `additionalProperties:false`.
- Each parameter type comes from `mapper.constructType(parameter.getParameterizedType())`
  (`:41`). No target bean class reaches this call. BPP independently does the same
  construction for runtime marking (`:354`) and binding (`:538`). The inherited
  generic requirement concerns all three uses of the effective type.
- `schemaFor` (`:49`) branches on arrays/collection content and map value types,
  booleans, numeric kinds, enums, strings/time/network/path families, Object, and
  beans. A map emits `additionalProperties` as its value schema and does not inspect
  its declared key type. Bean creation introspection emits primary-member types,
  property names, all discovered properties as required, and closed objects.
- Enum choices come from `String.valueOf` (`:90`), rather than binding-side
  annotation introspection. UUID is absent from the explicit scalar branch and
  reaches bean inspection. Enabled JsonUnwrapped is not checked in this traversal.
- Object emits an empty schema (`:99`). Cycle detection tracks raw classes in an
  active `Set<Class<?>>`; a repeated active raw class emits only `type:object`
  (`:104`). Classes are removed on return, so sibling reuse is distinct from an
  active cycle. The existing test explicitly names and asserts this fallback.

### Mapper ownership, names and metadata

- Production auto-configuration supplies `codecs.applicationConversion()` and
  `codecs.schemaTree()` separately (`LoomspanAutoConfiguration.java:84`).
  `LoomspanJacksonCodecs` keeps application conversion separate from schema JSON,
  planning, YAML and trace codecs. The schema JSON mapper enables exact decimals.
- BPP's constructor (`:129`) creates the generator with the schema mapper;
  `propertyTypes` (`:638`) and `convertValue` use the application mapper.
  Consequently naming strategies and effective application mixins are visible
  on the binding side while the current generation mapper is independently configured.
- `buildInputSchema` (`:333`) mutates the generated properties in place: remove
  implementation parameter name, set contract parameter name, apply metadata,
  and rewrite runtime leaves. Required names are removed/reinserted in a shared
  array (`:385`). The ticket's swapped-name case refers to this positional loop.
- SkillParam is selected from the contract parameter, falling back to the
  implementation parameter. Nonblank description text is assigned verbatim;
  requiredness overrides generation when metadata exists (`:366`). Optional
  primitive parameters are rejected before generation (`:243`).

### Runtime leaves, conversion and cleanup

- `applyRuntimeInputSemantics` (`:404`) recognizes byte[], Resource subtypes and
  InputStream subtypes through `isRefCapableBindableType` (`:662`); otherwise it
  descends items, typed-map values and bean properties using application names.
  These are existing runtime leaves, not attachment declarations.
- This marking runs after generation. `rewriteAsRefFriendlyString` (`:457`)
  clears the schema and installs string type, generic guidance and the boolean
  runtime marker. Any description already written at that node is replaced.
- `invokeSkillMethod` (`:482`) allocates the opened-stream list and invokes
  binding and JavaSkillInvoker inside a `try/finally` whose finally closes every
  tracked stream. Conversion of Resources to strings/bytes uses try-with-resources.
  InputStream conversion records opened/passed streams for invocation cleanup.
- `convertArgument` (`:531`) directly supports Resource, byte[], InputStream and
  Resource-to-string conversion, then directly returns assignable non-container
  simple values. Otherwise it calls `materializeValue` and finally
  `objectMapper.convertValue(materializedValue, parameterJavaType)` (`:567`).
- Materialization (`:570`) leaves Resource targets unchanged; recursively prepares
  maps, lists, arrays and bean-property maps; and converts Resource payloads where
  the target is String, byte[] or InputStream. The final Jackson conversion still
  receives the whole materialized container. The retained list probe describes
  actual prior serialization of a Resource; this research did not rerun the probe
  or establish additional affected shapes.

### Canonical foundation and runtime handoff

- `StandardSchemaCompiler.compile` (`internal/schema/StandardSchemaCompiler.java:37`)
  validates the profile, bundled meta-schema and object root, initializes the
  NetworkNT validator and returns CanonicalSchema. INPUT accepts nested empty
  schemas and schema-valued map additionalProperties. Generated runtime markers
  are permitted only on input string nodes. A description-only node currently
  reaches the ordinary-type requirement; only a literally empty node takes the
  unconstrained early return. This is a source observation relevant to described
  Object acceptance, not a completed test of generated Java integration.
- `CanonicalSchema` owns immutable copied trees, provider copies and standard
  instance validation. Provider copies walk actual schema nodes and remove the
  recognized framework annotations, preserving similarly named data properties.
- `SkillInputContract` currently stores `SkillInputSchemaNode` with contract kind;
  genericObject constructs the reduced open-object node directly. Resolver parses
  generated JSON, reconstructs reduced nodes and serializes them again. Its
  `fromManifest` still accepts removed `YamlSkillManifest.InputSchemaManifest`.
- In contrast, `YamlSkillDefinition.inputSchema()` (`:159`) and outputSchema
  (`:109`) already return CanonicalSchema. Manifest schema caching and copying
  reside in `YamlSkillManifest.java:51–70`.
- `CapabilityExecutionRouter.java:62` checks access, then calls validateExact
  before coordinated execution. Java execution in `ExecutionCoordinator.java:166`
  resolves references against the capability contract and then calls the Java
  invoker or hands YAML executor input/configuration to SkillExecutorInvocation.
  A raw `CapabilityMetadata.invoker()` call alone does not perform validation.
- `RefResolver.resolveArguments` distinguishes generic recursive reference
  resolution from explicit schema traversal. Explicit traversal follows properties,
  items and typed-map values and resolves only marked/attachment leaves; ordinary
  Object and strings remain unchanged. It still consumes reduced nodes.
- The existing custom validator supports marked runtime values and JSON
  compatibility checking, but also coerces some ordinary values and treats
  required null as missing outside its exact-path exception. Replacement and
  the private NetworkNT runtime-value view belong to PR 30.2.3.

  SkillExecutorInvocation and SkillTemplate are closed-allowlist public types.
  The ticket retains their declaration model and signatures.

  wiring seams, not consumer customization contracts.

  mapper naming and YAML-owned executor input/configuration affect authors.
  No new YAML feature, annotation or schema override system is selected.

  contract data; CanonicalSchema is the newly installed internal authority.

  source and trace content fidelity remain governed by AGENTS.md. This research
  changes no diagnostics or Console transport.
