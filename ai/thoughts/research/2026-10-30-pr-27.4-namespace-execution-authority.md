## Summary

PRs 27.1–27.3 already provide a canonical `SkillIdentity`, immutable namespace-generation capture, reachable admission checks, retained leases, and entry-scoped root admission IDs. `ExecutionBinding` already contains both a selected generation and its authoritative snapshot, validates their association, and preserves them through mission and branch copies. Runtime tool discovery and dispatch currently look only in that selected generation, and the existing access guard evaluates roles without source namespace or declared-call checks.

The existing configuration plumbing is split among session creation and execution-time lookups. Session creation selects entry maximum depth, trace policy, and recorded quota settings once. Model/provider lookup, mission timeout, and attachment materialization select the binding's generation. Shared quota enforcement also currently selects that generation. All usage counters remain on the one session. Worker execution explicitly captures and installs bindings; Spring caller identity is installed separately in an isolated context around Java/REST implementation execution.

The preparation-time REST invoker already captures the canonical qualified name and its owning generation ID. Planner prompts list bound canonical names; generated plan and step selections currently use exact string lookup without invoking the common parser. Ordinary model tool dispatch is delegated to the pinned Spring AI tool loop. These facts describe the current integration points, not a new authorization, routing, budgeting, or cancellation architecture.

## Detailed findings

### 1. Canonical identities and authoritative capture

- `src/main/java/ai/loomspan/internal/core/SkillIdentity.java:6` is the common internal identity record. `parse` requires exactly one hyphen; component grammar permits ASCII letters, digits, and underscores with a letter/underscore first. Namespace case alone normalizes via `Locale.ROOT`; skill case is preserved. Namespace maximum is 32 and combined maximum is 64. It neither trims nor provides aliases.
- `src/main/java/ai/loomspan/internal/skill/SkillAdmissionSnapshot.java:8` copies the namespace map and validates that each key matches its generation's namespace. Its entry identity selects `entryGeneration`; `generation(namespace)` rejects a namespace absent from capture. It retains whole generations, not an independently callable set of every member.
- `src/main/java/ai/loomspan/internal/skill/SkillGeneration.java:20` owns immutable capability and definition maps, visibility, opaque ID, and runtime. Capability keys are canonical and must match identity ownership. `owns` compares the exact captured metadata instance, rather than name equality alone.
- `src/main/java/ai/loomspan/internal/core/ExecutionBinding.java:13` contains session, nullable mission, physical branch, generation, and snapshot. Construction checks snapshot membership by object identity, branch session, and mission session. `sessionOnly` selects the snapshot entry generation. `withMission` and `forkBranch` preserve generation and snapshot; there is currently no child-generation transition helper or explicit entry/current namespace accessor.
- `src/main/java/ai/loomspan/internal/core/ExecutionBindingScope.java:12` is the sole ambient holder. Scoped operations restore the exact prior binding in `finally`, including throwable paths. Binding another session within the scope is rejected. Threads do not inherit this ordinary `ThreadLocal` automatically.

### 2. Admission already checks retained dependency edges

- `SkillGenerationManager#capture` captures one coherent reachable namespace association and obtains a combined retained lease; `validateAdmission` delegates to `SkillDependencyValidator#checkAdmission`. `DefaultSkillTemplate#prepareMap` captures root metadata, validates input, and validates the reachable snapshot before returning prepared input (`src/main/java/ai/loomspan/internal/skillapi/DefaultSkillTemplate.java:147`).
- `src/main/java/ai/loomspan/internal/skill/SkillDependencyValidator.java:322` traverses each source definition's declared `allowedSkills`. Missing children become validation issues. Each edge compares the **source definition namespace** with the target namespace; a foreign target must be captured Public. The check occurs before recursive visit, so an already-visited target still receives the incoming-edge check.
- The check uses existing parsed definitions/contracts, not caller role filtering. Optional and role-restricted branches participate in reachability; child RBAC remains a runtime concern.
- `SkillAdmissionSnapshotTest#validatesEveryIncomingEdgeEvenWhenItsTargetWasAlreadyVisited` builds a graph where `a-root` reaches `a-target` and `b-bridge`, then `b-bridge` refers back to Private `a-target`. Admission rejects the callback while direct entry into `a-target` remains valid (`src/test/java/ai/loomspan/internal/skill/SkillAdmissionSnapshotTest.java:79`). This is existing early callback-denial coverage.

### 3. Discovery and independent execution paths

- `DefaultToolSurfaceService#visibleToolsFor` delegates to `DefaultSkillVisibilityResolver`.
- `src/main/java/ai/loomspan/internal/skill/DefaultSkillVisibilityResolver.java:24` loads the current YAML definition from `ExecutionBindingScope.requireCurrent().generation()`. It iterates only that definition's direct allowed names, excludes self, resolves each from the same generation, and filters through `AccessGuard#canAccess`. Consequently the current implementation has no retained-foreign-generation lookup here.
- `src/main/java/ai/loomspan/internal/runtime/tool/DefaultCapabilityInvoker.java:57` binds each visible capability into a callback. It finds declared input bindings by exact canonical name. Invocation records tool usage and planning/task status, assembles any declared input bindings, validates assembled input, opens a tool frame, and calls the router. Both ordinary callbacks and assigned planned dispatch reach this path.
- `src/main/java/ai/loomspan/internal/core/CapabilityExecutionRouter.java:54` checks `AccessGuard`, validates ordinary/assembled input, checks explicit-session consistency, and requires current-generation ownership before calling `ExecutionCoordinator`. It does not switch the generation.
- `src/main/java/ai/loomspan/internal/core/ExecutionCoordinator.java:82` also requires current-generation ownership. It resolves definitions in the binding's generation, creates a `MissionContext` with the existing parent, installs `withMission`, and invokes Java/REST, TypeSafe, or a model execution engine. `executeBound` again checks access. String-based coordinator entry resolves only within the current generation (`requireCapability`, around line 497).
- `DefaultSkillTemplate#executePrepared` reaches the same router for host roots (`src/main/java/ai/loomspan/internal/skillapi/DefaultSkillTemplate.java:290`). The root session has no mission yet. A child's active mission supplies its actual source skill; root handling and child handling are therefore observably different contexts.
- Direct coordinator calls exist in tests and internal entry methods, while production root and bound tool calls use the router. None of these public Java modifiers establish a supported application extension surface.

### 4. Existing guard and caller identity

- `src/main/java/ai/loomspan/internal/security/DefaultAccessGuard.java:30` delegates role checks to `SkillRoleEvaluator`; it currently does not evaluate namespace visibility, source declarations, or snapshot ownership. Explicit invocation authentication wins over the session fallback. `SkillRoleEvaluator` is the existing shared Spring authority evaluator with configured role prefix and hierarchy.
- The root facade separately uses that same role evaluator in `DefaultSkillTemplate#authorize`, after capturing trusted authentication at its existing operation boundary.
- `src/main/java/ai/loomspan/internal/security/ScopedAuthentication.java:24` saves the exact previous `SecurityContext`, creates a fresh context, installs caller authentication, and restores the previous object on close. `ExecutionCoordinator#executeBound` opens this scope **inside the actual Java/REST worker** before calling the invoker. The same caller is preserved as argument/session state; the namespace is not a different caller.
- `JavaSkillAuthenticationScopeIntegrationTests#restoresExactContextsAcrossNestedSuccessAndDenialOnReusedWorker` exercises nested identity restoration, denial, null identity, and business exceptions with real method security. `#simultaneousWorkersUseCapturedCallerWithoutSharingMutableContexts` exercises two workers with barriers. Existing source expressly scopes identity to managed synchronous proxy work; arbitrary host Java threads are outside this mechanism.

### 5. Mission ancestry, async workers, and cancellation

- `src/main/java/ai/loomspan/internal/core/MissionContext.java:35` retains skill name, session, parent, frame ID, and its own lifecycle. Child mission construction keeps the parent's session and registers against the admitted root lifecycle. Plans, successful-direct-child evidence, completed task results, and diagnostic deltas are mission-owned.
- `src/main/java/ai/loomspan/internal/runtime/MissionWorkExecutor.java:38` captures the current binding before submission and installs it inside the callable. It registers the owning future and records mission start on the worker. Its caller waits with the captured current-generation mission timeout. Submission, timeout, interruption, cancellation, and physical completion retain existing lifecycle/cutoff handling.
- `StepLoopMissionExecutionEngine` similarly captures the mission binding (`:210`), installs it inside its mission callable (`:219`), and uses the configured current-generation timeout (`:97`). Parallel task scheduling forks `PhysicalBranchContext` while retaining mission, session, generation, and snapshot (`:421` onward). `executeAssignedTask` installs the worker binding (`:653` onward).
- `ExecutionCoordinator` returns diagnostics to the parent in `finally` (`:284` onward). It currently derives that diagnostic binding by replacing the mission on the child binding; generation/mission association matters when namespaces differ.
- `PhysicalBranchContext#push` checks the one session's maximum depth against inherited and local mission frames (`src/main/java/ai/loomspan/internal/core/PhysicalBranchContext.java:91`). Branch forks retain inherited ancestry rather than starting depth from zero.
- `SkillReachableAdmissionTest#timeoutResponseRetainsWholeSnapshotUntilPhysicalWorkReturns` protects resource ownership after a timeout. `#nestedExecutionRejectsAndReleasesWhileValidationAndHandoffPreparationStayAllowed` protects nested-root semantics, with validation and handoff preparation distinct from execution.

### 6. Current versus entry configuration map

| Concern | Current source selection | Existing state/owner |
| --- | --- | --- |
| Definitions and effective per-skill model | `ExecutionCoordinator` generation lookup; immutable `YamlSkillDefinition` execution config | Current binding generation |
| Chat connection/credentials | `SpringAiChatClientAssembler#create`, line 84, chooses captured generation runtime connection | Prepared provider resources |
| Native TypeSafe connection | `TypeSafeExecutor`, line 32, binding generation runtime | Prepared native resources |
| Mission timeout | `MissionWorkExecutor#timeout`, line 28; `StepLoopMissionExecutionEngine#timeout`, line 97 | Existing mission future/lifecycle |
| Provider timeout/retries | `SpringAiProviderIntegration#create` and per-driver construction; `ProviderAttemptCallAdvisor` | Captured selected connection runtime |
| Attachment maximum size | `DefaultMissionInputMaterializer#maxSizeBytes`, line 35 | Current binding runtime; existing materialization checks |
| Session quotas | `DefaultSessionUsageService#quotas`, line 28, currently binding generation runtime | One session's atomic shared usage snapshot |
| Maximum depth | `LoomspanSessionRunner#executeAdmittedRoot`, line 293 onward, captured entry runtime | Final session field |
| Trace persistence | Same session creation path | One entry-scoped trace |
| Configured trace limits | Same path, `ConfiguredLimitsSnapshot.from(entryRuntime.session.quotas)` | Entry quota-only snapshot |

`ExecutionRuntime` copies supported settings when constructing a generation, including provider options, credentials, request timeout/retry policy, all session quotas, max depth, mission timeout, and attachment size. Its close is one-shot and destroys only that generation's connection registry.

`DefaultSessionUsageService` increments the same `SessionUsageSnapshot` for skill invocations, tool invocations, model calls/usage units, provider attempts, and linter retries. Model response/usage enforcement occurs after recording; provider attempt reservation already uses its existing atomic pre-send check. There is no namespace-specific counter store. Session creation is performed when admitted work actually executes, but it uses the retained snapshot, so a queued handoff's settings do not depend on the then-current registry.

The direct engine materializes its input inside `MissionWorkExecutor`; the step engine also uses the existing materializer. Materializer size checks use the current generation. Java/REST argument reference resolution uses `RefResolver`, not an added attachment-materialization subsystem.

### 7. Model plan, step, and ordinary tool selection

- `DefaultPlanningService#buildPlanningPrompt` (`src/main/java/ai/loomspan/internal/runtime/planning/DefaultPlanningService.java:632`) lists bound `BoundCapability.name()` values unchanged and asks for those exact task capability names. Parent plan identity comes from `definition.identity().toString()`. Existing framework planning/evidence/task-count guidance uses those canonical values.
- `#parseNormalizedPlanTree` (`:798`) unwraps JSON/YAML fences, parses a tree, then normalizes plan/task statuses and assigns framework plan ID. It currently does not parse/canonicalize capability identities. `PlanStructureValidator#validate` compares task `capabilityName` text directly to the visible names (`src/main/java/ai/loomspan/internal/runtime/planning/PlanStructureValidator.java:92`). Plan output and source diagnostics are separately retained by the planning/model trace paths.
- `StepLoopMissionExecutionEngine#parseStepAction` (`:1175`) deserializes JSON into `StepAction` and handles final-output shape. `StepActionValidator#validateToolBindingAndArguments` (`src/main/java/ai/loomspan/internal/runtime/step/StepActionValidator.java:99`) compares tool names to exact bound names and the assigned task. Dispatch then selects the same bound callback by exact name (`StepLoopMissionExecutionEngine:1141`). It currently has no common-parser normalization at deserialization.
- `src/main/java/ai/loomspan/internal/springai/SpringAiToolCallbackAdapter.java:20` builds `FunctionToolCallback` with the bound name unchanged, schema unchanged, and callback invocation to `BoundCapability`. No framework encoding/translation is present.
- `SpringAiModelInteraction#doCall` (`src/main/java/ai/loomspan/internal/springai/SpringAiModelInteraction.java:35`) supplies these callbacks to `ChatClient` and delegates ordinary tool-loop resolution to Spring AI. It passes raw system/user text and returns response content plus advisor context. The model assembler uses Spring AI 2.0.0 from the POM, with one tool loop exercised by `SpringAiChatClientAssemblerIntegrationTest`.
- The framework sources inspected contain no separate provider-specific tool-name translation or provider naming validator beyond canonical identity construction and the Spring AI callback/provider adapter boundary. Exact pinned dependency constraints and the interception point for normalized **ordinary tool selection** remain planning integration questions; they are not evidence for weakening the canonical identity contract. No external provider documentation was consulted in this research.
- Existing binding/result correlation already uses exact canonical declaration keys: `DefaultCapabilityInvoker` matches input producers against plan capability names and completed result skill names; `StepLoopMissionExecutionEngine` records completed task results with accepted task names; output bindings/forwarding use their parsed declared skill references. This provides the correlation path to audit alongside selection parsing.

### 8. REST closure, IDs, and lifecycle

- `src/main/java/ai/loomspan/internal/skill/SkillGenerationManager.java:218` issues IDs using one manager UUID/prefix plus monotonically increasing ordinal. It computes canonical `name = definition.identity().toString()` for every definition.
- REST capability preparation at `:244` captures `handler`, canonical `name`, and that generation's `generationId` in the invoker closure. `invokeRest` at `:458` creates `RestSkillInvocation(name, arguments, generationId)` directly. It neither resolves live publication nor reads routing identity from invocation arguments. The ticket's requested closure mechanism therefore already exists and is a concrete retained-generation test target.
- `src/main/java/ai/loomspan/api/RestSkillInvocation.java:11` has the unchanged three components. It recursively freezes map/list containers and preserves leaf identity/null values. Its Javadoc currently calls it an immutable application handoff without spelling out qualified target versus entry ID semantics.
- `DefaultSkillInvocationHandoff` stores its ID from `prepared.snapshot().entryGeneration().id()` during preparation (`:80`). That field remains readable independently of later ownership release.
- Existing manager lease/retirement and framework physical-work ownership provide delayed cleanup. Namespace execution does not require a new callback shape, routing field, resource acquisition on ID read, or durable generation mapping.
