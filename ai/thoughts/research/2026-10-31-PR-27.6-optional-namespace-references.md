## Summary

Both input boundaries named by the ticket are shared in the checkout.
`DefaultSkillTemplate.captureRoot` strictly parses every root argument; both
handoff overloads call its preparation methods. `YamlSkillCatalog` uses a known
owner namespace for both configured startup resources and supplied documents,
and validates structured references before deserializing and compiling runtime
definitions. Existing semantic records, graph checks, runtime access, model
selections, catalog lookup, REST closures, and observations use canonical
qualified identities.

Evidence parsing already records original token columns and compiles Boolean
trees rather than rewriting strings. Current source, focused tests, README,
and authoring guidance agree that references must be qualified. PR 27.6
explicitly supersedes that rule only at authoring and root-operation inputs.

## Detailed Findings

### 1. Identity grammar and ownership

- `src/main/java/ai/loomspan/internal/core/SkillIdentity.java:6` is an internal
  record with namespace and local-name components. Its constructor normalizes
  namespace case only, validates ASCII components, limits namespace length to
  32, and enforces total identity length 64 including the separator.
- `SkillIdentity.parse` at line 18 requires exactly one hyphen with nonempty
  components. Local names, whitespace, extra hyphens, slash/colon separators,
  and non-ASCII components fail; local case remains significant.
- `SkillMethodBeanPostProcessor.java:202` constructs Java identities from
  `annotation.namespace()` and either explicit local name or method name.
  Java namespace assignment and its `default` value already exist.
- `YamlSkillCatalog.java:144` sets startup ownership to `default`;
  `checkedSupplied(String namespace, ...)` at line 165 normalizes supplied
  ownership before checking documents. Source labels and target availability
  do not establish ownership.

### 2. Host entry and handoff

- `DefaultSkillTemplate.java:81-113` contains both validation and all four
  invocation overloads. They converge through `prepareObject` (line 116) or
  `prepareMap` (line 142), then `captureRoot` (line 148), currently calling
  `generationManager.capture(SkillIdentity.parse(skillName))`.
- Capture precedes Object null rejection/conversion and Map validation. Once
  captured, preparation uses `captured.snapshot().entry().toString()` and the
  exact entry generation to require capability metadata, validate input and
  revalidate admission. Root RBAC follows preparation. Leases are released on
  failure and temporary validation completion.
- `DefaultSkillInvocationHandoff.java:34-43` calls the same Object/Map prepare
  methods. Admission captures authentication and reserves root ownership;
  invocation uses the stored prepared snapshot, not a second target lookup.
  The passed name also remains in failure-context strings; actual execution
  and session identity come from prepared capability/snapshot metadata.
- `DefaultSkillCatalog.java:64` independently uses strict `SkillIdentity.parse`
  and looks only in its immutable entry map. This is a different supported
  contract from the root boundary and is explicitly outside PR 27.6 scope.

### 3. Shared document loading and structured reference validation

- `YamlSkillCatalog.checkedConfigured` and `checkedSupplied` share
  `loadDefinition(resource, source, bytes)` at line 329 and `readManifest`.
  Supplied documents become UTF-8 byte resources; startup resources are read
  once. `YamlSkillSource.java:10` clones and retains original source bytes,
  source labels, and resource information independently of semantic objects.
- `readManifest` validates the local declaration identity, REST/TypeSafe field
  restrictions, concurrency, output bindings, forwarding, and allowed children
  before `treeToValue(root, YamlSkillManifest.class)` at line 453.
- Reference families are `allowed_skills[].name` (line 535),
  `output_from.skill` (line 494), `allowed_skills[].input_bindings.*.skill`,
  and `output_bindings.*.skill` for `from: child_result` (line 639). Input
  bindings from parent input contain no skill identity. Prompt prose,
  descriptions, property names, pointer paths, and business values are not
  reference positions.
- `reference(...)` at line 757 currently strictly parses a reference and adds
  source/skill/field diagnostic context on failure. Allowed-child duplicate
  detection uses a `Set<SkillIdentity>`, and forwarding/output producer
  comparisons also compare parsed identities. Raw binding validation at line
  668 separately calls the strict parser for child-result producers.
- `AllowedSkillConstraint.from` compiles allowed-child identities and input
  bindings. `YamlSkillDefinition.java:41` defensively copies its manifest,
  constructs the definition identity from owner plus local declaration name,
  strictly parses forwarding, and compiles output bindings. Its runtime
  getters expose canonical names and prepared binding records. Declaration
  names stay local; original YAML is separately retained.
- REST and TypeSafe declarations forbid parent composition fields. They can
  still be targets of a model-backed parent's authored references. Java
  targets are fixed annotation registrations, not YAML wrapper declarations.

### 4. Evidence expressions and diagnostics

- `YamlSkillCatalog.compileEvidenceContract` at line 831 parses immediate-root
  output-property `evidence` strings, checks references against direct allowed
  children, and produces one immutable `EvidenceContract`.
- `EvidenceExpressionParser.java:12` tokenizes the original string. Grammar
  gives `and` precedence over `or`, supports parentheses, treats whole-token
  AND/OR case-insensitively as reserved, and recognizes qualified identities
  such as `and-search` as identifiers. It records token start + 1 on each leaf
  and on `ParseException`.
- `parsePrimary` at line 61 constructs `EvidenceExpression.Skill` from token
  text. That leaf's string constructor at `EvidenceExpression.java:22`
  strictly parses `SkillIdentity`; the leaf stores identity and column. The
  Boolean tree already has structured canonical rendering and reference sets.
- Catalog invalid-direct-child diagnostics use `referenceColumn` at line 894
  to locate the original leaf. Unique case-insensitive child matches produce
  a suggestion. Evidence source text remains on the manifest output property;
  canonical expressions are separate compiled semantics.

### 5. Dependency, access, and captured execution paths

- `SkillGenerationManager.java:160-181` sends both publication preparation and
  validation through `new YamlSkillCatalog(...).checkedSupplied(view.namespace(), ...)`
  followed by the same `SkillDependencyValidator.check`. Validation allocates
  no generation. Startup also uses catalog checking before preparation.
- `SkillDependencyValidator.java:40` builds the candidate's own complete
  declaration/fixed-Java overlay and external namespace metadata. It does not
  recover omitted candidate skills from an old candidate generation.
- `visit` at line 327 traverses exact allowed-child names, reports missing
  targets, and allows same-namespace calls or a PUBLIC foreign target.
  `ChildInputBindingDeclarations` checks direct producers, self-dependencies,
  producer task counts, and cycles using already compiled canonical records.
  Forwarding/output schema and output binding checks follow the same graph.
- `SkillGenerationManager.capture` at line 309 traverses strict qualified
  child identities while holding registry synchronization, retains each
  reachable namespace generation, and gives `validateAdmission` the captured
  association. `SkillAdmissionSnapshot` resolves structured identities.
- `SkillGeneration.java:56-70` validates owner and canonical capability and
  definition keys. Runtime lookup has no local alias table.
- `DefaultAccessGuard.java:57` checks actual snapshot ownership, entry target
  or declared source child, namespace visibility, and RBAC. The execution
  router checks access before switching to the target context.
- `PlanStructureValidator.java:269` and `StepAction.java:24` strictly parse
  model-generated choices. These are downstream selections, not authored
  references. Canonical provider names and exact bound-tool matching remain
  part of the existing execution contract.
