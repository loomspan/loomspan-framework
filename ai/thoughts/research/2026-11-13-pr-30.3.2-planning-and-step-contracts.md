## Summary

The shared schema compiler, canonical validator and per-request native-output path already exist. `ModelInteractionRequest` carries an explicit canonical generation contract. The planner currently sends null in that slot and owns JSON/YAML parsing, fence removal and status aliases. The step engine also sends null; its assigned action and final envelope remain its existing local protocol rather than a provider-native general action schema.

Semantic planning checks and bounded action correction already have distinct owners. Step argument and final trees are decoded through an injected mapper; the default schema mapper now enables BigDecimal, unlike the ticket's historical anchor. Explicit null argument roots still become indistinguishable from omission in record binding and later become empty maps. The step input-guidance consumers still refer to the superseded schema-node API. Planning and engine fixtures still instantiate removed output-manifest types. Full-root build limitations from PR 30.3.1 are historical evidence only; no build was rerun here.

## Detailed findings

### 1. Existing canonical/native path

- `src/main/java/ai/loomspan/internal/schema/StandardSchemaCompiler.java:15` owns one local Draft 2020-12 profile with INPUT, OUTPUT and PLANNING roles. `compile` checks profile vocabulary, bundled meta-schema and initialized validators. Remote fetching is disabled. PLANNING has output-like restrictions: typed maps and unconstrained leaves are not accepted. Nullable property types are supported, but the complete root is an object. `pattern` is outside the profile.
- `src/main/java/ai/loomspan/internal/schema/CanonicalSchema.java:10` stores a defensive tree snapshot and initialized validator. `tree()` and `providerTree()` return detached copies; the latter strips only known annotations at schema nodes. Completed validation errors are returned; operational failures propagate.
- `src/main/java/ai/loomspan/internal/model/ModelInteractionRequest.java:11` carries `CanonicalSchema outputContract` independently of capabilities and the planning flag.
- `src/main/java/ai/loomspan/internal/springai/SpringAiModelInteraction.java:54` exposes the inability control only in STANDARD mode outside initial planning. It puts explicit contracts into `OutputSchemaCallAdvisor.OUTPUT_CONTRACT_KEY` and planning into `PLANNING_CALL_KEY`; planning input contains no attachment media when supplied by the planning service.
- `src/main/java/ai/loomspan/internal/outputschema/OutputSchemaCallAdvisor.java:109` bypasses ordinary output acceptance for planning calls. Its normal path selects the final/projected schema, performs bounded ordinary correction and preserves response facts. The planner therefore remains responsible for plan acceptance and correction.
- `src/main/java/ai/loomspan/internal/chat/ProviderAttemptCallAdvisor.java:70` calls `NativeOutputContract.prepare` before sending. It retains provider attempt/retry/usage ownership and records canonical and prepared schema facts.
- `src/main/java/ai/loomspan/internal/springai/NativeOutputContract.java:42` formats per-request typed option copies for shared OpenAI Responses, native Anthropic and native Gemini. OPENAI rejects open objects and declared optional properties before send; Anthropic rejects open objects and omits its evidenced unsupported assertions from detached provider copies. Local contracts retain all assertions. This constrains a framework-owned planning contract independently of arbitrary user schema policy.

### 2. Planner request, parsing and semantic acceptance

`src/main/java/ai/loomspan/internal/runtime/planning/DefaultPlanningService.java` owns these paths:

- Lines 59–101: one total planning validation retry; JSON and YAML mapper dependencies; structural/task-count/evidence validators; injectable runtime plan-ID supplier.
- Lines 300–426: initial request then structure validation, typed conversion, task-count constraints, evidence coverage, input dependency bindings and output producer bindings. Structural and typed/evidence/binding failures share one correction allowance. Only an accepted attempt stores a plan and emits creation; accepted attempt and retry-sequence identity are required.
- Lines 432–435: `PlanInputBindingDependencyValidator` and `PlanOutputBindingProducerValidator` retain separate authority. The first preserves unique producer/direct dependency rules, the second output producer uniqueness.
- Lines 480–503: positive required/minimum children must be visible before any model call; maximum-only invisible children do not cause this preflight failure.
- Lines 505–550: planner uses the effective execution identity, a planning frame, `SkillPromptComposer.composePlanningPrompt`, canonical user-message formatting and descriptor-only input. Its `ModelInteractionRequest` currently sets `planning=true, outputContract=null` and no callable tools.
- Lines 633–732: prompt illustrates capabilityName, createdAt, VALID, tasks with taskId/title/PENDING/capabilityName/intent/dependsOn/expectedOutputs/parallelGroup/note. It instructs raw JSON, exact names, earlier-unit dependencies, grouping, evidence and task counts. Runtime planId is absent from the prompt.
- Lines 799–875: current parser unwraps fences/YAML document prefix, tries JSON then YAML, normalizes status values and replaces any model planId with a generated ID. `convertPlan` binds into the existing records. Parser exceptions currently propagate from the request method rather than entering semantic correction.
- Lines 910–986: broad status aliases include plan success/executing-like tokens and task success/running/waiting/failure-like tokens. These are internal parser fallbacks explicitly named for removal by the ticket, not supported application API.

`src/main/java/ai/loomspan/internal/runtime/planning/PlanStructureValidator.java:31` accepts only an object with tasks array. It enforces exact executing/visible capability identity, nonblank unique task IDs, dependency arrays with nonblank string references, no unknown/self/forward/same-unit dependencies, exact parallel-group grammar, group width and contiguity. Its existing pattern is a semantic check, not a schema-profile keyword. It does not itself constrain all initial statuses or validate createdAt/title/intent/expectedOutputs.

Record semantics are distinct from the prompt example:

- `ExecutionPlan.java:18`: planId/capabilityName nonblank; createdAt nonnull; missing/null plan status defaults VALID; tasks defaults empty.
- `PlanTask.java:22`: taskId/title nonblank; task status required; capabilityName/intent/note blank normalize to null; dependency/output lists default empty; nullable parallelGroup is preserved. Structural validation separately requires capabilityName and dependsOn. These facts are the existing evidence for requiredness decisions, rather than an inference from the illustrative JSON alone.
- Enum records represent later runtime states too. The ticket's initial VALID/PENDING constraint is narrower than these execution enums.

### 3. Step protocol, precision and null arguments

- `src/main/java/ai/loomspan/internal/runtime/step/StepLoopMissionExecutionEngine.java:176` takes an internal injected schema mapper. At line 190 it stores that mapper unchanged. The type reader and strict inability reader are derived from it. `LoomspanJacksonCodecs.java:39` now enables `USE_BIG_DECIMAL_FOR_FLOATS` on default schemaTree, but another supplied mapper can differ. Shared-codec precision changes are not required to explain this current path.
- Engine lines 911–1000 own invalid-action retry count, linter/schema/evidence counters, complete candidate correction evidence and final-only versus assigned prompt selection. An invalid action is corrected once before terminal failure. Completed work is not dispatched again to correct a final candidate.
- `callModelForStep` at lines 1092–1120 sends `planning=false`, no model tools and `outputContract=null`. The step interaction assembly filters ordinary semantic validators; the step engine retains local acceptance ownership. A new general StepAction/native output protocol is explicitly excluded by this ticket.
- `parseStepAction` at line 1205 unwraps existing step fences, strictly recognizes inability declarations, otherwise binds StepAction using the injected mapper. Final-only mode accepts a bare object via a separate tree-reading branch. Both record and bare-tree decoding affect decimal fidelity. Unknown unrelated fields remain tolerated by `StepAction`.
- `StepAction.java:17` binds nullable `Map<String,Object> toolArguments` and `JsonNode finalResponse`. Binding collapses omitted and explicit null argument roots. `canonicalSelection` canonicalizes CALL_TOOL identity; inability declarations use a separate exact raw-field validation path.
- `StepActionValidator.java:45` rejects CALL_TOOL in final phase and refuses final completion while any accepted task is incomplete. Assigned validation checks exact taskId, IN_PROGRESS state, exact allowed tool binding, projected binding ownership and local canonical input validation before dispatch.
- `StepActionValidator.java:161` and engine invocation normalize null arguments to `Map.of()`. Nested object nulls remain values. The ticket targets the model decoding boundary's explicit-null distinction, not these generic/internal omission semantics.
- Final serialization at engine line 1476 returns string values as strings and serializes other JSON trees with the mapper. Canonical output validation, output composition and evidence validation happen before acceptance; precision must survive decoding to reach those checks intact.

### 4. Canonical input guidance consumers

`SkillInputContract.java:8` now holds CanonicalSchema and uses `schema.tree()` for empty-input checks. `StepPromptBuilder.java:243–341` still invokes old node methods (`properties`, `required`, `isObject`, `dispatchProofSupported`, typed additional-properties traversal) and passes that value to old-schema traversal helpers. `SkillInputPromptRenderer.java:10` still accepts `SkillInputSchemaNode` in its rendering helpers while reading `contract.schema()`. The old node class remains in the tree, but the contract no longer returns it.

These consumers implement meaningful existing guidance: projected ownership boundaries, {} eligibility, required unbound fields, compact/verbose depth thresholds, typed maps, optional-parent scoping and exact authored descriptions. PR 30.3.1's results explicitly hand these consumer restorations to PR 30.3.2. Their shape-summary behavior is not a substitute for canonical validation or dispatch authorization.

### 5. Wiring, options and isolation

- `LoomspanAutoConfiguration.java:356–357` injects both planning codecs into DefaultPlanningService; lines 424–442 supply schemaTree to the step engine. `PlanningServiceTestFactory` and deterministic planning-test constructors also pass planningYaml.
- `SpringAiChatClientAssembler.java:111–145` chooses the captured runtime/connection, combines a detached complete typed provider-default snapshot with target execution options, and creates standard or step clients. Step mode filters ordinary final semantic advisors and still has one Spring AI tool loop plus provider attempt advice.
- Engine uses forked execution bindings for grouped workers (lines 438 and 478), preserving pre-unit evidence and mission write fences. Request contracts are explicit immutable values; no mutable conversation store exists in these request records.
- Offline option identities, caps and routing constraints are already fixture data in `OrdinaryNativeOutputIntegrationTest` (six route identities, 1024/4096/2048 caps, 400 rejection, 503 retry, tool continuation and schema/text isolation). Those tests exercise ordinary consumer wiring; they do not currently demonstrate planner wiring or model overrides for the newly migrated planner.
