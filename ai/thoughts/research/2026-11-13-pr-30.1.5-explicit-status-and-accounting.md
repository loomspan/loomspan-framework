# Research: PR 30.1.5 explicit status and accounting

**Researcher:** Codex (model identity unavailable). **Profile:** full, approved by
the developer's `proceed` answer after Step 0. **Date:** November 13, 2026,
America/Los_Angeles. Initial checkout was clean. This stage changed only this

## Research question

Map the existing three chat integrations, status/evidence mapping, attempt and
usage ownership, pre-dispatch boundary, validators and planning consumers for
`ai/thoughts/tickets/loomspan-pr-30.1.5-reject-explicit-refusal-and-incomplete-responses-with-faithful-accounting.md`.
The ticket owns the classifier and faithful accounting; PRs 30.3.1/30.3.2 own
later migrated output/planning consumers and must exercise that classifier.

## Summary

The current checkout has the three migrated official Spring AI adapters. The
provider-attempt advisor already captures rich messages, ordered parts,
generation metadata and response metadata from PR 30.1.2. Its returned-response
branch still unconditionally records a succeeded outcome. Its retry catch wraps
only the physical downstream call; extraction, response trace and usage
accounting occur outside it. CanonicalToolCallingManager validates the entire
selection set before delegation but has no explicit response-status check.

Pinned local RC2 source exposes Responses status/refusal/incomplete reason and
Anthropic finish reason/native response. Gemini exposes candidate finish reason,
but omits native finish details and top-level promptFeedback. The existing
Responses HTTP interceptor captures failed-envelope original JSON into bounded
diagnostics before the SDK's code/message-only exception, but does not expose a
response/usage object for response accounting. No fixed dependency or candidate
repair was verified during this research. These are exact inspected source
observations, not fresh end-to-end reproductions or a completion claim.

## Current runtime map

  Java release is 21. The three dependencies are `spring-ai-openai`,

  creates official Responses, Anthropic or Gemini models. TYPESAFE is a separate

- `SpringAiChatClientAssembler:54-65` constructs Spring AI ToolCallingAdvisor

### Provider attempt, response and failure ownership

`src/main/java/ai/loomspan/internal/chat/ProviderAttemptCallAdvisor.java`:

1. `adviseCall:58-75` requires call-local ModelTraceContext/current binding,
   checks interruption, reserves provider-attempt quota, allocates the physical
   identity and records MODEL_REQUEST_SENT.
2. `:77-105` catches RuntimeException only from the downstream physical call.
   It translates the original failure, applies ProviderRetryDecider, records one
   failed outcome and MODEL_ATTEMPT_FAILED, registers terminal failure linkage,
   then rethrows or waits interruptibly and retries.
3. `:107-117` links the physical attempt to the returned ChatClientResponse,
   records succeeded, extracts usage, records MODEL_RESPONSE_RECEIVED and calls
   SessionUsageService.recordModelResponse, then returns. No explicit rejection
   classification is currently performed.
4. `responsePayload:226` retains generations plus generationMetadata entries,
   typed finishReason/contentFilters and response metadata/id/model.
   `messagePayload:162` retains exact nullable text, metadata, ordered canonical
   parts, calls/arguments and responses. Existing evidence is richer than the
   historical ticket's original message-only anchor.

`ProviderRetryDecider.decide` only retries classification TRANSIENT and respects
enabled/maxAttempts/backoff/jitter/Retry-After. `SpringAiProviderIntegration.translate`
preserves current HTTP status policy and cancellation/SSL/transport distinctions.
Its Responses failed-envelope policy uses observed error types
`rate_limit_exceeded`, `provider_overloaded`, `provider_unavailable`, `timeout`,
`server`, `unmapped` as transient; this is separate from refusal/incomplete.
Unknown failure is not automatically transient.

`DefaultExecutionTraceRecorder:52-76` separates receipt and attempt-failure facts.
Failure diagnostics consist of bounded Java stack followed by supplied provider
diagnostics. `DefaultExecutionStateService:319-350` delegates those existing
facts, while `:505` registers provider failure linkage on the writable binding.
`LoomspanSession.registerProviderFailure` retains throwable/attempt associations.
No new observability subsystem is present or required by the ticket.

### Usage and cancellation/quota collisions

- `ModelUsageExtractor.extract:16-69` reads response metadata usage. Currently
  `hasExactUsage:67` requires at least one positive count; otherwise it estimates
  available prompt/response text, or returns UNAVAILABLE when neither exists.
  Thus supplied all-zero native usage currently falls through the same heuristic
  path as absent usable counts. Native usage is retained in ModelUsageRecord.
  The ticket explicitly requires missing/zero controls; planning must address
  their precise evidence without silently changing unrelated usage policy.
- `DefaultSessionUsageService.recordModelResponse:59-70` updates modelCalls and
  token totals and records metrics, then enforces max-model-calls and max-usage-units.
  A quota exception can therefore occur after accounting has already happened.
  `reserveProviderAttempt:75-94` rejects before a new physical send when quota is
  exhausted. These exceptions currently remain outside the physical-call retry catch.
- `runIfWritable:184-188` uses the current execution binding's write fence.
  Late usage/outcome writes are gated by existing execution ownership.
  `SessionUsageSnapshot.recordModelUsage:90` increments response counts once.
- `ProviderAttemptCallAdvisor.waitInterruptibly:134-146` restores interruption
  and throws CancellationException, then checks interruption before any later send.
  Existing tests distinguish interrupted-backoff and pre-send interruption.

### Dispatch, validators and planner consumption

- `CanonicalToolCallingManager.executeToolCalls:39` validates bound callbacks,
  every generation and every complete ToolCallPart before delegation. It rejects
  invalid/unbound selections and mixed planner inability controls atomically.
  It preserves unchanged original message/generation/parts and only rebuilds a
  renamed tool-call part. It has no usage ownership or status classifier.
- `OutputSchemaCallAdvisor:109`, `LinterCallAdvisor:88` and
  `EvidenceContractCallAdvisor:61` obtain downstream response before extracting
  and validating candidate text. They do not broadly catch downstream provider
  exceptions to turn them into correction requests. A terminal exception from
  the inner provider boundary escapes before candidate validation.
- `SpringAiModelInteraction.doCall:72-82` extracts final text after ChatClient
  completes. `DefaultPlanningService.requestPlanAttempt:525-538` calls the
  interaction, then invokes `parseNormalizedPlanTree`; provider failure escapes
  before parsing. Its catch records model invocation failure and propagates.
- Ordinary mission and step-engine interaction sites are respectively
  `DefaultMissionExecutionEngine:132` and `StepLoopMissionExecutionEngine:1117`.
  Their future schema/planning migration belongs to 30.3.1/30.3.2; a new
  classifier in those consumers would duplicate the ticket's authority.
