# Research — PR 37.2 startup paths

## Research question

Map the existing startup discovery, literal lookup, relative-path derivation, supplied-document validation, tests and authoring guidance that govern PR 37.2.

## Summary

`YamlSkillCatalog` delegates configured locations directly to Spring's `ResourcePatternResolver`. It reads the resources returned by that resolver and retains each original location in `YamlSkillSource`. Startup YAML always belongs to `default`. The loader has no path-case validation at this revision. Spring's default case-sensitive matcher can discard a mixed-case filename or extension before returning candidates.

The observation package already derives descriptive relative paths. `SkillSourcePathResolver` uses only the filename for a literal location and a fixed-prefix-relative path for patterns. It supports the classpath, all-classpath and filesystem examples protected by its tests. It currently runs while assembling observation catalog entries, after YAML loading, and validates safe relative structure without enforcing lowercase.

Supplied documents already follow the ticket's identity/label distinction. Public `validate` and `prepare` validate their namespace with `SkillIdentity.requireNamespace`, and the catalog validates manifest `name`. `SkillDocument.sourceName` is an exact, arbitrary diagnostic label throughout YAML parsing, variable staging, validation issues and observation source display. Blank and duplicate labels have their own document errors.

## Detailed findings

### Configured startup discovery

- `LoomspanProperties.Skills` defines `locations` as `List.of("classpath:/skills/**/*.yaml")`. Setting null or an empty list restores that default. The configured list is copied. The binding class is Spring integration machinery, while the property and its documented behavior are author-facing configuration. See `src/main/java/ai/loomspan/autoconfigure/LoomspanProperties.java:414`.
- `LoomspanAutoConfiguration#skillGenerationManager` captures skill-loading properties and supplies `YamlSkillCatalog` with a new `PathMatchingResourcePatternResolver`, the framework YAML codec and startup variable resolution. See `src/main/java/ai/loomspan/autoconfigure/LoomspanAutoConfiguration.java:155`.
- `SkillGenerationManager#initializeStartup` calls `checkedConfigured(true)` and builds the Private `default` generation. It separately creates generations for fixed Java declarations in other namespaces. Directory names have no ownership role. See `src/main/java/ai/loomspan/internal/skill/SkillGenerationManager.java:89`.
- `YamlSkillCatalog#checkedConfigured` resets the owner to `default`, discovers resources, stores the resource URI/description as diagnostic source, and collects each loaded definition's issues. A discovery exception produces an ERROR with source `<configured-resources>`. See `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:140`.
- `discoverResources` loops over configured strings and invokes `resourcePatternResolver.getResources(location)` verbatim. It keeps existing resources, ignores `FileNotFoundException` for absent roots, wraps other `IOException` as discovery failure and sorts by URI/description. It does not deduplicate overlapping configured locations. See `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:286`.
- `loadDefinition(DiscoveredYamlSkillResource)` reads all source bytes, constructs `YamlSkillSource(resource, originalLocation, bytes)` and enters the ordinary manifest compiler. Path spelling is not examined before opening the resource. See `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:317`.
- `DiscoveredYamlSkillResource` carries only the original nonblank location and nonnull resource. It carries no precomputed relative path. See `src/main/java/ai/loomspan/internal/skill/DiscoveredYamlSkillResource.java:7`.
- Diagnostic `describe(Resource)` uses `resource.getURI().toString()` and falls back to `getDescription()` on `IOException`. See `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:1112`.

The current loader accepts whatever resource locations the injected Spring resolver resolves. The framework imposes no local list of allowed URL schemes. Its normal wiring uses Spring's standard resolver. There is no application-facing resolver replacement SPI.

### Dependency implementation and candidate enumeration

The checked-out build uses Spring Core `7.1.0-RC2`, visible in the PR 37.1 test logs. Its matching source archive is available locally at `C:/Users/mgiacomi/.m2/repository/org/springframework/spring-core/7.1.0-RC2/spring-core-7.1.0-RC2-sources.jar`.

The following observations come from `org/springframework/core/io/support/PathMatchingResourcePatternResolver.java` inside that exact source archive.

- `getResources` at lines 365–395 distinguishes `classpath*:` from other locations. All-classpath lookup searches modules and classpath resources. A pattern dispatches to `findPathMatchingResources`; a literal non-all-classpath location delegates to `getResource`.
- `determineRootDir` at lines 801–810 strips trailing path portions until the remaining portion after the URL prefix contains no pattern. The root is the fixed directory portion before wildcard matching.
- `findPathMatchingResources` at lines 685–782 resolves that root, then dispatches jar URLs to jar enumeration and ordinary roots to filesystem enumeration, with additional supported Spring resource cases.
- Jar enumeration computes each candidate's exact jar-entry-relative string and applies `getPathMatcher().match(subPattern, relativePath)` before creating the returned resource. The cached path is shown at lines 865–899 and the uncached path follows the same matching rule around lines 953–969.
- Filesystem discovery obtains a `Path` from the root URI or resource file, walks it with `Files.walk(..., FOLLOW_LINKS)`, applies `getPathMatcher().match(resourcePattern, cleanPath(path.toString()))`, sorts and constructs `FileSystemResource` objects. See lines 1012–1101.
- All-classpath module scanning also applies the configured matcher or exact equality before returning resources. See lines 1131–1144.

Loomspan does not install a custom matcher or set its case sensitivity. A pattern ending in lowercase `.yaml` can therefore omit a differently cased candidate before Loomspan's read loop. No framework source currently performs an additional enumeration to observe those omitted candidates. Existing tests exercise actual filesystem and exploded classpath lookup, while packaged-JAR and custom-resource coverage for startup discovery was not found in the focused inventory.

This is source inspection, with no dependency-source edits, dependency upgrades, web research or test execution during Step 1.

### Existing descriptive relative-path derivation

`SkillSourcePathResolver` is an internal observation collaborator. `DefaultRegisteredSkillCatalog` constructs it and calls `resolve(definition.source())` while assembling YAML declaration entries. See `src/main/java/ai/loomspan/internal/runtime/observation/catalog/DefaultRegisteredSkillCatalog.java:28` and `:39`.

The resolver follows these existing rules.

- A nonnull supplied label returns verbatim before resource or path interpretation. See `src/main/java/ai/loomspan/internal/runtime/observation/catalog/SkillSourcePathResolver.java:33`.
- It locates the first `*`, `?` or `{` after the location's first colon, so the star in `classpath*:` is excluded. A location without a pattern uses `Resource.getFilename()`. See the `resolve` and `firstPatternIndex` methods at lines 41 and 72.
- For patterns it chooses the directory separator immediately before that first pattern, resolves the fixed prefix, normalizes root and resource URIs and selects the longest matching root URI string. It removes that prefix to obtain a relative string. See lines 47–65.
- Safe-structure validation replaces backslashes with slashes, rejects blank/absolute/scheme/drive forms and rejects empty, dot and parent segments. It returns the joined segments. It does not check uppercase characters. See lines 104–126.
- Failed root resolution or relativization produces an exception naming the resource description. The helper does not enumerate directory entries or read archive entry spelling itself.

The diagnostic root calculation exists after discovery and is currently owned by an observation package. The startup loader does not call it. The public API does not expose either this resolver or `YamlSkillSource`.

`YamlSkillSource` stores defensive copies of source bytes, the original startup location or supplied label, and the resource. `diagnosticName()` returns the supplied label if present, otherwise the resource description. See `src/main/java/ai/loomspan/internal/skill/YamlSkillSource.java:14`, `:26` and `:54`.

### Supplied YAML and public reload boundaries

`SkillDocument` is the supported public record `(String sourceName, String yaml)`. Its current Javadoc identifies it as a YAML document supplied for a complete update without a more detailed path distinction. See `src/main/java/ai/loomspan/api/SkillDocument.java:3`.

`SkillReloader` exposes two validation overloads and preparation overloads for visibility, explicit variables and publication labels. They all carry supplied documents, namespace and complete execution configuration. The preparation wrappers reach `prepareInternal`. `validate` and `prepareInternal` call `SkillIdentity.requireNamespace` before forwarding into the generation manager. See `src/main/java/ai/loomspan/internal/skill/DefaultSkillReloader.java:36` and `:76`.

`SkillGenerationManager#validate` and `#prepare` create `PreparedCandidateVariables` and use `checkedSkills` to invoke a fresh catalog's `checkedSupplied(namespace, ...)`. Preparation checks staged and resolved content, then constructs the detached runtime. See `src/main/java/ai/loomspan/internal/skill/SkillGenerationManager.java:162` and `:177`.

`PreparedCandidateVariables` uses `document.sourceName()` unchanged as the authored YAML source, map key and issue source. It skips malformed entries so the catalog can own their structural diagnostics. See `src/main/java/ai/loomspan/internal/skill/PreparedCandidateVariables.java:30` and `:44`.

`YamlSkillCatalog#checkedSupplied` validates its namespace using `SkillIdentity.requireNamespace`. `checkSuppliedDocuments` reads each label unchanged, rejects null/blank labels, enforces exact label uniqueness, rejects null YAML, wraps UTF-8 bytes in a `ByteArrayResource` and records the label in diagnostic sources and `YamlSkillSource`. It does not parse the label as a URI or resolve it as a file. See `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:170` and `:181`.

Manifest declaration validation constructs `SkillIdentity(namespace, skillName)`, thereby applying the exact component grammar, reserved substring exclusions and combined pair limit implemented by PR 37.1. See `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:776` and `src/main/java/ai/loomspan/internal/core/SkillIdentity.java:4`.

`SkillDependencyValidator` uses the same source's `diagnosticName()` for dependency issues. The existing observation `sourcePath` field receives the supplied label verbatim through `SkillSourcePathResolver`. No pathname-case rule exists at either supplied ingress.
