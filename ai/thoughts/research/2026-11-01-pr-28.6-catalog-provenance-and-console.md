# Research: catalog execution classification and declaration provenance

**Date:** 2026-11-01T12:24:56-08:00

## Research Question

Map current Framework and Console catalog contracts against `ai/thoughts/tickets/loomspan-pr-28.6-catalog-provenance-and-console.md`: Java execution classification, YAML and annotated provenance, executor identity and implementation, REST removal, CapabilityKind assessment, current readers/fixtures, compatibility marker, and verification/documentation owners. This is Step 1 in pipeline mode, selected profile `full`, approved by the developer with “proceed.”

## Summary

The public catalog already uses `SkillKind` directly and correctly describes executor YAML leaves as `JAVA`. Generation validation and routing retain YAML definitions independently of execution kind. Diagnostic catalog entries currently expose `source` as a combined execution/provenance discriminator: all non-TypeSafe YAML definitions, including executors, become `source: YAML`, without executor identity or Java implementation fields. Java-only diagnostic records reject YAML/path fields.

The nested `loomspan-console` Go service/DTOs, MCP schemas and text, TypeScript unions, browser rendering, and tests still implement the earlier mutually exclusive Java-versus-YAML convention. Several Console consumers still accept the removed `REST` skill concept. Java's shared HTTP fixture generator has already converted its former REST declaration to executor YAML, while some Go tests retain REST expectations. No implementation or tests were run during this research.

`CapabilityKind` was removed in PR 28.3, and fresh searches find no remaining production/test references or translation callers. PR 28.5 already established explicit failure contracts and retained the Maven-derived unreleased snapshot compatibility marker; this checkout contains that implementation. All sources are in this single Git repository, including Console, its canonical Agent Skill, and shared fixture corpora.

## Detailed Findings

### 1. Classification, declaration ownership, and reference-only registrations

- `src/main/java/ai/loomspan/api/SkillKind.java:4` has only `YAML`, `JAVA`, `TYPESAFE`. This is supported Application API under the closed allowlist.
- `src/main/java/ai/loomspan/internal/core/CapabilityMetadata.java:12` stores `SkillKind` directly. `SkillSource` (`internal/core/SkillSource.java:4`) is a three-field internal diagnostic record: sourcePath, beanName, method. There is no public declaration-provenance API.
- `SkillMethodBeanPostProcessor.java:198` registers reference-only executors into `executorsByName`. Their `SkillExecutorRegistration` carries qualified identity, config path, Java access policy, `SkillSource(null, beanName, method.toGenericString())`, and invoker. `registerSkillMethod` at line 216 independently creates callable metadata with `SkillKind.JAVA` and annotated bean/method provenance.
- `SkillGeneration.java:70-105` owns separate immutable callable and executor maps, YAML definitions, and executor configuration. Separate identity maps allow a callable and executor to share a qualified name. Definition validation expects executor form to match JAVA, TypeSafe to match TYPESAFE, and model form to match YAML. Executor-only entries are absent from `capabilities`, which feeds both catalogs.
- `SkillGenerationManager.java:207-253` constructs validated/public metadata from these facts. Each YAML definition retains its own source; executor leaves get JAVA and `SkillExecutionDescriptor.none()`. At present their `CapabilityMetadata.source` contains only the declaration source label, with no Java implementation fields.
- `SkillDependencyValidator.java:33-35,118-123` carries resolved executor bindings in `CheckedSet.executorBindings`, keyed by callable identity. A binding contains the referenced registration, selected immutable configuration, and generation ID. Preparation is metadata-only and does not retain foreign execution resources; admission resolves against selected immutable generations.
- `SkillGenerationManager.java:127-137` captures active per-generation inspection catalogs under its monitor and copies immutable entries afterward. Its fixed executor registrations are available independently from active configuration and runtime resources. `capture` at line 302 selects reachable callable generations and referenced executor namespaces without exposing executors as callables.
- `DefaultSkillCatalog.java:24-46` builds `SkillDescriptor` from callable metadata and directly copies `metadata.kind()`. No intermediate enum translation exists. `ExecutionCoordinator.java:104,157-174` looks up the YAML definition independently and then selects execution by SkillKind; both Java forms use its JAVA branch, with executor argument construction using captured binding.

### 2. Current diagnostic catalog and Java DTO boundary

- `DefaultRegisteredSkillCatalog.java:23-47` checks `definitions.containsKey(name)` first. That lookup already honors declaration ownership rather than excluding JAVA definitions. The definition branch emits `TYPESAFE` or `YAML` based solely on `definition.typesafe()`, resolves its source path, decodes the original bytes as strict UTF-8, and emits output schema from tool metadata. It supplies no Java location or executor identity.
- The following branch handles annotation-only JAVA with beanName/method and no YAML/path. It supplies null output schema, consistent with Java result metadata.
- `RegisteredSkillEntry.java:6-41` defines the current entry and summary shapes. `source` is accepted only as YAML/TYPESAFE/JAVA. Manifest sources require sourcePath, forbid Java fields, and require YAML in detail. JAVA requires beanName/method and forbids sourcePath/YAML. There is no executor field or separate execution-kind/provenance field.
- `SkillSourcePathResolver.java:34-68` returns application-supplied logical source labels unchanged. For file-discovered YAML it derives a descriptive filename/relative path using configured resource roots. Locations are not invocation identities. UTF-8 decoding preserves authored comments and line endings (`DefaultRegisteredSkillCatalog.decode`, line 101).
- `ObservabilityDtos.java:37-53` defines separate summary/detail records with the same fields and delegates validation to RegisteredSkillEntry. Jackson omits null location/YAML fields; detail outputSchema is always serialized, including null.
- `ObservabilityDtoMapper.java:16-25` copies those fields explicitly, so a diagnostic shape change has an explicit mapper consumer in addition to the catalog and record constructors.
- `DefaultRegisteredSkillCatalogTest.java:52-72` currently asserts that executor YAML has diagnostic source YAML, a path, original YAML, and no Java fields. Its helper at line 93 mocks all YAML definition metadata as YAML, including executor form. Existing focused coverage preserves original CRLF YAML and exact case-sensitive lookup.
- `ObservabilityJsonCodecContractTest.java:47-71` exercises production codec round trip and rejects Java+YAML and YAML+Java combinations under the old discriminator convention.

### 3. Go application-client and service validation

- `loomspan-console/AGENTS.md` requires Java/Go/TS/fixtures to move together, exact-version matching, direct signature changes, no fallback/alias/migration reader, and preserved diagnostic content/access boundaries.

Besides validating values, it checks raw field presence: JAVA forbids sourcePath/yaml even when null/empty; other sources forbid beanName/method. Summaries also forbid detail-only yaml/outputSchema. Framework already owns the classification, declaration source bytes and executor binding; consumers present its diagnostics. The ticket addresses observable developer inspection of one callable's two aspects. Existing source ownership, immutable generation/catalog construction, shared HTTP DTO validation, MCP mapping and UI location rendering are the relevant owners. The ticket authorizes direct current-contract changes with no aliases, fallback readers, duplicate classification or new executor lifecycle/catalog.
