## Detailed findings

### Configuration, concrete resources and lifecycle ownership

`pom.xml:90` explicitly declares `org.apache.httpcomponents.client5:httpclient5`;
its version is managed by imported dependency management. The current TypeSafe
guide and timeout fixture name Apache 5.6.1. The POM project version and bundled
documentation skill both identify `1.0.0-beta.9-SNAPSHOT`.

`LoomspanProperties#validateRequiredFields` (`src/main/java/ai/loomspan/autoconfigure/LoomspanProperties.java:218`)
requires a nonblank TypeSafe key and validates explicit service prefixes as
absolute HTTP(S), with host and without query/fragment. Shared header validation
accepts TypeSafe custom headers but rejects Authorization case-insensitively
(`:263`). Existing provider-option validation rejects OpenAI/Gemini options when
their driver does not match. TypeSafe model aliases reject thinking levels
(`:311`). Manifest validation also prevents chat-only fields in native leaves.

`TypeSafeClient` stores one endpoint, API key, static headers, immutable Apache
request/connection settings, and one pooled closeable client per connection
(`src/main/java/ai/loomspan/internal/typesafe/TypeSafeClient.java:35`). It defaults
to `https://api.typesafe.ai` and constructs the endpoint by removing trailing
slashes and appending `/v1/systemone`. This retains `/api` for the documented
OpenRouter prefix. It sets Bearer auth and custom headers on each POST. Both
Apache automatic retries and redirects are disabled (`:67`).

`NamedAiConnectionRegistry` constructs either a concrete TypeSafeClient or the
existing Spring AI chat runtime (`src/main/java/ai/loomspan/internal/autoconfigure/NamedAiConnectionRegistry.java:19`).
`ProviderConnectionRuntime` requires exactly one native/chat resource and
matching driver (`src/main/java/ai/loomspan/internal/provider/ProviderConnectionRuntime.java:8`).
`requireChatModel()` rejects native resources. There is no dummy chat model or
new provider extension interface. Registry shutdown is idempotent and closes
both concrete resource kinds through its single destroy path (`:95`).

Construction failures close the current unregistered runtime, when available,
then previously built resources. Safe configuration exceptions are rethrown;
other RuntimeExceptions are replaced by a connection/settings diagnostic without
an attached cause (`:55`). Cleanup methods invoke the common destroy loop but
discard its returned cleanup exception (`:102`). This is current behavior,
including existing chat construction tests, rather than a new ticket decision.

### Resolved request, attempts, taxonomy and retries

`MissionWorkExecutor#executeEvaluation` wraps native execution in the same mission
worker/lifecycle infrastructure (`src/main/java/ai/loomspan/internal/runtime/MissionWorkExecutor.java:126`).
`TypeSafeExecutor#execute` reads the captured execution binding/generation,
resolves the PR 27.2 declaration once, copies in the configured provider model
verbatim, and serializes the request before entering the loop
(`src/main/java/ai/loomspan/internal/typesafe/TypeSafeExecutor.java:30`). The same
String request is reused for retries.

Every iteration checks interruption and lifecycle openness, reserves the existing
provider-attempt quota, creates attempt metadata, records MODEL_REQUEST_SENT,
then calls the transport once (`:52`). HTTP failures pass through the connection's
translator and existing ProviderRetryDecider; failed-attempt metadata records
classification, category, HTTP status when present, retry decision, delay,
source, summary and diagnostics. Nonretry outcomes register provider failure and
throw. Retry sleeping is interruptible and the next iteration rechecks openness.

`TypeSafeClient#translate` maps native 529 to TRANSIENT/PROVIDER_OVERLOADED
(`:149`). Native transient statuses are 408/429/500/502/503/504/529. The translator
preserves captured error body, status and Retry-After parsed as seconds or HTTP
date. IOException roots map to transient connectivity, with SocketTimeoutException
mapping to timeout. This native mapping is separate from chat transport mapping.

### Response fidelity and usage

Transport 2xx success reads the entire response stream as UTF-8 without a native
response byte ceiling (`TypeSafeClient.java:107`). HTTP errors capture at most
1 MiB, expose `truncated`/`captureLimitBytes`, retain complete Unicode characters
at the boundary, and abort truncated streams instead of draining the remainder
(`:109`). The successful result limit is not coupled to error capture.

After a writable successful HTTP response, the executor decodes the envelope as
a generic JSON tree. Malformed text is retained in `rawBody`; decoded content
is retained as `envelope`, with string-valued served model copied to diagnostics
when available (`TypeSafeExecutor.java:95`). It records successful attempt outcome,
response trace, and response usage before throwing decoding/extraction failures.
The sole answer extraction condition is object-valued `answers`; complete contents
are serialized directly (`:124`). Unknown answer names, empty answers, extension
fields, scalar values inside answers and unexpected values are not validated or
repaired. Missing model/usage metadata does not prevent success.

`nativeUsage` accepts nonnegative integral JSON input/output token counts that fit
int and whose long-computed sum fits int (`:138`). Complete usable counts yield
EXACT, including explicit zeros. Other shapes yield zero accounting placeholders
and UNAVAILABLE, retaining a deep copy of native usage when supplied. No native
text estimate or HEURISTIC branch exists. Only successful transport responses
enter this path; error-body usage is not decoded for accounting.

`DefaultSessionUsageService#recordModelResponse` writes under the existing binding
write gate, updates response-based modelCalls/units once, then enforces existing
quotas (`src/main/java/ai/loomspan/internal/runtime/usage/DefaultSessionUsageService.java:59`).
Provider attempts are separately reserved before sends (`:73`). Question count
does not multiply the counters. Diagnostic cost stays in retained native metadata;
these response counters are not a billing ledger.

### Timeout and physical cancellation

Explicit `request-timeout` configures Apache response timeout and connection socket
timeout (`TypeSafeClient.java:55`). Connect and pool lease timeout are not changed.
The existing reflection fixture asserts three-minute connect/lease defaults;
omitted response/socket values remain unset and effective socket inactivity comes
from Apache SocketConfig.DEFAULT's three minutes. The body-throttling fixture
shows progressing chunks can take longer than explicit timeout while delayed
headers time out. There is no added total elapsed per-attempt deadline.

Each send registers a FutureTask cancellation handle whose `cancel()` invokes
`HttpPost.cancel()` directly; `finally` unregisters it (`TypeSafeClient.java:85`).
`MissionLifecycle#registerPhysicalFuture` tracks the handle alongside framework
futures and immediately cancels registration after cutoff. Mission cancellation
cancels registered handles. The executor checks interruption/open state after send,
and response trace/usage services also use existing write gates. MissionWorkExecutor
owns the surrounding worker interruption and bounded cleanup behavior.

### Native trace producers and consumers

Native request/response data carries `payloadType: evaluation`, endpoint,
requested model, request or envelope/rawBody, and optional served model. Existing
`ModelExecutionIdentity`/`ModelTraceContext` add framework model, connection,
driver, provider model, skill, evaluation segment, retry sequence and attempt
identity. The surrounding root generation supplies declaration/generation
provenance; no new public observer API exists.

`DefaultExecutionTraceRecorder` writes normal MODEL_REQUEST_SENT,
MODEL_RESPONSE_RECEIVED and MODEL_ATTEMPT_FAILED records, with existing bounded
stack evidence plus provider diagnostics
(`src/main/java/ai/loomspan/internal/core/DefaultExecutionTraceRecorder.java:45`).
`recordAgainstFrame` uses `binding.runIfWritable`; the same shared canonical
capture/chunk machinery applies to native payloads. NdjsonTraceRecordWriter
serializes canonical TraceRecords without a native rewrite branch. The existing
derived ExecutionJournalProjector/observer exception is separate from canonical
native evidence and invoke results.

The Java corpus fixture `native-evaluation-success` constructs native request and
chunked response records (`src/test/java/ai/loomspan/internal/runtime/trace/ConsoleTraceFixtureCorpusTest.java:988`).
Its Go consumer test reads logical request/response content, asserts descriptor
availability/completeness, and retains a business-state `Authorization` key
verbatim (`loomspan-console/internal/traceanalysis/fixture_corpus_test.go:84`).
The fixture uses existing attempt and payload representations, not fake chat
messages. Same-version Console compatibility policy applies; no legacy reader or
new format bridge is present.

`TraceRecords#parseModelDetail` recognizes evaluation before applying chat message
assumptions and displays the native object as ordinary formatted JSON
(`loomspan-console/web/src/observability/TraceRecords.tsx:228`). Rendering uses a
preformatted content view (`:404`). `TraceRecords.model.test.tsx:112` covers native
request, envelope, malformed rawBody and chunked content.

## Open questions for planning and verification

1. What fresh fixture/assertion evidence will close native terminal errors,
   disabled/exhausted retries, error-body usage rejection and the expanded
   successful-response accounting matrix? Existing implementation branches and
   helper tests establish behavior but not all acceptance combinations.
2. How will construction-failure cleanup of an actual native pooled client be
   observed, including failure after one native resource has been built? Current
   registry fixtures demonstrate chat resources; normal native shutdown is covered.
3. What native capture-disabled/truncated and failure evidence assertions are
   necessary in addition to the existing generic writer/consumer coverage and
   native success corpus? Capture semantics must remain truthful and unchanged.
4. Implementation must recheck current official TypeSafe/OpenRouter API documentation
   and confirm the effective Apache dependency version. Research made no external
   documentation/live API requests; credentials and live acceptance are not assumed.
5. The registry currently replaces generic construction exceptions and drops cleanup
   failures. Planning must assess ticket scope for construction diagnostic fidelity
   against repository instructions, without inventing masking or content rewriting.

These are technical assurance/scope questions resolvable by the subsequent
planning and verification stages; no missing developer decision prevents Step 2.
