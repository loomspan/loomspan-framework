## Summary

Root pre-checks directly call `SkillRoleEvaluator` with the capability's policy. Runtime planner filtering and dispatch use `DefaultAccessGuard`, which combines captured callable authority with the same low-level evaluator. Executor leaves currently carry their YAML role policy in capability metadata; their captured executor registration independently contains the Java declarative policy. The admitted snapshot already holds the registration needed by the ticket, while invocation already routes through actual managed Spring proxies and scopes the resolved caller on the mission worker thread.

No new public authentication representation is needed to describe the existing flow: the five-component `SkillExecutorInvocation` has business/configuration maps and identity strings only. Registration policy and retained generation identity live internally in `SkillAdmissionSnapshot.ExecutorBinding`.

## Detailed findings

### Policies, resolution, and evaluation

- `src/main/java/ai/loomspan/internal/security/SkillAccessPolicy.java:9` is the immutable internal constituent policy: `UNRESTRICTED`, `DENIED`, or `ROLES`, with roles and an annotation flag. `permitAll()` and `denied()` mark supported Java annotations. An explicitly empty Java roles declaration remains `ROLES`; empty YAML roles become unrestricted through `yamlRoles` at line 42.
- `SkillAccessPolicyResolver.java:13` uses Spring's `SecurityAnnotationScanners.requireUnique` for `DenyAll`, `PermitAll`, and `RolesAllowed`. Its `resolve` method scans the canonical method and target class, preserving Spring precedence and ambiguity behavior rather than merging declarations.
- `SkillRoleEvaluator.java:12` owns the `AuthoritiesAuthorizationManager`, configured once with optional `RoleHierarchy`, and obtains its prefix from optional `GrantedAuthorityDefaults` (default `ROLE_`). Each role is prefixed exactly as supplied. `canAccess` at line 21 treats roles as alternatives within one policy. `checkAccess` at line 32 throws `AccessDeniedException` with the capability name.
- Current role evaluation accepts one `SkillAccessPolicy`, not a composed constituent list. The ticket specifies conjunction between the existing YAML and captured Java constituents while retaining their internal alternative semantics.

### Root validation, invocation, and handoff

- `src/main/java/ai/loomspan/internal/skillapi/DefaultSkillTemplate.java:145` captures the root through `SkillGenerationManager.capture`; `prepareMap` at line 158 validates/normalizes input and then calls `validateAdmission` using the retained snapshot.
- `validatePrepared` at line 193 captures authentication from the configured `SecurityContextHolderStrategy`, calls `authorize`, and closes the temporary generation lease in `finally`. No application method executes during this path.
- `authorize` at line 281 directly calls `roleEvaluator.checkAccess(prepared.capability().name(), prepared.capability().accessPolicy(), authentication)`. It has the complete admitted snapshot available through `PreparedInput`, but currently supplies only capability policy to the evaluator.
- Synchronous `invokePrepared` captures caller authentication, authorizes before session creation, and closes leases on pre-session failures. Its overload with explicit captured authentication starts the session and sends the prepared root through the execution router. The new session stores the caller, allowing router calls with null invocation authentication to use the session fallback.
- `DefaultSkillInvocationHandoff.java:39` calls the same template preparation and authorization before creating the admitted root. Its internal payload retains prepared snapshot/input and the captured `Authentication`. Later `invoke` uses that payload, rather than the invocation thread's security context. It is single-use; release or cutoff clears the payload.
- `DefaultSkillTemplateTest#validateUsesInvocationPreparationAndCallingAuthenticationWithoutExecution`, `#handoffCapturesPreparedInputAndCallingAuthentication`, and the failure/observer tests establish the current facade boundaries. `SkillReachableAdmissionTest` establishes entry-only RBAC without eager child RBAC and temporary validation without reservation.

### Planner filtering and execution authorization

- `src/main/java/ai/loomspan/internal/skill/DefaultSkillVisibilityResolver.java:24` requires the active source mission/session, reads that captured source's YAML `allowedSkills`, resolves each candidate in the snapshot, and invokes `AccessGuard.canAccess` before returning metadata. Discovery executes no business method or argument-dependent advice.
- `src/main/java/ai/loomspan/internal/security/DefaultAccessGuard.java:27` resolves the caller with explicit invocation authentication taking priority over session authentication. This is also used by `ExecutionCoordinator` for Java invocation.
- `canAccess` at line 36 and `checkAccess` at line 45 currently evaluate only `capability.accessPolicy()`. Both also apply `hasCallAuthority`; `checkAccess` preserves a distinct denial for unauthorized captured source/target calls.
- `hasCallAuthority` at line 54 requires the matching session, exact metadata ownership in the captured target generation, and either the captured entry target (no source mission) or a direct allowed-child declaration from the actual current source plus captured target namespace visibility. Retaining a namespace alone cannot grant callable authority.
- `CapabilityExecutionRouter.java:60` repeats `accessGuard.checkAccess` before input validation and dispatch. It subsequently verifies current-session binding and exact captured metadata ownership.
- `ExecutionCoordinator.java:103` checks access again before switching to the target mission. Thus planner publication does not replace dispatch-time checks. Its call-authority checks occur against the source binding before creating the child binding.
- Existing authority tests are `NamespaceAccessGuardTest` (four cases covering exact retained ownership, declared children, same-namespace private calls and private callbacks) and `NamespaceExecutionAuthorityIntegrationTest`. `DefaultAccessGuardTest` covers unrestricted/denied roles, absent callers, session fallback, and explicit caller priority.

### Captured executor policy and lifetime

- `src/main/java/ai/loomspan/internal/core/SkillExecutorRegistration.java:9` stores identity, config path, resolved Java `accessPolicy`, source and an invoker. It is reference-only and is not callable metadata.
- Shared discovery assigns this policy in `SkillMethodBeanPostProcessor#registerExecutor` at line 208; callable Java metadata uses the same resolver in `registerSkillMethod`. `completeDiscovery` also applies shared verification of actual JSR-250 advice for both forms.
- `SkillGenerationManager#prepareCatalog` at line 224 builds executor-leaf metadata as `SkillKind.JAVA`, retaining its YAML definition and `SkillAccessPolicy.yamlRoles(definition.rbacRoles())`. It does not copy the foreign executor policy into the leaf capability.
- `SkillGeneration.java:84` owns the namespace's immutable capabilities, definitions, fixed executor registrations and executor configuration. Callable and executor indexes are separate. `owns` uses exact metadata object identity.
- `SkillGenerationManager#capture` at line 298 selects one active generation per reached namespace under the registry monitor, follows root-reachable allowed-child edges, and captures executor namespaces for reached executor leaves without traversing unrelated callable declarations. It increments ownership of each selected generation.
- `validateAdmission` at line 348 runs the dependency validator outside the monitor. `SkillDependencyValidator#checkAdmission` at line 77 validates the reached immutable graph and returns an admitted snapshot with executor bindings.
- `SkillDependencyValidator#resolveExecutor` at line 165 resolves the registration in the selected owner's executor index, enforces dependency namespace visibility, selects the configuration map, and records that owner's generation ID. This is the shared preparation/admission binding rule, not an invocation-time live lookup.
- `SkillAdmissionSnapshot.java:8` contains entry identity, immutable namespace-generation associations and per-skill `executorBindings`. Each `ExecutorBinding` contains the actual `SkillExecutorRegistration`, immutable configuration and generation ID. `executorBinding(skillName)` at line 34 fails explicitly when no binding was admitted.
- `ExecutionCoordinator.java:169` reads the parent's captured snapshot binding to build the executor invocation. No live registry or configuration rebinding occurs there.
- `ExecutorDependencyResolutionTest#retainedBindingAndTargetBasePublicationRemainCoherentAcrossForeignReplacementRemovalRecreation` verifies retained configuration/generation selection. Its line 126 asserts that registrations are the same fixed object across ordinary public replacement/recreation. Public publication changes documents/configuration/visibility, not Spring annotation policy. Tests distinguishing different captured Java policies can therefore use internal snapshots/generations/registrations; this does not imply adding a public policy mutation facility.
- `ExecutorDependencyResolutionTest#executorRetentionDoesNotTraverseUnrelatedDeclarationsOrGrantCallableAuthority` already checks executor-only namespace retention and undeclared sibling denial. Its concurrent admission test verifies expensive validation does not lock out publication.
- `ExecutorGenerationExecutionIntegrationTest#retainedWorkUsesCapturedConfigAndIdentityAcrossReplacementRemovalAndRecreation` covers the real facade/handoff path, configuration identity, caller identity, namespace withdrawal/recreation, unchanged Spring bean lifetime and absence of executor callability.

### Actual proxy advice and worker authentication

- `src/main/java/ai/loomspan/internal/core/JavaSkillInvoker.java:22` fetches the current Spring-managed bean by name, selects a method invocable on its actual runtime proxy, and invokes it with actual bound arguments. Result conversion is shared between callable and executor forms. It unwraps only invocation infrastructure through the existing failure policy.
- `SkillMethodBeanPostProcessor#completeDiscovery` at line 63 checks method invocability and applies `Jsr250EnforcementVerifier`. Unsafe private/final/static methods on CGLIB proxies fail startup.
- `Jsr250EnforcementVerifier.java:26` checks that each supported annotation has the actual standard JSR-250 advisor attached and applicable to the final proxy method and target class. It inspects metadata/advisors and does not invoke the application method.
- `ExecutionCoordinator.java:162` resolves the trusted caller once for Java work. Inside `missionWorkExecutor.execute`, it opens `ScopedAuthentication`, resolves references, and invokes either the captured executor registration or Java capability. Both forms run under the same scope with actual arguments.
- `ScopedAuthentication.java:21` creates a fresh security context, installs the resolved caller and restores the exact previous context object when the scope closes. It does not mutate session authentication.
- `MissionWorkExecutor.java:39` captures `ExecutionBinding`; its submitted callable restores this binding on the actual worker thread. Java authentication scope is installed inside that callable by the coordinator.
- `JavaSkillAuthorizationIntegrationTests` compares Spring proxy results and the constituent evaluator over default/custom/empty prefixes, hierarchy, alternatives, PermitAll, DenyAll, empty roles, JDK interface policy and Spring ambiguity rules.
- `JavaSkillAuthenticationScopeIntegrationTests` exercises nested scopes, success, denial, business failures, reused worker restoration and simultaneous isolated contexts. These tests directly exercise scoped security against real Spring beans rather than every framework entry/child/executor combination.
- `SharedJavaDiscoveryInvocationTest#realMethodSecurityIsPreservedForBothRoles` parameterizes actual JDK/CGLIB method-security behavior across both roles. It also covers class-level executor policy and failure when applicable JSR-250 enforcement is absent. These are shared-discovery/invoker tests, separate from YAML constituent composition at facade/filter/router boundaries.
