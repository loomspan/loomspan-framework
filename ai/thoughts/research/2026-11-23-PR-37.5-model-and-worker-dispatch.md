## Summary

`BoundCapability` already binds a resolved `CapabilityMetadata` to an invocation closure. Its name is the metadata identity rendered with a colon. `SpringAiToolCallbackAdapter` currently copies that name directly into the provider `ToolDefinition`. `CanonicalToolCallingManager` validates returned selections by parsing them as Loomspan identities, obtains the parsed colon spelling and compares it against callbacks on the current request. It still contains a response-copy branch for canonical renaming, although the strict parser introduced by PR 37.1 now returns the same spelling for every accepted input.

The planning and worker path already carries capability names separately from provider callback adaptation. Planning prompts enumerate `BoundCapability.name()`. `PlanStructureValidator` parses root/task selections as qualified Loomspan references and checks exact membership. `StepPromptBuilder` repeats the accepted task capability in the assignment and JSON envelope. The step parser invokes `StepAction.canonicalSelection()`, and `StepActionValidator` then requires membership among visible tools and equality with the assigned task capability before invocation. The engine's worker model request carries an empty capability list. It returns structured text that the engine interprets, so a provider function name and a worker `toolName` have separate entry paths.

Canonical trace capture records model-returned tool names and argument strings directly from Spring AI message parts before ordinary dispatch. Tool lifecycle records separately identify resolved callables through `capabilityName`, and model metadata carries the executing `skillName`. The request payload captures ordered messages and optional output-schema evidence. It currently does not contain an inventory of offered function definitions. Actual HTTP request assertions in integration tests establish the offered provider surface.

Existing tests cover exact callback invocation, complete-response validation before side effects, message fidelity, assigned task constraints, provider status rejection, captured generation authority and authorization restoration. Many of these tests still contain the earlier single-hyphen encoding, camelCase declarations or case-normalization expectations. Those are source-visible test inputs, with no claim that they pass at this checkout. Earlier ticket completion records assign these consumer conversions and their verification to PR 37.5 or final integration.

## Provider request and dispatch path

### Resolved callable binding

1. `ExecutionCoordinator` determines ordinary versus explicit-step execution from the YAML definition. It creates the model interaction and binds the current visible surface before calling the selected mission engine. See `src/main/java/ai/loomspan/internal/core/ExecutionCoordinator.java:201` and `:207`.
2. `DefaultSkillVisibilityResolver.visibleSkillsFor` verifies the current source mission/session, gets the containing definition, iterates its declared allowed children and resolves each exact `SkillIdentity` through the captured snapshot. Missing or inaccessible children are omitted from the visible list. This uses the callable snapshot and `AccessGuard.canAccess`, and skips the current skill itself. See `src/main/java/ai/loomspan/internal/skill/DefaultSkillVisibilityResolver.java:24`.
3. `DefaultCapabilityInvoker.bind` associates each resolved metadata object with the applicable declared input bindings and a closure capturing session, authentication and source owner. No returned provider name participates in this binding. See `src/main/java/ai/loomspan/internal/runtime/tool/DefaultCapabilityInvoker.java:62` and `:75`.
4. `BoundCapability` retains metadata and invocation. `name()` delegates to metadata, `metadata()` exposes the resolved object internally, and invocation copies arguments into an unmodifiable ordered map before calling the closure. Assigned invocation separately carries task ID and prior result snapshots. See `src/main/java/ai/loomspan/internal/runtime/tool/BoundCapability.java:21`, `:37` and `:46`.
5. `CapabilityMetadata.name()` returns `identity.toString()`. Its constructor requires the internal `CapabilityToolDescriptor.name` to equal this resolved name. The descriptor is therefore currently an internal Loomspan descriptor, even though the provider adapter consumes its description/schema. See `src/main/java/ai/loomspan/internal/core/CapabilityMetadata.java:25` and `:41`.

### Adapter and request preparation

`SpringAiToolCallbackAdapter.adapt` maps each bound capability to an anonymous Spring `ToolCallback`. At line 26 its `ToolDefinition` uses `capability.name()` directly. The callback retains the same bound object. Its call overload parses the raw argument document with `OrdinaryToolArguments`, invokes that bound capability and uses Spring's `DefaultToolCallResultConverter`. Existing exception wrapping preserves an existing `ToolExecutionException` or wraps a different exception with the same definition. See `src/main/java/ai/loomspan/internal/springai/SpringAiToolCallbackAdapter.java:19`.

`SpringAiModelInteraction.doCall` builds a `ChatClient` request with the supplied system/user input. It adapts capabilities when the list is nonempty. In standard nonplanning mode it also adds the Framework inability control callback `loomspan_cannot_complete`, even when there are no application capabilities. This control has its own explicit JSON argument contract and is distinguished by callback type. See `src/main/java/ai/loomspan/internal/springai/SpringAiModelInteraction.java:41` and `:62`, and `PlannerInabilityTool.java`.

The production assembler installs one `ToolCallingAdvisor` with `CanonicalToolCallingManager` around Spring's real manager. See `src/main/java/ai/loomspan/internal/springai/SpringAiChatClientAssembler.java:49` and `:65`.

### Current selection validation

`CanonicalToolCallingManager.resolveToolDefinitions` validates every application callback definition by `SkillIdentity.parse` and equality with its round trip. An actual `PlannerInabilityTool` receives separate handling. It asks the delegate for definitions and validates those too. See `src/main/java/ai/loomspan/internal/springai/CanonicalToolCallingManager.java:27`.

`executeToolCalls` performs the following operations before any callback side effect. See the same file at line 39.

- It enforces output-repair dispatch state and rejects a provider response whose status is incomplete or otherwise rejected by the driver classifier.
- It requires request options implementing `ToolCallingChatOptions` and obtains callbacks only from that request's options.
- It builds a set of application callback definition names, parsing each through `requireCanonical`.
- It walks all response generations and all complete `ToolCallPart` entries. It leaves other rich parts alone and ignores partial streaming tool-call parts for selection purposes.
- It handles an exact `loomspan_cannot_complete` name only if the Framework control callback is bound and requires the control to be the response's sole tool selection.
- For each application call it executes `SkillIdentity.parse(call.name()).toString()`, checks that parsed name against the bound set and rejects null/blank arguments before Spring can replace them with `{}`.
- It delegates the response after all selections have passed.

The method's `changed`, `changedResponse`, replacement `ToolCallPart` and replacement `Generation` machinery was written for a parser that normalized names. At this checkout `SkillIdentity.parse` requires exact lowercase components and `toString()` recreates the exact same colon-qualified string. The rename branch at lines 81–88 has no accepted input that makes its inequality true. `StepAction.canonicalSelection` and `PlanStructureValidator.canonicalSelection` likewise round-trip a strict spelling now. These are verified source facts for planning to evaluate within the explicitly requested exact-dispatch work.

### Matching Spring implementation

### Prompt and action handling

`StepPromptBuilder.buildAssignedStepPrompt` reads the exact accepted task `capabilityName` and emits it as all of the following. See `src/main/java/ai/loomspan/internal/runtime/step/StepPromptBuilder.java:47`, `:80` and `:106`.

- The assignment's `Exact capability/tool` value.
- The single available tool for that assignment.
- The JSON-encoded `CALL_TOOL.toolName` illustration.

The prompt explicitly requires the assigned task/tool and forbids choosing another task or calling the parent. `StepLoopMissionExecutionEngine` makes the action-generation request with `List.of()` capabilities at lines 1126–1128. The worker model's answer is JSON text, distinct from native provider function-call dispatch.

`parseStepAction` retains the original response string for action evidence/correction, reads its JSON tree/typed action and invokes `parsed.canonicalSelection()` at line 1255. That method parses `toolName` as a strict Loomspan qualified identity and builds a new `StepAction` with the same arguments. Bad grammar becomes action-correction feedback. Explicit null `toolArguments` is rejected before dispatch, while omission follows existing empty-map behavior. Planner inability and final response have their existing separate envelopes. See `src/main/java/ai/loomspan/internal/runtime/step/StepAction.java:23` and `StepLoopMissionExecutionEngine.java:1216`.

`StepActionValidator.validateAssigned` requires the exact task ID and an IN_PROGRESS task before checking the tool. `validateToolBindingAndArguments` requires the name to be in the current visible tool set and exactly equal to that accepted task's capability, then validates declared binding ownership and model arguments. It never retries a lookup in another namespace. See `src/main/java/ai/loomspan/internal/runtime/step/StepActionValidator.java:66`, `:111`, `:121`, `:133` and `:153`.

`invokeAssignedAction` validates again, finds the visible `BoundCapability` with exact name equality and calls `invokeAssigned` with accepted task ID and prior-result snapshots. See `StepLoopMissionExecutionEngine.java:1163` through `:1208`. Automatic contribution-free assignment dispatch enters the same validator/invoker using the assigned task's name. See lines 900–925. It sends no worker model call.

## Provider evidence and resolved trace identity

`ProviderAttemptCallAdvisor` is the final pre-provider advisor and records one sent request, received response and usage contribution per physical attempt, including rejected status evidence before throwing. `NativeOutputContract.prepare` runs before capture. The raw response is observed before `CanonicalToolCallingManager` returns to dispatch. See `src/main/java/ai/loomspan/internal/chat/ProviderAttemptCallAdvisor.java:60`, `:81` and `:134`.

Its current request payload stores ordered message maps and, when present, canonical/prepared generation schema evidence. It does not serialize `ToolDefinition` objects or callback names into an offered-tools array. See lines 208–224. A provider integration can inspect the actual HTTP request body to establish the function definitions sent by the official adapter. Request trace continuation messages can also include earlier assistant calls and tool responses with the names exchanged.

`messagePayload` stores exact nullable text, message metadata, ordered rich parts and assistant `toolCalls` entries containing `id`, `name` and `arguments`. Tool response entries contain the recorded `id`, `name` and content string. `partPayload` retains original tool-call objects, payloads and attributes, as well as reasoning and unknown provider parts. No Loomspan identity parser is used in this capture. See `ProviderAttemptCallAdvisor.java:225`, `:235`, `:245` and `:255`.
