# Research — Explicit-step action acceptance, failure identity, and ordered joins

## Research question

Where does the current checkout establish the model-action protocol, active assignment, failure identity, and parallel join behavior that [PR 29.2](../tickets/loomspan-pr-29.2-step-planner-inability.md) will extend?

## Summary

The developer confirmed the Full 5-Step Pipeline after automatic triage. The working tree was clean on `main` at `e8de226`, the committed PR 29.1 baseline. This step read code and existing tests without executing tests. `mvn -version` reports Maven 3.9.6 and Java 21.0.2 on Windows.

Explicit-step execution already separates plan generation, model action correction, framework dispatch, assignment outcomes, and final synthesis. Its ordinary parallel join waits on submitted futures in accepted order, folds every ordinary outcome, and currently propagates the first failure in that order. The standard-control implementation supplies the shared exception, failure identity, diagnostics, and caller feedback. Its recording entry point currently requires an active `MODEL_CALL` frame, while step actions are parsed under the enclosing `STEP_EXECUTION` frame after the model frame closes.

## Detailed findings

### Routing, action parsing, and result acceptance

- `src/main/java/ai/loomspan/internal/core/ExecutionCoordinator.java:177–196` selects the step engine and `STEP_EXECUTION` interaction only for an explicitly enabled YAML planner. It binds visible tools against the captured generation and caller authentication before invoking the engine. `LoomspanAutoConfiguration.java:424–463` wires the internal engines and coordinator as integration machinery. `SpringAiModelInteraction.java:41–75` exposes the existing standard control only in standard, non-planning calls and uses the same request flow for text and attachment-bearing inputs.
- `src/main/java/ai/loomspan/internal/runtime/step/StepLoopMissionExecutionEngine.java:219–249` starts usage, materializes input and invokes the planning service before entering the action loop. `:856–897` opens the step frame with trusted assignment facts and short-circuits the model loop when the bound capability is eligible for framework dispatch. That path validates its synthesized tool call, then rechecks lifecycle and task validity before invocation (`:1122–1130`). Neither initial planning nor automatic assignment dispatch uses the step-response parser.
- `StepActionType.java:6–16` contains `CALL_TOOL` and `FINAL_RESPONSE`. `StepAction.java:13–36` ignores unknown properties, binds nullable fields, and canonicalizes only tool selection. `StepLoopMissionExecutionEngine.java:1175–1232` retains the original response in the caller, unwraps the candidate with whitespace/fence handling, deserializes the action, and in synthesis wraps an object without `stepAction`, `action`, or `finalResponse` as bare successful output. A bare reason object therefore remains ordinary candidate output today. The shared planning mapper enables unknown-property failure (`src/main/java/ai/loomspan/internal/serialization/LoomspanJacksonCodecs.java:35–36`), but the action record opts out. The standard inability tool uses a reader with local duplicate-key and trailing-token checks (`PlannerInabilityTool.java:35–37`); that reader is not the step parser.
- `StepActionValidator.java:34–84` validates synthesis and assignment separately. Assignment checks use the exact trusted task ID and current `IN_PROGRESS` state in the admitted plan before enforcing the bound capability and argument contract. Final validation checks response presence and complete task status (`:205` onward). The prompt envelopes live in `StepPromptBuilder.java:104–169`. Corrective instructions and full rejected-candidate evidence live in `StepActionCorrection.java:38–57`.
- `StepLoopMissionExecutionEngine.java:898–1028` uses one bounded malformed-action retry for either parsing or contextual validation. It writes rejection evidence and the next prompt includes the rejected candidate as quoted data. A parsed action has a `STEP_ACTION_PROPOSED` record before contextual validation. `FINAL_RESPONSE` alone currently enters output composition and schema/linter/evidence validation with separately tracked retry budgets. Accepted actions write `STEP_ACTION_VALIDATED`. A tool exception exits through the step catch (`:1031–1058`) and never cycles back to model action generation.
- `StepLoopMissionExecutionEngine.java:493–536` gates output forwarding, complete output assembly, and synthesis on successful accepted work. Fully bound assembly and designated-child forwarding return without model synthesis. Mixed assembly uses a synthesis contribution and records final assembly only after a successful contribution. A synthesis failure leaves already folded task successes available in the mission. Root finalization retains the root plan and validator outcomes independently of the trace outcome (`ExecutionCoordinator.java:262–279`).

### Admitted work, cancellation, and failure selection

- `StepLoopMissionExecutionEngine.java:375–416` checks lifecycle, unit feasibility, and `max_steps` capacity before admitting a unit. Each member occupies one assignment slot. Completion reserves one slot when synthesis is required. All members of a group use the same immutable pre-unit result and summary snapshot. Parallel admission transitions the whole ordered unit to `IN_PROGRESS` before submission (`:417–446`, `:606–641`); serialized execution admits one member at a time (`:463–488`).
- Each submitted member receives an isolated forked branch. `MissionLifecycle.admitUnit`, `taskStarted`, `registerFuture`, and `publishOutcome` track admission, physical start and returned outcomes separately (`src/main/java/ai/loomspan/internal/core/MissionLifecycle.java:159–232`). Ordinary `RuntimeException` failures from `executeOneStep` are recorded and returned as `AssignedTaskOutcome.Failure` by `StepLoopMissionExecutionEngine.java:644–686` unless the thread is interrupted. A returned failure is a regular future value, so it neither cancels siblings nor stops the coordinator from getting subsequent futures. An exception escaping the callable uses the separate exceptional join path (`:689–719`).
- `StepLoopMissionExecutionEngine.java:739–811` folds in accepted member order. A successful outcome completes the task and records its result and success credit. A failed outcome marks the task failed and plan stale, and supplies no dependency result. The current failure note says `Tool … failed` for any assignment failure, including a model or validation failure that precedes invocation. A successful sibling remains in the folded plan. Only after folding does `propagateFirstFailure` select the first failed outcome (`:722–729`). That selector does not currently consult the shared classification. The next unit and synthesis are after this propagation point.
- The owning future is waited on under the mission timeout, and the cancellation paths consult `MissionLifecycle.primaryCancellation()` (`StepLoopMissionExecutionEngine.java:264–327`). `beginCancellation` records the first cause and failure ID, moves to cancelling, and requests interruption of admitted futures. Open-work checks are ancestry-wide and exclude cancelling/cut-off missions. General writable checks permit some cancelling-phase publication before cutoff (`MissionLifecycle.java:249–286`, `:345–373`, `:408–449`). Cutoff cleanup folds available outcomes, marks unresolved admitted tasks failed, leaves never-admitted tasks pending, and fences physically late state and trace writes (`StepLoopMissionExecutionEngine.java:1442–1518`). An ordinary nested timeout or depth failure can be an individual member outcome before owning cancellation is considered.

### Failure identity, evidence, and caller boundaries

- `src/main/java/ai/loomspan/api/PlannerInabilityException.java` is already in the supported allowlist (`src/test/java/ai/loomspan/architecture/LoomspanPublicSurfaceArchitectureTest.java:38`). Its reason constructor preserves the validated string via `getMessage()`. `SkillFailurePolicy.java:12–37` recognizes infrastructure wrappers and subclasses of `RecoverableSkillException`; it does not unwrap arbitrary application exceptions. `StepLoopMissionExecutionEngine.unwrapMissionFailure` presently returns its argument unchanged (`:1552–1555`).
- `LoomspanSession.recordFailure` is the first-record authority (`:147–199`). It keys by the effective throwable's identity, derives `kind: planner_inability` from the effective subtype, preserves `exceptionMessage`, and emits the bounded stack diagnostic followed by an optional additional diagnostic only on first recording. `TraceDiagnostic.plannerInabilitySignal` uses the existing 1 MiB UTF-8 capture limit, a character-safe truncation boundary and `text/plain; charset=utf-8`. `ExecutionBinding.recordPlannerInability` binds first recording to an ancestry-wide open check, interrupt check and live `MODEL_CALL` leaf. `PlannerInabilityTool.accept` supplies the standard call's ID/name/raw arguments to this entry point. The ordinary `DefaultExecutionStateService.recordFailure` records the active leaf through a general writable check and has no optional-diagnostic parameter (`:495–501`).
- `StepLoopMissionExecutionEngine.callModelForStep` opens a model frame and closes it in `finally` before returning the model text (`:1062–1106`). Its caller then proposes and validates the action under the active step frame (`:928–965`). `trustedStepIdentity` supplies `planId` and `stepNumber`, plus `assignedTaskId`, capability and group facts when there is an assignment (`:814–830`). Synthesis has no assignment. The step and task catches, capability invoker and mission coordinator can each record the propagated throwable. The registry returns the first failure ID without appending diagnostics again.
- `ProviderAttemptCallAdvisor.java:102–112` records the provider response and then updates model usage before returning to the consumer. `DefaultSessionUsageService.java:58–69` charges model calls/usage and checks both quotas at that boundary. Transport attempts and actual tool invocations have their own existing reservations. The step worker sends no Spring AI callback tools (`StepLoopMissionExecutionEngine.java:1089–1090`). The model response record can therefore exist even when a post-response quota failure prevents the step parser from proposing an action.
- `DefaultCapabilityInvoker.java:216–227` records a failed invocation and propagates the effective exception rather than recording a result. `SpringAiChatClientAssembler.java:64–76` produces standard failed-call feedback using `SkillFailurePolicy.recoverable` and adds `kind` for the shared subtype. This boundary already works across an intervening explicit-step invocation when a standard descendant declares inability. `ExecutionCoordinator.java:198–224` records or reuses the failure ID for completion, with existing primary cancellation handling. `LoomspanSessionRunner` and the public facade retain the originating exception on direct/admitted failure. Recoverability and the failed root's completion linkage are separate facts.
