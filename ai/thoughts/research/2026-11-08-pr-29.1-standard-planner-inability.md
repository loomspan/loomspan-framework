## Failure identity, lifecycle, and observability

- `RecoverableSkillException.java:8–22` accepts a non-null, nonblank message and returns it unchanged to its superclass. `SkillFailurePolicy.java:12–40` unwraps reflection, proxy, worker-future, and Spring AI tool infrastructure wrappers. An ordinary application wrapper remains the effective exception. `TraceFailureMetadata.java:18–25` labels effective recoverability and type. It is also used for noncanonical frame/context facts, while `LoomspanSession.java:147–208` owns `ERROR_RECORDED` payload and identity. That method locks, deduplicates on effective throwable identity, records existing causal links through the cause chain, and stores the exact `exceptionMessage` separately from contextual `message`. The existing `diagnostics` list contains one `JAVA_STACK_TRACE`.
- `DefaultMissionExecutionEngine.java:107–157` opens the `MODEL_CALL` frame before invoking Spring AI. Within dispatch, the current `ExecutionBindingScope` already owns the session and physical branch leaf. `DefaultExecutionStateService.java:496–501` uses the same leaf and lifecycle write fence for failure recording. `DefaultMissionExecutionEngine` records a model failure before closing that frame. Its attachment catch at lines 144–154 then wraps every runtime exception in a normal `IllegalStateException` suggesting media support. The original throwable is recorded, but the new outward wrapper is terminal under the existing policy. This behavior can affect propagated recoverability and terminal/lifecycle failures as well as the proposed inability.
- `LoomspanSession.java:155–160` returns the first failure ID without replacing first origin or diagnostics. `DefaultCapabilityInvoker.java:81–92, 140, 223` accounts for real application calls and records failure at later boundaries. `ExecutionCoordinator.java:200–228` distinguishes lifecycle cancellation and propagates failure; `MissionWorkExecutor.java:73–114` handles timeout, interruption, authoritative cancellation, and worker wrapper propagation. `LoomspanSessionRunner.java:325–346, 397–412` links root failure at completion and suppresses observer failure onto a primary execution failure. `DefaultSkillTemplate.java:243–267` uses the same completion callback for direct and admitted roots and preserves an existing `SkillException`. A recovered child can still have its own failure record while the root has no completion failure.
- Lifecycle admission and cleanup write authority differ. `MissionLifecycle.java:194–198, 399–438` shows `requireOpenForNewWork` checks the entire ancestry for `OPEN` and framework cutoff. `ExecutionBinding.requireWritable` calls the separate ancestry guard that still permits writes during `CANCELLING`, while cleanup records are settling. The existing `runWhileOpen` helper checks under the ancestry locks. Worker timeout is enforced by `Future.get` in `MissionWorkExecutor.java:69–79`, and provider backoff has its own interruption check. A dispatch decision and its first write must respect these boundaries. A plain write guard alone is not evidence of open admission.
- `ProviderAttemptCallAdvisor.java:64–107` reserves and traces each physical attempt, catches provider-chain exceptions for retry/translation, then records returned responses and charges usage before returning to the tool advisor. `DefaultSessionUsageService.java:59–99` enforces post-response model-call/usage quotas and pre-send provider-attempt quota and counts application tools at the existing invoker boundary. A successful provider response can therefore be captured and accounted before an ensuing dispatch failure; a quota can stop dispatch first. No tool invocation is created until the application callback reaches `DefaultCapabilityInvoker`.
- `BoundedStackTraceCapture.java:13–27` and `TraceDiagnostic.java:4` establish the 1 MiB text diagnostic budget and record fields. Stack capture deliberately normalizes carriage returns at lines 72–86. `ProviderFailureGuidance.java:52–58, 85–97` separately bounds UTF-8 guidance without stack normalization. The repository JSON codecs use distinct mappers (`LoomspanJacksonCodecs.java:30–47`); YAML enables strict duplicate detection, while schema-tree and canonical-trace mapper configuration do not explicitly enable it. A closed tool-argument validation must account for parser handling of duplicate keys and trailing input; converting directly to a typed/coercing representation does not establish the required original shape.
