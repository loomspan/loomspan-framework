## Summary

bundled authoring skill. Current registered kinds are YAML, JAVA, and REST; current
connection drivers are OPENAI, ANTHROPIC, GEMINI, and OLLAMA. YAML parsing,

carry arbitrary payload objects, while the Console model-detail renderer currently
interprets those objects exclusively as chat messages or response content strings.

## Detailed findings

### Manifest and request-side authoring boundary

`src/main/java/ai/loomspan/internal/skill/YamlSkillManifest.java:29` defines strict
manifest fields. Its `Field` enum and setters track declaration presence separately
from values, including explicitly null/false/empty fields. This is already used by
REST and forwarding exclusions. No `typesafe` field exists.

`YamlSkillCatalog.java:315` reads and validates definitions. REST returns early
without model configuration; other YAML declarations require a configured model,
validate output/linter/concurrency settings, compile evidence, and derive thinking
settings. `resolveEffectiveThinkingLevel` supplies the existing default only when
the selected alias supports thinking. `readManifest` at line 400 reads the YAML
tree first, performs raw-shape checks, then converts it to the manifest class.

`LoomspanJacksonCodecs.java:35` owns the YAML codec with strict duplicate detection
and unknown-property rejection. Resource content is read as bytes by
`YamlSkillCatalog`; it is not Spring configuration placeholder-expanded. Supplied
`SkillDocument` content enters the same rules. Existing `prompt` setter strips
text; that is the chat prompt field, not evidence that new TypeSafe string values
are stripped.

`YamlSkillCatalog.java:787` and `:919` enforce object-root input schemas and recurse
through properties/items. Attachment input nodes already exist for other skills.
Supported input vocabulary is the existing manifest AST, with no numeric bounds,
minimum/maximum array length, or general JSON Schema language.

`YamlSkillDefinition.java:19` defensively copies the manifest at construction,
returns copies from accessors, preserves declared-field tracking after conversion,
and captures execution configuration, evidence, source bytes, and allowed-child
constraints. Its current rest/non-rest constructor condition requires execution
configuration for all non-REST YAML. Output schema is currently the authored schema;
there is no derived TypeSafe declaration/request representation or template resolver.

The accepted ticket specifies registration syntax/literal checks and invocation
resolution once after ordinary input validation. Fixed question IDs/types, escaped
single-pass `${/input...}` substitution, primitive request shapes, and generated
descriptive schemas are new TypeSafe behavior. The existing JSON tree codec and
JSON Pointer library are available; shared binding paths have a separate narrower
object-field grammar. The accepted feature does not expand that binding grammar.

### Input normalization and direct/child execution

`DefaultSkillTemplate.java:152` validates prepared root input and `:270` dispatches
through `CapabilityExecutionRouter`. Its generation capture precedes conversion
and validation, protected by `SkillGenerationExecutionIntegrationTest:55` and
`:91`. `CapabilityExecutionRouter.java:59` applies access checks, full receiver
validation through `SkillInputValidator.validateExact`, ownership/session checks,
and hands normalized input to the coordinator. `executeAssembled` supplies exact
paths for author-bound subtrees, retaining their separate no-coercion contract.

`SkillInputValidator.java:25` defines ordinary versus exact validation. At `:253`,
ordinary number values are returned as Number and numeric strings use
`Double.parseDouble`; finite Double/Float checks here apply only under exact
policy. Thus a TypeSafe request-side finite/JSON-compatible check remains a
distinct ticket requirement even after ordinary input validation. Open branches,
maps/lists, exact paths, and optional values have existing owners.

`ExecutionCoordinator.java:101` loads a YAML definition only for `YAML_SKILL`.
It creates a child mission inside the captured execution binding, opens the
mission frame, and checks access. At `:154`, JAVA/REST run through
`MissionWorkExecutor`; other YAML creates `ModelInteraction`, binds visible
tools, and enters ordinary or step-loop mission execution. There is currently no
TypeSafe leaf branch. Frame closure, primary cancellation and failure ownership
are coordinator concerns shared by both paths.

`MissionWorkExecutor.java:37` propagates the captured binding onto physical work,
records mission start, registers the owning future, waits under the captured
mission timeout, and handles cancellation/interruption/cutoff cleanup. The same
executor serves direct and model execution. `MissionLifecycle.java:26` owns
admission, cancellation, write fencing, hierarchical cancellation, and the 250 ms
cleanup grace. It tracks and cancels futures; this currently supplies no direct
Apache request cancellation integration. `requireOpenForNewWork`,
`runIfWritable`, and `requireWritable` are the authoritative existing controls.

### Generations, output metadata, bindings, and forwarding

`SkillGeneration.java:58` currently accepts YAML or REST capabilities as definition
owners. It captures immutable capability/definition maps, public and registered
catalogs, and its execution runtime. `SkillGenerationManager.java:504` builds the
whole executable generation. REST resolves a handler invoker; chat YAML uses the
coordinator path and publishes `CapabilityKind.YAML_SKILL`. Capability tool
metadata receives the already-computed effective output schema.

`SkillGenerationManager.java:442` resolves effective output schema, recursively
following `output_from` and detecting forwarding cycles. Otherwise it emits
authored schema metadata for non-REST YAML. The metadata representation supports
the ticket's type/properties/required/enum/description/boolean additionalProperties
vocabulary. `DefaultSkillCatalog.java:30` uses `metadata.tool().outputSchema()`;
it does not independently infer output contracts.

`SkillGenerationManager.java:308` validates parent output bindings using available
source and destination schemas. `checkBindingCompatibility` at `:379` checks
types (including integer→number widening), nullable incompatibility, enum
intersection, array items, known nested properties, and required closed-object
conflicts. Unknown/open branches retain partial evidence rather than complete
subtyping proof. `OutputBindingComposition` selects actual values and validates
the assembled destination at runtime. Destination matching/canonicalization
uses `OutputSchemaValidator.propertyNamesMatch`; source value lookup stays exact.

`ChildInputBindingDeclarations.java:14` independently validates parent paths,
producer topology and dependencies. It does not run the parent's output-schema
compatibility checker for child receiver inputs. `CapabilityExecutionRouter`
validates the fully assembled actual receiver input under exact subtree policy.

`StepLoopMissionExecutionEngine` already retains accepted child task results and
returns designated `output_from` text without parsing, synthesis or output
validation after all accepted work finishes. `RESULT_FORWARDED` is emitted by
`DefaultExecutionTraceRecorder.java:99`. `DesignatedChildResultIntegrationTest:59`
uses public `SkillTemplate`, real HTTP fixtures and model/Java/REST producers;
`:185` and `:190` cover parallel-root isolation and captured schema/target after
reload. Its existing tests assert later accepted work completes and no parent
final model request occurs. Effective inherited schema is metadata, not a new
parent validator.

### Connections, configuration, resource ownership, and provider attempts

`AiDriver.java:3` lists four chat drivers. `LoomspanProperties.java:128` validates
connections, driver-specific options, request timeout, credentials, headers, and
retry policy. `:249` permits static headers only for OPENAI/ANTHROPIC. `:268`
validates model alias connection and provider-model presence. Current model
entries also declare thinking-levels. Existing `request-timeout` accepts exact
whole milliseconds between 1 and Integer.MAX_VALUE, and excludes OLLAMA.

`ProviderConnectionRuntime.java:8` requires a non-null Spring AI `ChatModel`,
driver, attempt ownership, retry policy and failure translator. The record is
internal despite being public. `NamedAiConnectionRegistry.java:20` constructs
each through `SpringAiProviderIntegration`, rejects enabled framework retries
for opaque clients, and cleans partially built resources on construction failure.
`:91` provides idempotent shutdown, closing chatModel as DisposableBean or
AutoCloseable. Both normal and construction-failure cleanup share that owner.

`ExecutionRuntime.java:14` owns prepared generation properties, trace persistence,
and the registry, defensively copies connection/model/session settings, and closes
the registry once. `LoomspanAutoConfiguration.java:185` supplies the generation
runtime factory; `LoomspanAiAutoConfiguration.java:31` exposes the active runtime's
registry as an infrastructure bean with destruction suppressed at that bean.
The generation owns disposal. Captured roots and delayed descendants retain the
runtime they captured. Skill-only updates retain settings; explicit existing
`ExecutionConfiguration` publication supports prepared replacement resources
with credential references. The ticket does not authorize a new credential hot
reload mechanism.

`ExecutionConfigurationParser.java:25` defines closed candidate configuration
fields, resolves `api-key-ref` and `header-refs` through Environment or a supplied
host map, then binds/validates `LoomspanProperties`. It uses the same existing
connection/model keys. `DefaultSkillChatModelResolver` currently selects registry
entries; the Spring AI assembler assumes their chat models.

`ProviderAttemptCallAdvisor.java:65` is the chat-specific retry loop. Each send
reserves usage quota, assigns call-local `ModelTraceContext` attempt identity,
records request, delegates exactly once, translates failures and applies shared
`ProviderRetryDecider`, records decision/delay evidence, and waits interruptibly.
Success records attempt outcome, response evidence and model usage. This advisor
requires Spring AI requests/responses; the shared policy, taxonomy, trace and usage
services are independent of those types.

`SpringAiProviderIntegration.java:379` currently maps HTTP 408/429/500/502/503/504
as transient; 529 is permanent SERVER_ERROR. The ticket explicitly scopes the
new 529 overload mapping to System One. Chat diagnostics are independently bounded
at 1 MiB with `truncated` and `captureLimitBytes`. The POM declares Spring AI,
Jackson 3 (`tools.jackson`), MockWebServer tests, and Java 21, but no explicit
Apache HttpClient 5 dependency. No System One endpoint, transport, or extractor
exists in this checkout.

### Usage and native trace evidence

`ModelUsageRecord.java:5` stores int prompt/completion/total units, precision and
optional native usage. It rejects negative counts and totals smaller than either
component. `SessionUsageSnapshot.java:89` increments response-based modelCalls
and precision counters. `DefaultSessionUsageService.java:59` records response
usage and enforces existing call/unit quotas while writable; `:72` reserves
provider attempts and enforces their quota before send. HTTP-error usage ingestion
is not a separate existing accounting path. The current chat `ModelUsageExtractor`
accepts ChatResponse and can estimate text; TypeSafe's accepted exact/unavailable
mapping is new protocol-specific extraction into the existing record.

`ModelTraceContext.java:18` owns logical retry identity and physical attempt
metadata. `ModelExecutionIdentity` records configured framework model, connection,
driver, provider model and thinking level. `DefaultExecutionTraceRecorder.java:45`
and `:52` already accept Object request/response payloads with existing model
record types. `DefaultExecutionStateService.java:287` forwards them; recorder writes
obey the captured binding write gate. Existing failed attempts preserve provider
diagnostics, category, retry decisions and stack evidence.

`DefaultExecutionTraceHandle.java:546` converts payloads to JSON and emits chunk
envelopes/records when serialized payloads exceed the existing chunk threshold.
This is evidence transport, not a successful provider response byte ceiling.
`NdjsonTraceRecordWriter` writes canonical content without field-name rewriting.
`ExecutionTraceProperties` selects trace persistence; the feature's capture
statements must match these real controls and any explicitly represented omission.

`ExecutionJournalProjector.java:72` derives compact journal events from canonical
records and applies the repository's supported field-name redaction exception to
eligible journal content. Failed model attempts become compact warnings without
diagnostic bodies. `ExecutionJournalProjectorTest:24`, `:45`, and `:92` establish
this separate projection. Canonical traces, tool inputs and returned values are
outside that exception. The user instructions prohibit broadening it or adding
content classification/masking.

### Current catalogs and protected Console/MCP consumers

`SkillKind.java:4` exposes YAML/JAVA/REST as Application API. Internal
`CapabilityKind.java:5` maps execution kinds to that enum. The deliberate TYPESAFE
addition is the only public API change specified by the accepted roadmap.
`SkillDescriptor` needs no new fields.

`DefaultRegisteredSkillCatalog.java:35` branches YAML/REST definitions, publishes
kind name as source, derives sourcePath, decodes captured original bytes and emits
tool outputSchema. Java uses bean/method. `RegisteredSkillEntry.java:9` separately
validates source-specific locations, detail YAML and summaries. Source is a distinct
serialized contract, not acceptance implied by adding a Java enum value.

`SkillSourcePathResolver.java:31` returns suppliedLabel verbatim; only discovered
resources use existing configured-root/filename path rules. Thus arbitrary
nonblank supplied `SkillDocument.sourceName` labels already have an established
inspection path without filesystem normalization. `DefaultRegisteredSkillCatalog`
emits original YAML, not the copied manifest or resolved input request.

Console's Go `internal/observability/service.go:281` accepts source YAML/REST/JAVA
and checks nonblank sourcePath versus Java bean/method. At `:299`, details require
valid outputSchema object text and YAML for manifest sources. `dto.go:134`
rejects fields that are inapplicable even when explicitly null/empty, and forbids
detail YAML/outputSchema in summaries. Its UnmarshalJSON methods enforce these
contracts. `internal/mcpadapter/output_schemas.go:286` separately defines the
YAML/REST/JAVA source alternatives; `skills.go:38` describes unchanged manifest
text and renders non-Java YAML. These consumers presently reject TYPESAFE.

TypeScript `web/src/api/contracts.ts:125` and `:135` defines summary/detail source
unions. `SkillCatalog.tsx:67` and `SkillDetail.tsx:71` already render non-Java
source text, labels and unchanged YAML as text. Their tests contain REST and
opaque-label precedent. This rendering requires no new dashboard.

`web/src/observability/TraceRecords.tsx:14` defines only chat request/response
detail shapes; `:234` requires `messages` and `:250` requires string `content`.
At `:878`, it reads model payloads from inline content or reconstructed content
ranges and parses JSON. Native evaluation payloads need a coherent discriminator
and existing JSON/text presentation, including raw malformed response text.
Go `internal/traceanalysis/parser.go`, `payload.go`, `attempts.go`, `record_facts.go`
and enum validation consume canonical records and opaque/chunked semantic content;
their existing parser constraints continue to apply. The ticket requires updating
any affected current consumers when emitting native evidence, not in final guidance.

## Open questions for planning and implementation

No unresolved product choice requires developer input in this research. Concrete
implementation decisions still belong to the next stages:

1. Exact internal representation of a TypeSafe declaration, compiled single-pass
   template and immutable resolved request, using existing Jackson values/vocabulary.
2. Concrete shared registry resource ownership after replacing the non-null chat-only
   runtime boundary, including construction-failure and generation-retirement cleanup.
3. Apache version from dependency management, actual connect/response/lease timeout
   settings and omitted defaults, and real request cancellation linkage with the
   existing lifecycle. The ticket forbids an added total-attempt deadline mechanism.
4. Minimal native model payload/metadata representation for resolved request,
   envelope/raw text, endpoint/served model and extraction outcome, with all affected
   Java/Go/TypeScript fixtures and honest capture state.
5. Focused fixture selection covering shared request semantics once and route/entry
   differences specifically, plus actual consumer checks and architecture allowlists.
6. Live API documentation recheck required by 27.3; credentialed live checks are
   optional evidence distinct from fixtures. Settled local Score/request forms must
   not silently narrow when provider documentation differs.

These are bounded implementation/verification choices under the accepted roadmap,
not authorization for generalized provider/templates/schema/binding systems,
answer validation, new accounting policy, routing/scoring patterns, or new SPI.
