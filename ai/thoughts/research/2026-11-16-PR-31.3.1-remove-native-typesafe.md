**Date:** 2026-11-16 22:00:17 PST

## Research question and scope

Map the current native TypeSafe implementation, its consumers and supported contracts for
`ai/thoughts/tickets/loomspan-pr-31.3.1-remove-native-typesafe.md`, following the approved
Full 5-Step Pipeline. The ticket authorizes removal of native grammar, driver, dispatch,
resources, obsolete classifications and historical shapes, with no compatibility shims
and no `consoleCompatibilityVersion` increment. Framework-local acceptance does not wait
for Extensions reruns; advanced consumer qualification belongs to 31.3.2.

Both checkouts were clean during inspection. Framework HEAD is above; Extensions HEAD is
`4a52c70` (`Implement TypeSafe executor and packaged consumer recipe`). No production,
test, configuration or product documentation was changed during research. No tests ran.
Metadata came from `bash ai/scripts/spec_metadata.sh`.

## Summary

Native execution remains a distinct third skill form and public catalog kind. Its three
implementation classes are coupled through YAML parsing, model/connection configuration,
generation catalogs, root/child dispatch and provider resource ownership. Console still
accepts `TYPESAFE` catalog entries and has a special `payloadType: evaluation` renderer.
Three coordinated native trace fixtures and a native REST detail fixture model these
contracts. Generic binding/publication/namespace tests also use native leaves.

The replacement already exists in the sibling Decisions pack: reference-only
`default-typesafe`, supported v1 invocation, ordinary executor YAML, `config.request` and
pointer `config.bindings`, full JSON results, existing diagnostic records. Generic executor
numeric decoding, namespace capture, authorization, lifecycle and accounting tests exist
independently of native TypeSafe. The old unversioned invocation production type is already
absent; the closed allowlist already includes only the exact two v1 extension types.

## Detailed findings

### Native declarations, validation and schemas

- `src/main/java/ai/loomspan/internal/skill/YamlSkillManifest.java:23,83` declares
  `TYPESAFE`, a copied JSON declaration, compiled `TypeSafeDeclaration`, setters and
  declaration-presence tracking.
- `YamlSkillDefinition.java:18,111,158,237` declares `Form.TYPESAFE`, chooses the generated
  descriptive schema, exposes native declaration accessors and copies the native state.
- `YamlSkillCatalog.java:328` requires native input schemas, rejects attachment annotations
  recursively and requires a TypeSafe driver for a selected Framework model alias. At
  `:346` ordinary chat leaves reject that driver. At `:475` declaration-form selection
  distinguishes executor/native/model, checks field presence and compiles native grammar.
  Generic unknown-field and structural validation are separate catalog concerns.
- `internal/typesafe/TypeSafeDeclaration.java:21` owns native question validation,
  `${/input...}` substitution, detached request creation and descriptive schema generation.
  `TypeSafeDeclarationTests` and `TypeSafeSkillIntegrationTest` protect native-specific
  numeric/substitution/schema behavior. Those behaviors are not the pack's binding syntax.
- `SkillDependencyValidator.java:110,244` resolves generic executor bindings and explicitly
  excludes executor leaves from output-schema resolution. Existing runtime binding checks
  remain distinct from native generated output metadata.

### Public classifications and generation catalogs

- `api/SkillKind.java:6` contains `YAML, JAVA, TYPESAFE`.
- `SkillGeneration.java:91` and `SkillGenerationManager.java:219,249` map executor definitions
  to JAVA, native definitions to TYPESAFE, ordinary model definitions to YAML.
- `internal/runtime/observation/catalog/RegisteredSkillEntry.java:29` validates all three
  kinds and enforces YAML versus Java provenance. Executor-backed JAVA entries already
  carry YAML source plus executor identity and implementation location.
- `src/test/java/ai/loomspan/architecture/LoomspanPublicSurfaceArchitectureTest.java:37`
  includes exact v1 `SkillExecutorInvocation` and `ExecutorDiagnostics`; `:79` separately
  classifies the three technically public native implementation classes as internal.
  Removing internal classes changes the implementation allowlist, not the supported API
  package boundary. `ApplicationApiValueTest` and catalog tests assert native kind values.

### Dispatch, provider configuration and resource ownership

- `ExecutionCoordinator.java:104,163` includes native definition validation and dispatches
  TYPESAFE through `MissionWorkExecutor.executeEvaluation`. The neighboring JAVA path
  already handles ordinary executor-backed YAML with captured executor binding, resolved
  input, scoped authentication, v1 handoff, live lifecycle reads and closed diagnostics.
- `MissionWorkExecutor.java:121` wraps `TypeSafeExecutor` in the shared mission worker.
  The same class owns generic execution timeout/cancellation cleanup.
- `internal/typesafe/TypeSafeExecutor.java:17` owns native request construction, provider
  admission/retries, automatic native usage and model request/response evidence, returning
  extracted object-valued `answers` rather than the full envelope.
- `AiDriver.java:8` declares TYPESAFE. `LoomspanProperties.java:221,263,269,309` has native
  validation/default/header/thinking checks. Additional Spring metadata mentions TypeSafe
  static headers. `ExecutionConfigurationParser` handles the generic native connection and
  credential-reference path; executor maps are a separate literal configuration boundary.
- `NamedAiConnectionRegistry.java:30` constructs native clients directly, while other
  drivers use `SpringAiProviderIntegration`. It retains generic retry ownership validation,
  failure cause/suppressed cleanup evidence, idempotent destruction and chat-model cleanup.
- `ProviderConnectionRuntime.java:8` stores mutually exclusive ChatModel/TypeSafeClient
  resources; its `chat` factory and `requireChatModel` serve ordinary providers.
- `SpringAiProviderIntegration.java:111`, `SpringAiChatOptionsContributor.java:24` and
  `NativeOutputContract.java:61` exclude TYPESAFE in otherwise generic provider switches.
  `NativeOutputContract` is the chat structured-output implementation, not a TypeSafe-only
  class. `ProviderAttemptCallAdvisor.java:70` uses it for ordinary native chat requests.
- `pom.xml:98` directly depends on Apache `httpclient5`. Repository production imports of
  `org.apache.hc` appear only in `TypeSafeClient`. Generic JDK HTTP application tests and
  Spring provider integrations are independent consumers, not evidence that this direct
  dependency serves another Framework implementation.

### Retained generic numeric and execution boundaries

- `YamlValues.java:22,57` has ordinary and exact-decimal constructors, timestamp handling,
  finite/nonfinite reporting, cycle detection, duplicate rejection and bounded alias
  expansion. Exact JSON-bound decoding also serves ordinary input/output schema literals;
  the presence of TypeSafe precision tests is not evidence it is exclusively native.
- `SkillDocumentValuesTest`, `ExecutorConfigurationTests`, `ExecutorConfigurationStartupTests`
  and `ExecutorDeclarationTests` cover the separate ordinary config boundary, exact data
  keys, null/container distinctions and declaration presence restrictions.
- `ExecutorDependencyResolutionTest` covers reference-only registrations, local/qualified
  namespace visibility, selected configuration paths and composed authorization.
- `ExecutorGenerationExecutionIntegrationTest:60` exercises captured foreign configuration
  across replacement/removal/recreation and public retirement notifications; related tests
  cover publication and authority without introducing native clients.
- `ExecutorInvocationLifecycleIntegrationTest:123,161` and `MissionLifecycleTest` cover
  live remaining budget, expiry to zero, no deadline, ancestor/shutdown limits, cleanup
  grace separation, interruption and late completion/write fencing.
- `ExecutorAccountingIntegrationTest:28,86,100` exercises a mixed ordinary OpenAI parent
  and application executor, executor-only zero native accounting, actual application retries,
  unknown usage and successful HTTP followed by decode failure, without Console.
  `ModelUsageExtractorTest` covers unavailable native model usage.

### Existing replacement and build identities

Earlier owning handoff is `loomspan-pr-31.2.2-typesafe-executor-consumer.md:915`.

`../loomspan-extensions/extensions/decisions/docs/executor.md`.

- Coordinates: Framework `ai.loomspan:loomspan-spring-boot-starter:1.0.0-beta.10-SNAPSHOT`;
  pack `ai.loomspan:loomspan-decisions:0.1.0-SNAPSHOT`; independent example
  `ai.loomspan.examples:support-triage:0.1.0-SNAPSHOT`. These are local unpublished builds.
- `@SkillExecutor(name="typesafe", config="typesafe")` registers reference-only
  `default-typesafe`; application leaf declares `executor: typesafe` in default.
- Namespace map is `loomspan.executor-config.default.typesafe`. Skill config accepts
  `request`, optional `bindings`, `api_key`, `base_url`. Executor map accepts captured
  `api_key`/`base_url`; present skill keys win, invalid present values fail rather than
  falling back. Applications supply resolved credentials; no native alias/interpolation.
- Request has explicit provider `model`, `state`, `questions`; bindings map request-target
  RFC 6901 pointers to input-source pointers. Empty source selects all input; present null
  stays null; missing object source omits; missing array source and overlapping targets fail.
- Pack returns complete native JSON serialized to String across the existing Java
  passthrough boundary, including JSON null/string/envelope/unknown/refusal/usage values.
  Business consumer paths begin `/answers/...`, e.g. `/answers/repeat/noul`.
- Domain validation happens before send at every invocation, not publication. No generated
  output metadata/early schema parity, native attempt reservation/usage aggregation or
  immediate physical cancellation guarantee is added. Existing cooperative lifecycle and
  physical work/resource retention remain the boundary.
- Prior handoff verified pack install/verify and standalone installed-JAR example against
  Framework source `d992449e8eba0734c466de9a1f05526c840ba608`; this removal ticket records a
  new Framework source/build identity for 31.3.2. Historical passes are not new verification.
