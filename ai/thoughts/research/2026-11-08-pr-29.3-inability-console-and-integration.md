# Research on planner inability in Console and MCP

## Research question

For [PR 29.3](../tickets/loomspan-pr-29.3-inability-console-and-integration.md), where do accepted inability, its originating invocation, the rejected response, and actual parent feedback enter the current trace? How do existing Console and MCP reads expose those records, and what integration verification remains after PRs 29.1 and 29.2?

## Summary

At `afde893`, Java emits explicit `kind` in `ERROR_RECORDED.data`, opaque accepted-signal diagnostics, and a shared structured chat-message shape. Console already indexes failure identity, frame relationships and diagnostics, and already reads large model payloads. The typed failure projections omit `kind`, the source-focused browser panel is gated on root failure, and the browser's dedicated response viewer expects obsolete `content` while its request viewer requires non-null text and discards calls/responses. The existing canonical record, failure, frame and content identities connect the evidence required by the ticket.

## Detailed findings

### Java failure identity, scope and diagnostics

- `src/main/java/ai/loomspan/api/PlannerInabilityException.java` is the single supported Java addition, extending `RecoverableSkillException` with a `String` constructor. `src/main/java/ai/loomspan/internal/core/SkillFailurePolicy.java` owns effective throwable identity and recoverability. `LoomspanSession.java:153` deduplicates by effective throwable, retains origin on the first record, sets canonical classification and exact `exceptionMessage`, and owns `kind` from the subtype. It removes caller context's `kind` before writing the canonical value. An ordinary application wrapper can have its own terminal fact and earlier `causedByFailureId`. Terminal linkage is supplied separately at root completion by `LoomspanSessionRunner.java:404` and the existing completion path.
- `src/main/java/ai/loomspan/internal/springai/CanonicalToolCallingManager.java:39` visits every response generation, checks actual request bindings and rejects mixed selections before delegation. `PlannerInabilityTool.java:48` validates the closed reason object and records the ID, exact control name, and unparsed Spring AI argument string on the active model frame. `SpringAiChatClientAssembler.java` handles an enclosing standard callback failure and supplies the actual tool response; the child itself does not continue. The parent response object contains the exact four selected keys for inability and ordinary recoverable feedback omits `kind`.
- `src/main/java/ai/loomspan/internal/runtime/step/StepLoopMissionExecutionEngine.java:831` creates plan and step identity from Framework state and adds the assigned task identity only for assignment. The frame opens at `:885`, accepted inability at `:1039` records exact response bytes on that step frame, and the contextual `message` identifies assigned task or final synthesis. The message is a display fact, independent of exact reason. `:1203` parses the original inability object before ordinary coercion. Parallel settle/fold uses the existing unit join and authoritative cancellation, then classification and accepted task order (`:464` and `propagateUnitFailure`).
- `src/main/java/ai/loomspan/internal/core/ExecutionBinding.java:92` requires the expected frame type and existing writable ancestry guard. `TraceDiagnostic` retains a UTF-8-safe prefix within the existing 1 MiB limit. `LoomspanSession.java:198` keeps stack ordinal zero and accepted signal ordinal one. Application-thrown instances use the same kind but the existing Java origin and no accepted signal. The exact reason is independent of the bounded text and can include leading/trailing whitespace and CRLF.

### Console failure facts and retrieval

- `loomspan-console/internal/traceanalysis/failures.go:28` associates explicit metadata `failureId` and optional earlier `causedByFailureId` with record and frame. `validateDiagnostics` at `:74` runs on either inline or reconstructed `ERROR_RECORDED.data`. It validates canonical classification, exact nullable `exceptionMessage` presence, recoverable Java blank semantics and bounded opaque diagnostics. It currently has no `kind` check. The raw member map already distinguishes missing members from present JSON null. The generic diagnostic `kind` values are opaque labels and are a separate field from failure `kind`.
- `failures.go:154` sets `Terminal` only via `TRACE_COMPLETED.terminalFailureId`. Successful completion forbids a link, while failed and aborted completion require a resolvable link. The function does not enforce TERMINAL classification for a completion-linked failure. `processor.go:391` resolves frame assignments, then builds `failureResult` (`model.go:220`), the failure index (`processor.go:461`) and per-record facts. Go opens the canonical failure scope with explicit IDs, not records adjacent to a failure.
- Browser failure listing follows `query_facts.go:412`, including persisted `failureSummary` at `:490`, the public `FailureSummary` at `dto.go:322`, and the separate Browser mapper and `failureDTO` in `internal/browserapi/trace_analysis.go:274` and `:688`. MCP consumes the separate `record_facts.go:143` materialization of `RecordFacts.Failures`, then `internal/mcpadapter/traces.go:678` and `:691`, `internal/mcpadapter/trace_contracts.go:275` and the record output schema at `internal/mcpadapter/output_schemas.go:257`. Neither projection currently includes the discriminator. Provider-attempt links are independent and have their existing response field and content references.
- `query_diagnostics.go:16` selects a descriptor by existing failure ID and ordinal, reads canonical inline or chunked data and returns opaque decoded text. `record_facts.go:166` issues the equivalent MCP diagnostic `contentRef`. MCP's `LOOMSPAN_query_trace_records` accepts `filter.failureId`, `LOOMSPAN_query_trace_frames` has `DETAILED` assignment and hierarchy, and `LOOMSPAN_read_trace_content` exposes exact bounded ranges with continuation. There is no standalone MCP failures tool. MCP result pagination is limited by its existing 32 KiB encoded result budget. A truncated-signal fixture can use leading/trailing declaration whitespace or argument formatting to exceed capture size with a short exact reason, so the two limits are independently observable through current paths.
- Frame assignment is attached explicitly to `STEP_EXECUTION` open data and propagated from the nearest assigned ancestor by `internal/traceanalysis/frames.go:54`, `:143`, `:481` and `:530`. Detailed browser and MCP frame results already carry plan, task and step fields for that assignment (`internal/browserapi/trace_analysis.go:153`, `internal/mcpadapter/traces.go:605`). Those fields describe the nearest assigned ancestor and can refer to an enclosing assignment for a nested synthesis or a standard child. The origin frame ID, type, route and the first error's separate context summary remain authoritative. Final synthesis is recorded as the canonical context message on its actual step frame, without an assigned task of its own. Missing task or a route name alone does not identify synthesis.

### Browser selection and model detail

- `loomspan-console/web/src/observability/TraceExplorer.tsx:326` resolves the explicit failure selection or completion default, fetches failure facts, selects the actual `failure.frameId` at `:356`, and already supports selected failure, record and frame navigation at `:505`. `TraceRecords.tsx:1088` exposes `View error` on records with typed linked failures. `TraceExplorer.tsx:536` opens the failure panel for a selected failure in a successful trace, but `TraceFailureFocus.tsx:16` still suppresses the source/route/skill/actions unless the root is failed or aborted. On a failed trace, that focus panel labels the root terminal ID even when a different failure is selected. `TraceFailureDiagnostic.tsx` already follows selected nonterminal failures, shows classification, exact exception message, contextual message and explicit cause links, and has scope-aware load, wrap, copy and download paths for the existing descriptors. `contracts.ts:279` and `:343` define the frame and failure browser shapes.
- `src/main/java/ai/loomspan/internal/chat/ProviderAttemptCallAdvisor.java:156` captures `{messages:[...]}` in instruction order and at `:190` captures `{generations:[...]}` in returned order before callback dispatch. The same `messagePayload` maps Spring AI role name and nullable `text` for each message. Assistants carry ordered `toolCalls` with nullable ID, name and raw argument strings. Tool-response messages carry `toolResponses` with nullable ID, name and exact `content`. Empty arrays remain empty, empty strings stay distinct from null, absent result output yields a null generation entry, and no response yields an empty generations array. A Spring AI decoding failure with no response follows existing provider attempt diagnostics. `TypeSafeExecutor.java` uses the distinct `payloadType: evaluation` shape.
- `TraceRecords.tsx:229` still reads a string `text` on every request message and a single response `content` string, with JSON pretty-printing on the latter. Its dedicated renderer at `:403` displays role/text or one `<pre>`. The response action at `:1007` is keyed to the record type, and `:880` reads inline JSON or reconstructs using `readCompleteContent` (`:197`) before parsing. Inner raw strings are separate from outer JSON and need no second JSON parse. `TraceRecords.model.test.tsx` covers inline/ranged chat details and native evaluation; its chat fixtures are still in the old shape. `TraceRecords.raw.test.tsx` and `TraceRecords.results.test.tsx` contain additional chat record examples. Go model attempt parsing and usage consume record facts/metadata. Go generic content references transport the full model data independently of TypeScript parsing.
- `src/main/java/ai/loomspan/internal/runtime/observation/LiveActivityProjector.java:126` uses request/response record type and attempt/usage metadata; it does not depend on a chat `content` field. `src/main/java/ai/loomspan/internal/runtime/trace/ExecutionJournalProjector.java:65` skips model request/response payloads, and its `summarizeError` at `:249` selects existing error fields. The existing derived observer journal exception at `:346` remains isolated from canonical traces and model content. `ExecutionJournalProjectionContractTest` covers representative projected events and raw-record exclusions.

## Historical context and related research

- [Accepted design](../phases/planner-failure-recovery.md) assigns exact failure/diagnostic ownership and limits continuation to existing standard callers. It does not establish a link from a declaration to a unique parent message by array position, provider ID uniqueness, timing or name. Parent feedback evidence is the actual recorded tool-response message with supplied fields. The reason and evidence cannot establish business effects, safe replay, or whether another authorized action exists.
