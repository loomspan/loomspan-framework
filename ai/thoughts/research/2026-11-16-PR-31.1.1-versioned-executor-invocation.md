## Summary

There is one production construction of the current five-component public invocation record, in `ExecutionCoordinator`. Exact parameter registration and managed-proxy invocation already share the callable Java infrastructure. The handoff freezes map/list containers but preserves arbitrary leaf identities, including Resources.

Mission execution time and cancellation cleanup time are separate existing concepts. `MissionWorkExecutor` enforces a captured mission timeout with timed `Future.get`; `MissionLifecycle.deadlineNanos` is the cancellation cleanup deadline, not an execution deadline. Framework shutdown owns and publishes another deadline. Explicit step planning has a separate timed submission path in `StepLoopMissionExecutionEngine`, relevant to parent budget observation.

No executor diagnostics capability exists in the current supported API. This ticket owns declarations and JSON surface selection; 31.1.2 owns bounded snapshot/recording and its failure containment tests. Native TypeSafe remains implemented and tested today; its removal and coordinated consumers are later ticket work.

## Detailed findings

### Current invocation, registration, and execution

- `src/main/java/ai/loomspan/api/SkillExecutorInvocation.java:12` is a public record with `input`, `skillConfig`, `executorConfig`, `skillName`, `executorConfigGenerationId`. Its constructor rejects nulls and blank identity strings, preserves nonblank string text, and recursively copies maps/lists.
- `src/main/java/ai/loomspan/internal/util/ImmutableContainers.java:16` copies map/list containers using identity tracking, rejects recursive containers, preserves nulls and shared noncyclic structures, and leaves Resources, arrays, DTOs and other non-container leaves unchanged. This is existing business configuration/input behavior, distinct from the new restricted diagnostic JSON surface.
- `src/main/java/ai/loomspan/internal/core/SkillMethodBeanPostProcessor.java:193` accepts exactly one parameter equal to `SkillExecutorInvocation.class` and rejects varargs. It registers an invoker using `JavaSkillInvoker`, not a separate execution implementation.
- `src/main/java/ai/loomspan/internal/core/SkillExecutorRegistration.java:8` stores a typed `Function<SkillExecutorInvocation,String>`, identity, selected config path, access policy and source location. It is internal despite Java-public visibility.
- `src/main/java/ai/loomspan/internal/core/JavaSkillInvoker.java:21` invokes the final managed bean/proxy. Null becomes empty text; String returns exactly; all other successful values serialize with the application mapper. Exceptions are propagated by the shared failure policy. This remains important for a decisions result that is itself a JSON String or JSON null.
- `src/main/java/ai/loomspan/internal/core/ExecutionCoordinator.java:112` constructs a MissionContext with the existing parent mission; `:147` opens the mission frame; `:160–170` submits JAVA work and constructs the invocation after reference resolution. Executor configuration/registration/generation identity comes from the captured admission snapshot, and skill config/name comes from the executing YAML leaf. Both direct and child execution reach this construction.
- `src/main/java/ai/loomspan/internal/skill/SkillDependencyValidator.java:108` resolves executor bindings for the checked set. Its output-schema resolution at `:224–245` excludes executor definitions from generated metadata. Executor references remain dependencies, not callable tools or child grants.

### Lifecycle owners and timing

- `src/main/java/ai/loomspan/internal/runtime/MissionWorkExecutor.java:28` obtains the mission timeout from the captured generation, falling back to the constructor timeout. `:36` captures binding/lifecycle and submits work; `:76` waits with that timeout in milliseconds. Cancellation/interruption flows install the primary cause, cancel futures, wait for bounded cleanup, clean frames and preserve caller interruption.
- `src/main/java/ai/loomspan/internal/runtime/DefaultMissionExecutionEngine.java:85` routes ordinary model work through MissionWorkExecutor.
- `src/main/java/ai/loomspan/internal/runtime/step/StepLoopMissionExecutionEngine.java:229–295` instead owns a parallel existing submission/timed-get path. This path is an ancestor of executor calls from explicit planning and is a relevant deadline bookkeeping site, even though executor execution itself uses MissionWorkExecutor.
- `src/main/java/ai/loomspan/internal/core/MissionContext.java:47–65` creates a MissionLifecycle with a monotonic time supplier and registers it with the session's admitted Framework root. It retains parent ancestry independently of the worker's ambient binding.
- `src/main/java/ai/loomspan/internal/core/MissionLifecycle.java:32–49` owns a ReentrantLock-protected OPEN/CANCELLING/CLOSED state, atomic primary cause, cleanup deadline, owning/task/physical futures, atomic framework cutoff and volatile framework deadline. `beginCancellation` establishes cleanup grace (`CLEANUP_GRACE = 250 ms`) and clamps it by Framework deadline. `awaitCutoff` consumes that existing grace without renewal.
- MissionLifecycle's ancestry helpers lock from root to child; admission requires every owner OPEN; writes remain possible during cancellation until closure, then are fenced. `frameworkCutoff` deliberately publishes without waiting for ancestry locks and interrupts known futures. These properties already protect late physical work.
- `src/main/java/ai/loomspan/internal/core/FrameworkExecutionLifecycle.java:149` closes root admission and establishes one shutdown deadline. Existing roots receive it; newly registered missions inherit it. AdmittedRoot tracks all missions and releases generation ownership only after logical root release and physical completion of all started mission work (`:335–385`).
- No existing mission execution-deadline field supplies the requested remaining-time read. The cleanup deadline cannot represent it. The current sources expose no public cancellation/deadline or physical-future registration API to executors.

The ticket's settled semantics are inputs to planning: live read-only cancellation/remaining time, empty for no execution deadline, zero at expiry, parent/shutdown limits, no deadline renewal at executor entry, no new scheduler or cancellation machine, no public transport cancellation/accounting API, no promise of immediate physical cancellation, and no newly invented post-return restriction or monitoring guarantee.

### Diagnostics declaration boundary

There is no existing `diagnostics()` or developer-authored info/warn/error facility in the public API. `TraceRecordType` contains existing automatic model/tool/error records rather than a new executor diagnostic record. The ticket embeds the binding Phase 2 design and assigns implementation to 31.1.2.

This ticket must settle signatures and supported concrete JSON values once, documented for 31.1.2. The existing research at `ai/thoughts/phases/decisions-executor-pack-research.md:85–131` describes Jackson streaming with instance-local write constraints and bounded traversal/output sinks; interfaces alone do not exclude user-executing Map/List/Number implementations. It is evidence for the later recorder, not an implemented capability or permission to accept arbitrary DTOs.

The handoff must distinguish declaration completion from recording completion. An inert implementation cannot be claimed as diagnostics support. The ticket explicitly allows precise intermediate compilation debt assigned to 31.1.2 instead of compatibility plumbing. Ordinary new diagnostic validation/capture/recording/fallback failures must not affect business success or replace original business failure; existing automatic observation keeps its existing semantics. Caller evaluation before method entry and JVM-wide failures are outside that guarantee. Recording limits, notices and failure-injection tests are 31.1.2 work.
