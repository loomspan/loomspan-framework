## Summary

PR 27.1 has already introduced canonical qualified identities, Java namespace assignment, namespace-owned immutable generations/catalogs, and internal target-specific validation/preparation foundations. The current active manager still stores only one global generation. Public preparation/validation remains default-only and includes file/skill-only overloads that inherit current settings. `DefaultSkillReloader` serializes expensive preparation with a global lock, then checks the global active ID at publication.

Existing machinery includes a UUID-prefix/atomic-counter generation ID allocator, detached generation construction, independent runtime/provider registries, lifecycle admission synchronization, per-generation owner leases, retirement selection outside callback delivery, fixed registration initialization, and strict candidate configuration parsing. Contract validation currently operates over one namespace's supplied definitions and assigned fixed Java metadata. There is no active multi-namespace registry, generation visibility property, removal API, or external metadata overlay in this checkout.

Research was read-only except this artifact. No tests were run; test descriptions below are source evidence, not execution results.

## Detailed findings

### 1. Supported API and namespace foundations

- `src/main/java/ai/loomspan/api/SkillReloader.java:9` exposes `validate()`, `validate(documents)`, `validate(documents, configuration)`, matching preparation overloads, a host-map credential preparation overload, `publish(update)`, `snapshot(namespace)`, and framework-wide `onGenerationRetired(listener)`.
- `PreparedSkillUpdate.java:7` documents the candidate ID independently of its base and exposes candidate catalog metadata. Its default `close()` is inert for application-implemented objects; only the private framework `Candidate` is accepted for publication.
- `SkillCatalog.java:11` exposes canonical namespace, opaque generation ID, immutable skill list, and qualified lookup. `DefaultSkillCatalog` constructs eager descriptors from capability metadata. Catalog metadata owns no executable lease.
- `SkillIdentity.java:6` is the shared internal parser/formatter. Namespace normalization lowercases only ASCII namespace case through `Locale.ROOT`; invalid characters/whitespace are rejected. Namespace limit is 32, combined identity limit 64, and exactly one hyphen separates components. Local name case is preserved.
- `SkillGeneration.java:41` checks that every capability and definition belongs to its namespace and has an exact qualified map key. It validates YAML/REST/TypeSafe kinds, builds namespace-identifying empty catalogs, and keeps immutable map copies. It has no visibility field.
- `NamespaceIdentityFoundationTest.java:40` protects internal namespace-specific feedback and candidate construction. Its manager methods accept a namespace but still inherit existing settings; these are internal foundations, not the selected public publication shape.

### 2. Current coordination, captured base, and publication

`DefaultSkillReloader.java:28` owns separate `preparationLock` and `publicationLock` objects plus a framework-instance owner token. `prepareWith` at line 97:

1. Holds `preparationLock` for base reading and all construction.
2. Uses `lifecycle.whileAdmissionOpen` to read `generations.active().id()`.
3. Runs the supplied construction function.
4. Checks lifecycle again and closes a successfully constructed candidate if shutdown was observed.
5. Returns a private `Candidate(owner, baseId, generation)`.

`publish` at line 122 rejects a foreign/fabricated candidate before changing it, then takes publication lock, candidate monitor, and lifecycle admission monitor. It checks candidate published/closed flags and the current global generation ID against `baseId`. It activates through the manager, marks ownership transferred, and dispatches returned retirement outside these locks. Rejection closes an unpublished candidate; repeated rejection cannot close an already-published generation. Candidate close currently calls generation close while holding the candidate monitor, but is outside the registry/publication boundary in rejection paths.

The base is captured before construction, distinct from the candidate's allocated ID; there is presently no absent-base case because `active()` initializes a generation. There is no dependency revision precondition to preserve or remove in the current implementation.

### 3. Registry, initialization, capture, retirement, and physical ownership

- `SkillGenerationManager.java:62` stores `AtomicReference<SkillGeneration> active`, not a namespace map. `generationMonitor` guards published-generation owner state, listener registrations, activation, capture, and retirement selection.
- `afterSingletonsInstantiated` at line 98 initializes fixed dependencies and installs `prepare()` if active is null. `active()` at line 104 calls that method lazily when empty. This currently permits initialization from early internal bean acquisition; absence has no independent meaning yet.
- `activateAndSelect` at line 563 swaps the single active reference under `generationMonitor`, adds candidate owner state to `published`, marks the old state superseded, and selects eligible retirement.
- `capture()` at line 577 ensures startup exists, then selects the active generation and increments its owners under `generationMonitor`. The returned `Capture` contains that generation and one idempotent `OwnerLease`.
- `OwnerLease.close` at line 667 decrements ownership under the same monitor, selects retirement, then dispatches outside it. `destroy()` marks all published states superseded and dispatches eligible retirements outside the monitor. Existing retained owners continue to govern eligibility.
- `dispatch` at line 629 closes generation resources and independently catches listener failures. Callback selection respects the supplied lifecycle delivery predicate. No replay, ordering, retry, or durable-delivery mechanism exists; shutdown can omit delivery.
- `FrameworkExecutionLifecycle.java:94` executes short update actions under the same `monitor` as admission closure. `closeAdmission` does not wait. Its `AdmittedRoot.releaseGenerationIfSafe` defers release while any mission retains physical work, even when the logical response has terminated. Existing execution snapshot retention is single-generation in this slice.

### 4. Preparation flow and candidate-local mutable state

`SkillGenerationManager` currently offers these internal paths:

| Path | Configuration/catalog source |
| --- | --- |
| `prepare()` (line 115) | Configured resources, current properties and policy |
| `prepare(documents)` (line 122) | Supplied documents, current properties and policy |
| `prepare(namespace, documents)` (line 129) | Target-qualified supplied documents, current properties and policy |
| `prepare(documents, configuration, credentials)` (line 150) | Fresh parsed properties and `new YamlSkillCatalog(parsed.properties())`, default namespace |
| Corresponding validation paths | Same parsing/checking without runtime construction or generation ID allocation |

`currentProperties/currentCatalog/currentPolicy` at lines 183–201 read active runtime state or startup fallback independently. Explicit configuration parsing also assigns startup `skills` locations to parsed properties; supplied-document loading does not need discovery. The explicit path parses without resolving references first, checks skill declarations/contracts, then reparses with resolved credentials and constructs resources.

`YamlSkillCatalog.java:57` stores mutable namespace and `skillsByName`, diagnostic-name/source maps, warning sink, and log flags. `checkedSupplied(namespace, documents, ...)` sets target namespace. `reset()` at line 214 clears mutable maps. Every catalog used concurrently needs its own instance; current auto-configuration's supplier creates a new instance, while several tests use mocks or fixture suppliers and need separate examination during implementation.

`YamlSkillDefinition.java:36` copies the mutable manifest at construction and copies exposed schemas/manifests defensively. Its constraints and prepared binding lists are copied. Qualified references are stored as structured identities. Source bytes are frozen by `YamlSkillSource` and supplied documents are encoded into candidate-local byte resources. `YamlSkillCatalog` validates model/connection availability while loading declarations (`resolveModelCatalogEntry`, line 397), so candidate configuration is part of manifest validation, before provider construction.

`prepareCatalog` at manager line 518 allocates a globally distinct ID with `UUID` prefix and `AtomicLong`; overflow fails rather than reusing. It includes only fixed Java capabilities assigned to the checked namespace, builds supplied capability metadata/REST invokers with that candidate ID, then creates the runtime. Constructor failure closes a runtime it already owns. Allocation order is construction order, not a publication ordering promise.

### 5. Current contract validation and metadata read audit

`SkillGenerationManager.check` at line 266 is the preparation/validation owner:

- Starts with parser issues and namespace-filtered fixed Java metadata.
- Detects supplied/fixed name collisions.
- Resolves every supplied input contract through `SkillInputContractResolver`.
- Checks the fixed REST handler declaration count without constructing a handler during validation.
- Checks all allowed child references against the candidate namespace's known names, preserving suppression of secondary missing-reference noise for failed documents.
- Calls `ChildInputBindingDeclarations.validate` for declared input binding paths, direct producer references/counts, overlap, self-dependencies, and child-result dependency cycles.
- Resolves output schemas through `output_from` chains with a visiting identity set, reporting forwarding cycles; builds a candidate-local effective-schema map.
- Validates output binding source/destination paths, producer counts, primitive/nullable/enum/array/object compatibility against available schemas.
- Returns immutable issues/contracts/schema maps. Any ERROR makes validation feedback metadata empty and makes preparation fail before runtime construction.

`resolveOutputSchema` at line 462 currently traverses only supplied definitions and candidate names. It derives schema strings from YAML/TypeSafe output schema metadata, excludes evidence orchestration annotations, and publishes the derived result in `CapabilityToolDescriptor.outputSchema`. Fixed Java/REST output remains unspecified when no schema is available. There is no external registry resolution, visibility check, transitive return-to-candidate rule, or shared admission dependency validator yet.

The read inventory is concrete:

| Read | Lifetime/ownership evidence |
| --- | --- |
| Namespace, qualified names, kinds, descriptions, source labels, immutable schema strings | Scalar/record metadata; generation close does not modify it |
| `SkillInputContract` / recursive `SkillInputSchemaNode` | Schema nodes copy nested maps/lists; no provider or bean calls |
| `YamlSkillDefinition` constraints, `outputFromIdentity`, input/output schemas | Defensive manifest/schema copies and immutable prepared lists; no provider calls |
| Fixed Java registration input/tool metadata and access policy | Completed metadata snapshot from discovery, not invocation |
| REST bean names during declaration checking | Fixed initialized list; validation checks count only |
| Candidate properties for model selection | Fresh parse on explicit configuration path; mutable candidate-owned values |
| Runtime/client/invoker resources | Constructed after checking; current validation never invokes them |

`SkillGeneration.close()` only closes its `ExecutionRuntime`; it does not erase metadata or destroy Java beans. Consequently these audited metadata reads are independently usable after generation retirement and do not themselves require executable-resource ownership. If implementation introduces reads into runtime resources, the existing owner lease is the available protection and must be audited for that added use. The current validation code has no temporary external lease because it has no external view.

### 6. Execution configuration, credentials, and resources

`ExecutionConfigurationParser.java:45` requires a non-null document, parses duplicate keys strictly, checks top-level `loomspan`, and allowlists connections/models/session plus only `execution-trace.persistence`. It rejects unknown and host-only keys. Exact existing nested fields include provider options, millisecond request timeouts, retries, explicit credential references, quotas, depth, mission timeout, and attachment max size. Fresh Spring `Binder` construction produces a new `LoomspanProperties`; `afterPropertiesSet` validates it, and omitted fields use built-in defaults. There is no parser-level previous/startup inheritance.

Environment references and explicit host maps are separate paths. The host map is copied in the reloader before construction and rejects missing, blank, and unused values without Environment fallback. Validation does not resolve references. Existing generic host-map error wrapping and field-path-only credential error text predate this ticket; repository AGENTS.md forbids broadening content rewriting/classification mechanisms. The present research does not endorse those diagnostic choices as new requirements.

`ExecutionRuntime.java:20` snapshots properties (session/quotas/attachments, connections/options/credentials/retries, models) and owns one `NamedAiConnectionRegistry`. `close()` is idempotent. `NamedAiConnectionRegistry.java:19` creates clients independently per registry, cleans partially constructed connections on constructor failure, and has idempotent `destroy()`. The generation's runtime factory in `LoomspanAutoConfiguration.java:177` constructs a fresh registry/runtime. No provider sharing pool exists.

### 7. Fixed Java registrations and startup wiring

`SkillMethodBeanPostProcessor.java:57` completes discovery under synchronization and returns `List.copyOf` registration metadata. It inspects real Spring beans/proxies, verifies JSR-250 enforcement, and builds Java invokers with reflected argument binding, result conversion, and existing security propagation. The declaration namespace comes from `@SkillMethod.namespace`; default is `default` and identity normalization is shared. No skill implementation is invoked by registration metadata construction.

Manager `initializeFixedDependencies` at line 682 captures Java metadata and sorted REST bean names under narrow initialization synchronization. `requireRestHandler` at line 691 lazily resolves and reuses one handler under synchronization. Validation only inspects declaration count. Current `afterSingletonsInstantiated` creates one default generation, which includes only default-assigned Java methods; non-default fixed registrations are available to internal target-specific preparation but do not yet cause separate startup generations.

`LoomspanAutoConfiguration.java:167` wires the manager with a fresh catalog supplier, inputs, beans, startup properties, Environment and runtime factory. `skillLoadingPropertiesSnapshot` at line 186 copies startup discovery locations and model/connection selection metadata. This is internal Spring composition, not a bean-replacement contract.

## Architecture documentation and historical context

The existing pattern is detached complete generation construction followed by atomic activation, lease-governed retirement, and application-owned external staging/readiness. The accepted namespace design retains those owners while changing registry selection and publication granularity. It explicitly forbids a second parser, inheritance, per-namespace preparation locks/queues, dependency-revision publication preconditions, reverse callers, registration activation workflows, and multi-namespace transactions.
