## Research Question

Map the current declaration, reference, Java registration, generation, candidate,
validation, and public catalog implementation for
`ai/thoughts/tickets/loomspan-pr-27.1-canonical-namespace-identities.md`.
Distinguish existing executable behavior from the accepted namespace design and
the later tickets' integration responsibilities.

## Summary

The checkout currently owns one active global `SkillGeneration`. Declaration
names, capability names, definition keys, catalog names, and authored references
use the same local string. YAML and Java registration independently enforce the
local ASCII grammar. No namespace identity type or namespace owner exists in
these generation/catalog paths. The accepted design explicitly changes this
contract while retaining local declaration components.

Preparation already creates immutable metadata and a separately identified
executable candidate. Validation already shares declaration and contract checks
without allocating a generation or constructing provider/REST resources. Public
catalogs are eager, unfiltered, sorted immutable metadata with no lease. The
startup catalog bean and no-argument `SkillReloader.snapshot()` are the current
acquisition mechanisms.

Research made no production, test, or documentation changes. The only new file is
this artifact. The initial checkout was clean. No tests were run during research;
test statements below describe inspected source, not executed results.

## Detailed Findings

### Declaration parsing, references, and diagnostic fidelity

- `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:55` defines
  `^[A-Za-z_][A-Za-z0-9_]{0,63}$`. `readManifest` at line 404 checks the raw YAML
  object's local `name`, description, forbidden/unknown fields, output forwarding,
  bindings, and allowed children before mapping into `YamlSkillManifest`.
- `checkedConfigured` at line 141 discovers startup files; `checkedSupplied` at
  line 163 copies supplied YAML into UTF-8 resources. Both reset mutable maps and
  collect document-specific issues. Supplied source labels remain arbitrary
  exact diagnostic text; duplicate labels are checked separately from skill names.
- `addDefinition` at line 244 keys by `manifest().getName()` and reports both
  duplicate locations. `getSkills()` returns an immutable list, in discovered
  resource order; this catalog is a mutable preparation parser, distinct from the
  public immutable metadata catalog.
- `validateRawOutputFrom` at line 476 validates its target with the local-name
  pattern and compares the authored target directly to authored allowed-child
  names. `validateRawAllowedSkills` at line 524 uses the same local-name pattern
  and exact-string duplicate set. Optional children undergo those checks too.
- `validateRawBindings` at line 631 validates each `child_result.skill` with that
  same local-name pattern. `validateRawOutputBindings` at line 608 compares a
  producer directly to allowed-child names and the parent's local declaration.
- `compileEvidenceContract` at line 824 compiles output-property evidence against
  direct child names. `EvidenceExpressionParser` currently tokenizes identifiers
  as letter/underscore followed by letters/digits/underscores; it cannot consume
  qualified hyphenated names. Evidence expressions are authored reference-bearing
  content in addition to the explicitly listed allowed-child/forwarding/binding
  fields. Original expression text and parse columns participate in diagnostics.
- `src/main/java/ai/loomspan/internal/skill/YamlSkillDefinition.java:15` is an
  immutable record that defensively copies its mutable manifest. It stores parsed
  `AllowedSkillConstraint` and an `EvidenceContract`, but not an owning namespace
  or parsed skill identity. `outputFromSkill()` at line 107 reads the manifest's
  string. `outputBindings()` at line 111 rebuilds binding objects on each call.
- `AllowedSkillConstraint` stores a string name and immutable input-binding list.
  Its `from` factory converts authored fields during preparation.
  `ChildInputBinding` stores a nullable string producer; it currently requires only
  a nonblank, unpadded producer for `CHILD_RESULT`. Preparation adds the stricter
  local grammar. `ChildInputBindingDeclarations.validate` checks direct producers,
  self references, cycles, counts, and schema paths using string-keyed maps.

### Java registration and runtime metadata

- `src/main/java/ai/loomspan/api/SkillMethod.java:17` has `name` (default empty)
  and mandatory `description`; it has no namespace element. An empty name uses the
  canonical method name.
- `src/main/java/ai/loomspan/internal/core/SkillMethodBeanPostProcessor.java:211`
  registers canonical Spring-discovered methods, validates the same local-name
  grammar independently, and places metadata in `capabilitiesByName` under that
  name. Bean/method location is the diagnostic `id` and source, not another name.
  A collision reports both registrations. Discovery preserves proxy/interface,
  method security, lazy-bean, bridge-method, argument-schema, and invocation rules.
- `CapabilityMetadata` currently stores a string name and enforces that the tool
  descriptor has the same name. It does not parse an identity or enforce namespace
  ownership. `CapabilityToolDescriptor` is shared by Java and YAML/REST preparation.

### Generation invariants, preparation, and validation

- `src/main/java/ai/loomspan/internal/skill/SkillGeneration.java:17` owns an opaque
  ID, capability and definition maps, a public catalog, an internal observation
  catalog, and an optional executable runtime. Capability keys must equal metadata
  names; definition keys must equal local manifest names. Definitions require a
  matching YAML/REST/TypeSafe capability. Maps are copied, and ownership compares
  the exact metadata instance. `close()` closes only the optional runtime.
- `SkillGenerationManager` at line 50 holds an `AtomicReference<SkillGeneration>`
  for the single active generation. Startup initializes fixed Java registrations
  and REST handler declarations, prepares configured YAML, then activates it.
  Fixed registrations are global rather than grouped by namespace.
- Its `check` at line 247 builds one names map from all fixed Java registrations
  plus supplied definitions, resolves inputs, detects declaration collisions and
  unknown children, checks bindings, and derives output schemas, including
  forwarding chains. All its definition/contract/schema maps currently use local
  names. Named failed documents suppress dependent unknown-child noise only for
  their names; a nameless failure suppresses all such secondary noise.
- `validationResult` at line 229 returns no skill metadata on any error. Otherwise
  it combines all fixed Java registrations and all checked definitions into sorted
  `ValidatedSkill` names/kinds. `SkillValidationResult` independently enforces
  immutable lists and the no-partial-metadata-on-error rule.
- `validate` requires startup-fixed discovery to have completed. The explicit
  configuration path parses configuration without credential resolution and uses
  a fresh YAML parser. It does not call `prepareCatalog` or the runtime factory.
- `prepareCatalog` at line 498 validates first, then issues an ID using a manager
  UUID prefix plus a monotonic counter. It constructs metadata, definition keys,
  and a runtime. REST invoker closures capture the declaration's skill name and
  that candidate's generation ID before publication. These existing closures are
  the current authority for REST handoff identity.
- `DefaultSkillReloader.prepareWith` at line 105 serializes preparation, captures
  the current base ID, constructs a detached generation, performs a post-build
  shutdown check, and returns an opaque candidate. `publish` checks owner,
  closed/published state, current base ID, and lifecycle before activation.
- Its private `Candidate` at line 221 already returns `generation.id()` and
  `generation.skillCatalog()`, rather than the base ID/catalog. Closing an
  unpublished candidate releases its runtime; published ownership transfers to
  existing manager retirement/lease machinery.

### Public catalog, acquisition, and execution boundaries

- `src/main/java/ai/loomspan/internal/skillapi/DefaultSkillCatalog.java:16`
  eagerly constructs `SkillDescriptor` values from metadata into a `TreeMap`,
  rejects duplicate names, freezes the map and list, and retains only metadata
  and a generation ID. Lookup currently checks null then uses the exact string;
  malformed strings and missing local names both return empty. It owns no runtime
  lease and does not perform access filtering.
- `SkillCatalog` has `generationId`, `skills`, and `skill`, without namespace.
  `SkillDescriptor` and `ValidatedSkill` constructors currently require nonblank
  names, without reference parsing. Their returned values come from preparation.
- `SkillReloader.snapshot()` and `DefaultSkillReloader.snapshot()` currently return
  the active global generation's catalog. `LoomspanAutoConfiguration.java:237`
  separately exposes that startup catalog as a Spring bean; the reloader is wired
  immediately afterward. The injected startup object stays immutable when active
  generations change.
- `DefaultSkillTemplate.java:140` captures one generation for map preparation;
  `requireSkill` at line 274 looks up a string and checks returned metadata name
  equality. Root role enforcement uses resolved metadata. `ExecutionBinding`
  carries one generation; `DefaultAccessGuard` enforces existing role policies on
  capability metadata and caller authentication. These paths currently have no
  namespace or cross-namespace visibility context.

## Historical Context and Normative Ticket Boundary

`ai/thoughts/phases/skill-namespaces.md` is the accepted normative design, not a
description of current executable behavior. Its Identity rules (line 71),
Generation layering (line 83), Catalog contracts (line 106), reference validation
(line 132), and Java assignment (line 369) establish canonical references,
independent limits, qualified comparisons, namespace-owned generations/catalogs,
and metadata-only acquisition. Namespace renaming is new creation plus old
removal with explicit reference updates; no rename/inheritance API is selected.

The ticket explicitly authorizes destructive API/behavior changes without shims,
and forbids temporary bridges across the five slices. PR 27.1 owns shared parsing,
generation/catalog invariants, annotation/API shape, and focused checks. PR 27.2
owns active registry acquisition, startup grouping, and management integration;
PR 27.3 owns root admission; PR 27.4 owns model/child dispatch; PR 27.5 owns
observation consumers. Intermediate downstream build blockers must be named and
recorded for rerun, never represented as passes or bridged with dual formats.
