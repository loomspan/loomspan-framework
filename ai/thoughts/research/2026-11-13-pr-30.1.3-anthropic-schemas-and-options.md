## Summary

The root project uses Boot 4.2.0-RC2, Spring AI 2.1.0-RC2 and NetworkNT 3.0.9. Anthropic remains the official Spring AI native model, with Spring AI ChatClient/tool-loop ownership. ### 2. Tool schema flow

- `SpringAiModelInteraction.java:59–65` adapts bound capabilities into callbacks and adds the existing planner-inability control where applicable.
- `SpringAiToolCallbackAdapter.java:18–28` passes `capability.inputSchema()` directly into `FunctionToolCallback.inputSchema`, retaining canonical names and descriptions. It does not reshape tool schemas.
- RC2 `AnthropicChatModel.java:1652–1684` parses the schema as a map, copies nested `properties` into `Tool.InputSchema.Properties`, copies root `required`, and builds a tool. It does not copy root `additionalProperties`, description or other authored root entries. Nested map-valued schemas are embedded unchanged in the property values. The mapper does not explicitly enable native strict tools.
- SDK arbitrary-property construction can carry all root entries: retained direct-SDK fixture `docs/maintainers/probes/tbd-06/src/test/java/AdditionalAdapterTest.java:23–30`. This locates the transport distinction; it is not an implemented Spring AI fix.
- The existing tool manager/loop remains owned by `SpringAiChatClientAssembler` and `CanonicalToolCallingManager`. Typed-map Java generation, runtime-value traversal, validation, binding and authorization have separate owners (30.2.2/30.2.3); adapter fixtures can exercise authored standard schemas without implementing those migrations.

### 3. Options and native output configuration

- `EffectiveSkillExecutionConfiguration.java:6–12` contains framework alias, connection, driver, provider model ID and optional thinking level. There is no additional capability/strategy field.
- `LoomspanProperties.java:566–583` exposes model alias connection/model/allowed thinking levels. `YamlSkillCatalog.java:350–369` validates and resolves the effective level; `:392–397` applies the existing default level when a model supports thinking. These are existing configuration contracts, not a new SPI.
- `SpringAiChatOptionsContributor.java:36–46` maps all Anthropic levels through `budget()`: low 1024, medium 4096, high 8192. It sets max tokens to max(default 4096, twice budget), then calls `thinkingEnabled`. Existing unit fixture `SpringAiChatOptionsContributorTest.java:49–67` explicitly protects legacy low/medium/high values of 4096/8192/16384 max tokens for `claude-sonnet-4`.
- RC2 options support `thinkingAdaptive()` (`AnthropicChatOptions.java:755`), `effort(OutputConfig.Effort)` (`:823`), and `outputConfig(OutputConfig)` (`:813`). `DEFAULT_MAX_TOKENS` is 4096 (`:81`). Native effort/adaptive availability is source evidence; selected `claude-sonnet-5-5` wire behavior is not yet tested by the existing root contributor fixtures.
- RC2 `outputSchema(String)` (`:650`) reconstructs an SDK format and omits `$schema` and `$defs`. The raw native `outputConfig` path accepts the supplied SDK configuration; `AnthropicChatModel.java:992–993` forwards it into the request.
- RC2 options `mutate()` copies the native output config (`AnthropicChatOptions.java:520`). The retained fixture copies `defaults.getOutputConfig().toBuilder()`, replaces `format`, builds a new config and passes that per-call config through ChatClient (`CustomizationTest.java:26–33`). The probe verifies native schema equality and effort; AdapterTest separately asserts the generation cap remains 123.
- `SpringAiChatClientAssembler.java:103–130` resolves the captured connection and installs contributor options with `builder.defaultOptions(...)`. Both standard and step assembly use this path. Existing output validation (`OutputSchemaCallAdvisor.java:95–118`) augments prompts and validates responses rather than attaching native per-call schemas; ordinary native-output orchestration belongs to 30.3.1 and planning/step integration to 30.3.2. `ModelInteractionRequest` currently has no native-schema member.
