## Summary

The v1 invocation and its six diagnostic signatures already exist. `diagnostics()` currently throws an explicit `UnsupportedOperationException`; there is no diagnostic recorder, disabled-capture mechanism or temporary no-op implementation. The preceding ticket reports a coherent build and completed required verification, so its hypothetical diagnostic compilation debt is absent in this checkout.

## Detailed findings

### Supported v1 declaration and construction

- `src/main/java/ai/loomspan/api/extensions/v1/ExecutorDiagnostics.java:23` declares exactly `info`, `warn`, and `error`, each with `(String)` and `(String, Object)` overloads, returning void. It is a Framework-supplied capability, not a registration SPI.
- Its Javadoc at line 8 and PR 31.1.1 execution notes fix the JSON surface: null; exact String/Boolean; Byte/Short/Integer/Long; finite Float/Double; BigInteger/BigDecimal; exact HashMap/LinkedHashMap and JDK Map factory concrete classes with String keys; exact ArrayList and JDK List factory classes; reference arrays and primitive boolean/byte/short/int/long/float/double arrays. Custom implementations/subclasses, DTOs, arbitrary Number types, adapters, characters/char arrays, arbitrary JsonNode subclasses and implicit string conversions are outside that surface. Exact-class recognition precedes traversal.
- `SkillExecutorInvocation.java:18` is final with private construction. It captures immutable business map/list containers through `ImmutableContainers`; resource leaves preserve identity. It exposes skill/config-generation identity and live read-only cancellation/deadline suppliers. `diagnostics()` at line 54 currently throws.
- `src/main/java/ai/loomspan/internal/core/ExecutorInvocations.java:14` provides private construction through one cached MethodHandle. The constructor signature currently contains three maps, two strings, a BooleanSupplier and a remaining-time Supplier. This is internal machinery, not supported application construction.
- `LoomspanPublicSurfaceArchitectureTest.java:38` explicitly allowlists `ExecutorDiagnostics` and the exact v1 invocation. The supported set is 25 direct-package API types plus these two v1 types. It is closed rather than a whole-package SPI.
- `SkillExecutorRegistration.java:8` contains resolved executor `SkillIdentity`, configuration path, access policy, source and a typed invocation function. `SkillAdmissionSnapshot.java:11` captures the selected registration, immutable configuration and configuration-owner generation ID per executing YAML skill. Invocation does no live lookup or rebind.

### Direct and child executor boundaries

- `ExecutionCoordinator.java:136` begins `executeBound`; line 156 opens the existing mission frame. Its parameters include the objective and existing trace-safe mission input. Line 168 selects the admitted executor binding; lines 169–172 construct and invoke the handoff with resolved input, YAML config, executor config, skill name, executor generation ID and live lifecycle accessors.
- `MissionWorkExecutor.java:43` captures the current `ExecutionBinding`, starts the mission lifecycle and executes the callable in that binding on the mission worker. Timeout, interruption, cancellation and shutdown use its existing cutoff/cleanup flow. It records mission starts through the existing usage service. The physical worker may remain alive after logical completion when application work is uncooperative.
- `DefaultCapabilityInvoker.java:80` is the tool boundary for child calls. It records tool admission/accounting, assembles arguments, opens `TOOL_INVOCATION`, records a linked or unplanned start, calls `capabilityExecutionRouter`, then records a result only on successful return. Exceptions take its failure branch, record failure/classification and rethrow. These records already surround executor-backed YAML children; they are not a missing executor-specific start/stop stream.
- `DefaultExecutionStateService.java:66` opens mission frames through the existing `ROOT_MISSION` frame type. The opening path captures target namespace and executing generation, uses the mission's existing frame ID, pushes onto the branch and rolls back on a failed open record. Closing at line 133 checks current branch ownership and active-frame identity before recording and closing.
- `ExecutionCoordinator.java:199` catches execution failures and uses existing canonical failure recording; its `finally` closes the frame, closes lifecycle state, finalizes root traces and preserves existing cleanup semantics. `closeMetadata` at line 353 supplies completed/failed/aborted status and failure linkage. Existing frame-open and frame-close timestamps supply lifecycle timing. The code does not create a separate executor-operation span.
- The coordinator's frame parameters contain skill route/objective/input; they do not presently add explicit selected executor registration identity/configuration-owner generation evidence. The selected binding provides those facts at dispatch. This is distinct from the frame's executing YAML namespace generation.
- Root Java/executor successful strings return directly from the work callable; child tool result payloads use the existing `TOOL_CALL_COMPLETED` path. Planning must account for the actual existing evidence paths rather than assume every root invocation already emits a tool result record.

### Resource input and failure semantics

- `ExecutionCoordinator.java:406` uses declared attachment schemas when preparing mission input evidence. Attachment placeholders carry existing attachment metadata/ref information; Resource leaves are not eagerly read by this path. `traceSafeJavaInput` at line 415 retains existing resource/stream/byte-array placeholder handling for annotation-only Java input. These are preexisting input-evidence controls, separate from diagnostic JSON capture.
- `JavaSkillInvoker.java:21` invokes the final managed proxy, propagates invocation failures via `SkillFailurePolicy`, converts Java null to empty output, passes strings unchanged and serializes other successful results using the business-value mapper. That result conversion is execution work, not diagnostic capture.
- `SkillFailurePolicy.java:12` unwraps only recognized transparent reflection/future/Spring AI wrappers, bounded to 64 steps with cycle detection. It recognizes designated `RecoverableSkillException` without searching arbitrary application causes. Other exceptions remain terminal under current execution policy.
- `ExplicitJavaFailureHandlingIntegrationTest` already covers both Java roles through direct, standard-tool and explicit-step execution. The source-aligned Java API docs describe direct propagation, standard corrective feedback and explicit-step termination with no automatic replay. New diagnostic severity does not currently participate in this policy because recording is not implemented.

### Canonical records, content, ordering and observation

- `TraceRecordType.java:3` is the current closed Java event enum. It includes frame/tool/evidence/error events and payload chunks, but no diagnostic or system-notice events. `TraceFrameType` classifies execution scopes separately.
- `TraceRecord.java:14` carries trace/session identity, one sequence, timestamp, record type, optional frame/parent/frame type/route, thread name, metadata and `JsonNode data`. Its constructor copies metadata and deep-copies data. The data field is the existing content path required by the ticket.
- `LoomspanSession.java:720` serializes append access under its lock, delegates framed/unframed appends to the trace handle and translates IOException to IllegalStateException. An already-failed canonical failure recording makes subsequent appends return. Ordinary automatic-observation exceptions retain current execution semantics.
- `DefaultExecutionTraceRecorder.java:196` funnels framed records through the current `ExecutionBinding.runIfWritable`, augments existing metadata and appends to the explicit frame. Other paths resolve the active frame or plan frame from the current binding. These APIs currently expect an installed binding; a retained diagnostic handle used from another thread cannot assume that caller thread has one.
- `ExecutionBinding.java:88` delegates writable admission to `MissionLifecycle.runIfWritable`. The immutable captured binding contains session, mission, physical branch, generation and admission snapshot. It can be retained for lifecycle checks independently of the caller's thread-local binding.
- `DefaultExecutionTraceHandle.java:204` has synchronized framed append. It augments executing namespace/generation from the frame and calls `appendInternal` at line 337. That method rejects completed traces, converts data, increments the existing AtomicLong sequence and emits canonical records. Clock timestamps are resolved inside `buildRecord`; a known fixture timestamp override exists. There is no diagnostic sequence.
- Data over the existing 4096-character chunk threshold becomes a logical envelope plus `PAYLOAD_CHUNK_APPENDED` records. The ordinary logical record includes the original JsonNode for optional observation publication. Distinguish one logical diagnostic event from its physical content chunks when counting records in tests.
- `toJson` at line 517 deep-copies supplied JsonNode; other objects go through the canonical mapper's `valueToTree`. Existing generic conversion/chunking does not bound arbitrary diagnostic traversal before construction. Existing Jackson codecs distinguish application conversion and canonical traces (`LoomspanJacksonCodecs.java:27`).
- Optional observation publication is separate from canonical persistence. `LoomspanSession.java:679` contains optional observation close failures without changing canonical finalization. No Console connection is necessary for canonical tracing or public executor execution.

### Derived journal policy and API projection

- `ExecutionJournalProjector.java:84` switches known record types into journal entries and returns null for unhandled records. Frame lifecycle, tools, failures, results and other existing events have projections; new diagnostic vocabulary is currently absent.
- Its existing field-name treatment at line 365 is explicitly documented as the narrow supported derived-journal/observer exception. Canonical record payloads remain outside that exception. The ticket does not authorize removing or broadening it.
- `SkillExecutionViewMapperTest`, `ExecutionJournalProjectorTest` and `ExecutionJournalProjectionContractTest` establish the existing derived-view boundary. Adding canonical record vocabulary need not imply a new public event type or supported Java API type.

## Open questions for planning

These are already authorized implementation choices, not developer approval gates:

1. Select finite numeric message/data/depth/traversal/event/total budgets and separate reserved notice capacity; define exact explicit complete/truncated/unavailable/failure payload states and system-notice reasons.
2. Select the bounded Jackson capture algorithm and handling of very large BigInteger/BigDecimal values before conversion, malformed Unicode/escaping size, cycles, supported factory collection classes, and concurrent mutations within the fixed JSON surface.
3. Define capture/append/close linearization using retained invocation/frame/binding identity, including retained handles on application threads and cutoff while physical work continues. Existing lifecycle admission and canonical sequence remain authoritative.
4. Map missing executor identity/generation and root-result evidence onto existing observation paths without duplicate child/tool lifecycle or failure records, preserving the stated containment boundary and existing resource-valued input handling.
5. Select internal failure-injection seams for capture, append, fixed fallback notices and logging; tests must prove successful results and original failures survive new-path ordinary failures without recursively inspecting rejected content.
