## Summary

Executor YAML skills currently support optional input and output JSLT transforms
and ordinary input schemas. Root `output_schema` and
`output_schema_max_retries` are forbidden by declaration presence. Catalog
preparation returns executor definitions before the model output-schema and
evidence preparation path.

Direct, ordinary-tool and explicit planned calls all execute executor leaves
through `ExecutionCoordinator`. Its `publishExecutorResult` method receives the
ordinary executor String, optionally transforms it, records raw and published
evidence, and returns the one String consumed downstream. Existing structural
validation already parses exactly one complete JSON value with lossless numeric
decoding and reports JSON locations and constraint keywords. It does not rewrite
successful text.

Immutable definitions already retain compiled output schemas and transforms.
Complete generation preparation precedes publication, and invocation admission
captures namespace generations. Effective output metadata currently excludes
executor definitions explicitly. Forwarding metadata is derived recursively
from the selected producer.

## Detailed findings

### Declaration ingress and preparation

- `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:317`
  loads a manifest, validates required name/description and input schema, then
  returns an executor definition at line 326. Model form continues through
  output schema, evidence, linter and model configuration validation.
- `YamlSkillCatalog.java:475` selects the form from root executor presence and
  owns raw-tree applicability. Its executor forbidden-field list includes
  `output_schema`, retries, model execution, child, linter and output composition
  fields. The rule rejects presence even for null and empty values.
- `YamlSkillCatalog.java:811` validates a model output schema. With a schema and
  absent retry setting, it stores the existing model retry default. It compiles
  through `compileSchema` at line 846 and emits complexity warnings. Existing
  retries must be between zero and the configured constant maximum.
- `YamlSkillManifest.java:62` compiles authored output JSON with
  `StandardSchemaCompiler.Role.OUTPUT` and `Origin.AUTHORED`, caching the result.
  `setOutputSchema` at line 384 retains a detached tree and clears the cache.
  Declaration presence is tracked independently of values.
- `StandardSchemaCompiler.java:30` copies and walks the tree, requires exact
  root `type: object`, validates the supported Draft 2020-12 subset and initializes
  its networknt validator. Scalar and array roots fail the root rule. Numeric
  minimum/maximum and ordinary nested types are supported. The compiler disables
  remote resource fetching beyond its known schema meta-resources.
- `StandardSchemaCompiler.java:79` permits `x-loomspan-evidence` only as a
  nonblank String on an immediate root OUTPUT property. `YamlSkillCatalog.java:854`
  then parses those expressions and requires references to direct allowed
  children. Executor preparation currently returns an empty evidence contract
  before this method. These are distinct structural and child-evidence checks.

### Definitions, generations and admission

- `YamlSkillDefinition.java:79` makes a defensive manifest copy at construction.
  `copyManifest` at line 239 retains authored schema trees and shared immutable
  compiled schemas with `copySchemasFrom`, as well as compiled transforms.
  Its `outputSchema()` at line 145 exposes the compiled schema internally.
  `outputSchemaMaxRetries()` at line 194 returns zero when no value is stored.
- `SkillGenerationManager.java:152` parses complete execution configuration,
  checks all supplied documents and dependency metadata, requires valid results,
  then prepares a complete generation. It invokes no executor business method.
  `publish` at line 286 swaps the candidate under the generation monitor only
  when the expected target base still matches. A preparation failure occurs
  before publication and cannot replace the active generation.
- `SkillGeneration.java:91` retains immutable definition and capability maps,
  executor registrations and detached immutable executor configuration. Executor
  YAML leaves are JAVA capabilities whose source remains YAML.
- `SkillGenerationManager.java:313` captures one coherent generation per
  reachable namespace and retains an owner lease. Admission validates metadata
  against that snapshot. `ExecutionCoordinator.java:98` selects definitions from
  the captured target generation, so runtime result processing uses the captured
  definition. Replacement does not mutate this definition.

### Executor publication and failure boundary

- `ExecutionCoordinator.java:170` resolves caller arguments, applies the optional
  input transform, obtains the captured executor binding and invokes the Java
  handler on mission work. Diagnostics close in a finally block. Only successful
  handler return reaches `publishExecutorResult` at line 342.
- Without an output transform, publication returns the exact ordinary result
  String. Top-level calls record `executorOutput`; nested calls retain ordinary
  tool evidence. No JSON admission occurs in this branch.
- With a transform, `YamlSkillDefinition.java:50` evaluates the compiled
  expression and wraps failures with the qualified skill and
  `output_transform failed`. `ExecutorTransform.java:46` parses one complete JSON
  value using trailing-token rejection and lossless numeric decoding, evaluates
  JSLT once, and serializes the complete result. Its object filter preserves null
  fields and empty containers. Any JSON result root is accepted, including
  strings with JSON quotes, numbers and null.
- Transform success records `executorOutput`, `outputTransformStatus` and
  `skillOutput` on the executor frame. Transform failure records raw evidence,
  failed status and failure detail, then throws. These metadata writes are best
  effort under ordinary lifecycle, trace access and size controls.
- The coordinator catch at line 213 records the failure and rethrows. Frame and
  root trace closure follow in finally. `LoomspanSession.java:153` maintains
  identity-based failure bookkeeping and examines cause chains, allowing shared
  propagation to refer to an existing recorded failure.
- `CapabilityExecutionRouter.java:85` dispatches shared capability execution to
  this coordinator. Model execution engines and native-output correction remain
  separate from the executor branch.

### Existing output validation and diagnostics

- `OutputSchemaValidator.java:31` requires a compiled canonical schema, rejects
  blank/non-JSON/trailing-token text, and validates the decoded tree. Its mapper
  retains big decimal and big integer values. It returns a passed verdict or
  structured issues and does not return rewritten JSON. Operational exceptions
  propagate instead of becoming schema mismatch verdicts.
- Schema issues contain instance location, networknt error text, schema location
  and keyword. Parser issues contain `$`, `invalid_json`, bounded parser reason,
  line/column/offset and escaped nearby fragment. `OutputSchemaValidationIssue`
  applies existing diagnostic length/resource bounds.
- `OutputValidationPolicy.java:19` builds schema outcomes from attempt count,
  retry allowance, status, failure mode and a bounded issue list. A first failed
  attempt with zero retries is EXHAUSTED. The policy is stateless. Execution
  paths own attempts, retrying and recording.
- `OutputSchemaCallAdvisor.java:114` owns ordinary model validation and bounded
  correction. It records outcomes and throws the package-private
  `LoomspanOutputSchemaValidationException` after exhaustion. This exception
  includes qualified skill, attempts, failure mode and first issue in its
  message. The step engine has its separate validation/retry flow at
  `StepLoopMissionExecutionEngine.java:1406`.
- `DefaultExecutionStateService.java:479` records an output outcome against the
  current branch, mission diagnostics when owned, and canonical trace. Existing
  coordinator finalization retains the root mission outcome and merges nested
  diagnostic deltas. This mechanism already carries schema outcomes through
  direct and nested executions.

### Effective output metadata and consumers

- `SkillDependencyValidator.java:223` recursively resolves output schemas. A
  forwarding parent inherits the selected child's effective schema. The
  authored-schema branch at line 244 explicitly excludes executor form.
- `CanonicalSchema.java:16` derives a detached structural tree with
  execution-local annotations removed. Authored schema, structural metadata and
  child evidence are separate representations.
- `SkillGenerationManager.java:240` creates `CapabilityToolDescriptor` with the
  checked effective output schema. Public `SkillDescriptor`, registered catalog
  and existing observation consumers receive that generation-owned metadata.
  A missing schema is null.
- `SkillDependencyValidator.java:195` uses effective producer schemas for existing
  bounded output binding checks. `checkAdmission` at line 76 recomputes reachable
  outputs and compares prepared schema structures, rejecting changed effective
  contracts that require caller republication. Key order and formatting are
  compared as JSON trees.
- `ChildInputBindingAssembler.java:30` accepts exactly one successful direct
  result per child source. `AcceptedResultDecoder.java:18` losslessly decodes the
  accepted transport String, preserving plain text on parse failure. Invalid
  producer execution never becomes an accepted successful source. The step
  engine retains accepted-task outcomes, applies dependency settlement, and
  forwards the selected successful String without reconstruction.
