## Summary

Java already records executor diagnostics as ordinary events in the existing
executor mission frame. All message, severity, optional JSON and explicit capture
states are in `TraceRecord.data`, including when the ordinary chunk writer stores
that data in physical chunks. The current Go reader's closed vocabulary does not
include the two Java values. Go record queries, MCP mapping and browser content
retrieval already provide the required descriptor/content-reference mechanisms.

The current UI has chronological record rows and multiple lazy detail readers;
its default record selection omits executor diagnostic types and frame-open/close
records. The generic TypeScript `TraceRecord.type` is currently `string`, not a
closed enum. Separate Framework failure linkage drives existing failure styling.
Usage calculations are tied to native model response events and terminal snapshots,
not arbitrary diagnostic JSON. Java accounting reserves native provider attempts
only through explicit service calls made by native provider execution paths.

## Settled requirements and prior-ticket handoff

The ticket is the controlling acceptance source. The embedded Phase 3 contract
requires reuse of `LOOMSPAN_query_trace_records` and
`LOOMSPAN_read_trace_content`, existing type/frame filters, canonical sequence,
bounded pages/continuations, inline limits, opaque references and bounded ranged
reads. Diagnostics are records in existing frames, never additional frames or a
parallel stream. Notices have no developer severity. Error diagnostics do not
establish invocation failures or provider attempts. Missing diagnostics/notices
establish no capture cause. Complete retained notices do not make discarded
evidence recoverable. No diagnostic-specific tool/endpoint/store/index/service,
severity filter, notice filter bypass, sequence/cursor format or summary fields
is part of this ticket. Compatibility remains the exact current release string.

The execution notes of
`ai/thoughts/tickets/loomspan-pr-31.1.2-bounded-executor-diagnostics.md` establish:

- Types `EXECUTOR_DIAGNOSTIC_RECORDED` and
  `EXECUTOR_DIAGNOSTIC_SYSTEM_NOTICE_RECORDED`.
- Developer payload: `severity` INFO/WARN/ERROR, optional `message`,
  `messageState` COMPLETE/TRUNCATED/UNAVAILABLE, `dataState`
  ABSENT/COMPLETE/UNAVAILABLE/CAPTURE_FAILED, `data` only for COMPLETE (including
  explicit JSON null), and `reason` for incomplete capture. Message-only calls
  produce ABSENT data. Truncated messages retain an exact Unicode prefix.
- System payload: `reason`, fixed `message`, optional bounded `originalMessage`
  and `originalMessageState`; no developer severity or rejected structured data.
- Reasons: UNSUPPORTED_VALUE, CYCLE, MESSAGE_LIMIT, DATA_LIMIT, DEPTH_LIMIT,
  TRAVERSAL_LIMIT, NUMBER_LIMIT, CAPTURE_FAILURE, RECORDING_FAILURE,
  INVOCATION_EVENT_LIMIT, INVOCATION_BYTE_LIMIT.
- Capture limits: message 8 KiB UTF-8, supplied JSON 32 KiB, developer envelope
  48 KiB, depth 32, 4,096 values plus keys, numeric bit length and absolute decimal
  scale 4,096. Invocation attempts 128, attempted envelope bytes 256 KiB, four
  ordinary 2 KiB notices, one separately reserved 2 KiB limit notice and four
  fallback warning attempts. These are already-selected producer bounds.
- Captured handles serialize append/close, retain lifecycle ancestry, suppress
  reentry and close on physical executor completion or cutoff. No new lifecycle
  facility is needed for reader integration.
- Existing mission frame open data carries `executorName` and
  `executorConfigGenerationId`. Successful root converted output is recorded in
  `FRAME_METADATA_RECORDED.data.executorOutput`; children reuse ordinary tool
  completion. Failure classification and tool boundaries remain authoritative.
  Actual executor mission frames currently use ROOT_MISSION, including children;
  frame association must follow recorded identity instead of assuming
  SKILL_EXECUTION.
