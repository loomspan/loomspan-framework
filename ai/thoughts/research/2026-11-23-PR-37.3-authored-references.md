# Research — PR 37.3 authored references

## Research question

Map the existing producers, compilation, lookup, access checks, runtime consumers, fixtures and documentation for allowed children, executor references, child-result bindings, output forwarding and evidence expressions. Establish the original interpretation of existing dependency fields before their conversion.

## Summary

The checkout already resolves bare authored references in the containing namespace and colon-qualified references in the specified namespace. PR 37.1 changed the shared `SkillIdentity` codec because hyphens are now valid component characters. `YamlSkillCatalog` uses that helper for every listed structured reference family and separately compiles evidence tokens with its owner namespace. Runtime references are stored as identity objects or colon-qualified strings and select exact keys.

Callable lookup and executor lookup remain separate. Dependency validation checks namespace visibility, callable existence, executor existence and binding producer membership. Runtime discovery and dispatch additionally apply captured ownership and caller authorization. The evidence parser distinguishes whole operator tokens from qualified identifiers, preserving authored columns and expression text in the source/schema.

Many existing test strings and documentation snippets still encode the former single-hyphen qualified identity. The pre-series codec establishes the original target deterministically. The PR 37.1 ticket records 20 residual YAML/executor cases, and broader namespace, dependency, binding and evidence tests contain further canonical-name and old normalization expectations. This research ran no tests and makes no new passing-test claim.

## Exact identity and historical target interpretation

`src/main/java/ai/loomspan/internal/core/SkillIdentity.java:4` is an internal record with constructor validation. Each component must match `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`, use 1–64 ASCII characters and omit reserved substrings. The pair satisfies `namespace.length + 2 + localName.length <= 64`.

- `parse`, line 14, requires one colon with nonempty components.
- `resolve`, line 25, parses any reference containing a colon and otherwise constructs a pair using the supplied owner. It does not search registered names or infer a namespace from a hyphen.
- `toString`, final method, renders the exact pair with a colon.

The original implementation was inspected with `git show c271b80:src/main/java/ai/loomspan/internal/core/SkillIdentity.java`. It allowed ASCII letters/underscores in components, folded namespace case, used exactly one hyphen as a qualified separator, and treated a reference containing a hyphen as qualified. A bare reference without a hyphen used its containing owner. Thus original `warehouse-lookup` meant `(warehouse, lookup)` independently of the containing namespace. Original `infrastructure-sql` meant `(infrastructure, sql)`. Original `default-invoiceParser` meant `(default, invoiceParser)` and its declaration must also be reconciled with the new component grammar.

PR 37.1 added legitimate hyphenated local declarations and already converted some direct dependency fields, including `src/test/resources/skills/valid/allowed-skills-root.yaml`, whose children are now `default:allowed-visible-skill` and `default:disallowed-visible-skill`. A blanket conversion of every current hyphen-bearing value would misinterpret these newer local names. The pre-series file, declaration target and prior commit diff provide the provenance for conversion.

## Evidence tokenization and operator behavior

`src/main/java/ai/loomspan/internal/runtime/evidence/EvidenceExpressionParser.java:21` accepts an optional owner context. The one-argument overload requires already-qualified leaves because it passes null ownership. Parsing resets its stored context, offset and lookahead on each call.

- `parseOr`, line 40, and `parseAnd`, line 52, give AND higher precedence and flatten nested same-kind expressions.
- `parsePrimary`, line 64, creates a typed leaf using `resolve` with ownership or `parse` without ownership. Exceptions become `ParseException` at the original token's 1-based start column.
- `nextToken`, line 103, reads an identifier until whitespace or a parenthesis. Colon and hyphen characters stay inside the token and are validated by `SkillIdentity`.
- Only a whole token equal to `and` or `or`, ignoring case, is classified as an operator. `orders:and` and `orders:or` are identifier tokens and therefore reach exact identity validation. `orders:and or lookup` under owner `orders` consequently has two leaf identities and one OR operator through the existing implementation.
- Initial underscore or non-ASCII letter may enter identifier scanning, but exact identity validation rejects the resulting leaf. Digit-initial input enters the invalid-token path.

Existing parser tests retain case-insensitive operators. The ticket requires bare `and`/`or` as operators and qualified operator names as skills. It does not explicitly change operator case behavior. Exact component grammar still applies to identifiers.

The catalog currently contains a case-insensitive suggestion branch for an unmatched direct evidence reference (`YamlSkillCatalog`, line 941). With exact lowercase component validation, a case-changed identifier fails before direct-child membership. Existing wrong-case/ambiguous-case tests and documentation describe the earlier suggestion route. This is an observable sequencing fact for planning and test updates.

## Architecture and reuse map

Existing authority already flows from authored YAML through `SkillIdentity`, prepared constraints/bindings/evidence, dependency metadata, captured generation association and invocation access checks. The callable index and executor index remain independent. Bindings and evidence select only declared direct callables and consume exact runtime result identities. The shared assembler owns source selection for both input and output binding composition.

The investigation found a casing-suggestion branch whose former test setup conflicts with current exact lowercase identity validation. It also found overloads for ownerless evidence parsing and internal string constructors, all with checked-in callers. No dead-code removal or additional public extension requirement was established in this research.
