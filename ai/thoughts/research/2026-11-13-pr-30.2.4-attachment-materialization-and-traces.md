## Detailed findings

### Canonical declaration and loading boundary

- `src/main/java/ai/loomspan/internal/schema/StandardSchemaCompiler.java:48`
  recursively checks actual schema nodes: `properties`, `items`, and
  schema-valued `additionalProperties`. Nullable type arrays produce an ordinary
  type for annotation placement checking; nested shape-free INPUT nodes remain
  supported. The shared compiler is already the declaration authority.
- `StandardSchemaCompiler:93` checks attachment metadata only for INPUT string
  leaves, exact fields, supported `media_type`, and nonempty/nonblank string
  `allowed_content_types`. It currently does not call Spring's MIME parser.
- `src/main/java/ai/loomspan/internal/schema/CanonicalSchema.java:12` stores an
  immutable compiled snapshot; `tree()` returns a defensive tree copy.
  `providerTree()` removes recognized annotations at actual schema nodes while
  retaining similarly named ordinary properties and standard keywords.
- `YamlSkillManifest:56` lazily compiles its raw JSON input tree;
  `YamlSkillDefinition:159` exposes `CanonicalSchema inputSchema()`.
  `YamlSkillCatalog:823` delegates input declaration validation to that compiler;
  `compileSchema:828` catches `DeclarationException` and reports its schema path
  through existing catalog diagnostics. Skill/source context comes from catalog
  error construction. The retained TypeSafe attachment walker at line 500 still
  takes the removed input manifest class.
- `CanonicalSchemaTest.attachmentShapesAndProviderCopiesVisitOnlySchemaNodes`
  already covers single, nullable, nested, array-item, object-array and map-value
  annotations and provider stripping. Other foundation cases reject malformed
  metadata, invalid placement, unknown fields, and the removed attachment type.
  The malformed-metadata fixture containing an unknown extra key with MIME `x`
  does not establish MIME syntax rejection.

### Existing first-pass validation and input routing

- `src/main/java/ai/loomspan/internal/runtime/input/SkillInputValidator.java:22`
  recursively admits Java values before shared NetworkNT evaluation. It checks
  actual JSON values at marked/attachment leaves against their canonical leaf
  schema and checks strict `ref://` syntax for attachment strings.
- `Admission.visit:63` currently admits direct Resource at an attachment leaf
  without reading it, puts null in a private structural view and marks that view
  adapted. `weakenRuntimeLeaves:166` replaces marked/attachment leaf schemas with
  `{}` for surrounding validation after all actual leaves were visited.
  This is the current first-pass admission, not the accepted descriptor-contract
  validation following successful attachment materialization.
- Ordinary Java runtime markers are separately handled for Resource,
  InputStream and byte[]. Their nonconsuming validation and conversions were
  established by PR 30.2.3 and are distinct from attachment materialization.
- `propertySchema:159` already prefers named properties over typed additional
  properties. Actual null and missing values remain separate; standard parent
  requiredness, closure, siblings and bounds run on the private structure.
- `DefaultSkillTemplate.prepareMap:165` validates before invocation. The capability
  router's validated dispatch boundary is documented by current PR 30.2.3
  research; the coordinator itself is not the sole admission entry point.
- `SkillInputValidatorTest.attachmentFirstPassRemainsSeparateAndNonConsuming`
  covers Resource admission and separation from InputStream/byte[] at an
  attachment leaf. It does not exercise resolved resource content validation.
- `src/main/java/ai/loomspan/internal/vfs/InputReferenceTraversal.java:15`
  already selects named schemas, typed map schemas and item schemas with JSON
  tree traversal. Explicit input resolves only marked or attachment leaves;
  generic input retains separate recursive reference resolution.

### Materialization, resources and descriptor values

- `DefaultMissionInputMaterializer.materialize:55` uses original mission input
  or an empty map. Undeclared input returns rendered ordinary text without
  attachment traversal. Declared input currently calls removed `fromManifest`
  at line 72 before walking the old node representation.
- `materializeNode:96` visits attachments before any null branch. Objects select
  only named properties; unnamed values pass through unchanged. Arrays recurse
  by index. Container copies use `Map.copyOf` and `List.copyOf`. Paths use dots
  and bracket indices; this is separate from the JSON Pointer diagnostics
  already used by the shared validator.
- `materializeAttachment:140` accepts strict references or direct Resources.
  References resolve through the existing `RefResolver`/session VFS boundary.
  Direct Resources use source `resource`. Already-open Resources fail the
  repeatability check. No public registration API is involved.
- `detectContentType:200` detects common images/PDF/TXT/JSON/CSV by filename
  extension, then uses the single allowed type, then octet-stream. Raw string
  membership at line 174 compares allowed types. The signature switch at line
  248 is lowercase literal MIME matching. The authored declaration is retained
  separately in descriptor metadata.
- Image signature validation reads a 16-byte header in its own closed stream;
  JPEG/PNG/GIF/WebP signatures are the existing checks. Other media kinds do not
  use that image check. This establishes content checks, not provider acceptance.
- `contentLength:298` invokes Resource.contentLength before the bounded digest
  stream. `digest:311` counts bytes in 8192-byte reads, rejects over the configured
  limit, hashes SHA-256, but currently returns null on IOException. Size metadata
  comes from the earlier contentLength call, not the digest count.
- Runtime configuration captures the current generation's
  `session.attachments.maxSize`; default materializer limit is 20 MiB.
  `LoomspanProperties.Session.Attachments:385` permits zero or larger values.
- `LoomspanAttachment.descriptor:29` records attachment flag, fieldPath, nullable
  name, MIME contentType, enum mediaType, source, optional size/hash, and metadata.
  It excludes Resource. `Map.copyOf` rejects its inserted null name.
  `RenderedMissionInput:14` similarly uses `Map.copyOf` for rendered input.
- `src/main/java/ai/loomspan/internal/util/ImmutableContainers.java:12` already
  copies nested map/list containers immutably, preserving nulls and all other
  leaf identity, with repeated-container support and cycle rejection. This is
  existing shared copying machinery relevant to this ticket.

### Coordinator frame input

- `ExecutionCoordinator.execute:110` captures original mission input in its
  mission context. `executeBound:140` builds mission frame parameters before
  opening the owning frame and dispatching execution.
- `traceSafeMissionInput:403` currently calls a removed-manifest walker with
  `definition.inputSchema()`. That walker recognizes old `type: attachment`,
  visits named properties and item schemas, and uses dotted/bracket paths.
  Object/list containers are already null-preserving immutable wrappers.
- `attachmentPlaceholder:466` records attachment metadata and the exact reference
  or Resource filename/source without reading bytes. It is pre-materialization
  evidence and does not claim successful MIME, digest or size validation.
  It currently enters for null too, and its Map.copyOf rejects a missing name.
- The distinct Java-input diagnostic helper at line 412 already handles runtime
  objects. Its legacy redacted labels do not authorize new masking or field-name
  classification. This ticket's canonical attachment descriptors are declared
  runtime metadata; no caller content sensitivity classification is authorized.

### Engines, trace ownership, journal and observer

- `DefaultMissionExecutionEngine.executeMission:88` materializes within the
  captured mission binding, before planning and output composition's potential
  no-model completion. Planning gets traceSafeInput only when attachments exist;
  execution passes the complete RenderedMissionInput to the model request.
  Existing descriptor helper is at line 211.
- The standard engine wraps generic noncancellation model failures at line 151
  with skill/model/driver/media context and currently appends unsupported-media
  advice. Cancellation and designated failures are excluded by its helper.
- `StepLoopMissionExecutionEngine:236` materializes before initializing planning
  and before the plan-required check. It passes Resources on execution steps
  (`new RenderedMissionInput` at line 949), while step prompts use the descriptor
  tree. Existing descriptor helper is at line 1494; model request data already
  includes attachment descriptors at line 1144, which is not per-mission metadata.
- `SpringAiModelInteraction:57` uses `MimeTypeUtils.parseMimeType` and
  ChatClient's `user.media(mime, resource)`. It retains Spring AI tool-loop
  ownership. There is no upload lifecycle or native generated-media return API.
- `TraceRecordType:8` already declares FRAME_METADATA_RECORDED.
  `DefaultExecutionTraceRecorder.recordResultAssembled:73` and
  `recordResultForwarded:93` locate the exact owning mission frame using captured
  missionFrameId, route and mission frame type, then use the normal recorder
  boundary. These are existing ownership patterns.
- `ExecutionStateService`/`DefaultExecutionStateService` provide state-service to
  recorder operations and writable-binding checks. Generic planning/step record
  methods append against explicit frames. `LoomspanSession.appendTraceRecord:719`
  is the canonical handle writer; trace content remains independent of journal
  projection. No supported application API/SPI is involved in these seams.
- `ExecutionJournalProjector.project:31` iterates a record list;
  `project(ExecutionTraceHandle):45` streams records into the same stateless
  appendRecord. `skillLifecycleEntry:93` emits SKILL_STARTED/SKILL_FINISHED with
  skill name and finished status only. There is no current frame aggregation.
- The projector's existing recursive `sanitize:358` applies its field-name
  redaction exception to existing derived payloads. The ticket explicitly retains
  that exact exception for the new journal attachment collection, while canonical
  records retain full descriptor values.
- `SkillExecutionViewMapper:40` maps journal entries directly, converts object
  payloads to event details, and preserves frameId/route. `DefaultSkillTemplate:252`
  delivers this mapped finalized history to the observer. No new public event or
  endpoint shape is necessary to carry an attachments collection in details.
