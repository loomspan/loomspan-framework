## Summary

PR 30.2.1 introduced immutable `CanonicalSchema` and NetworkNT evaluation, and
PR 30.2.2 changed `SkillInputContract.schema()` and Java generation to this authority.
The ordinary input resolver, validator and reference walker still use
`SkillInputSchemaNode`. Their callers include public `SkillTemplate` preparation,
canonical capability routing and the ordinary tool loop. Callback input decoding
currently belongs to Spring AI's `FunctionToolCallback<Map<String,Object>,Object>`.

The accepted ticket moves ordinary structural assertions to NetworkNT, preserving
original runtime values through narrowly marked Java leaf adaptation, and corrects
callback decimal/root/complete-document handling before capability invocation.
Existing declaration generation, Java conversion and stream cleanup already own
their respective responsibilities. Attachment materialization and binding
projection/composition have subsequent explicit owners.

A fresh root compile failed with 43 initial missing-manifest-type diagnostics.
This is the documented migration baseline, not new runtime acceptance evidence.
Focused source-slice launchers already exist for canonical schemas and Java
declarations; full public, provider and architecture tests are transitively blocked.

## Detailed findings

### 1. Canonical schema foundation and generated inputs

- `src/main/java/ai/loomspan/internal/schema/CanonicalSchema.java:12` stores a
  defensive schema snapshot and initialized NetworkNT validator. `tree()` returns a
  copy; `providerTree()` removes recognized framework annotations only at schema
  nodes (`properties` values, `items`, schema-valued `additionalProperties`). A
  property whose data name matches an annotation remains a property.
- `CanonicalSchema.validate` returns completed NetworkNT errors. Its private
  per-call execution configuration asserts formats and sets evaluation step/depth
  limits to zero. Operational exceptions propagate.
- `StandardSchemaCompiler` enforces the supported Draft 2020-12 profile, bundled
  meta-schema checks, initialization and no remote resource fetch. Complete roots
  must have exact string `type: object`; nested INPUT leaves may be `{}` or
  description-only. Nullable ordinary type arrays, scalar enums, exact names,
  bounds, supported formats and input typed maps are represented in the actual tree.
  Generated false property schemas support binding ownership. General references,
  composition and arbitrary unknown keywords are outside the profile.
- `StandardSchemaCompiler` recognizes boolean
  `x-loomspan-runtime-ref-capable` only on generated INPUT string nodes. Authored
  schemas cannot add that metadata. Attachment metadata is a separate recognized
  input-string annotation and not an alias for a Java runtime handle.
- `src/main/java/ai/loomspan/internal/runtime/input/SkillInputContract.java:7`
  already contains `CanonicalSchema`. `genericObject()` compiles an open object
  contract; `allowsEmptyInput()` consults root required presence.
- `src/main/java/ai/loomspan/internal/serialization/LoomspanMethodInputSchemaGenerator.java:44`
  generates exact canonical method contracts, including parameter descriptions and
  requiredness. Runtime leaves (Resource, InputStream, byte[]) are marked string
  nodes before bean traversal. `Object` has no constraints. Typed maps use
  schema-valued `additionalProperties`; DTO properties are closed/required.
  Resolved generic types, map-key declarations, recursion and effective
  JsonUnwrapped checks were already handled by PR 30.2.2.
- `SkillMethodBeanPostProcessor:216` publishes the canonical tree string and stores
  the canonical Java-reflected contract. It does not need old schema generation.
- `YamlSkillManifest` stores raw schema JsonNodes and compiled canonical schemas.
  `YamlSkillDefinition:159` already exposes `CanonicalSchema inputSchema()` and
  `hasDeclaredInputSchema()` distinguishes an authored contract from generic input.

### 2. Resolver and validator remaining representation

`src/main/java/ai/loomspan/internal/runtime/input/SkillInputContractResolver.java`
still accepts/constructs old manifest/node representations:

- `resolveJavaCapability:32`, `resolveYamlCapability:39` and
  `resolveFromToolSchema:52` create contracts from old parsed nodes.
- `fromManifest:79` names removed `YamlSkillManifest.InputSchemaManifest`.
- `fromJsonSchema:101`, `fromJsonNode:117` and `toJsonSchemaNode:219` form a custom
  node parser/serializer. The custom node carries string enums and scalar type
  names, rather than the current canonical semantics.
- Autoconfiguration supplies the application-conversion mapper to the resolver;
  the canonical schema mapper is separately available from `LoomspanJacksonCodecs`.

`SkillInputValidator:20` exposes `validate` and `validateExact`; both return the
internal `SkillInputValidationResult(valid, normalizedInput, issues)`. Internal
issues retain path, code, message and rejectedValue. The public exception issue
type intentionally contains path/code/message only; public API shape is separate
from internal diagnostic fidelity.

The remaining implementation is a custom structural/normalization walker:

- `validateExact:26` bypasses walking for generic contracts with no exact paths.
  Otherwise it calls `validateNode` with old `SkillInputSchemaNode`.
- `validateUnconstrained:75` recursively checks JSON values, rejects non-string
  map keys and non-finite Float/Double, and copies maps/lists. Ordinary other
  Numbers are returned. Arbitrary Java objects, Resource/InputStream and byte[]
  are rejected by this unconstrained path.
- `validateObject:134` treats required null as missing except an exact-policy ANY
  exception, then applies `String.valueOf` to object keys. It validates typed
  additional properties, checks closure and walks ordinary declared children.
- `validateOpenBranch:185` copies ordinary undeclared open values without the
  same recursive JSON-value restriction unless the exact policy applies.
- Integer/number/boolean branches parse strings under non-exact policy. Date
  validation normalizes several non-ISO forms under non-exact policy. The ticket's
  standard no-coercion semantics explicitly supersede these ordinary behaviors.
- `validateString:310` accepts marked runtime Resource/InputStream/byte[] using
  `acceptsRuntimeRefValue:341`; otherwise it checks text, enums and date handling.
- `validateAttachment:352` separately accepts strict ref strings or Resource.
  This existing first-pass attachment exception is distinct from this ticket's
  Java adapter and the next ticket's MIME/materialization work.
- `DeepInputValues.immutableCopy` enforces string keys while detaching containers;
  it clones byte[] values. The accepted adapter contract additionally requires
  original runtime leaf identity to reach binding, so copy behavior matters.

The ticket's accepted mechanism is already specified: separately validate actual
JSON values at marked Java leaves using their canonical schema; accept only the
existing direct runtime kinds there, without reads; create a private structural
view replacing accepted runtime objects with null and marked schemas with `{}`;
then evaluate the surrounding canonical assertions through NetworkNT. Every
occurrence must be checked before shared item schemas are weakened. Actual null
must independently satisfy the canonical leaf. Original inputs and schemas remain
unchanged; the private view/schema are not provider or diagnostic evidence.

### 3. Public entry and capability ordering

`src/main/java/ai/loomspan/internal/skillapi/DefaultSkillTemplate.java:118`
captures the generation before object conversion. Object overloads perform
application mapper conversion; map overloads pass the map to `prepareMap:165`.
This ticket explicitly avoids redesigning the object/DTO overload.

`prepareMap` selects the captured capability, normalizes null-map behavior using
the contract, validates before generation admission, throws public validation
issues on rejection, and retains the prepared validation result. Invocation then
authorizes with captured/current authentication and executes the validated map.
Capture leases are closed on failures. `validate()` uses the same preparation
and authorization boundary without execution.

`CapabilityExecutionRouter:62` checks AccessGuard before validation, validates the
complete receiving arguments, then verifies explicit session/current binding and
generation ownership before `ExecutionCoordinator.execute`. Assembled inputs
call `validateExact` with binding paths and retain their distinct exception prefix.
The accepted migration changes ordinary validation semantics, not the binding
assembly ownership or authorization order.

`DefaultCapabilityInvoker:120` validates assembled receiving inputs before its
tool frame, records original argument/failure evidence, and delegates through the
router. The ordinary no-binding route also reaches the router. Invalid inputs do
not reach target execution; logging/planning effects belong to the existing loop.
The ticket does not add batch rollback or retry policy.

### 4. Reference resolution, Java conversion and cleanup

- `src/main/java/ai/loomspan/internal/vfs/RefResolver.java:19` distinguishes generic
  recursive reference resolution from explicit-contract resolution. Explicit
  resolution follows declared properties, typed map values and array items;
  only runtime-marked or attachment leaves call `resolveArgument`. Unconstrained
  explicit values and undeclared open values remain literal, including ref text.
  The walker still consumes old schema-node APIs.
- `DefaultRefResolver` resolves only strings matching exact `^ref://\\S+$` through
  the existing VFS/session access boundary. Non-reference values are returned.
- `ExecutionCoordinator:166` resolves arguments for Java execution after public
  or router validation and authorization, before executor/BPP invocation. Its
  separate trace/attachment helpers still use removed input manifest types.
- `SkillMethodBeanPostProcessor:333` binds method parameters inside `try/finally`
  and closes opened streams after success, conversion failure and body failure.
  `convertArgument:380` owns Resource/byte[]/InputStream conversions. Ordinary
  containers/DTOs use the application mapper. Resource-valued supported containers
  preserve assignable handles through `bindMaterializedContainer:418`; existing
  nested materialization owns content conversion. Validation permission does not
  promise every runtime-kind/target combination can bind.

### 5. Callback ingress and Spring AI ownership

`src/main/java/ai/loomspan/internal/springai/SpringAiToolCallbackAdapter.java:20`
builds `FunctionToolCallback<Map<String,Object>,Object>` with the capability's
name, description and input schema. Its lambda calls `capability.invoke(arguments,
null)` after Spring AI decoding. Result conversion is owned by FunctionToolCallback.

`BoundCapability:56` snapshots the outer map, turns null arguments into `Map.of()`,
and calls its bound invocation. Its constructor always constructs
`ChildInputBindingProjection`, including empty bindings, so real construction
currently crosses a downstream canonical-migration blocker.

`CanonicalToolCallingManager` checks provider response acceptance, all tool
selection names and the bound callback surface before delegate execution. It
preserves original argument text and provider evidence when creating a canonical
name execution copy. It delegates actual execution to Spring AI
`ToolCallingManager`, retaining its loop, callbacks, feedback and result handling.
It has separate planner-inability control handling; that control already uses a
reader with whole-document and duplicate-tree-key checks at
`PlannerInabilityTool:38`. That reader does not decode ordinary callbacks.

`LoomspanJacksonCodecs` separates application conversion, YAML, planning, schema,
trace and observability mappers. Schema-tree decoding enables BigDecimal for
floating values; the ticket calls for a local ordinary callback reader with
lossless decimals and FAIL_ON_TRAILING_TOKENS, not a global Spring AI mapper change.
Object-root checking must occur before BoundCapability's null-to-empty adaptation.

## Open questions for implementation planning

No unresolved developer/product decision was found. Planning still needs to
select the smallest reproducible real-source test slice for restored input and
ordinary callback behavior while preserving explicitly downstream-owned sources.
Real BoundCapability construction crosses ChildInputBindingProjection even for
empty bindings; public map invocation crosses full generation/coordinator source
dependencies. Those dependencies must be represented by executable restored seams
or explicit named blocked checks, without claiming mocks/stubs prove full dispatch
and without migrating binding/output/planning merely to make the root compile.

The attachment first-pass Resource/ref allowance and generic-reference behavior
are preservation seams. Their implementation details must retain ordering without
performing 30.2.4 MIME/materialization/descriptor work here. Marker-only runtime
adaptation must distinguish actual null from accepted-handle placeholders and
keep diagnostics rooted in original values. These are settled requirements, with
routine implementation choices left to planning rather than new escalation.
