# Research — executor output transform

## Research question and execution context

Map the current code, tests and authoring guidance relevant to
`ai/thoughts/tickets/loomspan-pr-31.4.3-executor-output-transform.md`.
This is Step 1 of the developer-approved Full 5-Step Pipeline. The ticket asks
for an optional executor-only root `output_transform` that publishes any JSON
value after successful executor work. The ticket excludes executor output
schemas, provider-pack migration and supported Java extension API changes.

The initial checkout was `main` at the commit above, with only the ticket
untracked and no tracked or staged changes. Research modifies only this
artifact and runs no tests. `bash ai/scripts/spec_metadata.sh` supplied the
metadata above. The script supplied no thoughts-system researcher, so Codex is
recorded. The executing model identifies as GPT-6.1 Sol. The ticket names
GPT-6.2 Sol for implementation, which is a later stage.

## Summary

The current checkout implements executor `input_transform` through raw-tree
declaration validation, catalog-time JSLT compilation and immutable definition
capture. It has no `output_transform` declaration or execution path.

Both direct and child execution reach the executor branch in
`ExecutionCoordinator`. That branch receives an ordinary String result from
the captured Java registration after shared Java return conversion. All
downstream consumers receive that returned String. Planning result bindings
decode accepted result text separately, while designated-child forwarding
returns the retained String directly.

Canonical diagnostics currently record successful root executor text as
`FRAME_METADATA_RECORDED.data.executorOutput`. Child tool results record the
returned text through the ordinary tool result event. The root executor
metadata write currently runs only for top-level invocation. No distinct
published executor skill result or output-transform failure evidence exists
today.

## Detailed findings

### YAML declaration and preparation

- `src/main/java/ai/loomspan/internal/skill/YamlSkillCatalog.java:386` decodes
  manifest YAML through `SkillDocumentValues`, validates required fields and
  selects declaration form from root `executor` presence. Unknown fields fail
  typed binding. The catalog is shared by startup and supplied-document checks.
- `YamlSkillCatalog.java:475` owns declaration applicability against the raw
  tree. Executor leaves reject model execution, planning, child, linter and
  output-schema fields by presence. Model form rejects `config` and
  `input_transform`, including null and malformed values. `output_transform`
  currently reaches unknown-property rejection.
- `YamlSkillCatalog.java:496` validates `input_transform` as an object with
  exactly `language` and `expression`, requires exact textual `jslt` and a
  nonblank expression, and retains authored expression text. At lines 424 and
  437 it removes that separately handled field before ordinary binding, then
  compiles it with resource diagnostic provenance. Compile errors become
  structured field-path failures at `input_transform.expression`.
- `src/main/java/ai/loomspan/internal/skill/YamlSkillManifest.java:18` tracks
  explicit declaration presence. Its input-transform declaration and compiled
  object are separate internal state, outside normal JSON binding. The
  prepared expression is held alongside original declaration data.
- `src/main/java/ai/loomspan/internal/skill/YamlSkillDefinition.java:67` copies
  the manifest when constructing a definition. `copyManifest` at line 225
  copies authored fields and separately retains the immutable compiled input
  transform at line 257. `manifest()` also returns a defensive copy.
- `YamlSkillDefinition.java:24` exposes the current input-transform presence,
  JSON admission and application operations. It wraps transform failures with
  qualified skill identity and `input_transform failed`. It has no successful
  executor-result processing operation.

### Existing JSLT and JSON machinery

- `pom.xml:53` pins `ai.loomspan.thirdparty:jslt` version
  `0.1.15-jackson3-cf30e6d`. `third-party/jslt/pom.xml` identifies upstream
  commit `cf30e6d9be247d489dac6bf53bf930322c8fd663`. The dependency and bootstrap
  from PR 31.4.1 already exist.
- `src/main/java/ai/loomspan/internal/skill/ExecutorInputTransform.java:30`
  compiles with JSLT `Parser`, authored source name and
  `.withObjectFilter("true")`. The latter preserves constructed null and empty
  container values. `apply` converts a JSON-only map to a Jackson tree,
  evaluates once, requires an object root and converts its values back to Java.
  It therefore currently exposes only map-input/map-output transform behavior.
- Its recursive value checks preserve null, exact textual keys, list order,
  finite scalar numbers, BigInteger and BigDecimal. They reject runtime handles,
  non-string object keys and nonfinite numbers. The result conversion also
  rejects constructed nonfinite numbers, including nested values.
- `src/main/java/ai/loomspan/internal/serialization/LoomspanJacksonCodecs.java:39`
  builds the schema-tree mapper with `USE_BIG_DECIMAL_FOR_FLOATS`. It is shared
  infrastructure and has no global trailing-token option enabled.
- `src/main/java/ai/loomspan/internal/runtime/input/AcceptedResultDecoder.java:10`
  has a private JSON mapper with big integer/decimal preservation and
  `FAIL_ON_TRAILING_TOKENS`. It decodes accepted transport text to immutable
  Java values. Its parse-failure behavior returns original text. This is the
  binding decoder's established behavior.
- `src/main/java/ai/loomspan/internal/outputschema/OutputSchemaValidator.java:22`
  and `OrdinaryToolArguments` also use strict trailing-token parsing for their
  own boundaries. The current transform engine does not parse result text.

### Executor execution and successful result conversion

- `src/main/java/ai/loomspan/internal/core/CapabilityExecutionRouter.java:54`
  is shared by direct and child invocation. It validates the receiving input
  contract and routes through the captured generation to the coordinator.
- `src/main/java/ai/loomspan/internal/core/ExecutionCoordinator.java:98`
  obtains the YAML definition from the captured target generation. Its JAVA
  branch at line 168 runs on `MissionWorkExecutor` under scoped caller
  authentication. Input reference resolution precedes optional input transform.
- At line 183 the coordinator calls exactly one captured executor registration
  with a Framework-created v1 invocation. Input, skill config, executor config,
  identity, generation and live lifecycle observations remain separate values.
  Diagnostics close in `finally` when executor work returns or throws.
- `src/main/java/ai/loomspan/internal/core/SkillMethodBeanPostProcessor.java:192`
  builds reference-only executor registrations with a String-returning invoker.
  `src/main/java/ai/loomspan/internal/core/JavaSkillInvoker.java:21` invokes the
  managed bean and performs shared successful-result conversion. A null or void
  return becomes empty text, a String is returned exactly, and another Java
  value is serialized with the application ObjectMapper. The output-transform
  ticket's ordinary executor result text therefore refers to this already
  converted String.
- The coordinator currently returns that text immediately after optional root
  diagnostic recording. There is no executor retry loop here.
- `src/main/java/ai/loomspan/internal/runtime/MissionWorkExecutor.java:38`
  submits one bounded callable, applies the existing lifecycle and cancellation
  rules, and propagates its exception. `SkillFailurePolicy` recognizes designated
  recoverable application exceptions. `ExecutionCoordinator.java:223` records
  failure and closes the mission frame, preserving terminal failure linkage.

### Direct calls, ordinary tools and planning consumers

- `src/main/java/ai/loomspan/internal/skillapi/DefaultSkillTemplate.java:284`
  executes through the router and returns `String.valueOf(result)`. The
  coordinator's executor String therefore reaches public direct callers.
- `src/main/java/ai/loomspan/internal/runtime/tool/DefaultCapabilityInvoker.java:172`
  routes ordinary and assembled child arguments to the same execution router.
  It records success and the returned result only after execution succeeds,
  then returns that result. Failure records use the shared tool failure path.
- `src/main/java/ai/loomspan/internal/springai/SpringAiToolCallbackAdapter.java:36`
  invokes the bound capability and converts the result with Spring AI's ordinary
  tool result converter. There is no authored-transform operation in this adapter.
- `src/main/java/ai/loomspan/internal/runtime/step/StepLoopMissionExecutionEngine.java:811`
  retains completed task result text in the owning mission after successful
  execution. `MissionContext.java:164` snapshots that text and decodes it once
  with `AcceptedResultDecoder` for later binding selection.
- `src/main/java/ai/loomspan/internal/runtime/input/ChildInputBindingAssembler.java:30`
  selects exactly one accepted successful direct result for `child_result`,
  traverses the already decoded object path and inserts the selected whole
  value into detached receiving input. No transform is reapplied here.
- `StepLoopMissionExecutionEngine.java:522` selects the captured designated
  child task, verifies its skill binding, records `RESULT_FORWARDED` and returns
  `CompletedTaskResult.result()` unchanged. All accepted work has completed
  before this branch. The parent adds no result parsing or final synthesis.

generic record/data tooling reads canonical payloads. The ticket does not request
a REST/SSE, acquisition or named diagnostic-record protocol change.

## Open questions for planning

There is no developer decision required from this research. Planning still
needs to choose the internal representation for reusable JSLT evaluation and
the strict result-text parser, including an explicit empty-input check and
finite-number handling. It must specify distinct raw/published diagnostic
evidence for roots and children and transform failure evidence after successful
executor work. Those implementation decisions can use the existing boundaries
documented above and the ticket's exact acceptance requirements.
