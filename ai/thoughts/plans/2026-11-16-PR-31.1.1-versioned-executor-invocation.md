# Versioned executor invocation and cooperative lifecycle implementation plan

## Overview

Replace the unversioned invocation record with the exact Framework-created v1
handoff, preserve captured business values and generation identity, and expose
live read-only lifecycle observations. Settle diagnostic declarations and their
restricted JSON contract; bounded recording remains owned by 31.1.2.

This is Steps 2 and 3 of the developer-approved **Full 5-Step Pipeline**. The
initial Framework checkout was clean; the research artifact and these plans are
ticket-owned. No source changes or verification runs occurred during planning.

## Current state analysis

- `SkillMethodBeanPostProcessor:193` checks the exact unversioned parameter;
  `SkillExecutorRegistration:8` stores its invocation function.
- `ExecutionCoordinator:160–170` is the only production constructor site. It
  runs after reference resolution and uses captured registration/configuration.
- `ImmutableContainers` recursively copies maps/lists and retains other leaf
  identities. Preserve this business-value contract, including Resource handles.
- `MissionWorkExecutor:36–76` submits work and waits with a mission timeout.
  `StepLoopMissionExecutionEngine:229–295` has a separate timed submission path
  that can be the parent of executor work.
- `MissionLifecycle.deadlineNanos` is cancellation cleanup grace. It cannot be
  reused as execution remaining time. `frameworkDeadlineNanos` is separately
  published by `FrameworkExecutionLifecycle`, including to late-registered missions.
- `LoomspanPublicSurfaceArchitectureTest` hardcodes both the direct API package
  inventory and recursive signature package check. Both need deliberate updates.
- No developer diagnostic recording facility exists. The native TypeSafe
  implementation remains present and is inventoried for later removal.

## Desired end state

Exactly these new supported top-level types live in
`ai.loomspan.api.extensions.v1`:

```java
public final class SkillExecutorInvocation {
    public Map<String, Object> input();
    public Map<String, Object> skillConfig();
    public Map<String, Object> executorConfig();
    public String skillName();
    public String executorConfigGenerationId();
    public ExecutorDiagnostics diagnostics();
    public boolean isCancelled();
    public Optional<Duration> remainingTime();
}

public interface ExecutorDiagnostics {
    void info(String message);
    void info(String message, Object data);
    void warn(String message);
    void warn(String message, Object data);
    void error(String message);
    void error(String message, Object data);
}
```

Invocation has no public/protected constructor, setter, builder, lifecycle
registration hook, factory, or subclass contract. Final private state keeps the
five captured values and private JDK supplier-backed lifecycle observations.
Keep constructor validation and map/list copying semantics of the old record.
Capture the actual mission/lifecycle in the suppliers; never re-read an ambient
binding when a consumer accesses the invocation from another thread.

Use one small internal factory, provisionally
`ai.loomspan.internal.core.ExecutorInvocations`, with a cached private-constructor
MethodHandle obtained through `MethodHandles.privateLookupIn`. The project runs
on the classpath and has no module descriptor. This avoids creating a public
construction or lifecycle SPI solely for cross-package Java access. Initialization
failure is an internal execution failure, not a compatibility fallback. Tests may
use this internal factory for isolated value tests; supported consumer integration
tests obtain the object only by invoking a YAML executor leaf through the facade.
The internal helper requires a reasoned architecture allowlist entry if public
visibility is needed for cross-subsystem tests/callers.

### Diagnostic declaration and honest staging decision

`ExecutorDiagnostics` is a read-only capability declaration, not a registration
SPI. Application implementations are never discovered, registered, or selected.
Only the exact invocation class is accepted by `@SkillExecutor` registration.
No public level enum or independently selected presentation version is introduced;
the six methods select exactly `info`, `warn`, or `error` for developer calls.

The JSON value surface is fixed now for 31.1.2:

- Null; exact String and Boolean; exact Byte, Short, Integer, Long, Float, Double,
  BigInteger and BigDecimal. Floating values must be finite.
- Objects with String keys: exact `HashMap` and `LinkedHashMap`, and JDK immutable
  factory maps created by `Map.of`, `Map.ofEntries`, or `Map.copyOf`.
- Lists: exact `ArrayList` and JDK immutable factory lists created by `List.of`
  or `List.copyOf`.
- Java reference arrays, and primitive boolean/byte/short/int/long/float/double
  arrays. Character values and char arrays are unsupported.
- Subclasses/custom Map/List/Number implementations, arbitrary DTOs, Jackson
  adapters or arbitrary JsonNode subclasses, custom iterables, and implicit
  `toString()` conversions are unsupported. The future recorder must recognize
  supported concrete classes before traversal, not call user collection methods
  merely to decide whether a value is supported. Known JDK factory concrete
  classes can be derived from controlled exemplars rather than broad class-name
  prefixes. Container cycles are rejected within traversal budgets.

`Object` is the Java entry signature for this restricted value set; it does not
authorize arbitrary-object serialization. This diagnostic surface is distinct
from existing business input/configuration maps, whose leaf semantics stay intact.

For this intermediate ticket, `diagnostics()` explicitly throws
`UnsupportedOperationException` with a clear unavailable-capability message.
Do not return null, supply a no-op recorder, silently discard events, or add a
disabled-capture option. This is a visible current limitation, not completed
diagnostics. It allows real lifecycle/API checks to run without implementing
31.1.2 early or manufacturing compilation debt. Record this staging choice and
restoration owner in ticket execution notes. Product docs state the actual current
unavailability without ticket numbers or future-delivery promises. The six
diagnostic methods have declarations only, so no inert recording implementation
exists. 31.1.2 replaces the unavailable accessor with the real invocation-scoped
capability and owns bounded Jackson snapshot/capture, lifecycle closure,
notices/fallback, and failure-containment verification.

The settled future method guarantee covers ordinary failures after entering a
diagnostic method, including Framework notices and fallback reporting. It excludes
caller expression evaluation and JVM-wide failures, and does not rewrite existing
automatic observation semantics. Level never changes outcome or retries. Do not
test or claim those recording guarantees as implemented by this ticket.

### Live lifecycle semantics

- Add execution-deadline bookkeeping to `MissionLifecycle`, separate from cleanup
  grace. Establish it once at the existing bounded submission boundary, before
  the worker can construct/use an invocation. Both MissionWorkExecutor and the
  explicit step-loop submission owner must establish it.
- Use the same captured timeout used by enforcement, with monotonic arithmetic
  and bounded/saturating conversion. Do not start a fresh budget at executor
  entry, child entry relative to ancestors, diagnostic access, or retry.
- Align the existing timed wait with that original established deadline so
  submission or setup cannot silently renew the budget. Preserve existing
  timeout exception/failure/interruption/cleanup behavior and timeout precision;
  account explicitly for the existing millisecond timed-get behavior.
- Remaining time is the minimum applicable remaining mission/ancestor execution
  budget and published shutdown deadline. Compute it live through the captured
  mission ancestry. Empty means no established applicable deadline; expired means
  `Duration.ZERO`, never negative. Cancellation cleanup grace is never included.
  A raw internal mission can have no deadline; ordinary public executions have
  the configured positive mission timeout. Do not add a no-timeout setting.
- `isCancelled()` observes cancellation of the current mission or any ancestor,
  including Framework cutoff. Successful normal closure is not itself a new
  cancellation event. Use existing primary-cause/state authority, synchronized
  or atomically published as appropriate. Mere deadline expiry is still directly
  observable as zero before the enforcement thread publishes cancellation.
- Accessors never clear interruption. The executor separately checks its thread's
  interrupt flag; an unrelated interrupt need not mutate Framework cancellation
  state. Public caller interruption through the existing cancellation path must
  become observable. Do not expose mutation, abort I/O, add a scheduler, register
  physical cancellation callbacks, or hold trace/write locks just to read state.
- Preserve shutdown's lock-free cutoff publication, first-cause selection,
  existing write fencing and physical generation/resource retention. No new
  post-return accessor prohibition or post-completion monitoring guarantee.
