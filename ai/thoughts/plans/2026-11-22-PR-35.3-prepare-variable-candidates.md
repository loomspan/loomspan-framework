## Desired End State

Every supported preparation overload resolves all selected occurrences from one copied explicit map or normal `Environment.getProperty(name)`. A name is looked up once per candidate. Repeating preparation, even with the same publication version and documents, performs a fresh resolution. Publication consumes only the prepared generation. Actual executor invocations observe resolved namespace and leaf data from the appropriate retained namespace generations.

Staged validation performs zero value lookups, provider constructions and application calls. It checks marker names, authoring structure, allowed fields, publication target, declarations, dependencies and all constraints whose operands are known. Only value-dependent constraints and effective keys await preparation.

## Implementation Approach

### Candidate ownership and sequence

Introduce one internal preparation representation, preferably adjacent to `SkillGenerationManager`, owning the authored execution document and ordered authored skill documents for the current call. Reuse `AuthoredYamlVariables` for selection, marker grammar, paths, alias bounds, terminal strings and collision diagnostics. Keep this representation short-lived and local to validation/preparation.

The preparation sequence is the following.

1. Copy public explicit-map inputs at the `DefaultSkillReloader` boundary and capture the existing preparation view exactly once. Preserve source labels and original skill bytes.
2. Compose the current execution document and every current supplied skill document. Discover all selected markers and validate their shape/name before consulting the source. All three sections participate, including skill-only names.
3. Validate authored structure and decidable constraints with the staging path. Do this against the current call's documents, independently of any earlier `validate` call.
4. Resolve distinct names into an insertion-ordered candidate-local map from the selected source. Use `environment.getProperty(name)` directly in host mode. Use only the copied map in explicit mode. Reject missing/blank required values and unused explicit entries. Return exact strings to substitution. Do not parse returned text as YAML or perform another placeholder expansion.
5. Materialize the execution tree and executor config portions of skill documents using that memoized map. Apply normal typed binding and full property validation to execution settings. Build catalog definitions with resolved config overrides and check the complete resolved dependency graph.
6. Construct runtime/provider clients only after successful resolution and full validation. Capture the resolved properties, immutable namespace data and immutable skill configs into the resulting generation. Discard temporary authored/resolution state after the call.

Avoid shared caches, global source state and namespace locks around lookup or construction. The existing manager view, runtime construction and publication lifecycle remain the concurrency primitives.

### Staged unknowns and decidable validation

Replace the fixed textual sentinel with explicit internal knowledge of unresolved marker nodes. A marker always produces a nonblank string. Structural positions requiring a map/list remain invalid when occupied by a marker, because resolution cannot produce that required type. The namespace-name entries themselves sit outside the selected boundaries and remain immediately checkable.

Expose only the small internal node inspection/projection operations needed from `AuthoredYamlVariables.Document`. Retain unresolved key/value identity and source paths through staging. Do not manufacture plausible provider settings or substitute arbitrary strings to make an otherwise invalid provider object pass validation.

The staging parser checks root/section allowlists, literal field names, known nested shapes and literal scalar conversion. For connections with markers, validate each known leaf constraint and each cross-field rule whose inputs are known. If needed, factor connection validation into reusable per-field and cross-field operations so resolved and staged paths share the existing constraint definitions. Unknown keys defer their own allowlist and collision checks until resolution. A dynamic sibling key can satisfy or change a required field, so absence/applicability checks must account for that uncertainty. A marker in a value does not hide an invalid literal sibling field or literal header key.

Examples of checks that still run during staging include an invalid literal duration or retry bound alongside a marked API key, an invalid literal driver, malformed literal headers, known incompatible option blocks, known missing required settings, foreign executor namespaces, malformed declarations and unknown executor identities. A marked driver defers driver-dependent authentication/applicability checks. A marked retry operand defers only comparisons requiring that operand. Full resolved validation runs through the ordinary validator in every case.

Executor annotation selection follows the same knowledge rule. Check a wholly literal path normally. If an unresolved key can determine a missing segment, defer that selection. A known scalar/list at a required map position fails immediately, since markers produce strings. Keep reference identity, namespace visibility, declaration, contract and output graph checks active even when a configuration selector is deferred. Add a small explicit staged mode/knowledge input to the internal dependency checker, with full checking as the ordinary startup/admission/preparation behavior. Do not globally skip dependency validation for candidates containing any marker.

### Skill declaration fidelity

Keep the original BOM-aware bytes and `SkillDocumentValues` lossless declaration decoding. Add an internal catalog/decode route that accepts a resolved config override, keyed to the current supplied document/source identity. Validate declaration form and root shape from the original declaration, then install the selected resolved ordinary YAML config at the existing config boundary.

A staging route can omit unresolved config data from Jackson conversion while retaining its authored structure and marker knowledge for map/key checks. The resolved route must validate textual config keys and immutable container copying after substitution. Literal schema decimals, input/output contracts, transforms, source labels and authored YAML diagnostics follow their existing decode path. Never serialize a resolved whole skill back to YAML merely to call the catalog again.

### Binding exact strings

Keep candidate binding detached from the host Environment after the initial lookup. Supply no placeholder resolver to the candidate `Binder`. Preserve exact header names through the existing separate header assignment. A copied explicit value such as `${region}`, a multiline JSON string or YAML-looking `a: b` reaches the typed provider/string or executor consumer intact. Host mode may return `west` from `Environment.getProperty("report.label")` when the host property is `${region}`, and that returned value is also terminal. Preserve ordinary Spring conversion for durations, booleans, numeric retry values and enums.
