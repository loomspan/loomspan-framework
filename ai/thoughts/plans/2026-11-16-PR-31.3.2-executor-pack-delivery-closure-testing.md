## Impacted Areas and Risks

- Extensions consumer harness currently assumes sequential observation/trace lookup.
  Concurrent tests must correlate each session, authenticate each worker and collect
  failures without cross-wiring settings or selecting another invocation's trace.
- Actual pack transport must stay installed and real. A fake executor, synthetic
  HTTP decoding test or remote server continuing after client return does not prove
  actual invocation/resource lifetime.
- Timing-only tests are weak. Use request/delegate/physical-return latches, bounded
  polling of concrete state and broad timing bounds only where deadline behavior is
  the behavior under test. Always release latches and settle workers in finally.
- Framework-native model attempt quota/usage differs from pack sends/provider usage;
  avoid conflating HTTP count, diagnostic data, native totals and unavailable usage.
- Trace import must use actual unmodified current-marker pack traces, authenticated
  browser controls and existing MCP tools. Do not adjust marker to `development` or
  replace actual transport/Console with internal fixture helpers.
- Diagnostic-only faults are contained; business serialization, caller evaluation
  and existing automatic observation retain existing semantics.

Compatibility classification follows the implementation plan: existing Application
API/configuration protected; no supported SPI/new API; current-run ephemeral trace
coherence and narrow same-version portable import; internal helpers not protected.
Existing native removals remain intentional, with no alias, shim, historical reader
or version increment. Canonical data remains unchanged; existing journal projection
exception stays confined to its current path.

## How to Run

Use commands listed verbatim in the implementation plan: Framework full tests,
install and Console corpus; Console Go tests and canonical verify/build; Extensions
validate, pack verify/install, standalone consumer verify; recipe execution.

New required actual Console command from Extensions root:

```powershell
mvn -B -f extensions/decisions/examples/support-triage/pom.xml -Pconsole "-Dloomspan.console.executable=C:/opendev/code/loomspan-framework/loomspan-console/build/loomspan-console.exe" verify
```

The explicit profile requires a real executable and must fail rather than skip if
missing. Default verify runs all Console-free consumer tests. Build Console with
`go run ./internal/buildtool build`, which injects the current POM version and checks
assets/toolchains. Exact pinned Go/Node/npm patches come from Console's own README;
the earlier ticket's known temporary Node directory may be used only after checking
actual versions. Do not work around exact-version validation.

Run a newly added class with `-Dtest=ClassName` during iteration, then the complete
suite once coherent. Run `LoomspanPublicSurfaceArchitectureTest` after changing any
production types. Reuse previous full checks only with unchanged exact source/build
identity and named prior command/result; post-removal consumer/new advanced cases
must execute here. For source changes, rerun affected checks. Final fresh reviewer
executes sufficient current verification independently, including the actual
Console harness and consumer qualification; its clean report establishes completion.
