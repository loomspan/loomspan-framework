# PR 28.4 Shared Declarative Authorization Testing Plan

## Change Summary

The implementation plan at `ai/thoughts/plans/2026-11-01-PR-28.4-shared-declarative-authorization.md` selects SkillRoleEvaluator as the single snapshot-aware composition/evaluation owner. Prepared-root validation, visibility and runtime dispatch must use its conjunction of YAML policy and captured executor policy; SkillMethod retains its Java constituent. Source/target callable authority, trusted caller selection and actual Spring proxy advice remain independent necessary boundaries.

This is pipeline Step 3, profile `full`, continuing directly from Step 2 in the same context. This artifact specifies tests; it contains no assertion that they have already run.

## Impacted Areas

- `internal/security/SkillRoleEvaluator.java`, `DefaultAccessGuard.java`: composition and explicit/session caller semantics.
- `internal/skillapi/DefaultSkillTemplate.java`: validate, invoke, and handoff pre-session checks with explicit PreparedInput snapshot.
- `internal/skill/DefaultSkillVisibilityResolver.java`, `internal/core/CapabilityExecutionRouter.java`, `ExecutionCoordinator.java`: existing consumers that must agree and still recheck actual dispatch.
- `internal/skill/SkillAdmissionSnapshot.java`, SkillGeneration, registration/admission fixtures: authoritative executor binding and retained ownership; no new production lifecycle facility is selected.
- JavaSkillInvoker, shared discovery, ScopedAuthentication and MissionWorkExecutor: unchanged invocation owners exercised by real proxy/framework tests.
- Authoring/API/README guidance enumerated in the implementation plan; public signatures/record shape and management catalog behavior remain protected.

All source paths above are under `src/main/java/ai/loomspan/`; test paths below are repository-relative.

## Risk Assessment

The highest risk is mistakenly OR-ing role lists or applying different callers to the two policies. Other risks are treating a missing binding as unrestricted, using a live registration rather than the admitted one, checking only at planner publication, conflating namespace retention with callable authority, eagerly checking child RBAC at entry, invoking advice during metadata checks, losing method advice on dispatch, and leaking caller context onto reused workers after failures.

Protected paths are the public facade/handoff behavior, five-component invocation record, documented roles/prefix/hierarchy and namespace rules, fixed Java registration lifecycle, failure/observer behavior, and metadata-only entry/discovery. There is no supported SPI or historical serialized policy contract. The obsolete internal scalar throwing method and direct scalar root/runtime selection should disappear atomically; do not test for simultaneous old and new behavior. Preserve current-run diagnostic fidelity and the unchanged ExecutionJournalProjector exception. No trace protocol/version migration, historical-reader test or Go test is required by this diff.

## Bug Reproduction / Failing Test First

**Name:** `executorJavaPolicyCannotBeBypassedByPermissiveYaml`.

- **Type/location:** unit, `src/test/java/ai/loomspan/internal/security/DefaultAccessGuardTest.java`.
- **Arrange:** an EXECUTOR YAML definition/capability with unrestricted YAML roles; a captured `SkillExecutorRegistration` requiring JAVA_WRITE; real matching owner generation and admitted ExecutorBinding in SkillAdmissionSnapshot; an ExecutionBinding.sessionOnly for that exact entry; caller has only ROLE_YAML_READ. The registration invoker is a counter that must remain zero.
- **Act:** call the existing `canAccess` and `checkAccess` guard APIs inside the captured binding with that caller.
- **Assert:** false and AccessDeniedException mentioning the callable skill; no business invocation. Optionally assert a caller with ROLE_JAVA_WRITE passes as the paired control.
- **Expected baseline failure:** DefaultAccessGuard currently evaluates only the capability's unrestricted YAML policy, so canAccess returns true and checkAccess does not throw. This test uses existing APIs and fails behaviorally before the new evaluator API exists.
- Run the isolated red test first and record its exact failure. Then implement Phase 1 and rerun it green. Do not weaken the expected denial to accommodate baseline behavior.

## Tests to Add/Update

### 1) `evaluatesCapturedConstituentsConjunctively`

- **Type/location:** parameterized unit, new `src/test/java/ai/loomspan/internal/security/SkillRoleEvaluatorTest.java`.
- **What it proves:** snapshot-aware boolean and throwing methods agree; only an executor definition gets a second constituent; the required admitted registration supplies that policy. Pure YAML, TypeSafe and Java SkillMethod keep their existing single-constituent behavior. There is no new default-deny regression for unprotected non-executors.
- **Fixtures/data:** real minimal immutable generations, definitions, capabilities and executor bindings; authenticated tokens with exact authorities and null authentication. Use cases below for default ROLE_ prefix; parameterize custom APP_ and empty prefixes and a hierarchy for representative conjunction cases.
- **Mocks:** none; use real SkillRoleEvaluator/AuthoritiesAuthorizationManager. Business invokers fail immediately if called.
- **Affected surface:** configuration/manifest behavior and internal implementation.
- **Compatibility expectation:** intended executor behavioral tightening; preserve other kinds and constituent semantics.

| YAML constituent | Java executor constituent | Caller authorities | Result |
| --- | --- | --- | --- |
| SALES or SUPPORT | DATABASE_WRITE or DATABASE_ADMIN | SALES + DATABASE_WRITE | allow |
| SALES or SUPPORT | DATABASE_WRITE or DATABASE_ADMIN | SUPPORT + DATABASE_ADMIN | allow |
| SALES or SUPPORT | DATABASE_WRITE or DATABASE_ADMIN | SALES only | deny |
| SALES or SUPPORT | DATABASE_WRITE or DATABASE_ADMIN | DATABASE_WRITE only | deny |
| SALES | SALES | SALES | allow |
| unrestricted | DATABASE_WRITE | unrelated or null | deny |
| SALES | PermitAll or unannotated/unrestricted | unrelated or null | deny |
| unrestricted | PermitAll or unannotated/unrestricted | null | allow declaratively |
| SALES or unrestricted | DenyAll | all listed roles | deny |
| unrestricted | explicitly empty Java RolesAllowed | authenticated caller | deny |
| empty/omitted YAML roles | DATABASE_WRITE | DATABASE_WRITE | allow |
| ROLE_SALES | unrestricted | ROLE_SALES with default prefix | deny |
| ROLE_SALES | unrestricted | ROLE_ROLE_SALES with default prefix | allow |

Prefix/hierarchy cases must satisfy **both** constituents through the configured evaluator: e.g. APP_ADMIN implies APP_SALES and APP_DATABASE_WRITE. Missing/null callers still cannot satisfy restrictive roles. Use a nonempty restrictive YAML policy with Java PermitAll as a direct guard against override semantics. No synthetic YAML DenyAll syntax is introduced.
