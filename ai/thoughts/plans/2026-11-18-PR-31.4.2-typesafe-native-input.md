# PR 31.4.2 native TypeSafe input implementation plan

## Overview

Make the Decisions executor consume the complete native request from
`SkillExecutorInvocation.input()`. Framework already owns ordinary input validation
and the optional executor-only JSLT transform. Decisions continues to own provider
validation, JSON serialization, transport, retries and the complete provider result.

Selected profile is `full`, approved by the developer after Step 0. The ticket's
implementation model is GPT-6.2 Sol. Steps 2 and 3 were prepared with GPT-6.1 Sol.

## Desired end state

A business-input triage leaf transforms `{ticket: ...}` into a request containing
`model`, `state` and `questions`. A direct native-input leaf omits the transform
and sends an equivalent request through the same Decisions code. Both use the
captured `typesafe` executor map for connection settings and return complete
provider JSON. Any nonempty TypeSafe leaf `config`, including the retired keys,
fails explicitly before HTTP. Framework's general executor `config` remains
available to other executors.

## Scope boundaries

Implementation belongs in the sibling Extensions repository. Framework changes
are current authoring guidance and pipeline artifacts. The existing supported v1
handoff, general config capability and generic JSLT implementation are sufficient.
Sidecar-suite qualification and live provider evaluation are separate future work
under the owning roadmap. Deterministic acceptance uses local HTTP stubs and test
credentials. Console protocol/version changes and new Java extension surfaces have
no role in this change.

## Contract and compatibility impact

| Surface | Impact and evidence | Treatment |
| --- | --- | --- |
| Application API | Supported Framework v1 invocation already exposes input and both config maps. Public facade and publication consumers exist in the example. | Use the exact existing API signatures. Public-surface delta is zero. |
| Supported SPI | Framework AGENTS.md establishes a closed API and no supported SPI or bean replacement contract. | Use ordinary installed-pack registration and existing test probes. |
| Configuration and manifest contracts | TypeSafe `config.request`, `config.bindings`, leaf `api_key` and leaf `base_url` are current documented behavior. Ticket and Pipeline notes authorize their retirement. | Atomic intentional break. Empty/omitted leaf config succeeds. Every leaf config key fails with its path. Executor config admits only `api_key` and `base_url`. |
| Persisted or serialized contracts | Native HTTP `model`/`state`/`questions` and complete result JSON remain the provider protocol. | Preserve provider validation, JSON fidelity and transport defaults. Change request provenance to invocation input. |
| Ephemeral diagnostic formats | Existing pack request/response/failure/retry diagnostics continue through v1. | Preserve exact business content, capture states, ordering and lifecycle containment. Existing size controls remain. |
| Internal or accidentally exposed implementation | Request template mapping and leaf-over-executor selector are internal implementation. | Delete obsolete pointer/lookup/bind code and unused selection helpers, updating callers and tests atomically. |

**Shim decision.** No shim. The ticket explicitly authorizes outright removal,
and all verified in-repository consumers migrate together. The intended break is
limited to TypeSafe leaf configuration. Provider-native input fields and captured
executor settings retain validation. Java-to-Go boundary coordination is
unnecessary because this changes no consumed trace/REST/SSE contract or marker.
Pipeline notes and this treatment are aligned.

## Material implementation decisions

1. Decisions validates empty TypeSafe leaf config and the allowed executor config
   fields before sending. Reject all leaf keys with actionable `skillConfig.<key>`
   errors. Recognize neither a request template nor a connection override there.
2. Copy and validate `input` as the sole native request, with errors rooted at
   `input`. Keep current JSON copy checks, finite-number precision, null fidelity,
   local Resource materialization and the 32 MiB body limit. Removing the mapping
   does not require removing supported native-value conversion.
3. `TypeSafeSettings.capture` takes only the captured executor map. Keep exact
   credential values, the required API key, default base URL, URL validation,
   prefix preservation and `/v1/systemone` appending. Capture once per send and
   reuse settings and serialized bytes across retries.
4. Migrate request fixtures to explicit native input or authored Framework
   transforms. Consumer helpers may expose clearly named native and transformed
   leaf constructors. They must emit actual new YAML and must not reconstruct the
   retired config contract in helper code. Update invocation arguments as needed.
5. Preserve direct native Resource coverage by supplying supported Resources in
   native input. Framework JSLT accepts JSON only, so transformed Resource input
   continues to follow Framework's existing rejection boundary.
6. Remove the leaf-owned branch of publication qualification. Retain the existing
   real concurrent old/new namespace settings test, retry bytes, endpoint/key
   assertions, shared transport and generation retention checks.

These choices reuse existing validators, copying, transport and test harnesses.
Deleting the mapping machinery removes a duplicate request-construction authority.
The two authored input routes converge at the same native request validator.

### Step 4 implementation handoff

Request preparation now rejects leaf keys and unknown executor settings, then
copies, validates and serializes the native input. Captured settings are used once
per transport send. The pack's executor registration and supported v1 handoff
keep their signatures. No Framework production types, Spring extension points
or Java-to-Go contracts changed. The old request mapping and setting-selection
machinery are deleted.

The recipe and installed consumer fixtures use the supported JSLT declaration
`language: jslt`. Fixtures that receive tool arguments from a mocked planner use
constant JSLT requests so they still exercise actual pack execution following
the original planner and quota paths. Direct-input cases pass the complete
native object through the supported facade. The opt-in Console fixture only
changes its request declarations.

The documentation and executable behavior are **aligned**. The pack reference
describes the current reproducible installed-JAR commands and treats Console
as an opt-in check. Exact prior Console evidence stays with the historical
delivery record and its versioned Extensions reference. The generic Framework
executor configuration, transform and child-binding topics retain their roles.

The companion testing plan records exact command results and artifact identities.
The worktrees contain only ticket-owned changes against Framework `c0128ac`
and Extensions `77e7e29`. Step 5 review and local commits remain outstanding.

## Performance and migration notes

Request copying and serialization remain once per invocation and retries reuse
the same bytes. Parent input assembly still precedes the optional Framework
transform. Existing connection pools, deadlines and retry policy remain intact.
The in-repository migration is atomic and introduces no transition format.
