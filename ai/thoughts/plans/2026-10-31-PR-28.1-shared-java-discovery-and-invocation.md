# PR 28.1 Shared Java Discovery and Invocation Implementation Plan

## Overview

Implement one discovery and Spring-proxy invocation foundation for directly callable `@SkillMethod` and reference-only `@SkillExecutor`. Add the three deliberately supported API types, share invocation-container copying, and replace Java exception-to-successful-text conversion with failure propagation. This is the Java foundation of the accepted configured-executor feature, not its complete runtime.

This is Steps 2–3 of the Full 5-Step Pipeline, approved by the developer's “proceed”. The checkout was clean before the Step 1 research artifact. The only existing run artifact is `ai/thoughts/research/2026-10-31-PR-28.1-shared-java-discovery-and-invocation.md`; no unrelated developer edits were found. Implementation belongs to the later fresh Step 4 context. No tests were run while producing this plan.

## Current State Analysis

- `SkillMethodBeanPostProcessor.java:43–202` owns one bean-discovery lifecycle, canonicalization, callable registration, schema/binding and invocation. `completeDiscovery()` scans lazy bean definitions and verifies the final proxy.
- `SkillMethodBeanPostProcessor.java:252–332` maps interface contracts through bridges. Its early return for a directly annotated implementation can bypass incompatible-interface checks; all matching contracts must be checked before a contract is selected.
- `SkillMethodBeanPostProcessor.java:483–565` selects the current Spring bean and invokes its proxy. It serializes all results and turns most runtime exceptions into text. Its cause-chain security bypass exists to avoid that transformation.
- `RestSkillInvocation.java:29–54` already has the required recursive map/list copy semantics. Other leaves remain the same objects; the copy does not read or freeze a `Resource`'s bytes.
- `Jsr250EnforcementVerifier.java:22` verifies actual applicable Spring advice. `SkillAccessPolicyResolver` already owns supported policy discovery. Both should be reused without a second authorization implementation.
- `SkillGenerationManager.java:443` freezes fixed callable registrations from this discovery owner. Generation storage, executor-only namespace activation and binding are explicitly PR 28.3 responsibilities; creating a second runtime registry here would contradict that ticket.
- `LoomspanAutoConfiguration.java:83–101` wires the obsolete transformer into the processor. The exact API and technically public internal allowlists are in `LoomspanPublicSurfaceArchitectureTest`; current API inventory contains 24 types.

## Desired End State

One completed discovery pass produces separate immutable callable and executor registration lists. Both roles use the same canonicalization, identity rules, interface compatibility, final-proxy checks, supported policy resolver/verifier, runtime method selection, invocation and result conversion. Executors have no `CapabilityMetadata`, tool descriptor, reflected invocation-record schema, public lookup, or `SkillTemplate` invocation route.

`SkillExecutorInvocation` is a five-component public record. All three maps are required and recursively copied into unmodifiable map/list containers; both metadata strings are required and nonblank. Preserve valid strings exactly. Do not parse the skill identity or generation ID in the value record: runtime identity selection remains at its existing owners. `RecoverableSkillException` validates a non-null, nonblank message and preserves its exact text and optional cause.

Successful null/void results become `""`; strings, including whitespace, are returned exactly; every other non-null result uses the application Jackson mapper. Application and serialization failures remain failures. A single internal policy recognizes only `RecoverableSkillException` after transparent reflection/proxy wrapper removal, stopping at any ordinary application exception.

### Key discoveries

The necessary abstraction is small: share the existing mechanics and split only declaration validation, schema ownership, argument construction and registration destination. No application resource lifecycle is needed. Spring core's `ReflectionUtils.invokeMethod` unwraps `InvocationTargetException`, preserves runtime exceptions/Errors, and can use `UndeclaredThrowableException` for checked throws; focused tests through actual proxies must establish those paths for the implementation.

## Implementation Approach

Retain `SkillMethodBeanPostProcessor` as the single existing discovery owner; its internal name creates no supported compatibility promise and does not justify a second scanner. Add one small internal executor registration value and one shared Java proxy invoker. Keep callable schema generation and typed/ref argument binding in the current owner or a focused helper if extraction reduces complexity; they remain callable-only. Do not introduce an interchangeable strategy/plugin hierarchy for two known roles.

Suggested implementation names are `JavaSkillInvoker`, `SkillExecutorRegistration`, `SkillFailurePolicy`, and `ImmutableContainers`. These are internal decomposition choices, not new extension contracts; implementation may choose equivalent names while preserving the ownership below. Prefer package-private helpers. A helper or registration used across API/internal packages may be technically public and must have a specific architecture-allowlist reason.

The executor registration contains only identity, exact config reference, supported policy, declaration source/location and a typed invoker accepting `SkillExecutorInvocation`. A JDK `Function<SkillExecutorInvocation,String>` or a single internal typed method suffices; do not reuse callable map input to encode the invocation record. Its invoker supplies one argument to the same shared Java invoker as callable methods. This is fixed registration data from the existing discovery lifecycle, not an independently mutable registry. It is the handoff consumed by PR 28.3.

### Role differences and justification

| Difference | Reason |
| --- | --- |
| Executor requires exactly one canonical `SkillExecutorInvocation` parameter; callable validates existing typed/`SkillParam` contracts. | Distinct settled invocation signatures. |
| Callable owns generated input schema, description and input contract; executor stores its exact config reference and no tool schema/description. | Referencing YAML owns executor-backed callability; config metadata is part of executor declaration validation/binding handoff. |
| Callable binds typed/reference arguments and closes opened streams; executor passes the defensively copied invocation record without coercing its leaves. | Required argument construction and resource semantics; same shared proxy call follows. |
| Registration enters callable metadata or the separate executor index. | Duplicate identities within a role fail while same identity across roles is valid. |

No further execution/security/result/lifecycle difference is selected. Annotation path syntax and subtree binding remain at PR 28.3's shared resolution owner; preserving a string here does not introduce a competing path validator.

### Alternatives considered

Leaving current discovery and copying unchanged cannot support executor declarations or shared semantics. A separate executor postprocessor would duplicate bridge/proxy/security rules and violate the ticket. A generic registry/strategy framework adds extension concepts without a demonstrated third role. Refactoring the entire generation system now would pull in PRs 28.2–28.4 and obscure this foundation's verification. Sharing the existing discovery owner plus a typed registration and invoker is the smallest complete design for this ticket and directly supports the accepted final architecture.
