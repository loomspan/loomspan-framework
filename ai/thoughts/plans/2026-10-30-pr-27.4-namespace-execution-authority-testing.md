# PR 27.4 Namespace Execution Authority Testing Plan

## Change summary and governing scope

Test retained cross-namespace dispatch with source-aware authorization and current/entry settings selection. Model selections pass through the common parser before exact bound lookup. Public REST values keep their shape and identify the captured executing target. This is pipeline Steps 2+3 under developer-approved **full** profile; source edits belong to Step 4.

Governing implementation plan: `ai/thoughts/plans/2026-10-30-pr-27.4-namespace-execution-authority.md`. Ticket/design requirements are normative. PR 27.5 observation wire/Console changes are excluded. No build or test was run during planning; expected pre-fix failures below come from source investigation.

## Impacted areas and risks

- Binding/snapshot, existing guard/role evaluator, discovery, router/coordinator and captured parent restoration: avoid a confused-deputy callback, retained-membership authority or foreign-generation metadata substitution.
- Managed Java/REST/mission/parallel workers: preserve caller SecurityContext isolation, session, ancestry, branch ownership, lifecycle and physical resource retention.
- Usage service/session setup/current runtime: every usage category obeys entry quotas; child provider/timeouts/attachments use target captured settings; trace policy/snapshot remain entry-scoped.
- Planning, steps and Spring AI single tool loop: namespace-only normalization must occur before exact bound matching without changing raw evidence, local case, callback surface, provider names or retry counts.
- REST closure/public docs: distinguish same local names and old target generation ID from entry ID after replacement/removal.

Protected surfaces are the supported API/SPI shape, configuration/manifest behavior and existing lifecycle/security invariants. Internal single-generation/local-name assumptions are intentionally replaced with coherent canonical runtime behavior, without dual-format tests or shims. Existing journal redaction exception is preserved unchanged; no new content classification or masking is tested or introduced.

### 5. Entry quota and shared counter categories

### 7. Timeout, depth and attachment split

- **Location/type:** namespace integration, existing timeout tests and `DefaultMissionInputMaterializerTest`.
- **Timeout:** a parent mission remains active while a child starts with its own timeout. Use bounded latch-coordinated work so the parent expires first despite a later child having more time; separately prove short child timeout fires under long parent. Delay a handoff beyond the configured mission duration before invoking and prove queue time did not expire it. Timeout response retains resources until physical work returns.
- **Depth:** choose smaller entry depth than child, cross namespace and exceed it without resetting ancestry; direct entry into child uses its own configured depth.
- **Attachment:** same resource/input passes existing parent materialization, then fails existing child materialization with a smaller captured limit. A larger child limit is not reduced to entry's limit; no session attachment budget.
- **Mocks:** in-memory resources; controlled external work. Use short budgets with generous outer wait bounds rather than exact wall-clock equality.
- **Surface:** execution configuration and internal lifecycle; preserve existing cancellation model.
