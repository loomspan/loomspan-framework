# TypeSafe executor and packaged consumer implementation plan

## Overview

Implement the callable TypeSafe integration in the independently versioned
`loomspan-decisions` pack and prove it through a separate application consuming
the packaged artifact. Run as Steps 2 and 3 of the approved Full 5-Step Pipeline.
The developer approved this profile with “proceed”. Both repositories were clean
at triage; the research artifact is pipeline-owned. This plan makes no production
changes. All pack code, tests, examples and product documentation belong in
`../loomspan-extensions`; Framework owns the ticket and pipeline artifacts.

## Desired end state

Installing `ai.loomspan:loomspan-decisions:0.1.0-SNAPSHOT` registers the
reference-only executor `default-typesafe`. An application explicitly publishes
ordinary executor YAML leaves and invokes them with supported APIs. A separate
support-triage Maven application runs local deterministic tests using the built
pack JAR and normal Boot discovery. All six ticket acceptance groups map to
executable checks in the accompanying testing plan. Documentation and ticket
handoff record the exact contract, tested versions, commands and evidence paths.

## Selected pack contract

### Registration and configuration

Add an implementation-detail bean with
`@SkillExecutor(name = "typesafe", config = "typesafe")` in the default namespace.
Keep it under `ai.loomspan.decisions.internal.typesafe`; annotation discovery does
not establish a Java SPI or bean-replacement contract. Auto-configuration owns its
construction and the existing singleton transport. Installation creates no
callable skills. Namespace configuration must contain the selected map, even when
empty: `loomspan.executor-config.default.typesafe: {}`. Selection is still subject
to ordinary Framework configuration/namespace rules.

Skill config accepts `request`, optional `bindings`, and the existing optional
`api_key` / `base_url` overrides. Namespace executor config supplies only the
existing transport settings `api_key` / `base_url`. Do not invent precedence for
model or request data: both belong to skill `config.request`.

```yaml
name: triage
description: Assess a support request
executor: typesafe
input_schema:
  type: object
  properties:
    ticket: {type: object}
  required: [ticket]
config:
  request:
    model: jev-latest
    state: null
    questions:
      repeat:
        type: noul
        instructions: Is this a repeat contact?
  bindings:
    /state: /ticket
```

### Binding and construction

`request` is a native request object, with explicit `model`, `state`, and
`questions`. `bindings` is an object mapping request-target JSON Pointers to
input-source JSON Pointers. It uses RFC 6901 escaping (`~0`, `~1`), with no embedded
substitution or legacy expressions. Empty source pointer selects the whole input
object; empty target pointer is rejected so the request root remains explicit.

Copy the request to detached JSON-compatible containers, resolve each input
pointer once, apply bindings, validate the resulting native request, serialize
once, then call the existing transport. A present JSON null is a value and is
preserved. A missing source removes its target object property; required native
fields then fail normal resolved-request validation. Targets require existing
parents; an object leaf may be replaced/added, and an existing array element may
be replaced. Missing-source omission targeting an array fails clearly rather
than shifting ordered criteria. Reject overlapping ancestor/descendant target
pointers so application map iteration order cannot change binding meaning.
Malformed pointer, missing parent, scalar traversal and out-of-range index errors
name the `skillConfig.bindings` entry. Do not mutate captured maps or input.

Preserve literal strings, maps, lists, booleans, nulls and received numeric values
without extra rounding/string conversion. Reject non-finite numbers, cycles and
unsupported Java values with a request/config path before send. Supported local
Spring byte-array, classpath and filesystem/path Resources may be materialized
once as UTF-8 text during construction, then validated in the native location;
do not reread on retries. Explicitly document these concrete supported types and
reject other Resource types before opening them. URL strings remain strings;
do not fetch remote content. JSON state also accepts native objects/arrays from
config/input; Resource content is text, not implicitly parsed JSON.

Validate pack config and resolved requests every invocation, outside transport
retry logic. Require nonblank textual model; supported native text/JSON state;
nonempty question map; object questions with exact supported type
`choice`/`noul`/`score`; documented native instructions/criterion forms; option-keyed
Choice criteria; ordered Score levels; optional Noul true/false criteria and its
required descriptive content. Apply the established provider fixture/documented
limits where relevant rather than introducing answer semantics. Reject unsupported
question/request capability fields (including Box/images) before transmission;
do not scan arbitrary authored state/instructions JSON field names and classify
their content. Unknown domain fields should report their configuration paths,
not be silently discarded. No startup/publication claim of domain validity.
Use ordinary IllegalArgumentException/IllegalStateException with descriptive paths,
not a new exception API or RecoverableSkillException feedback policy.

### Results and transport

Return a String containing JSON serialized from the complete decoded transport
Object. This uses existing String passthrough, preserving valid JSON null,
strings, arrays, scalars, complete envelopes, unknown fields, refusals and usage
without a second decode, wrapper or answer extraction. Business serialization
may fail execution. No provider answer/completeness/confidence schema enforcement.

Reuse captured settings, existing presence-based precedence, provider default,
prefix append behavior, disabled redirects/Apache retries, three-attempt policy,
live lifecycle accessors and normal diagnostics unchanged. The selected settings
are captured by transport once before its sends; request binding/materialization
does not repeat. Ensure local request failure sends zero requests. Do not add
duplicate executor start/stop/input/output or escaping-error diagnostics.

## Contract and compatibility impact

| Surface | Impact and evidence | Treatment |
| --- | --- | --- |
| Application API | Uses existing allowlisted SkillExecutor, v1 invocation, SkillTemplate and SkillReloader; no signature change | Preserve closed surface; consumer imports only supported types |
| Supported SPI | Loomspan has none; pack bean construction is integration machinery | Add no replacement/validation SPI or conditional missing-bean extension point |
| Configuration and manifest contracts | New pack-specific config inside existing executor/config YAML | Document selected names, pointers, null/omission and runtime validation; preserve generic Framework grammar |
| Persisted or serialized contracts | Native request construction uses existing TypeSafe protocol evidence | Keep native fields, values and ordering; no translation/legacy mode |
| Ephemeral diagnostic formats | Uses existing transport diagnostics and canonical recording | No new vocabulary, sequence, frame, retrieval or marker; preserve source content within existing bounds |
| Internal or accidentally exposed implementation | New pack request builder/executor; existing auto-config imports test grows | Treat as internal regardless of Java public modifiers; update exact test imports for annotation use |

No compatibility shim. No replaced native behavior is removed in this ticket.
The only public Java additions needed for wiring live under pack internal or
auto-config packages and are documented as construction machinery, not supported
consumer types. Do not add an application-facing pack Java API. Update existing
source import checks to permit the supported annotation without permitting broad
internal/autoconfigure imports. Java-to-Go coordination is not required because
the existing diagnostic envelope and vocabulary are reused unchanged.
`consoleCompatibilityVersion` remains unchanged. Pipeline notes are aligned.

## Testing strategy and performance

Request tests cover deterministic local validation and native construction. The
separate consumer covers real Boot discovery, public invocation/composition,
complete output and HTTP behavior through the packaged artifact. See the dedicated
testing plan for individual cases and acceptance mapping. Existing transport tests
remain the transport isolation/lifecycle proof, without repeating advanced
consumer qualification. One request construction/serialization and one response
serialization per invocation avoid repeated binding/materialization on retries.
Reuse the existing pool, watchdog, retry bounds and diagnostic capture controls.
