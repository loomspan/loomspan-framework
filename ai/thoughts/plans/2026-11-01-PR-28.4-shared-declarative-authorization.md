# PR 28.4 Shared Declarative Authorization Implementation Plan

## Overview

Make root validation, planner visibility, and dispatch evaluate the same captured declarative policies against the same trusted caller. An executor YAML leaf must satisfy its YAML policy **and** its captured Java executor policy. Keep role alternatives inside each constituent and preserve actual Spring advice at invocation. This is Steps 2–3 of the approved Full 5-Step Pipeline (`full`); this artifact authorizes no source changes in the planning stage.

## Current State Analysis

- `src/main/java/ai/loomspan/internal/skillapi/DefaultSkillTemplate.java:281` authorizes prepared roots directly against capability policy. Preparation already contains the admitted snapshot, and validation/handoff do not require a current execution binding.
- `src/main/java/ai/loomspan/internal/security/DefaultAccessGuard.java:36` combines captured source/target authority with scalar policy evaluation. Its `hasCallAuthority` at line 54 protects exact retained metadata ownership, entry identity, directly declared children, and captured namespace visibility. These checks must survive consolidation.

## Desired End State

One snapshot-aware implementation composes and evaluates declarative authorization:

| Callable declaration | Constituents |
| --- | --- |
| Annotation-only SkillMethod | Captured capability's Java policy |
| Model/TypeSafe YAML | Captured capability's YAML policy |
| Executor YAML leaf | Captured capability's YAML policy AND `snapshot.executorBinding(skillName).registration().accessPolicy()` |

Every constituent sees the same Authentication reference. Unrestricted/PermitAll cannot override a restrictive constituent; DenyAll and explicitly empty Java roles deny; role alternatives remain alternatives. Root validate/invoke/handoff pre-checks throw through existing boundaries, visibility omits denied candidates, and root/child dispatch checks again. Validation and discovery execute no application method, argument-dependent advice, provider, or resource-validation callback. Actual proxy advice can still deny declaratively visible work when invoked with real arguments.

Verification is the executable matrix and framework-boundary tests in the companion testing plan, followed by the architecture test and complete Maven suite.

## Implementation Approach

Extend **SkillRoleEvaluator**, the existing shared owner, rather than add another service. Add snapshot-aware `canAccess(CapabilityMetadata, SkillAdmissionSnapshot, Authentication)` and `checkAccess(CapabilityMetadata, SkillAdmissionSnapshot, Authentication)` entry points (nullable caller). Resolve the YAML definition in the capability's captured generation; only `Form.EXECUTOR` introduces a second constituent. Use the required admitted binding accessor for that form, then evaluate each constituent using the existing scalar predicate and the same caller. Missing executor binding is an explicit invariant failure, never permission to fall back to YAML-only evaluation. Do not infer executor form solely from JAVA kind or a nullable map lookup.

Keep scalar `canAccess(SkillAccessPolicy, Authentication)` as the constituent implementation and its direct Spring parity test seam; it is not an alternative runtime composition path. Replace the obsolete scalar throwing method with the snapshot-aware throwing method, retaining `Access denied for capability '<name>'` behavior. Root template calls supply PreparedInput.snapshot explicitly; runtime guard calls supply the current binding snapshot after existing callable-authority checks and resolve explicit/session authentication once for both constituents.

This reuses immutable admission facts without new state or cache. A separate composition service would duplicate the existing evaluation owner; embedding composition into AccessGuard alone would force pre-session roots to synthesize runtime bindings. Flattening roles is incorrect, and making no framework change leaves metadata admission/discovery inconsistent with execution. Retain separate callable-authority checks because generation membership alone cannot express who may call a capability.
