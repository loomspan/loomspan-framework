# Completed Trace File Publication Implementation Plan

## Overview

Publish `<sessionId>.<traceId>.execution-trace.ndjson` only after the complete canonical trace has been written and closed. Use a sibling `.in-progress` file while running, and preserve entry-namespace ownership, persistence decisions, grace deadlines, live reads, journal projection and authenticated artifact delivery.

Pipeline mode: Full 5-Step Pipeline (`full`), Steps 2 and 3. Baseline: `de4605d9aff641bca59bd19924b3961a1feb0a47`. Planning checklist complete: source/lifecycle, retention races, consumers, contracts, documentation, verification design. Only the supplied ticket and research were untracked at inspection; preserve them. This artifact specifies implementation; no production or test code was changed during planning.

## Current State Analysis

- `DefaultExecutionTraceHandle.java:89` selects one path already bearing the completed suffix and initializes it immediately. Its writer, live reader, snapshot and descriptor all use that path.
- `NdjsonTraceRecordWriter.java:31` opens, writes and closes on every append. No new writer flush/close lifecycle is needed.
- `DefaultExecutionTraceHandle.java:264` appends `TRACE_COMPLETED`, marks completed, then retains/deletes or measures the file. Subsequent calls return the cached optional descriptor.
- `LoomspanSession.java:642` projects the journal before handle finalization; finalization IOException follows the existing failed-core-finalization disposition and wrapper exception at line 707.
- `ScheduledCompletionGraceRetention.java:57` combines the retention decision, captured size, registration and scheduling. It can immediately discard on zero/elapsed grace, closure or scheduler rejection. Expiry and acquisition own an exact path.
- `DefaultExecutionObservationHandle.java:141` publishes to the catalog only after successful core finalization. `ObservabilityRestController.java:256` downloads by trace ID using the descriptor path. Console's `internal/applicationclient/artifact.go:129` streams that endpoint, without reconstructing Framework filenames.

Paths in the bullets above are relative to `src/main/java/ai/loomspan/internal/` unless otherwise stated. Research contains the full paths and caller inventory.

## Desired End State

An active trace exists only as `<completed-name>.in-progress` in the same entry-namespace directory. Live reads and journal projection read it. A retained finalization closes its terminal append, then performs one same-directory atomic rename; the first open of the completed name observes the entire unchanged NDJSON file. A descriptor is constructed and made available only after rename success. An immediately discarded trace is deleted under the active name without ever creating the completed name.

### Key Discoveries

- Closed-on-return appends already provide the required stream boundary; publication should reuse this behavior.
- Retaining first on the active path and renaming afterward leaves cleanup ownership stale. Renaming first and then deciding retention exposes completed files for scheduler rejection and other immediate discards. The retention collaborator must coordinate these operations.
- Grace expiry can race the return from finalization. Capture size before publication and use the retained result; do not re-read size afterward.
- Internal constructors and retention interfaces are changeable atomically. Their Java visibility creates no supported SPI.

## Implementation Approach

Use two immutable path identities and one current physical-path state inside the existing handle. Treat the explicit path accepted by synthetic constructors as the completed destination; derive its active sibling just as production does. The writer always targets active. Reads and snapshots use the current path; only successful publication switches it to completed. Publish path state safely to unsynchronized snapshot callers (volatile current path or synchronized access).

Keep `TRACE_STARTED.metadata.tracePath` as the path actually selected when recording starts: the active filename by default. It is a historical record and is never rewritten during rename. Preserve explicit deterministic metadata overrides in fixtures. Finalized descriptors carry the completed path. Document this distinction so the start record is not mistaken for the current downloadable location.

Use `Files.move(active, completed, ATOMIC_MOVE)` within the same directory. Do not fall back to copying or non-atomic publication. Unsupported atomic rename is an IOException and follows the established finalization failure path. The generated trace UUID avoids ordinary destination reuse; do not delete or reset the completed destination during initialization. No further record/file-content writes occur after publication.

For policy-discard candidates, change the existing internal retention operation to accept active and completed paths. Immediate retention deletes active. Scheduled retention owns the short transaction that decides, reserves scheduling, publishes and transfers exact-path deletion ownership. Use one package-private publication helper if needed to share the atomic rename with permanent retention; do not add a configurable publication SPI.

### Retention ordering and failure invariants

1. After the terminal append is closed, evaluate existing `expiresAt = terminalTimestamp + grace`; zero/elapsed grace and closed retention delete active and return empty.
2. Capture active-file size before scheduling/publication. Under the retention synchronization boundary register pending ownership, then obtain the scheduled task. Rejection removes pending state and deletes active without publication.
3. Coordinate pending expiry, closure and publication under that same boundary. Recheck expiration and ownership after scheduling, including an executor that runs the task before returning. A due/pending state must discard active and never publish. Expiry must not retain an active-path deletion captured outside the critical section that can run after rename.
4. If still retained, rename atomically and transfer ownership to the completed path before expiry/acquisition can act on published state. Acquisition indexes by completed descriptor path. Keep the original deadline rather than restarting grace at rename.
5. On rename failure remove pending registration, cancel any task, keep no finalized descriptor, propagate IOException and leave the active file available for diagnostics. Ensure no scheduled stale-path cleanup remains. Successful publication can naturally expire immediately afterward; return captured size and avoid a post-return filesystem dependency.
6. Preserve existing close semantics for already published retained files: cancel ownership/tasks without deleting files. Preserve leases deferring due deletion until the last reader closes. An expiry that wins before publication deletes the active file.

This is a bounded extension of the existing retention owner, not a separate reservation service. No new lifecycle object is exposed to applications. Tests must control scheduler execution rather than rely on sleeps.

The handle marks the terminal append completed once, rejecting late appends. Successful and discarded finalization cache their optional result. If rename or subsequent file finalization fails after the terminal record has been written, memoize the IOException and rethrow on repeated finalization instead of retrying publication, duplicating the terminal record or converting the failure into success. Existing session failure wrapping and failed observation remain authoritative. Keep this failure state within the handle; avoid broad session lifecycle redesign.

Alternatives rejected: keeping current behavior fails the collector outcome; copy/delete can expose partial files; rename-before-retention violates immediate-discard semantics; retaining active then renaming without coordinated ownership races expiry; a separately exposed reservation API adds unnecessary lifecycle concepts. The existing handle, per-append closure and exact-path retention provide the necessary responsibilities. No unrelated dead abstraction was established by the bounded investigation.

## Testing Strategy

Use real temporary files for publication and failure behavior, fixed/mutable clocks and a controlled scheduler for retention, and the existing observation/catalog/HTTP harness for authenticated downstream delivery. Assert physical NDJSON bytes and logical terminal reconstruction, not merely descriptor presence. The dedicated testing plan specifies cases, inputs, commands and exit criteria. No manual observation is required for acceptance.

## Performance Considerations

Publication adds one same-directory metadata operation and no file copy. Hold the retention lock only across the bounded schedule/rename/ownership handoff; do not hold it across artifact streaming. Capture size once. Per-record write behavior remains unchanged.

## Migration Notes

No migration or shim. Existing in-development single-name assumptions are replaced atomically across source, tests/builders and guidance. Interrupted active files may remain; their existence is not a completed-artifact signal and this change adds no scavenger.
