# PR 37.4 Explicit invocation and catalog identities Implementation Plan

## Overview

Make the supported Java root boundary accept the namespace and local name as separate arguments. Give validation and catalog metadata those same components so application code can pass them to invocation without decoding a reference. A namespace catalog accepts a local name and always selects its own namespace.

The governing ticket is `ai/thoughts/tickets/loomspan-pr-37.4-invocation-and-catalog.md`. Research is `ai/thoughts/research/2026-11-23-PR-37.4-invocation-and-catalog.md`. This is full-profile pipeline planning after local commit `200c09a`. The developer authorizes breaking changes, removal of old signatures and constructors, and current-state documentation. The orchestrator owns the eventual local commit. Planning runs no tests and changes only this plan and its testing companion.

## Desired End State

The public root signatures are exactly the following. Existing method counts and return types stay the same.

```java
void validate(String namespace, String localName, Object input);
void validate(String namespace, String localName, Map<String, Object> input);
String invoke(String namespace, String localName, Object input);
String invoke(String namespace, String localName, Map<String, Object> input);
String invoke(String namespace, String localName, Object input,
              Consumer<SkillExecutionView> observer);
String invoke(String namespace, String localName, Map<String, Object> input,
              Consumer<SkillExecutionView> observer);

AdmittedSkillInvocation handoff(String namespace, String localName, Object input);
AdmittedSkillInvocation handoff(String namespace, String localName,
                               Map<String, Object> input);
```

Public metadata has one canonical constructor per record and the following exact component shapes.

```java
record SkillDescriptor(String namespace, String localName, String description,
                       SkillKind kind, String inputSchema, String outputSchema) {
    public String qualifiedName() { return namespace + ":" + localName; }
}
record ValidatedSkill(String namespace, String localName, SkillKind kind) {
    public String qualifiedName() { return namespace + ":" + localName; }
}
```

The compact constructors validate the exact pair using the existing `SkillIdentity` implementation. They retain explicit null checks for record identity components and existing nonidentity fields, with `NullPointerException` for null required record fields and `IllegalArgumentException` for invalid spellings or lengths. `outputSchema` remains nullable. `qualifiedName()` is derived from the validated components, with no stored duplicate string. Remove `name()` and encoded-name constructors.

`reloader.snapshot("orders").skill("lookup")` returns the descriptor whose components are `orders` and `lookup` and whose qualified name is `orders:lookup`. Candidate catalogs use the same rule. `skill("orders:lookup")` fails local-name validation. For a well-formed local miss the lookup returns empty. A legal local name such as `warehouse-lookup` refers only to that local name in the selected namespace.

Every public root operation constructs the exact requested `SkillIdentity(namespace, localName)` before capture. Invalid identities keep the facade's existing `SkillException` wrapping boundary. Missing namespaces/skills fail without installing a namespace, authorizing another target or retrying another spelling. `AdmittedSkillInvocation` keeps its existing target-free methods.

Application code can use either metadata type directly.

```java
var checked = feedback.skills().stream()
        .filter(skill -> skill.localName().equals("lookup"))
        .findFirst().orElseThrow();
skills.validate(checked.namespace(), checked.localName(), Map.of());

var descriptor = reloader.snapshot("orders").skill("lookup").orElseThrow();
String result = skills.invoke(descriptor.namespace(), descriptor.localName(), Map.of());
var admitted = handoff.handoff(descriptor.namespace(), descriptor.localName(), Map.of());
try {
    admitted.invoke();
} finally {
    admitted.release();
}
```

## Implementation Approach

Keep identity authority at the explicit public boundary, then use the existing typed captured entry. Extend no admission state. Catalog and validation producers extract identity components directly from the existing metadata/definition identities. Use the existing exact grammar/combined limit once per incoming pair. Derive display strings from validated components.

Internal prepared execution helpers should use `prepared.capability().name()` or `prepared.snapshot().entry().toString()` for the diagnostic name after capture. Remove the now-redundant original caller target string from handoff payload/prepared helper arguments when it serves only that same diagnostic purpose. The admitted handle may retain the canonical string needed to report a consumed/released/cutoff handle. Do not add duplicate namespace/local state to the handle or parse a display string back to select execution.

## Planning Decisions and Handoff

- Explicit record components are namespace/localName. The qualified name is derived, keeping one source of identity truth and allowing direct caller reuse.
- Public required record fields keep null validation, while exact pair grammar/length uses the existing internal validator. Root methods preserve their exception boundary.
- Root capture remains before conversion/validation, and retained admissions use captured metadata. Remove redundant original-target plumbing where canonical metadata already supplies the same diagnostic value.
- Scoped catalogs validate a complete pair using their own namespace, which applies the combined limit even to a missing local target.
- All compile callers move in this ticket. Later provider/worker and Console behavioral obligations are explicitly recorded, with their raw payloads preserved.
- No developer question remains. Optional developer checks are none. Required assurance is executable.
