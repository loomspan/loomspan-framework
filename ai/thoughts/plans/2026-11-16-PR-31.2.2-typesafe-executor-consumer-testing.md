# TypeSafe executor and packaged consumer testing plan

## Change summary and impacted areas

The pack adds a reference-only executor, native request construction/validation,
explicit input binding and JSON-safe result text. A separate support-triage
application proves the installed JAR with normal Boot discovery and supported
Framework APIs. Production code/tests/example/docs live in Extensions; Framework
owns documentation routing and pipeline handoff artifacts. Read the governing
implementation plan alongside this plan.

## Risks and protected boundaries

- A transport unit test can hide executor discovery, generic binding and Java
  null/String conversion errors; the consumer must invoke the actual pack.
- Incorrect template binding can alter null/omission, question names, criteria
  order and received numbers; assert captured native requests, not Java helpers.
- Captured credentials/endpoint settings must retain existing precedence and
  reject invalid present overrides before send. Retries must retain body bytes.
- Malformed successful JSON must fail once; error decoding must not suppress
  retryable HTTP status. Redirect targets must receive zero traffic.
- Diagnostic bounds must not alter business results. Normal canonical trace
  evidence must preserve source content, including field names the derived
  journal intentionally handles differently.
- Supported Application API stays closed, with no internal/autoconfigure imports
  by consumer or pack and no new SPI. New pack config is a documented configuration
  contract; HTTP is the native serialized contract. Diagnostics reuse the current
  record/content system. No legacy compatibility path is introduced or retained.

## Existing coverage

Existing TypeSafeSettingsTest and TypeSafeTransportTest cover settings, endpoint
validation, retry status/count/body identity, redirects and complete JSON decoding.
TypeSafeTransportLifecycleTest and TypeSafeTransportDiagnosticsTest cover transport
lifecycle and capture containment. DecisionsAutoConfigurationTest covers current
transport construction/import boundaries. Framework's executor integration tests
establish ordinary publication/composition, generic binding and diagnostics, but
do not establish this external packaged executor. Retain existing checks and add
the consumer assertions below; no live calls, no implementation mocks in consumer.

## Failing test first

Add an executable registration test expecting the installed pack to supply the
reference-only `typesafe` executor and allow a YAML leaf invocation against a
local stub. On the baseline, dependency discovery supplies transport only, so
preparation/invocation cannot resolve the executor. Record this red evidence
before registration is added, or use an equivalent focused baseline check.
For this new feature the remaining cases establish the selected contract; do not
invent a pre-existing bug to justify every test.

## Tests to add or update

### 1. Native request construction and binding

Type: unit; location `extensions/decisions/src/test/java/ai/loomspan/decisions/internal/typesafe/TypeSafeRequestTest.java`.
Exercise the pure builder with native config/input JSON values. No HTTP mock is
needed. Assert detached construction and no mutations; model/request requiredness;
each question type and mixed questions; text/object/array state; native structured
instructions and criterion entries; Choice keys; Noul true/false; ordered Score
criteria; BigInteger/BigDecimal inputs preserved as received; finite-number rules.

Exercise escaped pointers, whole-input empty source, nested/array replacement,
added object field, explicit null, missing-source object omission, missing required
state failure, malformed pointer, missing/scalar parent, invalid index, omission
from array and overlapping target rejection. Assert configuration paths.
Exercise each documented local Resource type with a counting stream/read fixture,
and reject unsupported/remote Resource types without opening them. Plain remote
URL strings must remain unchanged and unrequested. Images/Box and unsupported
capability fields fail before transport; arbitrary JSON keys in state remain data.
Surfaces: new configuration contract, native serialization and internal builder.

### 2. Auto-configuration and supported import boundaries

Type: focused Spring integration/source architecture; update
`DecisionsAutoConfigurationTest`. Verify one shared transport, executor registration
bean and shutdown cleanup. Exact allowed Framework imports may add SkillExecutor;
keep v1 parameter/diagnostics only and reject internal/autoconfigure imports or
ConditionalOnMissingBean SPI. Consumer production/test source similarly uses only
allowlisted application API (plus ordinary Spring/Jackson/testing libraries).
Run Framework LoomspanPublicSurfaceArchitectureTest. No Framework API delta.

### 3. Dependency discovery, actual invocation and composition

Type: packaged application integration; location
`extensions/decisions/examples/support-triage/src/test/java/.../TypeSafeConsumerTest.java`
(split focused test classes as useful). Boot using the installed pack JAR and
normal auto-discovery, no pack auto-config/implementation imports or substitution.
Use public SkillReloader/SkillDocument/ExecutionConfiguration and SkillTemplate.
Verify install alone exposes no callable catalog skill; `default-typesafe` cannot
be called as a root. Publish explicit app YAML with selected default namespace
config and verify direct execution and public JAVA classification.

Use local native model stub for a parent invoking real executor children. Assert
valid `/answers/...` parent binding and unchanged complete response forwarding;
invalid missing/type binding triggers ordinary runtime failure. Show business
roles/input policy remain app-owned. No Console process or account is required.
Surfaces: existing Application API and configuration/binding contracts preserved.

### 4. Native wire types, precision and local rejection through invocation

Type: packaged consumer integration. Parameterize Choice, Noul and Score alone
and one mixed request. Assert captured POST JSON, model, question identity, native
text/JSON state and supported instruction/criterion forms, score order and source
numbers. Include direct BigDecimal/BigInteger input and a YAML config high-precision
decimal demonstrating accepted ordinary config conversion; compare to the value
actually decoded/received, never require impossible recovery of original digits.
Cover null/omission via binding, unsupported image/Box declarations, malformed
question/config/model and invalid pointer; all local failures produce zero HTTP
sends and no retry diagnostic. Native fixtures are synthetic, not inference.

### 5. Complete results across the real Java invocation boundary

Type: packaged consumer integration. Stub complete envelope with answers, unknown
nested fields, native refusal and usage. Assert parsed SkillTemplate result equality
to full source JSON, including high-precision response numbers and ordered arrays.
Also assert top-level JSON null, quoted/escaped String, boolean, number and array.
Accept unconventional/missing answers and confidence values without schema checks.
Malformed, empty and whitespace-only 2xx bodies fail after one send, with no
decoding-only retry. Large response evidence exceeding diagnostic bounds still
returns the complete business result. This is an ordinary resource-limit assertion,
not advanced fault injection. No answer extraction/wrapping/renaming.

### 6. Real transport behavior and captured settings

Type: packaged consumer integration. Exercise 429/503 with HTML/malformed JSON,
then success; assert exact number and byte-identical bodies and useful caught
failure/retry diagnostics. Exercise exhaustion at three sends. Redirect stub points
to second local server; invocation fails and second server gets zero requests.

Check skill-config auth/base precedence over namespace config, absent fallback,
present null/blank/non-string/invalid URL rejection before send, prefix preservation
and exact selected Authorization bytes. Inspect provider default through existing
settings tests, avoiding network access to the real provider; consumer invalid
credential absence must fail without a send. Use real test credentials only.
Do not generalize precedence to request.model or other settings. Concurrent
distinct-setting and publication qualification stay in 31.3.2.

### 7. Normal diagnostics and canonical evidence

Type: packaged consumer integration/file inspection. Enable standard canonical
trace retention under example `target`; invoke the pack successfully and with a
caught retry. Use public observer for completion and recorded files for canonical
evidence. Assert request endpoint/body/attempt, response, caught failure and retry
delay messages with existing developer levels, actual source data and record/frame
association. No secret-name heuristics or content replacement. The observer journal
is a derived projection with its existing field-name exception; do not confuse it
with canonical trace fidelity.

Keep diagnostics as `EXECUTOR_DIAGNOSTIC_RECORDED` and system notices as
`EXECUTOR_DIAGNOSTIC_SYSTEM_NOTICE_RECORDED`, within existing execution frames.
Inspect retained `data` content using existing descriptors, not invented summary
metadata. Existing optional retrieval tools are `LOOMSPAN_query_trace_records`
and `LOOMSPAN_read_trace_content`; no tool/store/frame/cursor/filter changes.
Normal evidence/result independence is required here. Advanced fault injection,
mixed-mission accounting and Console/MCP pagination/content qualification belong
to 31.3.2; extend the same harness there. Existing code anchors: Framework
TraceRecordType/TraceRecord and Console traceanalysis enums/parser/query_records,
mcpadapter traces/trace_contracts/output_schemas. No new reader protocol is needed.

### 8. Runnable recipe and documentation claims

Type: executable application plus documentation/source verification. Provide a
repeatable local stub command and complete source/YAML used by tests, sample input,
illustrative policy/result/refusal/error handling and expected trace paths. Assert
the documented run works without Console or real keys. Validate version coordinates,
optional live setup as application-resolved config, numeric/metadata/capability
limitations and Framework-accounted usage scope against executable paths. Update
pack indexes and minimal Framework authoring routing/coverage in the same change.
Do not put ticket receipts, future ticket promises or migration narratives into
current product docs.

## How to run

Framework working directory:

```powershell
./mvnw.cmd -DskipTests install
./mvnw.cmd -Dtest=LoomspanPublicSurfaceArchitectureTest test
```

Extensions working directory:

```powershell
mvn -B -f extensions/decisions/pom.xml test
mvn -B -f extensions/decisions/pom.xml verify
mvn -B -f extensions/decisions/pom.xml install
mvn -B -f extensions/decisions/examples/support-triage/pom.xml verify
```

The separate example command is required alongside pack verify: it consumes the
installed packaged artifact. Add/document its concrete runnable stub command in
the example POM/README, run it and record exact command/results in ticket notes.
Use Java 21, Maven 3.9+, Boot 4.2.0-RC2, Framework
1.0.0-beta.10-SNAPSHOT and pack 0.1.0-SNAPSHOT; record actually tested build/source
commits. Do not infer successful tests from historical 31.2.1 receipts.
