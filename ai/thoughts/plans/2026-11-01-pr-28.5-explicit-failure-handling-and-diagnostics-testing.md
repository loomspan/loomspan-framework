# Explicit failure handling and diagnostics testing plan

## Change summary and authority

Controlling implementation plan:
`ai/thoughts/plans/2026-11-01-pr-28.5-explicit-failure-handling-and-diagnostics.md`.
Ticket and research paths are recorded there. This is pipeline Step 3, profile
**full**, continuing in the Step 2 planning context. No tests were run during
planning; every command below is an implementation/review requirement, not a
claimed result. Suggested test/helper names may adapt to repository conventions
without changing the required assertions.

The change replaces broad standard feedback, arbitrary-cause identity reuse,
and inferred recovery display. Supported Java signatures and normal execution
budgets/deadlines remain protected. Canonical diagnostics and current Console
contracts change atomically without historical readers or shims.

## Impacted areas and risks

- Shared Java invocation, Spring callback wrapping and the actual manager's
  processor: terminal failures must not become feedback, and application wrappers
  must not inherit designation from a cause.
- Worker-future propagation and lifecycle ownership: normalization must never
  displace primary cancellation, timeout, shutdown or cleanup precedence.
- Capability failure recording, usage accounting and result binding: outer
  feedback must not produce successful credit/output; continuation must remain
  metered against the same session and parent deadline.
- Canonical identity/classification: a terminal application wrapper around an
  already-recorded recoverable cause must remain a distinct visible failure;
  provider correlation must remain independent.
- Journal/observer projection, Go parser/query/browser/MCP contracts and web:
  consumers must carry explicit facts, preserve exact text and avoid inferred
  correction. Recoverable plus completion-linked is a valid combination.
- Bounded capture/truncation and scoped journal behavior: no new content rewriting
  outside the known derived projection exception, and no loss of diagnostics.

## Failing tests first

1. In `LoomspanSessionTest`, record a `RecoverableSkillException` with a cause,

## Tests to add or update

### 1. Shared policy normalization and boundaries

**Type/location:** unit, existing `SharedJavaDiscoveryInvocationTest` plus a
focused `SkillFailurePolicyTest` if separating the expanded policy matrix improves
readability. **Surface:** Application API behavior and internal implementation.

Inputs use the same effective throwable across each recognized transparent
wrapper and nested recognized combinations. Cases:

| Effective failure | Expected classification/message |
| --- | --- |
| Recoverable with exact `"  correct this\n雪\t"` and diagnostic cause | RECOVERABLE; exact original message and cause retained |
| Ordinary runtime, checked exception, serialization failure or Error | TERMINAL; cause diagnostics retained, no feedback |
| IllegalStateException or SkillException around recoverable | TERMINAL; outer text retained |
| Recoverable wrapped in reflection/proxy, worker ExecutionException, real Spring callback ToolExecutionException | RECOVERABLE after known normalization |
| Recognized wrapper around application wrapper around recoverable | TERMINAL; normalization stops at application wrapper |
| Wrapper with null/self/cyclic/deep cause plumbing | Bounded termination, no arbitrary cause classification |

Use actual reflection/proxy and FunctionToolCallback execution for at least one
case of every introduced wrapper, rather than only constructing synthetic
exceptions. Observe actual `Future.get()`/mission worker behavior for
ExecutionException. Do not add unsupported wrapper transparency based only on a
constructed cause. Preserve existing null/String/JSON successful-result tests.

### 2. Shared two-role, three-route failure matrix

**Type/location:** integration; add a reusable test fixture/test class such as
`src/test/java/ai/loomspan/integration/ExplicitJavaFailureHandlingIntegrationTest.java`.
Use application-owned annotated methods with one selected behavior implementation
for `@SkillMethod` and `@SkillExecutor`; executor route is an actual YAML executor
leaf. Use real Spring-managed beans/proxies, captured generations, supported
facade and production manager wiring. No replacing internal Framework beans.

Parameterize both forms across designated recoverable, ordinary terminal,
transparent wrapped recoverable and terminal application wrapper. Include
whitespace/newline/Unicode message plus a distinct cause message to detect
substitution. The shared matrix's route expectations are:

| Route | Expected result |
| --- | --- |
| Direct SkillTemplate invocation | Exception through existing reporting boundary, no success return, preserved classification/message/cause and observer facts |
| Standard YAML parent with real callback/manager | Only RECOVERABLE yields failed/correction-permitted feedback; native response call ID/name match; terminal stops without next model turn |
| Explicit-step YAML parent | All tool failures terminate; no correction call, synthesis success, accepted result binding or successful-skill credit |

Use local deterministic provider responses for standard and step protocols.
Capture the next standard model request and assert the exact decoded tool
message and failed response ID/name. Assert failure canonical/tool records and
failed tool/skill close state exist **before** the model receives feedback, not
just after mission completion. Observer completed view must preserve available
failure facts on direct/step failure and on standard eventual success.

**Mocks:** protocol-compatible local endpoint/fake model and deterministic
application behavior only; do not mock the manager or exception processor in
the integration proving the hook. Focused lower-level tests may use capabilities
to isolate transport ID/name shape, but cannot replace the role matrix.

### 3. Canonical selection and terminal control propagation

**Type/location:** manager/integration additions in
`CanonicalToolCallingManagerTest`, production assembler integration and shared
failure fixture; existing lifecycle/authorization test owners for races.

- Retain full selection validation before any callback. Invalid/unknown or
  noncanonical selection must execute zero tools even if another selection in
  the response names a recoverable callback.
- Exercise authorization denial, quota exhaustion, timeout, explicit cancellation
  and shutdown through the actual standard boundary. Each propagates as terminal
  and produces no model correction; no blacklist is the implementation authority.
- Use latches/barriers for an application throwing recoverable after lifecycle
  cutoff. Assert existing primary cancellation and terminalFailureId remain
  authoritative, cleanup failure remains suppressed, and late writes remain
  fenced. Preserve existing shutdown-specific precedence rather than imposing
  a new one. Cover both Java forms in the shared lifecycle cases.
- Direct worker failure preserves effective message/cause after future unwrapping.

**Compatibility:** existing execution/security controls protected; internal
processor conversion deliberately removed.

### 4. Failure feedback cannot satisfy success or bindings

**Type/location:** shared integration fixture, existing capability/step tests and
`DeclaredChildInputBindingsIntegrationTest`.

Arrange a failed Java producer followed by standard continuation, including a
mission that ultimately returns successfully. Assert the failed attempt has
no `TOOL_CALL_COMPLETED`, successful task completion, successful direct-skill
credit, completed result, or output binding value derived from its feedback.
Keep failed tool/skill records visible. An attempted `CHILD_RESULT` or output
binding from the failed producer must reject through existing source validation
without invoking the receiving child or assembling success from feedback.
If a later successful reattempt produces a real result, only that result may
earn credit or feed a binding. Step tool failure still terminates before that
reattempt. Include both role variants, sharing fixtures.

### 5. Standard continuation accounting and parent deadline

**Type/location:** integration in shared fixture/assembler tests; focused
`SessionUsageServiceTest` checks only where needed to isolate a meter.

Drive deterministic failure → reattempt, failure → alternate tool, and failure
→ changed approach/final response. Capture snapshots before feedback, after
continuation and at quota exhaustion. Assert existing tool/model/provider/skill
counts and usage units are cumulative; failed attempts count, nothing refunds
or resets, provider sends correlate once, and success outcomes remain distinct.
Use small quotas that allow the first failure but reject the attempted next
work for each applicable meter; provider errors and application tool failures
are distinct. Model usage charging must follow existing semantics rather than
inventing units for responses that do not supply usage.

For deadline, coordinate a first recoverable attempt and delayed continuation
under one mission timeout; ensure cutoff occurs at the original parent budget,
with no new deadline on feedback/reattempt. Prefer controlled clock/latch
evidence and generous race tolerances over tight elapsed-time assertions.
Assert no late result credit/write. Existing step-slot and provider retry
counter semantics remain covered by their regressions; no recovery quota added.

### 6. Identity, canonical facts and provider correlation

**Type/location:** `LoomspanSessionTest`, `ExecutionTraceContractTest`, relevant
runner/coordinator tests. **Surface:** current diagnostics/internal recording.

- Same object through multiple recording boundaries emits one error and ID.
- Known transparent wrappers reuse ID in both “cause first” and “wrapper first”
  order; context summaries do not overwrite original canonical ownership.
- New equal-type/equal-text objects receive distinct IDs.
- New application wrapper around recorded cause receives distinct ID and nearest
  recorded cause link, retaining earlier record/classification. Include terminal
  wrapper around recoverable, terminal-around-terminal, and transparent layers
  inside the cause chain. Unrecorded cause creates no invented link/record.
- Several distinct failures may share provider attempt/retry IDs; provider
  correlation survives application wrapping without aliasing failure IDs.
- Cyclic/deep chains terminate; cycles do not force distinct application objects
  to alias. Concurrency still appends once per effective object; sessions isolate.
- Supplied context cannot override authoritative classification/message/type.
  Exact recoverable whitespace/Unicode is preserved, distinct from contextual
  `message`. Empty/null terminal text remains representable without cause fallback.
- Stack diagnostics retain cause and suppressed text; existing 1 MiB capture,
  UTF-8 correctness, explicit truncation and descriptors remain valid.

### 7. Journal and observer projection fidelity

**Type/location:** `ExecutionJournalProjectorTest`, shared integration observer
assertions, `SkillExecutionViewMapperTest` or facade tests as appropriate.

Verify explicit classification, exact exception text, contextual message and
recorded cause link where present. A recoverable error remains visible even
when standard mission succeeds. A recoverable direct/step error is not presented
as correction. Keep original `ExecutionJournalProjector` field-name behavior
within the derived journal/observer only; verify canonical diagnostics and
feedback preserve source content independently. Do not expand field heuristics
or introduce new rewriting tests. Existing truncation tests remain resource tests.

### 8. Java/Go current corpus and strict reader validation

**Type/location:** Java `ConsoleTraceFixtureCorpusTest`, Go
`internal/traceanalysis` tests and shared corpus.

Add semantic fixtures covering RECOVERABLE plus success, RECOVERABLE plus failed
completion, TERMINAL without completion linkage, and terminal application wrapper
linked to a preceding recoverable error. Include exact multiline message/cause,
distinct same-provider-linked errors, explicit diagnostic truncation and current
fixture parity. Update every existing ERROR_RECORDED fixture to the required
shape; retain provider-attempt semantics separately.

Negative current fixtures/tests reject missing/unknown/non-string classification,
recoverable missing/null/blank exceptionMessage, invalid message types, malformed
cause link or missing/self/forward cause target, and existing bad diagnostic
shapes. Nullable/empty terminal messages remain valid. Missing/different exact
release markers continue rejecting. Matching snapshot with obsolete failure data
also rejects; there is no inferred default classification or historical reader.

### 9. Browser/MCP transport and web interaction

**Type/location:** Go `internal/browserapi` and `internal/mcpadapter` contract and
semantic fixtures; query-facts tests; TypeScript failure tests and browser fixture
builders. **Surface:** current cross-component diagnostics.

Carry classification, exact exceptionMessage, cause identity and context summary
through semantic query and both transports. Verify serialized nullable text and
optional link treatment, existing content refs/diagnostic budgets, and byte-bound
pagination behavior with larger messages. Size failures stay explicit; no silent
message shortening. Update packaged runtime skill reference contracts and
deterministic evaluations if they enumerate or explain these fields.

UI tests cover all classification/completion combinations, including recoverable
completion failure. Render classification and completion separately, show exact
message versus context, navigate to recorded cause, retain copy/download and
truncation indicators, and render markup-looking exception/stack text inertly.
Assert absence of inferred “Recovered failure.” Keep existing terminal focus
based on explicit completion linkage.

Add one focused Playwright flow, e.g.
`web/e2e/failure-diagnostics.spec.ts`, using the existing consoleProcess fixture:
open an actual current trace, inspect recoverable and terminal-wrapper records,
follow cause navigation, and load diagnostics. This verifies live Go/browser/UI
transport together; unit snapshots alone cannot establish that connection.

### 10. Documentation and supported surface

**Type:** source/docs conformance plus architecture tests, not prose-mirroring
test code. Verify every changed guidance claim against tests 1–9 and final
production paths. Update the plan's named Java/skill-authoring topics, both
coverage tables, root README and affected runtime-inspection references. Explain
no automatic replay or explicit-step recovery. No product guidance names tickets.

Run `LoomspanPublicSurfaceArchitectureTest`; no added application type or leaked
internal signature/bean replacement contract is expected. Any new Java-public

Quote Maven property arguments so comma-separated selectors and dotted property

Maven wrapper, Go and the locked Node/npm versions are required. No live external
provider or credentials are needed. Tests must use bounded local fixtures.
