# PR 27.1 TypeSafe primitives implementation plan

## Overview

Deliver TypeSafe Choice, Noul, and Score as registered leaf skills through the four delivery scopes 27.2 → 27.3 → 27.4 → 27.5. PR 27.1 is acceptance coordination, not a second implementation. This is pipeline Steps 2/3 with profile `full`; the developer's current implementation request and `proceed` supersede historical creation-only notices. Preserve the five initially untracked user ticket files. No implementation is performed by this planning stage.

The accepted roadmap owns precise behavior; companion examples supply fixtures rather than live evidence. Reuse existing input validation, authorization, captured generations, mission lifecycle, retries, usage, bindings, and observation. The developer problem is a callable and discoverable native evaluation leaf whose business contract survives connection changes. Transport and deterministic pre-send validation belong to the framework; business judgments and side effects remain application concerns.

## Current State Analysis

There is no existing TypeSafe implementation. Strict YAML parsing and declared-field tracking exist in `src/main/java/ai/loomspan/internal/skill/YamlSkillManifest.java:29` and `YamlSkillCatalog.java:315,400`. `YamlSkillDefinition.java:19` copies manifests and currently distinguishes REST from chat YAML. Replace this internal restriction directly. Spring AI's attempt advisor is chat-specific, while shared retry decision, failure, quota, trace, and usage components accept native execution data.

`internal/core/ExecutionCoordinator.java:101,154` currently loads only chat YAML definitions and dispatches Java/REST directly. `MissionWorkExecutor.java:37` already provides captured binding, timeout, cancellation, and physical work coordination. `SkillGenerationManager.java:442,504` owns effective schema and registration. Binding compatibility already has its own authority (`:308,379`); forwarding already retains child text and joins accepted work.

The public kind enum and registered source validators know YAML/JAVA/REST only. Console Go validates these source alternatives separately; MCP has its own schema. Existing TypeScript model detail recognizes chat `messages` and response `content` only (`loomspan-console/web/src/observability/TraceRecords.tsx:14,234,250`). Native evidence must have coordinated consumers when first emitted.

## Desired End State

Authors declare fixed question IDs/types with templated state, instructions, and criteria, invoke through public SkillTemplate, and compose through existing parents. One immutable resolved request is validated before reservations and reused for retries. Both routes share one System One transport and preserve the complete object-valued `answers` as JSON text. Generated descriptive schema is owned by the captured declaration/generation and reaches tools, catalogs, bindings, forwarding, and Console. Successful empty or extended answers pass through without answer validation.

Key verification evidence is the dedicated testing plan, deterministic real-client fixtures, public facade integration, synchronized Java/Go/TypeScript corpora, and LoomspanPublicSurfaceArchitectureTest. Live calls, when available, supplement fixtures and are reported separately.

## Implementation Approach

Keep one TypeSafe-specific declaration/request owner, stored with the immutable captured YAML definition, which compiles string references, validates literals/resolved forms, and derives descriptive schema using the existing AST. Do not spread primitive rules across catalog, transport, and binding code. Keep one registry and one client per connection, with concrete chat/native resources rather than a dummy ChatModel or extensible provider framework. Native invocation runs inside existing MissionWorkExecutor and maps responses directly to existing ModelUsageRecord and trace services.

The alternative of adapting System One into fake chat simplifies a few signatures but loses native evidence and incorrectly invokes text estimation or repair. A generic provider framework creates an extension system beyond current needs. Direct concrete integration is the smallest complete choice. No newly discovered dead unrelated code is slated for removal; replaced chat-only restrictions and their obsolete tests must be removed or rewritten in scope.

## Implementation decisions and progress

Step 4 implements the four delivery scopes under the approved full profile. The original five untracked tickets remain intact; no commits or pushes were requested.

- `TypeSafeDeclaration` owns strict request validation, declaration-local immutable compiled token lists, detached resolution, and the generated descriptive schema. Runtime input never changes the declaration or catalog schema.
- `ProviderConnectionRuntime` now holds exactly one concrete chat/native resource. All existing chat construction sites use the deliberate internal chat factory; registry destruction closes either resource. No compatibility constructor or provider SPI was added.
- `TypeSafeClient` uses the managed Apache HttpClient **5.6.1**, one client per connection, with automatic retries and redirects disabled. Pinned actual configuration checks establish connect and lease defaults of 3 minutes, response timeout unset, connection socket timeout unset with effective SocketConfig socket inactivity of 3 minutes. An authored timeout sets response and connection socket inactivity while retaining connect/lease defaults. There is no total-attempt deadline.
- Native HTTP cancellation registers a cancellable physical future on existing MissionLifecycle; cancelling the handle aborts the Apache request. A real blocked-server test cancels without interrupting the sending worker and verifies a subsequent send uses a new socket. Mission expiry, caller interruption, framework cutoff, and interrupted backoff use the same authority and existing write fences.
- Successful bodies are complete, including >1 MiB answers on both route prefixes. Error capture independently reads at most 1 MiB plus one truncation-detection byte, keeps complete UTF-8 characters, and aborts oversized entities rather than draining an arbitrarily long remainder. Error diagnostics use the existing kind/contentType/text/truncated/captureLimitBytes descriptor consumed by Console.
- Native model payloads use `payloadType: evaluation`, request/endpoint/requestedModel, and envelope or rawBody plus optional servedModel. Existing counters receive native exact/unavailable usage before minimal answers extraction; no heuristic or error-body usage path exists.

Existing binding compatibility, receiver validation, exact source lookup, forwarding, and same-release trace checks remain their authorities. The native schema flows through their existing generation map without a new validator.
