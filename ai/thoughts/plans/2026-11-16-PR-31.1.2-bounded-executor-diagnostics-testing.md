# Bounded Executor Diagnostics Testing Plan

## Change Summary

Implement the six existing v1 diagnostic methods using bounded snapshots in the existing execution frame and trace sequence, with separate Framework notices. Preserve successful results, original executor failures, automatic observation semantics, resource input handling and accounting. Governing implementation plan: `2026-11-16-PR-31.1.2-bounded-executor-diagnostics.md` in this directory. Selected route is developer-approved full.

## Impacted Areas and Risk Assessment

- Invocation private construction and accessor; closed Application API must remain unchanged externally.
- JSON walker/output sink: exact approved container/scalar classes, preallocation/work bounds, cycles, Unicode, numbers and mutable source data.
- Captured binding/frame and local closure: cross-thread writes, sequence order, invocation isolation, cancellation and cutoff while physical work continues.
- Failure containment: ordinary capture, serialization, append, fallback serialization/append/logging and synchronous callback reentry.
- Trace vocabulary, physical chunking, content path and downstream closed validators.
- Existing executor start/stop/input/output/failure/accounting boundaries and derived journal exception.

Compatibility expectations: protect the existing v1 signatures, supported exact JSON contract, YAML/config/auth/lifecycle semantics and original result/failure behavior. Remove only the declaration-staging assertion that diagnostics is unavailable. Internal construction signatures can change atomically. New trace data is current-run diagnostic content; no historical fixture or compatibility shim is required. Marker remains unchanged. Go/TS/MCP/UI acceptance belongs to 31.1.3, with concrete unknown-vocabulary evidence required here.

## Existing Test Coverage

`VersionedExecutorInvocationTest`, `SkillExecutorTest` and `LoomspanPublicSurfaceArchitectureTest` cover the supported declarations/private construction. `ExecutorInvocationLifecycleIntegrationTest` has real ApplicationContextRunner public direct and deterministic standard/explicit child execution, worker retention and cancellation/shutdown cases. It currently explicitly expects diagnostics() to throw, providing a clear staging behavior to replace. `ExecutorGenerationExecutionIntegrationTest` and `ExecutorApplicationIntegrationTest` cover captured generation and actual resolved Resource inputs. `ExplicitJavaFailureHandlingIntegrationTest` protects both Java roles through direct/standard/explicit failure classification. MissionLifecycle, mission cutoff and trace/observation suites protect automatic paths. `ConsoleTraceFixtureCorpusTest` deterministically regenerates the shared corpus. None yet proves functioning bounded diagnostic capture.

## Tests to Add/Update

### 1. Approved JSON values and immutable snapshots

Type: unit in `src/test/java/ai/loomspan/internal/core/BoundedExecutorDiagnosticCaptureTest.java`, plus public integration snapshot/isolation cases. Construct actual approved exact mutable/factory maps/lists, empty/one/multiple JDK factory variants, nested nulls, all specified reference/primitive arrays and scalar numeric types. Prove `(String)` yields ABSENT and `(String,Object)` with null yields COMPLETE data:null. Verify arbitrary field names and content (`Authorization`, `token`, `api-key-ref`), controls, quotes, non-ASCII and whitespace retain exact values. After capture returns, mutate original nested maps/lists/arrays and confirm retained JSON is unchanged. Reuse acyclic aliases and verify both copies. Across two public invocations ensure budgets, notices and messages are isolated.

Use real Jackson capture; no mock object mapper. Affected surface: Application API and current-run trace. Expect no public-surface expansion, adapters or masking.

### 2. Unsupported and adversarial values never execute caller code

Type: capture unit. Supply custom Map/List/HashMap/ArrayList subclasses whose size/get/entrySet/iterator/toString throw or increment counters, arbitrary Number subclasses whose conversion/toString throw, hostile DTO getters and application-registered mapper serializers, non-string object keys, custom JsonNode subclasses, Character/char[], NaN/infinity and cycles. Assert unsupported code counters stay zero; recording produces explicit reason/state or fixed fallback and returns normally. Exact approved class recognition must precede traversal/conversion; never include rejected object text in notices/logs.

Also test hostile *permitted* values: very long Strings and map keys, enormous exact BigInteger bit lengths, BigDecimal with huge unscaled integer, Integer.MIN_VALUE/MAX_VALUE scales, and boundary finite numbers. Prove guards reject before costly decimal construction/conversion, and complete accepted numbers preserve value. Do not use only custom subclasses to test number bounds. Cycle fixtures include direct and mixed map/list/array cycles. Repeated acyclic alias is not a cycle.

Use bounded time assertions only as hang guards; assert work counters/output sizes and explicit states rather than performance guesses. Affected surface: Application API fixed value contract/internal capture safety.

### 3. Every resource budget and explicit state

Type: unit parameterized boundaries. Exercise just below/at/above 8 KiB UTF-8 message, 32 KiB data, 48 KiB envelope, depth 32, work 4,096, 128 event attempts and 256 KiB aggregate output. Include escape amplification (controls/quotes/backslashes), multi-byte code points and supplementary characters at the boundary; assert valid UTF-8/JSON, correct prefix and states, no invented suffix, retained exact message when it fits and no split surrogate pair. Check incomplete structured JSON is discarded, never parsed/repaired/returned as data. Verify DEPTH_LIMIT/TRAVERSAL_LIMIT/DATA_LIMIT/NUMBER_LIMIT states separately from generic CAPTURE_FAILURE. A throwing or concurrently mutated supported collection yields ordinary capture failure without retained live references; atomic snapshots during external mutation are not promised.

Flood invalid values to prove they count against attempts, at most four ordinary notices and four warning attempts occur, one separate reserved limit notice is attempted, then later payloads are not inspected. Fill aggregate developer bytes before the next event and assert the reserved notice remains possible. Repeated calls after suppression return without invoking capture or append. Count bytes charged on attempted append failure and prove no refund enables an unbounded loop. Mock only bounded internal collaborators/counters, not application behavior.

Affected surface: documented invocation limits, diagnostic current-run states. Distinguish complete notice content from unavailable discarded evidence.

### 4. Ordinary failure containment, fixed fallbacks and recursion

Type: unit in `DefaultExecutorDiagnosticsTest.java`; public integration in `ExecutorDiagnosticsIntegrationTest.java` through the managed executor. Inject RuntimeException independently at capture, serialization, developer append, fixed fallback envelope serialization, system-notice append and Java warning callback. Inject combinations where primary and both fallback paths fail. For every applicable seam, run a successful executor returning an exact String and one throwing a sentinel application/RecoverableSkillException instance; verify exact success or original failure causal identity is preserved. No diagnostic failure becomes ERROR_RECORDED, retry or successful failure output. Internal constructor-injected collaborators are testing seams, not public extension points or replacement beans.

Use a rejected payload with counters to assert it is traversed at most once and never touched by notice/logging. Inject a logger callback that throws and count maximum calls. Force synchronous append/log callback reentry into the same diagnostic handle and prove it returns without recursive work/reporting. A failed append is not retried; system notice delivery may fail and absence implies no recorded condition. Do not inject failures into existing automatic record paths and demand new containment there.

Explicitly demonstrate caller-expression failure before `info(message, expression())` propagates normally as executor work. Do not claim fatal JVM Error containment; code review confirms boundary catches ordinary exceptions without a broad Throwable swallow. Tests need not induce VM exhaustion. Affected surface: diagnostic guarantee and its documented limits.

### 5. Cross-thread ordering, closure and lifecycle fencing

Type: public integration plus narrow internal concurrency test where necessary. Share the Framework-created handle with several application threads, coordinated by barriers, with unique payload IDs. Wait for all calls before executor returns. Assert one logical record per captured call, one mission frame association, existing timestamps, unique monotonically ordered *canonical* sequence and no missing/duplicate IDs. Do not assert thread scheduling order or contiguous diagnostic sequences when other record types interleave. The handle introduces no diagnostic sequence.

After a successful return and after executor failure, retain the handle and call from another thread with an unsupported counter-bearing payload: no capture/append occurs and it returns normally. Race normal close with a blocked injected capture to prove the documented linearization; close waits for admitted bounded work or lifecycle revocation suppresses append. With the lifecycle harness, cancel/timeout/shutdown while uncooperative physical executor work continues, then attempt a diagnostic and assert no record/capture after cutoff. Include ancestor cutoff during child work and ensure no post-close record lands in a sibling/current caller frame. No reliance on the writer thread's ThreadLocal binding. Use bounded joins and finally release all latches.

Affected surface: Application API lifecycle, internal synchronization and diagnostic association. Existing parent budgets/cancellation and resource lifetime remain unchanged.

### 6. Automatic evidence, severity and outcome semantics

Type: extend public integration and reuse real existing suites. Cover root and standard/explicit child executor success/failure. Assert existing mission and tool boundary counts do not gain duplicate start/stop/failure records. FRAME_OPENED data includes canonical executorName and executorConfigGenerationId selected from captured registration, distinct from executing YAML generation. Open/close timestamps and completed/failed/aborted status remain present. Retained generation replacement/removal uses captured IDs. Input Resource remains the exact resolved handle; no new eager reads or arbitrary traversal.

Root success records exact already-converted executorOutput via the existing FRAME_METADATA_RECORDED content path; failed root has no fabricated successful output. Children continue using TOOL_CALL_COMPLETED; no extra output record is added for them. Developer `error` with successful return leaves successful outcome/accounting unchanged and creates no ERROR_RECORDED or provider attempt. System notices have no severity. Verify direct recoverable propagation, standard corrective feedback and explicit termination using existing deterministic HTTP tests; no replay, refund, fabricated result or mapped diagnostic severity. Ordinary automatic failure path tests remain valid.

Keep existing derived-journal tests: canonical content fidelity and the narrow existing projector/observer field-name exception remain distinct. New diagnostics may remain absent from public derived journal; do not create an extra public event API merely for canonical records.

### 7. Mixed corpus, physical chunks and downstream boundary

Type: Java fixture integration in existing `ConsoleTraceFixtureCorpusTest`. Add a deterministic valid trace mixing old records with developer diagnostics and system notices in one frame. Include at least one diagnostic above the 4,096-character physical chunk threshold yet below capture limits, data:null versus absent, original message/JSON fidelity, truncated-message and unavailable-data records. Check one logical event per captured call, canonical ordering, retained message/severity/data/states, no system severity and no ERROR_RECORDED for authored error. Reconstruct logical chunked content using existing helpers/content rules; verify ordinary content remains JSON in the existing data path.

Regenerate with existing property, then run normal corpus byte-for-byte verification. Do not alter transport fixtures or marker. Run Go corpus consumer to obtain concrete unknown-record failure (unless consumer already supports it); persist exact command, fixture name, record type and validation error in ticket Execution notes with 31.1.3 as restoration owner. Go enum/parser changes, MCP filtering/paging/ref reads, TS schema/UI display and absence interpretation acceptance are downstream, not gates to implement here. No new tools/indexes/streams/cursor or severity filters.

### 8. Supported declarations and authoring claims

Update staging lifecycle/accessor tests, the private-construction test helper, and any exact internal constructor assumptions. Run supported surface tests after production type changes; no additional supported type, public construction or internal signature leakage is allowed. Review actual README/Javadocs and routed authoring docs against tests 1–7. Document only current behavior: fixed budgets, accepted JSON, closure/concurrency, authored severity neutrality, bounded best-effort fallback, non-recovery of discarded payloads, and failure-containment exclusions. Update relevant Java/authoring coverage rows. Current declaration-only docs are aligned; after code changes leaving them unchanged would be documentation drift. No prose-only test is needed.
