# PR 37.2 startup path spelling testing plan

## Change summary

Startup resource discovery inspects exact relative path spelling before reading YAML. Its loader-owned Spring matcher enumerates case variants of the configured pattern, and strict validation rejects uppercase directory or filename components. Literal locations check only the filename, including caller spelling before lookup. Public supplied documents retain exact diagnostic labels independently of path checks.

The governing implementation plan is `ai/thoughts/plans/2026-11-23-PR-37.2-startup-paths.md`. Both plans were created in the same full-pipeline planning context. This stage runs no tests and changes no production or test code. Commands below are planned verification, not claimed results.

## Impacted areas and risks

| Area | Risk to verify |
| --- | --- |
| `YamlSkillCatalog` discovery and resolver ownership | Spring filtering hides bad candidates, absent paths acquire unwanted errors, configured ResourceLoader/classloader delegation is lost, or matching loads unrelated extensions. |
| Shared `SkillSourcePathResolver`, relocated to `internal.skill` | Fixed-prefix calculation diverges between loading and observation, `classpath*:` is mistaken for a wildcard, literal directories are checked, or encoded URI characters produce false uppercase errors. |
| Actual resources | Windows case-insensitive lookup accepts a wrong supplied filename or reports supplied casing instead of disk casing. Packaged JAR entries follow different lookup semantics. |
| Supplied documents | An arbitrary diagnostic label is accidentally treated as a path, altered, or withheld from feedback/source metadata. |
| Public surface and diagnostics | Internal helper relocation exposes API types or errors omit the relative path/offending component. |
| Documentation | Examples overstate tested resource support or imply that a directory assigns skill ownership. |

The configuration/manifest rejection is intentional and authorized. Existing startup ownership, exact labels, missing roots, selected `.yaml`/`.yml` extension behavior and runtime-independent validation remain protected behavior. Application API signatures stay as implemented. There is no resource resolver SPI to preserve. Current observation fields retain their schema and exact content.

## Tests to add or update

### 1. Real filesystem discovery matrix

Use `StartupSkillPathTest` with parameterized relative paths and actual `PathMatchingResourcePatternResolver` instances. Write fixtures at runtime with `Files.createDirectories` and `Files.writeString`. Avoid adding uppercase resource fixtures to the shared default test classpath, where unrelated startup tests could discover them.

| Relative path under `root/**/*.yaml` | Expected result |
| --- | --- |
| `orders/lookup.yaml` | Load exact `default:lookup`. |
| `Orders/lookup.yaml` | Error includes `Orders/lookup.yaml` and directory `Orders`. |
| `orders/lookup.YAML` | Error includes `orders/lookup.YAML` and filename `lookup.YAML`. |
| `orders/Lookup.yaml` | Error includes `orders/Lookup.yaml` and filename `Lookup.yaml`. |
| `lookup.yaml` | Root-level match succeeds under recursive pattern. |
| `orders/lookup.yml` | No definition under `.yaml`; succeeds when explicitly configured with `.yml`. |
| `orders/readme.txt` | Remains outside YAML pattern selection. |

Keep ordinary relative names lowercase in accepted cases. The absolute temporary root may contain uppercase letters or spaces and must succeed because it is the fixed prefix. Add a root with a space to exercise decoded URI handling. Use distinct local names when a success test loads multiple files, then assert deterministic sorted resource order.

These integration tests prove configuration/manifest behavior and useful current diagnostics. Use real resources without mocking filesystem matching.

### 2. Exploded classpath and all-classpath candidates

Use an isolated `URLClassLoader` rooted at a temporary directory containing `skills/` and create a `PathMatchingResourcePatternResolver` with that loader. Pass that exact resolver into the catalog. Cover `classpath:/skills/**/*.yaml` and `classpath*:/skills/**/*.yaml` with lowercase success, uppercase directory failure and uppercase extension failure.

Close the classloader with try-with-resources. Keep fixtures under a unique root or isolated loader scope so the parent classpath's skill corpus is not accidentally included. Assert the same exact relative error text as filesystem cases. The test must prove the supplied resolver's classloader/ResourceLoader continues to drive discovery after matcher configuration.

These integration tests cover configuration behavior and internal delegation. No hosted application, model provider or custom resolver SPI is needed.

### 3. Packaged JAR discovery

Build temporary JARs with `JarOutputStream`, explicit directory entries and UTF-8 definition bytes. Open them through an isolated `URLClassLoader`. Parameterize lowercase `orders/lookup.yaml`, uppercase directory `Orders/lookup.yaml`, and uppercase extension `orders/lookup.YAML` under `skills/`. Test both classpath prefixes through the ordinary catalog discovery path.

Add an explicit `jar:file:...!/skills/**/*.yaml` case using the temporary JAR URI, with a JAR filename or outer directory containing a space. Verify exact entry spelling is checked and URI escape hex characters are not mistaken for uppercase filename content. The valid case loads bytes normally. The invalid cases report relative entry path and component before manifest parsing. Use a deliberately malformed YAML body in one invalid candidate to prove path rejection precedes YAML parsing.

The test fixtures should match the same accepted JAR-root conventions used by Spring, while the actual configured glob remains lowercase. This validates the missing-candidate defect independently of host filesystem casing.

### 4. Caller spelling before lookup and literal scope

Use direct catalog construction with a small spying subclass of the concrete Spring resolver where a call-count assertion is required. Preserve its ordinary ResourceLoader behavior. This is a test seam for prelookup ordering, not an application extension contract.

| Configured location shape | Expected result |
| --- | --- |
| Literal `classpath:/skills/Orders/lookup.yaml` | Check only `lookup.yaml`; load successfully in `default`. |
| Literal file under uppercase parent with lowercase filename | Load successfully. |
| Literal `.../Lookup.yaml` with no such file | Error for supplied filename before resolver lookup. |
| Pattern `.../skills/**/Orders/*.yaml` | Error for caller relative component `Orders` before lookup, even with an empty root. |
| Pattern `.../skills/**/*.YAML` | Error for caller relative filename pattern `*.YAML` before lookup. |
| Pattern with uppercase text only in fixed root `.../Skills/**/*.yaml` | Root is outside relative check; lowercase candidates succeed. |

Preserve `*`, `**`, `?` and supported brace syntax while checking case in literal text of relative pattern components. Check only relative suffixes after the fixed prefix. Assertions should include full supplied relative suffix and offending component and should not require a new public exception type.

Add a conditional filesystem capability case when `Files.exists` confirms lowercase lookup resolves an uppercase actual filename. With supplied lowercase literal `lookup.yaml` and actual `Lookup.yaml`, require rejection reporting the actual filename. The case runs on this Windows workspace and is skipped only on a truly case-sensitive filesystem. Other prelookup and actual-pattern tests run on every host. Preserve logical path diagnostic spelling when a filesystem resource is a symlink.
