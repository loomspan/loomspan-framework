Implement composed execution through the immutable admission snapshot. Each child uses its captured target generation while preserving one session, caller, shared accounting and ancestry. Authorization uses the actual source before any context switch.

## Current state analysis

- `ExecutionBinding.java:13` already holds the snapshot and a validated selected generation. `sessionOnly`, `withMission`, and `forkBranch` preserve session/branch ownership. It has no target transition or explicit derived entry/current accessors.
- `SkillAdmissionSnapshot.java:8` owns the immutable namespace-generation association. `SkillGeneration#owns` requires exact captured metadata identity. `SkillDependencyValidator#visit` checks each declared incoming edge, including Private callbacks, during preparation/admission.
- `DefaultSkillVisibilityResolver.java:24`, `CapabilityExecutionRouter.java:54` and `ExecutionCoordinator.java:82` currently resolve/require only the selected generation. `DefaultAccessGuard.java:30` currently checks roles alone.
- `ExecutionCoordinator#executeBound` checks access after installing a child mission. That placement cannot be the source-authority check. Its parent diagnostic merge also derives a parent binding from the child generation.
- `DefaultSessionUsageService#quotas` uses current-generation settings, while `LoomspanSessionRunner#executeAdmittedRoot` already selects entry depth, trace persistence and configured quota snapshot once. Model/provider, mission timeout and attachment materialization already read current runtime.
- Managed mission and parallel workers explicitly capture/install bindings. `ScopedAuthentication` separately installs a fresh Spring SecurityContext around actual Java/REST worker execution and restores the exact previous context.
- The preparation REST closure already captures canonical qualified target identity and owning generation ID (`SkillGenerationManager#prepare`, `#invokeRest`). Add retained cross-namespace tests rather than another routing mechanism.
- Planning and step validation compare exact strings without common-parser normalization. The existing Spring AI adapter transmits bound names unchanged.

### Pinned Spring AI integration evidence

The locally installed Spring AI **2.0.0** source jars were inspected, matching `pom.xml`:

- `DefaultChatClientBuilder` has a constructor/ChatClient builder overload accepting `ToolCallingAdvisor.Builder<?>`. With no custom builder it auto-installs exactly one advisor with a `ToolCallingManager` backed by the observation registry.
- `ToolCallingAdvisor#adviseCall` obtains a provider response through the advisor chain, then calls `ToolCallingManager#executeToolCalls(prompt, response)` and uses the returned conversation history for the next turn.
- `DefaultToolCallingManager` matches response tool names exactly to callbacks in `ToolCallingChatOptions`, then consults its resolver. Its default resolver is empty; it owns ordinary tool execution, tool observations, exception processing and response history.
- The framework `ProviderAttemptCallAdvisor` records the actual downstream response before the tool manager runs. A manager decorator can create a canonical execution copy without mutating the original response or authored prompts.

## Implementation approach and decisions

1. Keep the existing snapshot as the single authority. Add structured target resolution on that existing type and derive entry/current namespace-generation accessors on `ExecutionBinding`; never store independently mutable namespace/generation copies.
2. Extend the existing `DefaultAccessGuard` and reuse `SkillRoleEvaluator`. Share the simple same-namespace/Public predicate with preparation/admission by extracting it from `SkillDependencyValidator#visit` into a narrowly scoped static helper on that existing internal validator (make the validator technically public only if needed for the cross-package call; keep its construction internal and classify exposure). No second authorization service is introduced.
3. Router and coordinator each authorize while the source binding is still installed. The coordinator alone creates the target generation plus child mission binding atomically. Remove or relocate the post-switch source-policy recheck rather than misclassifying the child as its own caller.
4. Use entry generation only for existing session quotas. Preserve all other established owners and accounting timing.
5. Normalize model identities only at semantic selection boundaries. Use a package-private Spring AI `ToolCallingManager` decorator, installed through the existing single advisor builder, to canonicalize an execution copy and delegate all actual tool execution/observations to the standard manager. No provider alias/resolver fallback.

## Phase 1: Authoritative bindings, resolution and source policy

### Changes required

- Extend `SkillAdmissionSnapshot` with structured resolution (`SkillIdentity` -> selected namespace generation -> canonical capability key), returning clear missing-capture/missing-target errors. Preserve exact ownership checks; same-name metadata from another generation is invalid.
- Extend `ExecutionBinding` with derived `entryGeneration`, entry/current namespace accessors, and an atomic transition accepting target identity/generation plus the newly created mission. Validate the target against snapshot identity; `forkBranch` and mission copies retain snapshot/session/branch. Do not introduce redundant namespace fields.
- Extend `DefaultAccessGuard` to verify explicit-session/binding consistency, target captured ownership, source declaration and namespace visibility, then target roles with existing trusted authentication resolution.
- Session-only root access is limited to the admitted snapshot entry and the session entry skill; Private host entry remains valid. During a child call derive the source from the actual current mission and its current captured generation, never `session.entrySkill`.
- A YAML source may call only its direct `allowedSkills`; a Java leaf has no declared children. Self-exclusion from discovery remains. Unknown/uncaptured target and undeclared target are denied independently of role permissiveness.
- Discovery resolves allowed names against the snapshot, validates the requested source matches the bound mission, and applies the same guard. It does not enumerate Public namespaces or all retained-generation members.
- Share the existing preparation visibility predicate with runtime; do not change preparation's reachability/RBAC split.
