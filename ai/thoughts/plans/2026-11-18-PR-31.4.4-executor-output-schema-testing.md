# Executor output schema testing plan

## Change summary

This plan verifies optional authored output schemas on YAML executor leaves through startup/preparation, public invocation, terminal failure, metadata and generation replacement. It accompanies `2026-11-18-PR-31.4.4-executor-output-schema.md` in the developer-approved Full 5-Step Pipeline. Planning has inspected source and tests and has run no verification commands.

## Impacted areas

- `YamlSkillCatalog` declaration applicability, compilation and child-evidence checks.
- `ExecutionCoordinator#publishExecutorResult`, shared `OutputSchemaValidator`, `OutputValidationPolicy` and `ExecutionStateService` outcome recording.
- Immutable `YamlSkillDefinition`, generation preparation/publication and invocation handoffs.
- `SkillDependencyValidator` effective schema resolution, forwarding, ordinary binding checks and fresh admission.
- Public `SkillTemplate`, `SkillReloader`, catalog metadata and observer events.
- Canonical raw/published completion evidence, output outcomes and failure linkage.
- Executor, output-contract, standard-schema and TypeSafe authoring topics and README routing/coverage.

## Risk assessment

The primary risk is accepting an invalid result after potentially side-effecting executor work. Tests must demonstrate failure before success publication and dependent execution, with exactly one business invocation. Other risks are validating raw rather than transformed output, changing formatting or numeric types, accidentally imposing an object root on transform-only results, inventing model correction, losing raw evidence, or selecting a replacement schema for already admitted work.

Application API signatures remain protected by the existing allowlist. Configuration and manifest behavior gains an optional field while preserving omission and transform-only semantics. Result text fidelity is a caller-visible transport obligation. Existing diagnostic shapes remain current-run formats. Internal public modifiers create no supported extension contract. The intentional removal is the obsolete blanket executor-schema rejection and tests that encode it. There is no supported SPI or historical diagnostic-reader obligation.

## Existing test coverage

- `ExecutorDeclarationTests` and `YamlSkillCatalogTests` currently include `output_schema` in executor forbidden-field tables. Those entries must be replaced by authored-profile tests while the retry prohibition remains.
- `OutputSchemaValidatorTest` and `StandardSchemaCompilerTest` establish strict complete JSON, root objects, constraints and numeric fidelity. Reuse their implementation without duplicating their entire matrix in executor integration tests.
- `ExecutorOutputTransformIntegrationTest` already exercises direct/ordinary/planned publication, bindings, scalar/null transform results, raw pass-through, one-call transform failure, diagnostic faults and retained transforms.
- `SkillGenerationManagerTest`, `SkillDependencyValidatorTest` and `SkillAdmissionContractsTest` establish structural catalogs, binding compatibility, forwarding and fresh admission.
- `DesignatedChildResultIntegrationTest`, declared-binding integration suites and `ExecutionCoordinatorOutputSchemaIntegrationTest` cover neighboring caller and model validation behavior.
- `LoomspanPublicSurfaceArchitectureTest` establishes the exact supported Java API. `ConsoleTraceFixtureCorpusTest` checks existing current Java diagnostic fixtures consumed by Console.

## Tests to add or update

### 1. Preparation and independent schema ownership

Location `src/test/java/ai/loomspan/internal/skill/ExecutorDeclarationTests.java` and the executor dynamic table in `YamlSkillCatalogTests.java`.

Use the real catalog, compiler and immutable definition. Existing configuration fixtures are sufficient. Mock no schema components.

- `acceptsExecutorOutputSchemaWithoutRetries` checks compiled schema retention, zero retries and detached manifest copies.
- `executorOutputSchemaUsesTheAuthoredObjectProfile` rejects scalar, array and nullable roots, empty schemas, unsupported keywords and malformed supported constraint values. Assert useful resource, skill and output-schema field context. Preserve ordinary shared null/missing declaration semantics through the real parser.
- `executorOutputSchemaRejectsEvidenceAndExplicitRetries` checks a valid immediate-root evidence expression, malformed/nested annotations, and explicit retry settings including null and zero both with and without a schema. An ordinary property named `x-loomspan-evidence` with a normal schema remains valid.
- Replace `output_schema` in the obsolete executor forbidden-field tables with these accepted/rejected schema cases. Retain every other forbidden declaration and its presence coverage.

Affected surface is Configuration and manifest contracts. The compatibility expectation is an optional schema with unchanged model schema profile and unchanged executor restrictions.

### 2. Effective schema metadata and ordinary binding rules

Location `src/test/java/ai/loomspan/internal/skill/SkillGenerationManagerTest.java` and `SkillAdmissionContractsTest.java`. Extend existing fixture patterns. Use actual generation preparation and dependency validation. Existing mocked registration discovery may supply a fixture executor, as these tests do not claim runtime invocation coverage.

- `executorAndForwardersExposeDeclaredStructuralOutputSchema` prepares a leaf and a forwarding chain, then compares effective schema JSON in tool descriptors, public catalog and registered catalog. Assert assertions, requiredness, descriptions and structure survive. The leaf owns the authored validator, forwarding parents retain none. No-schema executors and their forwarders expose null.
- `executorOutputSchemasParticipateInExistingBindingChecks` supplies closed known source paths with compatible and incompatible destination types and a missing source path. Acceptance and rejection follow existing bounded structural rules. No new parent-analysis algorithm is added.
- `forwardedExecutorContractChangesRequireFreshCallerPublication` publishes a foreign executor-backed producer schema, prepares a forwarding caller, changes the producer, and verifies fresh admission uses existing effective-contract comparison. Existing retained capture remains coherent. Use the existing preparation/admission helpers.
- Two leaves sharing one registration publish different schema structures independently. Assert metadata belongs to each leaf, then include real invocation in group 3 to show one leaf can pass and the other fail on the same executor text.

Affected surfaces are Configuration and manifest contracts and existing Application API descriptor behavior. Existing captured/fresh-admission rules are protected.

### 3. Exact result acceptance and publication order

Add `src/test/java/ai/loomspan/integration/ExecutorOutputSchemaIntegrationTest.java`, following `ExecutorOutputTransformIntegrationTest` with `ApplicationContextRunner`, `FixtureExecutor`, temporary YAML and the real public `SkillTemplate`. Use a local `MockWebServer` only for actual parent planning/tool requests. Mock neither validator, JSLT, execution coordinator nor child bindings.

- `schemaOnlyPublishesExactValidatedText` accepts an object containing probability 0 and 1, exact long decimal values where the contract allows them, and formatted whitespace. Assert the returned String equals the original raw String, with one executor call and no model requests. Inspect a PASSED outcome with attempt 1, retryCount 0 and maxRetries 0.
- `validatesTransformedObjectInsteadOfRawExecutorShape` returns the ticket's `answers.repeat.noul` envelope and projects the probability. The raw object would fail the closed published schema. Assert the transformed object passes, JSON number remains numeric, and raw/published evidence remains distinct.
- `sharedExecutorLeavesOwnDifferentResultContracts` returns the same ordinary text through two leaf declarations with different constraints and asserts independent success/failure.
- `schemaOmissionPreservesAllFourDeclarationCombinations` relies on the existing pass-through and transform-only parameterized tests for empty/plain/malformed raw text and quoted-string/scalar/null results. Add missing boolean/array coverage only if current tests lack it. Assert omission produces no schema outcome.
- Exercise one schema-bearing success with trace persistence disabled to prove diagnostic capture is not required for acceptance.

Affected surfaces are manifest behavior, caller result text and ephemeral diagnostics. Existing no-schema behavior is protected.

### 4. Strict invalid candidates and actionable diagnostics

Use parameterized tests in `ExecutorOutputSchemaIntegrationTest` with the ticket's closed numeric object schema.

- Schema-only candidates include blank text, plain non-JSON text, malformed JSON, two complete JSON values, trailing garbage, JSON scalar/array/null, wrong numeric type, below-zero/above-one values, present null, missing required key, misspelled key and an unexpected extra field.
- Both-fields candidates include string `"high"`, an out-of-range number and a missing `.answers.repeat.noul` that becomes present null. Add an expression omitting/misspelling the published key to distinguish `required` from `type`.
- Assert `SkillException` exposes the producing qualified skill and the issue location and keyword (`type`, `minimum`, `maximum`, `required`, `additionalProperties` or `invalid_json`) through the existing diagnostic outcome/exception chain. Retain the raw executor text and original candidate in their existing evidence/exception roles.
- Assert exactly one EXHAUSTED schema outcome, attempt 1, retryCount 0, maxRetries 0, one executor call and no provider call for direct execution. A successful transform followed by a schema mismatch retains succeeded transform status and raw evidence, with no successfully published `skillOutput`.
- Assert root trace failure linkage and one originating leaf failure. Ancestor/tool propagation may add their ordinary failure records, so compare authoritative failure IDs and origin rather than banning all propagation records.

These tests establish terminal behavior without a model retry path and preserve current-run diagnostic fidelity under ordinary resource limits.

### 5. Direct, ordinary-tool, forwarding and downstream consumers

Use the connected test fixtures from group 3.

- `allCallersReceiveTheValidatedCandidate` checks schema-bearing direct success, ordinary tool transcript content, planned `output_from` exact text and downstream `child_result` binding to a numeric input. Use the schema on the producing leaf and retain the parent's ordinary input/binding declarations.
- `schemaMismatchIsTerminalAcrossCallerRoutes` parameterizes direct, ordinary-tool and planned forwarding failures. A direct call makes zero provider requests. An ordinary call makes only its existing request selecting the tool. A planned call makes only its existing plan request. No correction/synthesis request follows the mismatch, and no successful tool completion appears for the invalid producer.
- `failedProducerPreventsDependentChildExecution` creates a plan with producer and dependent executor child, using a child-result input binding. Return an invalid producer result, then assert the dependent invocation count is zero and no accepted invalid source reaches the binding. Assert normal failed observer completion.
- `executorAndTransformFailuresKeepTheirExistingPaths` adds a schema alongside a throwing executor or failing transform. Assert the original failure, no schema outcome and no fallback. Existing transform integration tests continue to protect their full behavior.
- `diagnosticFaultsDoNotChangeSchemaAcceptanceOrAuthoritativeMismatch` follows the existing executor diagnostic fault seam. On a valid candidate publication returns the expected result, and on mismatch the schema failure remains authoritative. Limit injection to supported test diagnostic seams.

Affected surfaces are public invocation, ordinary tool/planning contracts and ephemeral diagnostics. Counts prove validation itself performs no additional business work.

### 6. Preparation rollback and captured schema generation

In `ExecutorOutputSchemaIntegrationTest`, use the real `SkillReloader` and `SkillInvocationHandoff` with one executor whose result can satisfy the old schema and violate the replacement.

- `retainedInvocationUsesItsCapturedOutputSchema` publishes schema A, creates a handoff, publishes schema B, then invokes both. Use the same result text that A accepts and B rejects. Assert old handoff success, fresh failure and exact generation IDs. Release the retained handoff in finally.
- `invalidSchemaPreparationRetainsTheActiveGeneration` attempts scalar-root, array-root and evidence-bearing candidates through `prepare`. Assert `SkillReloadException` with useful field context, unchanged active generation, and zero executor calls during preparation. Invoke the active leaf afterward to establish it still works.
- Real startup rejects invalid executor schemas through at least one `ApplicationContextRunner` case. This supplements the lower-level declaration tests and preparation boundary.

Affected surface is manifest lifecycle through the existing Application API. Publication remains atomic and admitted work retains its immutable generation.

## How to run

Use Java 21+ and Maven 3.9+. The environment has `mvn` and `JAVA_HOME` pointing to `C:/hamdev/jbrsdk21`, so Maven works even though `java` is absent from PATH. Commands below are PowerShell-safe. All test data is local. No live provider credentials or sibling pack checkout is required.

1. Red test before production edits

   `mvn '-Dtest=ExecutorDeclarationTests#acceptsExecutorOutputSchemaWithoutRetries' test`

2. Preparation and metadata

   `mvn '-Dtest=ExecutorDeclarationTests,YamlSkillCatalogTests,SkillGenerationManagerTest,SkillDependencyValidatorTest,SkillAdmissionContractsTest' test`

3. Executor connected behavior and lifecycle

   `mvn '-Dtest=ExecutorOutputSchemaIntegrationTest,ExecutorOutputTransformIntegrationTest,ExecutorInputTransformIntegrationTest,ExecutorInvocationLifecycleIntegrationTest' test`

4. Shared validator, model output, caller and diagnostic regression

   `mvn '-Dtest=OutputSchemaValidatorTest,StandardSchemaCompilerTest,OutputSchemaCallAdvisorTest,OrdinaryOutputAcceptanceTest,ExecutionCoordinatorOutputSchemaIntegrationTest,DesignatedChildResultIntegrationTest,DeclaredChildInputBindingsIntegrationTest,DeclaredOutputBindingsPlanningIntegrationTest,LoomspanPublicSurfaceArchitectureTest,ConsoleTraceFixtureCorpusTest' test`

5. Integrated suite after implementation and authoring changes

   `mvn test`

6. Diff hygiene

   `git diff --check`

The final independent review must run the new executor schema tests, preparation/metadata tests and architecture test in its own context, plus shared model/caller regression checks relevant to the actual diff. The full implementation run provides broader regression evidence. Review must investigate new findings or failures and broaden verification when needed. Record exact commands and actual counts/results. A full-suite failure requires attribution and a safe resolution or explicit escalation, never an unexplained completion claim.
