# Executor output schema implementation plan

## Overview

Implement optional skill-owned `output_schema` for YAML executor leaves. Validate the exact candidate String after the optional output transform and before any caller accepts it. Reuse the authored schema compiler, strict output validator, schema outcomes, captured generations and effective metadata resolver.

## Current state analysis

- `YamlSkillCatalog#validateDeclarationForm` rejects executor `output_schema` by presence. `loadDefinition` returns executor definitions immediately after input-schema validation, before model output/evidence preparation.
- `YamlSkillManifest#compiledOutputSchema` already compiles authored OUTPUT contracts using `StandardSchemaCompiler`. `YamlSkillDefinition` copies the canonical schema into its immutable generation-owned manifest.
- `StandardSchemaCompiler#compile` requires exact root `type: object`. The shared compiler checks evidence annotation placement, and `YamlSkillCatalog#compileEvidenceContract` checks expressions against direct children. Executor declarations have no allowed children.
- `ExecutionCoordinator#publishExecutorResult` is the common direct, ordinary-tool and planned-child publication boundary. It transforms once, preserves raw evidence, and returns the single String used by callers and bindings.
- `OutputSchemaValidator#validate` parses one complete JSON value losslessly, validates it, and returns a verdict without rewriting the successful String. `OutputValidationPolicy#schemaOutcome` produces existing PASSED/EXHAUSTED outcomes for one attempt and zero retries.
- `LoomspanOutputSchemaValidationException` is package-private below `internal.outputschema`. The coordinator lives in `internal.core`. Its constructor and existing diagnostic message already contain the qualified skill and first issue.
- `SkillDependencyValidator#resolveOutputSchema` excludes executor form from its authored-schema branch. Its existing recursion already propagates a selected child's effective schema through forwarding parents and applies existing binding/admission checks.
- `SkillGenerationManager` prepares before publication. The coordinator selects the definition from the invocation's captured generation. The existing definition copy and admission lifecycle supply the required reload semantics.

Source anchors and detailed current-checkout references are in `ai/thoughts/research/2026-11-18-PR-31.4.4-executor-output-schema.md`.

## Desired end state

| Leaf declaration | Published successful result |
| --- | --- |
| Neither field | Exact executor String, including empty or non-JSON text |
| Schema only | Exact original String after strict complete-JSON/object/schema validation |
| Transform only | Existing serialized JSLT result, with any JSON root |
| Both | Serialized JSLT result after object/schema validation of the transformed candidate |

Schema validation occurs once after successful executor work and optional successful transformation. A mismatch records one terminal schema outcome and fails the producing skill. The existing failure propagates through caller boundaries. No successful result or accepted child source is created from an invalid candidate. A dependent child remains unexecuted. Preparation rejects unsupported schema roots and executor evidence annotations. Explicit executor retry declarations remain forbidden.

## Implementation approach and decisions

1. Retain schema ownership on each immutable YAML definition. Reuse `validateOutputSchema` for executor preparation while assigning an implicit zero retry allowance for executor form. Retain the existing model default and validation behavior.
2. Compile the executor's evidence contract through the existing child-reference validation. All syntactically valid evidence expressions require direct children, and executor leaves have none. Thus every actual executor evidence annotation fails preparation without a second schema walker or field-name heuristic. The compiler already rejects invalid placements. A data property literally named `x-loomspan-evidence` remains ordinary schema data.
3. Reuse `LoomspanOutputSchemaValidationException` across internal packages by making its class public. Its package remains internal and outside the supported API. Avoid a parallel executor-specific exception or compatibility adapter.
4. Call `OutputSchemaValidator#validate(candidate, definition.outputSchema())` only when a schema exists, once after optional transformation. Use the existing one-attempt/zero-retry outcome policy and recorder. Never enter a model correction path.
5. Expose the authored structural schema by removing the executor exclusion from the existing metadata branch. Keep existing binding compatibility and fresh-admission rules as the single authority.

The unimplemented alternative would leave executor contracts unenforced and fails the ticket. Reimplementing schema checking, validation diagnostics, reload storage or metadata would duplicate existing authorities. No dead or unrelated abstraction was found that must be removed for this work. The obsolete executor-schema guard and its corresponding test expectations are removed in scope.

## Phase 2 — Validate at executor result publication

Modify `src/main/java/ai/loomspan/internal/core/ExecutionCoordinator.java` and the internal output-schema exception.

- Keep a reusable strict `OutputSchemaValidator` in the coordinator without introducing a bean or constructor extension point.
- Compute the candidate using the current optional transform. Retain existing executor/transform exception paths.
- Preserve raw executor evidence even when schema validation subsequently rejects the candidate. Record transform status independently of schema status. Emit successful `skillOutput` only after the candidate passes all declared result checks.
- With a schema, validate once, create a bounded existing `OutputSchemaOutcome` using attempt 1, retries 0 and the ordinary four-issue outcome bound, and record it with `ExecutionStateService#recordOutputSchemaOutcome`.
- On mismatch, throw the reused internal exception with candidate, issues and failure mode. Preserve the authoritative validation failure if a diagnostic write fails, following existing executor diagnostic containment patterns. Operational validator failures propagate as failures.
- On success, return the same candidate String. Omitting a schema creates no validation outcome and performs no extra parse.

Add `ExecutorOutputSchemaIntegrationTest` using the real public facade, real schema/JSLT/runtime paths, existing executor fixture and loopback model server. The testing plan defines failure routes, generation capture and diagnostic assertions.
