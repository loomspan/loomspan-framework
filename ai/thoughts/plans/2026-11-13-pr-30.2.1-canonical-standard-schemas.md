# Canonical standard schemas and lossless ingestion implementation plan

## Overview

Implement ticket `loomspan-pr-30.2.1-introduce-canonical-standard-schemas-and-lossless-ingestion.md` using one internal Draft 2020-12 compiler and NetworkNT 3.0.9 validator. Replace the declaration DTO dialect, preserve original schema/data values, validate the approved profile and annotation placements, and repair skill-document YAML precision before Jackson conversion. This is approved Full 5-Step Pipeline execution; Steps 2 and 3 share this planning context. Only the research artifact existed when planning began; there were no implementation changes to preserve.

The developer problem is that declarations, validation and schema conversion currently have different, sometimes lossy meanings. The shared compiler is framework responsibility because registration and every receiving boundary must agree on the contract. The new immutable compiled snapshot reuses existing generation ownership; it adds no registration service or application extension point.

## Current state analysis

- `pom.xml:52,93` already pins NetworkNT 3.0.9. Working Jackson 3 API examples exist in `docs/maintainers/probes/tbd-06/src/test/java/ValidatorTest.java`; they are retained evidence, not a production validator.
- `YamlSkillManifest.java:505,632` defines separate mutable input/output schema DTOs. Their coercing setters, string-only enums and reduced vocabulary cannot represent the accepted contract faithfully.
- `YamlSkillCatalog.java:801-1255` owns recursive declaration checks, including closure insertion, case folding and nested-array restrictions. These are superseded declaration behavior. The input object method also inserts closure; current source, rather than the historical input-open description in the ticket, establishes the legacy implementation.
- `YamlSkillCatalog.java:400-463` removes executor `config` before `valueToTree` and later restores raw config. `YamlValues.java:14-30` currently constructs decimals as floating point; `:33-66` owns cycle/expanded-value checks.
- `YamlSkillDefinition.java:43-76,109,159,236` provides registration copies, while `SkillGeneration` and `SkillAdmissionSnapshot` capture immutable definition generations. Preserve that lifecycle.
- Handwritten runtime input/output validators and schema projections remain consumers owned by later tickets. Deleting the obsolete declaration DTOs will expose those callers as intentional intermediate compilation failures.

## Desired end state

The production foundation accepts supported schemas, rejects unsupported declarations before evaluation, retains canonical annotations and exact numeric values, returns provider copies with only recognized schema annotations removed, and validates instances without coercion or mutation. It offers the same behavior for input/output/planning roles except the explicitly approved role restrictions. Skill YAML is JSON-safe before conversion; executor configuration retains its existing separate semantics.

Required evidence comes from normal root unit tests when the tree builds, plus an isolated focused run of the actual production foundation classes if downstream consumers prevent full compilation. The isolation must never make the normal project build appear green. The implementation and final review must record actual failures and restoration owners. Integrated consumer behavior is not certified by foundation tests.

## Scope and settled decisions

1. Introduce `ai.loomspan.internal.schema.CanonicalSchema` and `StandardSchemaCompiler` (nested enums/records may express role, declaration origin and diagnostics). The wrapper owns private defensive snapshots and the initialized NetworkNT schema. No mutable tree or evaluation context escapes. Use explicit INPUT, OUTPUT and PLANNING roles and AUTHORED/GENERATED origin, rather than a permissive global mode.
2. Keep raw authored trees in manifest schema fields using Jackson `JsonNode`, defensively copied on assignment/access. Remove `InputSchemaManifest` and `OutputSchemaManifest`, their legacy scalar deserializers if no longer used, and catalog structural validation implementations. Store canonical compiled snapshots in definitions at registration, reusing immutable snapshots during generation copies. Do not round-trip canonical schemas through the application-conversion mapper.
3. Catalog registration invokes the common compiler and translates its declaration failures through existing `invalidSkill`/`invalidNamedSkill` authoring diagnostics, retaining source, schema path and original detail. Definition accessor signatures become canonical internal schemas. Internal constructor changes are allowed; do not add compatibility overloads or retain old types for callers.
4. The schema walker visits only actual schema nodes: root, each value in `properties`, `items`, and schema-valued `additionalProperties`. It never interprets property names or values in annotation metadata as schema keywords. Use JSON Pointer escaping for locations; exact property names include casing, whitespace, dots, slashes and tildes.
5. Validate declarations using the bundled Draft 2020-12 meta-schema separately from profile checks and compilation. Permit the optional exact root `$schema` identifier `https://json-schema.org/draft/2020-12/schema`; do not infer other dialects. Reject references and other unsupported keywords before they can trigger resolution. Configure the registry so bundled standard meta-schemas work with remote retrieval disabled. Explicitly initialize validators before publishing the compiled snapshot.
6. Pin and document the 19 standard formats registered by NetworkNT 3.0.9: `date`, `date-time`, `duration`, `email`, `hostname`, `idn-email`, `idn-hostname`, `ipv4`, `ipv6`, `iri`, `iri-reference`, `json-pointer`, `regex`, `relative-json-pointer`, `time`, `uri`, `uri-reference`, `uri-template`, `uuid`. The inspected local sources JAR's `Formats.java` also contains nonstandard `alpha`, `alphanumeric`, `color`, `ip-address`, `phone`, `style`, `utc-millisec`; reject those and all unknown names. Use library validators and the default JDK regex implementation, with no custom format implementations.
7. Each validation creates an independent execution context with format assertions on and both evaluation limits explicitly zero. A completed validation returns full internal diagnostics; exceptions/operational aborts propagate as failures, never an empty error list or ordinary invalid verdict. No error-count budget, timeout or public knob is added.
8. Preserve exact numeric parsing in the shared schema JSON codec using BigDecimal for fractional JSON values. Skill YAML needs its own lossless numeric construction before tree conversion, including finite exponent forms and large integer values. Existing application conversion, canonical trace, planning codecs and ordinary Boot properties remain outside this codec change.
9. Preserve `YamlValues.read` and `documents` configuration behavior. Add a distinct lossless skill-document decoding entry point/helper used by catalog ingress. Remove/exempt only the actual top-level executor `config` subtree before the recursive JSON-compatibility check and conversion. Obtain that subtree using the existing ordinary YAML numeric construction, so its Java numeric kinds/domain values are unchanged; a second ordinary decode only when `config` exists is acceptable if needed. This is two construction policies at separate content boundaries, not two accepted schema dialects. Keep the existing timestamp-string rule, duplicate detection, alias/cycle and expanded-value controls in both paths. All non-config values must pass JSON key/value checks before `valueToTree`.
10. Extract the skill decoding/conversion seam into a small production helper independent of catalog runtime dependencies (for example `SkillDocumentValues` under serialization), returning the JSON-bound tree and separately retained config/presence. This makes the in-scope ingestion behavior directly executable even when downstream consumers block catalog compilation. Catalog still owns declaration-form checks and config top-level textual-key validation.

These choices settle the routine planning questions from research. There is no required developer decision.

## Supported profile details

| Area | Enforcement |
| --- | --- |
| Complete contracts | Root is an object schema with exact `type: object`; nullable roots, scalar/array roots and root `{}` are rejected. |
| Property schemas | Six ordinary types; explicit two-element type arrays containing one ordinary type and `null` in either order. No general unions. Plain `null` schemas are outside this property-tree profile. |
| Objects | Standard `properties`, `required`, boolean `additionalProperties`; omission remains open. Inputs additionally allow schema-valued `additionalProperties`. Do not require required names to have property declarations, reject differently cased names, or rewrite names. |
| Arrays | Homogeneous object-valued `items`, including nested arrays. Reject tuple/composition/reference features. |
| Shape-free values | `{}` at nested INPUT leaves, including input map values. Reject authored boolean schemas. GENERATED origin additionally permits `false` property schemas for ownership protection, without authorizing arbitrary boolean-schema locations. |
| Assertions | Scalar `enum` (including JSON scalar kinds and null), descriptions, supported formats, `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems`. Meta-schema validation checks keyword value shapes. Retain standard mathematical integer/numeric enum equality. |
| Unsupported | Unknown keywords, legacy `nullable`, schema-node `evidence`, old attachment fields/type, `default`, `pattern`, references/definitions/anchors, composition/conditionals/tuple schemas and unapproved assertions. Reject with the offending schema location. Unknown extensions are unsupported; do not remove arbitrary `x-*` from accepted schemas. Ordinary property names that equal a keyword remain valid data names. |

Do not add redundant custom instance validation. The walker restricts declaration vocabulary/role/placement; NetworkNT owns standard instance semantics and meta-schema keyword shapes.

## Recognized annotations

- `x-loomspan-attachment` is an INPUT string-leaf schema annotation, including explicit nullable strings. The exact object fields are `media_type` and `allowed_content_types`; retain supported media types `image`, `pdf`, `audio`, `video`, `file`, require a nonempty list of nonblank string content types, and reject malformed/unknown fields. Support immediate/nested properties, string array items, attachment fields under array-object items, and typed input map values. Keep surrounding standard constraints unchanged. MIME parser tightening and Resource adaptation are 30.2.4 work.
- `x-loomspan-runtime-ref-capable` is boolean metadata permitted only on GENERATED INPUT string leaves; authored use is rejected. Generation and native Resource/attachment behavior remain downstream. Provider copies remove this annotation at schema nodes.
- `x-loomspan-evidence` is one nonblank string only on an immediate root OUTPUT property. Preserve original expression text and exact property names. Reject root/nested/item/input/planning placements and non-string/blank values. Structural validation does not parse the expression grammar or resolve children.
- Provider copies deep-copy the canonical tree and remove only these recognized annotations at actual schema nodes. Preserve assertions, descriptions, similarly named ordinary properties and every other accepted value. Canonical data remains unchanged.
