## Overview

Offer a resolved callable as `namespace--local-name` to native provider function calling. Match returned names exactly against the callbacks bound to that request and invoke the captured callback. Plans and assigned worker actions use `namespace:local-name`. Preserve original model messages, argument strings and rich parts, with the resolved callable recorded separately in existing `capabilityName` metadata.

## Desired end state

For resolved child `order-support:find-order`, the actual provider HTTP request contains function name `order-support--find-order`. An exact returned call invokes that captured child. `order-support:find-order`, changed casing, a valid unoffered provider name and a callback offered only in another request all fail before side effects. Dispatch never decodes a provider name into a registry target.

The planner emits `capabilityName` values with colons. The assigned worker prompt shows `order-support:find-order`, and only a structured action carrying that exact assignment can execute it. A provider spelling or a different qualified target produces existing correction/failure behavior. Accepted plans and actions retain their original qualified strings and argument values.

Wire requests establish what the official adapter sends. Canonical response and continuation-request records retain the names exchanged with the provider. Tool lifecycle metadata and routes identify the resolved child with a colon. The same invocation establishes both representations.

## Implementation decisions

1. Render the provider function name inside `SpringAiToolCallbackAdapter` from `capability.metadata().identity().namespace()` and `.localName()`, joined with `--`. The declaration validator already enforces grammar, reserved substrings and the combined 64-character limit. Keep `BoundCapability.name()` as the Loomspan qualified reference used by planning, lifecycle and invocation.
2. Replace the internal wrapper name `CanonicalToolCallingManager` with `RequestBoundToolCallingManager` and update its direct callers/tests atomically. Its responsibility is request membership and preflight. Remove its identity parser and response-copy machinery. Returned provider names are opaque exact keys.
3. Preserve exact Framework inability handling by callback type. A callback named `loomspan_cannot_complete` must be the actual Framework control. A fake or conflicting binding is rejected. Keep the sole-control-selection rule and strict reason envelope.
4. Build application membership from the request callbacks and require exact `call.name()` membership for every complete returned tool selection before delegating the original `ChatResponse` object. Retain all-generation preflight and blank-argument rejection. Continue skipping partial streaming tool parts under existing behavior. The production delegate retains fallback disabled and uses only offered callbacks.
5. Validate callback/control bindings while resolving definitions, then return the delegate definitions directly. Remove the Loomspan qualified-name grammar check at this provider boundary. Provider spelling belongs to the adapter and request membership belongs to the manager. Internal tests that directly supply callbacks must use the spelling appropriate to the scenario.
6. Replace plan/action normalization terminology and redundant rebuilding with strict validation. The plan helper parses the supplied qualified string and returns that original string without `node.put`. `StepAction` exposes a validation operation for a `CALL_TOOL` selection, and the engine validates the parsed action without replacing it. Keep `SkillIdentity.parse` at these Loomspan protocol boundaries and exact visibility/assignment checks afterward.
7. Use existing resolved `capabilityName`, model `skillName` and frame `route` fields. The ticket needs coherent values and evidence, with no new trace payload schema. Raw record capture remains direct from Spring AI objects.

These choices reuse validated identities, existing bound callbacks, the Spring exact dispatcher, current worker validators and existing trace ownership. Removing the unreachable rename branches eliminates duplicate response construction and misleading normalization behavior. Reverse translation, global lookup and an additional identity abstraction would add a second target authority and conflict with the requested dispatch contract.
