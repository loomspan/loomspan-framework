# Generation-owned configured Java executor execution — implementation plan

## Overview

Implement ticket `ai/thoughts/tickets/loomspan-pr-28.3-generation-owned-executor-execution.md` through the existing namespace-generation owner, shared dependency policy and captured execution path. A YAML executor leaf is a callable Java skill whose declaration and operation data are YAML-owned; its reference-only Java registration and application configuration belong to the executor namespace generation. Remove obsolete REST execution and the redundant execution-kind translation.

Pipeline mode: Steps 2 and 3, selected profile **full**, approved by the developer with `proceed` on 2026-11-01. Starting production checkout was clean; the research artifact is the only preceding pipeline artifact. The ticket authorizes API/SPI/manifest/runtime breaks without shims. No developer decisions remain unresolved in this plan.

## Current State Analysis

PR 28.1 already supplies shared Java discovery/proxy invocation/result conversion. PR 28.2 supplies explicit YAML forms, the five-field public invocation record, immutable configuration and real startup ingestion. Runtime integration is absent:

- `SkillGenerationManager.java:99,229,305,439` initializes callable-only namespaces, rejects executor generation assembly, captures only callable references and freezes only callable registrations/REST handlers.
- `SkillDependencyValidator.java:40,64,314` already owns complete target overlay, reachable admission and namespace visibility, but traverses only callable edges.
- `SkillGeneration.java:70` assumes YAML definitions imply model/TypeSafe execution. `SkillAdmissionSnapshot.java:8` currently stores only selected generations.
- `DefaultSkillTemplate.java:166` validates input and admission outside capture locks, retaining the same snapshot for handoff/invocation.
- `ExecutionCoordinator.java:105,160` infers definition presence from kind and already shares Java direct execution with scoped authentication, reference resolution and bounded mission work.
- `CapabilityKind.java` has exactly one value per `SkillKind` and a `publicKind()` getter. It has no distinct execution behavior; remove it.
- `DefaultRegisteredSkillCatalog.java:34` also infers declaration source from kind. Definition ownership must become explicit independently of kind; comprehensive diagnostic provenance is assigned to PR 28.6.

The research's historical broad result identifies 54 remaining REST-runtime fixture cases across eleven classes. This is an investigation lead, not a current pass/fail result. Their orchestration/namespace assertions must survive migration to executor leaves.

## Desired End State

One namespace generation owns immutable callable metadata/definitions, its assigned fixed executor registrations and its executor configuration. Namespace replacement/removal/recreation uses existing leases, IDs, retirement and callbacks. Executor registrations never enter callable catalogs or tool lists. Same-role duplicates fail; cross-role same qualified names are valid.

Preparation checks the complete target candidate over foreign metadata without executing application code or retaining foreign resources. Publication checks only the target base. Capture atomically selects the root-reachable callable graph plus executor namespaces, and expensive validation/binding runs outside its monitor. Execution consumes the resulting captured registration, selected map and executor-generation ID without live lookup or rebinding.

Both Java declaration forms use one `SkillKind.JAVA` branch. Definition lookup depends on generation declaration ownership, not Java-vs-YAML classification. Public catalogs and validation classify executor leaves JAVA while retaining YAML definitions and exact original bytes.

## Implementation Approach and Decisions

1. Extend `SkillDependencyValidator` as semantic owner for exactly two roles: callable child and executor. Reuse SkillIdentity and one namespace-access rule, then apply role-specific existence/shape checks. A small internal role/result record is sufficient; no generic dependency framework.
2. Generation configuration is its own namespace map from existing ExecutorConfiguration, not a copy of foreign settings and not part of executor-managed resources. Assigned registrations are frozen once after shared discovery completes, and reattached on every target replacement/recreation.
3. The shared dependency owner validates annotation path syntax and map selection. Empty string is omission and returns an immutable empty map; reject whitespace-only/surrounding whitespace and empty dot segments; select exact case-sensitive keys without literal-dot fallback. Explicit absent/null/non-map selection fails. Domain keys/values are untouched.
4. Validate fixed candidate executor declaration paths and explicit own configuration references during startup/preparation, including executor-only candidates; this gives complete-candidate binding rather than a latent invalid fixed registration. Foreign checks are limited to references reached from candidate callable roots. Admission validates/binds only root-reachable executor dependencies; retaining a namespace is never a reason to validate its unrelated callables or dependencies.
5. Separate raw capture from validated execution without mutating a snapshot. `validateAdmission` should return an immutable snapshot containing the same entry/generations plus per-executing-skill executor bindings (registration, selected map, executor-generation ID). `DefaultSkillTemplate` uses that returned snapshot in PreparedInput; the original Capture lease still owns the exact same generation set. Update internal callers/tests directly. A narrowly named internal binding record avoids exposing runtime graphs through the public invocation record.
6. Preparation may compute the same binding results to establish validity, but must discard foreign bindings rather than store them in the candidate. Admission resolves anew against its selected generations; invocation only consumes its stored result. This is one resolver reused at distinct lifecycle boundaries, not three binders.
7. Capture follows callable edges recursively; an executor edge only selects/retains the executor namespace. It must not enqueue the executor identity as a callable or visit other definitions in that namespace. One selected map gives coherence when both edge roles reach the same namespace, including cycles across callable namespaces.
8. Lookup an optional YAML definition directly in the target generation. Its explicit form distinguishes model/TypeSafe/executor argument construction while SkillKind controls execution. In the shared Java branch resolve input references once, then invoke either callable typed binding or construct SkillExecutorInvocation from the admitted binding and definition. Both converge on existing JavaSkillInvoker, scoped authentication and MissionWorkExecutor.
9. Remove CapabilityKind because its entire inspected responsibility is one-to-one translation; use public SkillKind internally too. Do not add a provenance value to replace it. Definition ownership/form is already sufficient for Framework routing and source retention.

## Phase 1: Generation ownership and shared two-role resolution

### Changes Required

- `SkillGenerationManager`, `SkillGeneration`: freeze fixed executor registrations; initialize the union of callable/executor namespaces; store exact target configuration per generation; carry fixed registrations through replacement/recreation. Remove handler discovery/counting and unused bean-factory dependencies from constructors/autoconfiguration.
- `SkillDependencyValidator`: accept target executor registrations/configuration along with complete declarations, overlay foreign metadata excluding the old target, and share identity/visibility checks between two roles. Validate annotation paths and explicit map selections here. Preserve existing callable contract/input/output validation and document-issue suppression.
- `SkillGeneration`: validate executor definitions as JAVA declarations while preserving definitions; separate callable and executor key maps, immutable values and ownership assertions. Configuration must survive even without provider runtime/resources.
- `ExecutorConfigurationManagerTests`, validator/generation/startup tests: replace REST no-execution counters with annotated executor counters and assertions on generation data.
