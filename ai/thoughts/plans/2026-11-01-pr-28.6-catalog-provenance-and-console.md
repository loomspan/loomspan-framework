# Catalog execution kind and declaration provenance implementation plan

## Overview

Make the diagnostic catalog describe one callable skill with its actual execution kind and explicit declaration provenance. Executor YAML is Java execution with an authored YAML declaration and a referenced Java executor, rather than either a YAML execution or an annotation-only Java declaration. Move Framework, Go, browser, MCP, TypeScript and current fixtures together.

Pipeline: full, developer approved with “proceed” on 2026-11-01. Initial checkout was clean; the research artifact is the only prior addition. No developer decision remains outstanding.

## Current State Analysis

- `SkillGenerationManager.java:242-251` already classifies executor definitions JAVA, but constructs `SkillSource` with only a source label. `SkillDependencyValidator.CheckedSet` already contains resolved executor registrations keyed by callable name; it is the authoritative preparation-time source for executor identity and implementation diagnostics.
- `DefaultRegisteredSkillCatalog.java:33-45` finds actual definitions correctly, then incorrectly labels all non-TypeSafe definitions YAML and drops executor/Java provenance. Public `DefaultSkillCatalog` already copies `SkillKind` correctly.
- `RegisteredSkillEntry.java:6-39`, HTTP DTOs/mapping, Go raw-field and service validation, MCP schemas/text and TS unions encode the old Java-versus-YAML exclusivity. These are current diagnostic contracts, not supported application APIs.

- PR 28.5 failure semantics and current trace writer/readers are implemented. This work does not alter or duplicate that failure representation.

## Desired End State

The diagnostic wire contract replaces overloaded `source` with required `kind` and `declaration`. `kind` is the existing execution classification (`YAML`, `JAVA`, `TYPESAFE`), derived from `CapabilityMetadata.kind()`. `declaration` describes only where the callable was authored (`YAML` or `SKILL_METHOD`); it is not another execution classification or public Java API.

| Callable form | kind | declaration | Required location fields | Detail content |
| --- | --- | --- | --- | --- |
| Model manifest | YAML | YAML | sourcePath | original yaml, outputSchema |
| TypeSafe manifest | TYPESAFE | YAML | sourcePath | original yaml, outputSchema |
| Executor manifest | JAVA | YAML | sourcePath, executorName, beanName, method | original yaml, outputSchema: null |
| Annotated method | JAVA | SKILL_METHOD | beanName, method | outputSchema: null |

`executorName` is the resolved canonical qualified executor identity, even when YAML authored a local reference. Authored reference spelling stays visible in unchanged YAML. `registeredName` remains the callable's qualified identity; same-name callable/executor roles remain separate. `sourcePath` keeps existing descriptive path/opaque-label behavior and never becomes an invocation alias. Bean and method describe the registered Java implementation through existing discovery metadata, preserving proxy-aware discovery behavior.

Summary has registeredName/kind/declaration and applicable locations, plus the existing transport href where appropriate; it never has yaml or outputSchema. Detail additionally has yaml only for YAML declarations, and always has nullable outputSchema using existing schema semantics. Nonapplicable fields are omitted, not supplied as null/empty placeholders. All three manifest execution kinds can have original YAML; Java execution by itself never forbids it.

Validation admits exactly the four rows. Unknown kinds/declarations, REST, missing required locations, executorName on model/TypeSafe/SkillMethod, and incomplete Java implementation pairs fail. YAML declarations require nonblank sourcePath and original YAML; method declarations forbid sourcePath/yaml/executorName. Model/TypeSafe forbid Java locations. Go raw presence validation continues rejecting nonapplicable fields even when null/empty; it must branch on declaration and kind rather than JAVA alone. No old-source fallback is introduced.

### Key Discoveries

- `SkillGeneration.java:105-117` constructs both catalogs from immutable capabilities/definitions, so existing snapshots are the right owner; no executor catalog or lifecycle is needed.
- `SkillDependencyValidator.java:118-123` records the resolved registration under the callable key. Copy only identity/bean/method strings into diagnostic metadata. Do not copy foreign configuration, access policy, generation leases, or invokers into callable metadata.
- `ConsoleRestFixtureCorpusTest.java:165` emits executor YAML under the stale `skill-rest-detail.json` name. Rename that skill fixture to `skill-executor-detail.json` and update readers; keep generic transport names.
- Go DTO `UnmarshalJSON` validation is a separate consumer from service value validation (`dto.go:137-189`). MCP has another explicit DTO mapper and published JSON Schema union.

## Implementation Approach

Reuse the existing `SkillSource` diagnostic metadata and definition ownership. Extend it with nullable executorName; update all internal constructors directly. For an executor definition in `prepareCatalog`, read its checked binding and create SkillSource with original declaration label plus resolved executorName/beanName/method. This is an immutable diagnostic description of fixed registration identity/implementation, not a retained foreign configuration or execution binding. Model/TypeSafe and SkillMethod retain their existing source data. Actual YAML membership determines declaration; metadata.kind determines classification. No parsing YAML to infer execution.

Use strings or an internal-only two-value declaration type as appropriate within the diagnostic owner, but do not duplicate SkillKind. Wire values and matrix above are fixed. Prefer one location-validation owner in Java and one shared Go value validator plus its necessary wire-presence check. Preserve source decoding and schema generation.
