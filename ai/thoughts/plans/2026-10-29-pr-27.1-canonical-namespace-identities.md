# PR 27.1 Canonical Namespace Identities — Implementation Plan

## Overview

Implement the accepted identity and immutable namespace-catalog foundation. A declaration remains a local name; its authoritative owner produces exactly one canonical `namespace-localName` identity. Parse once at preparation or operation entry, retain a structured internal value, and use its canonical spelling for semantic names and keys. Preserve authored prompts, sources, expression text, and diagnostic evidence verbatim.

## Desired End State

Every valid identity has an ASCII namespace and local component, separated by exactly one hyphen. Namespace is lowercased with locale-independent semantics, local case is preserved, and no input is trimmed, encoded, truncated, or repaired. Namespace length is 1–32; identity length is at most 64, including the separator. Local declaration grammar independently remains `[A-Za-z_][A-Za-z0-9_]{0,63}`. Thus a valid standalone 64-character local declaration can still fail identity construction; `default` leaves 56 local characters.

One namespace owns each immutable executable generation and public catalog, including an empty catalog. Capability keys equal canonical metadata names; definition keys equal identity constructed from authoritative generation ownership and the local manifest name. Namespace ownership is validated rather than inferred from the first capability. Catalogs retain the opaque owning generation ID, contain canonical descriptor names, normalize lookup namespace case, return empty for valid absent/foreign identities, and reject malformed lookup arguments. Candidate catalogs/feedback include only the target's supplied declarations and fixed Java registrations.

## Implementation Approach

Reuse immutable generation/catalog/validation machinery. Introduce only the missing shared internal structured identity value, preferably `ai.loomspan.internal.core.SkillIdentity`, with canonical namespace and local-name components, `parse(reference)`, declaration construction from owner/local component, namespace validation/normalization, and one formatter. Keep constants/grammar/length rules there; remove duplicated local-reference regex checks and formatters. Tests may name concrete methods according to final implementation.

Retain the structured value in prepared objects that own identities/references, rather than reparsing canonical strings in getters or invocation loops. Existing String-facing semantic methods can format that stored value for current consumers. This is internal collaboration, not a new application extension API. For records, change components or choose an immutable class when necessary; do not create a global side map/cache of parsed names.

## Phase 2: Preparation parsing and canonical contract comparisons

### Changes required

1. Thread authoritative namespace into `YamlSkillCatalog` preparation, `YamlSkillDefinition`, manager check/preparation/feedback, and generation construction. Startup declarations have owner `default`; internal non-default preparation must be testable explicitly. Ownership must not be an authored manifest field or inferred from references.
2. Validate every declaration's complete identity before executable/tool filtering, including REST, TypeSafe and otherwise unoffered declarations. Keep local manifest `name` intact and store the constructed identity separately. Index duplicates/definitions/capabilities/schema maps by canonical identity.
3. Parse every authored allowed-child, optional child, forwarding target, input-binding producer and output-binding producer during preparation. Retain identity in `AllowedSkillConstraint`, bindings, definition forwarding, and compiled evidence leaves as appropriate. Freeze output bindings once rather than reconstructing reference-bearing objects on every access. Compare structured identities for duplicates, direct-child/self checks, forwarding and schema/binding resolution. Canonical String views may serve existing runtime maps without reparsing.
4. Extend evidence expression tokenization to allow a complete qualified reference as a leaf, then validate through the shared parser. Boolean operators, whitespace between tokens, precedence and diagnostic columns remain. `and-search`/`or-search` are identities, while bare `and`/`or` remain operators. Preserve original expression source; normalize only semantic leaves.
5. Filter fixed Java registrations by checked owner for feedback and executable generation. A non-target fixed registration must not enter candidate catalogs/feedback or cause a local collision. Preserve warnings, immutable results, empty metadata on errors and incomplete-proposal secondary-diagnostic suppression. Known valid diagnostic skill fields use canonical identities; invalid/unknown identities retain existing unavailable handling plus original raw error evidence.
6. Preparation captures canonical REST skill name and candidate generation ID in the existing closure. Validation must not allocate/reserve IDs, construct runtime/providers/REST handlers, invoke Java bodies or alter retirement/publication state. Preserve globally unique opaque manager IDs.

## Phase 3: Namespace generation/catalog and acquisition API

### Changes required

1. `SkillGeneration` explicitly owns canonical namespace; all constructors require ownership. Validate every capability belongs to it and each key equals `CapabilityMetadata.name()`. Validate definition owner/key against namespace plus local manifest name and matching capability kind. No local-key alternate path. Ensure any supplied catalog agrees on namespace and generation ID, or remove redundant catalog injection if unused rather than accepting contradictory ownership.
2. `DefaultSkillCatalog` constructor takes owner plus opaque generation ID, validates metadata ownership and uniqueness, copies sorted unfiltered descriptors and schemas, retains no runtime/generation lease. Add `SkillCatalog.namespace()`. Lookup parses once, canonicalizes namespace only, and searches this frozen map; foreign and unknown return empty; malformed fails. Empty catalog still returns owner and ID.
3. Replace `SkillReloader.snapshot()` with `snapshot(String namespace)` and remove injected startup catalog bean. Read namespace once, select generation once, reject missing/mismatched owner. No fallback, alias, live proxy or fresh acquisition on individual lookup. PR 27.2 supplies registry/removal integration.
4. Preserve candidate `generationId()`/`snapshot()` semantics; test new candidate ID differs from captured base and snapshot ID matches candidate even before publication/after close where currently metadata access is allowed. Retaining a catalog adds no executable resource ownership.
5. Update supported consumer tests to acquire through reloader with explicit `default`, use returned qualified descriptor names, and assert no startup catalog bean. Update direct test fixtures/builders for explicit owner/canonical keys; migrate touched production callers without new shims.
