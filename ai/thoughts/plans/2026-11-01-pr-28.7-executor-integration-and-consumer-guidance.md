## Implementation approach and alternatives

Add one focused application integration class, retain earlier owned tests, and supply a complete separate-application quickstart. A documentation-only finish would leave application I/O/reference composition unproven. Rebuilding all existing boundary tests in one giant fixture would duplicate already-meaningful suites and obscure ownership. A new examples module or Framework HTTP client is unnecessary: use the existing docs application pattern, JDK HTTP facilities in application code, and test-only local servers.

No new state/dataflow semantics are selected. Business inputs remain explicit, trusted IDs/caller come from captured execution, and immutable map/list containers retain ordinary leaf identity. Consumers own external side effects, I/O bounds and resources. The new tests must not obtain success through bypassing input validation, Spring proxies, standard manager processing, or live configuration rebinding.

Every necessary role difference must have a recorded concrete requirement and simplest shared alternative:

- Callable schema derives from reflected Java parameters; executor callable schema comes from YAML. Reflecting the invocation record would expose internal execution metadata as business input.
- Callable arguments bind typed parameters (including resource materialization); executor arguments construct the five-component record with preserved map/resource leaves. Both converge on the same managed invoker/result/failure path.
- Callable methods enter the callable index; executors enter the reference-only index, allowing equal identities across roles without direct executor callability.
- Executor annotation declares optional configuration path and requires exactly one invocation parameter; callable annotations require their own description/parameter contract. No separate scanner, security evaluator or resource lifecycle is justified.
- Executor YAML policy composes with captured Java policy; an annotation-only callable has only its captured Java declaration policy. Shared conjunction evaluation handles this distinction.

Resolve concrete in-scope duplicate/obsolete paths rather than inventing abstractions. If none are found, record evidence and leave sound production owners intact. Do not add tests that merely count filenames or freeze internal decomposition.
