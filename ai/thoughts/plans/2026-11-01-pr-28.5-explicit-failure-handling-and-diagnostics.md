## Desired end state and settled technical decisions

### One internal policy and narrow wrapper normalization

Extend the existing `SkillFailurePolicy`, making it accessible to internal
runtime/Spring AI packages as necessary; a Java `public` declaration in
`ai.loomspan.internal` adds no application API. Keep the designated subtype
check in this one policy. Its transparent set is exactly the concrete existing
infrastructure types: `InvocationTargetException`, `UndeclaredThrowableException`,
`ExecutionException` from worker futures, and Spring AI `ToolExecutionException`
from function callbacks. Unwrap only these types, with null/self/cycle/depth
protection. No `CompletionException` or generic cause-transparent category is
selected without actual production evidence.

Normalize where those boundaries already propagate failures, using the same
policy rather than separate `instanceof RecoverableSkillException` checks.
Keep future/callback outer diagnostics available in stack capture. Ordinary
application wrappers, including `SkillException` and `IllegalStateException`,
stop normalization and are terminal even with a recoverable cause. Do not walk
their causes for classification. No blacklist of terminal exceptions is needed:
only the designated recoverable subtype qualifies. Existing cancellation and
shutdown precedence is checked by its lifecycle owner before propagation and
must not be replaced by normalization of an unrelated worker failure.

### Standard feedback at the existing dependency hook

Configure the existing Spring AI manager's exception processor in production
assembly. It uses the shared policy on the received callback wrapper. Terminal
failures propagate (with errors and causes retained); designated failures return
feedback containing explicit failed/correction-permitted meaning and the exact
designated message. Use a serialized map such as
`{"status":"failed","correctionPermitted":true,"message":"..."}`; this
is tool feedback only, with no new Java result/outcome type. Serialize normally
so decoding preserves whitespace, Unicode and line breaks; never substitute
cause text, a stack, or a default message. The existing `ToolResponse` ID/name
identify the failed call; tests must assert them alongside the feedback body.
Retain `CanonicalToolCallingManager` and its complete-selection validation.

Neither the Java invoker nor capability invoker returns feedback as a successful
value. No retry engine, outcome wrapper, new quota, or processor bean override
contract is added. Step actions still invoke their bound capabilities directly
and propagate failures; existing invalid-action correction remains separate.

### Canonical field contract and identity

Keep the existing error record and payload model. At canonical recording emit:

| Location | Field | Meaning |
| --- | --- | --- |
| Payload | `classification` | Required `RECOVERABLE` or `TERMINAL`, assigned by the shared policy |
| Payload | `exceptionType` | Effective normalized throwable class |
| Payload | `exceptionMessage` | Effective throwable's exact nullable message; required nonblank String for `RECOVERABLE` |
| Payload | `message` | Existing contextual summary, distinct from exception text |
| Payload | `diagnostics` | Existing bounded stack descriptors with explicit truncation |
| Metadata | `failureId` | Existing stable identity |
| Metadata | `causedByFailureId` | Optional nearest already-recorded cause identity for a new application wrapper |
| Metadata | `attemptId`, `retrySequenceId` | Existing independent provider correlation |

Keeping payload `message` avoids a gratuitous contextual-field rename;
Console's existing `contextSummary` maps to it. Consumers expose explicit
`classification`, `exceptionMessage`, and optional `causedByFailureId` alongside
existing fields. Nullable/empty terminal exception messages must not be changed
into another throwable's text. `TraceFailureMetadata` uses the shared policy so
other existing failure projections get consistent details; canonical recording
overwrites any caller-provided classification/exception facts with authority.

Deduplication is by effective normalized throwable object identity only. Map
the normalized object and incoming transparent wrapper to that record so either
recording order reuses identity. Do not use type/message equality. For a new
application wrapper, inspect a bounded, identity-visited cause chain only for
the nearest already-recorded cause link and provider correlation; never return
that cause's failure ID as this wrapper's ID. Normalize recognized wrappers
when resolving an existing cause identity. Preserve the first record and origin.
Keep independent provider correlation even when several distinct failures share
an attempt. No recursive recording of all causes or new journal/graph is added.

Strict current Go readers require a valid classification and the recoverable
message contract, reject malformed optional links and links to a missing or
non-earlier recorded failure, and retain existing diagnostic validation.
They do not infer semantics from Java names. Completion's existing `terminal`
Boolean continues to mean “selected by terminalFailureId”; it is independent
of failure classification. A recoverable failure may be completion-linked in
direct/step execution; a terminal-classified provider failure need not be the
completion failure after a successful surrounding execution. Do not reject
these combinations or claim correction from them.

### Consumer rendering

Render recorded classification explicitly as “Recoverable failure” or
“Terminal failure,” with a separate completion-link indication when applicable.
Render the exact exception message separately from the context summary, and
offer the recorded cause link through existing failure navigation when present.
Do not label an unlinked failure “Recovered.” Keep stack content inert, with
existing progressive loading, byte limits and truncation labels. The journal
and observer summary carry classification/message/link facts where applicable,
without removing or extending `ExecutionJournalProjector`'s existing field-name
exception. Canonical data and feedback receive no content rewriting.

## Design tradeoffs and reuse

The framework owns exception meaning and controls; the model cannot infer these
facts reliably. Consumers need an authoritative record, not a second classifier.
Reuse the existing policy, Spring AI processor hook, capability failed recording,
session identity map, provider map, stack capture, metering, and projection/query
pipelines. New payload facts and one optional cause link fill the actual gaps;
no new evolving execution state is necessary. Trust/access boundaries do not
change. Business inputs and diagnostics retain content fidelity.

Doing nothing leaves broad feedback and identity conflation. A terminal-exception
list duplicates policy and misses future controls. Replacing the manager adds
unnecessary orchestration. A new failure graph or result wrapper adds state and
would threaten existing success accounting. All are rejected by the ticket.
Remove the obsolete arbitrary-cause identity reuse and “Recovered” inference,
and update tests that protect them. No unrelated dead-code cleanup is selected.
