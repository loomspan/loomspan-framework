## Current State Analysis

- `TypeSafeClient.java:35-75` owns one pooled Apache client per connection,
  appends `/v1/systemone`, retains prefix paths, and disables retries/redirects.
  `pom.xml:90` explicitly declares HttpClient 5; effective dependency management
  and the claimed 5.6.1 timeout defaults must be checked during implementation.
- `TypeSafeExecutor.java:30-147` resolves one request, reserves/traces every attempt,
  retries through existing policy, records successful-response usage before
  extraction, and returns complete object-valued answers without schema checks.
- `NamedAiConnectionRegistry.java:30-40` allocates native transport inline before
  retry-policy/runtime construction. A failure before assignment to `runtime`
  leaves its catches unable to close that client. `:55-63` drops a generic cause;
  `:102-109` drops cleanup exceptions. Existing registry test
  `genericGeminiConstructionFailureNamesOnlyApplicableSettings` asserts no cause,
  which protects an obsolete internal diagnostic behavior, not supported API.
- TypeSafe client tests protect routes, configuration, usage conversion, real
  cancellation, configured/omitted timeouts, and bounded error reads. Integration
  tests protect large results on both prefixes, 529 retry, extraction failure,
  quota stopping, generation capture, HTTP/backoff cutoff, and public invocation.
  Missing focused matrices include disabled/exhausted retries, terminal native
  HTTP statuses, error-body accounting, and unusable successful usage end to end.
- The Java native success corpus, Go content-range assertions, and TS model detail
  tests already understand native JSON/text. Native failure and native capture
  states need explicit evidence alongside existing shared trace machinery.

## Implementation Approach

Keep the existing transport/executor as the semantic authority. Strengthen the
single registry's ownership at allocation boundaries, retain diagnostic chains,
and test actual observable sends/usage/capture. The alternative of duplicating
native plumbing would enlarge the framework without solving an unmet contract.
Pure test-only work would leave known construction evidence/ownership defects.
No speculative abstraction is justified.

## Phase 1: Construction ownership and diagnostic fidelity

### Changes Required

`src/main/java/ai/loomspan/internal/autoconfigure/NamedAiConnectionRegistry.java`:

1. Resolve native retry policy/other potentially failing pure settings before
   allocating the native resource. Retain an explicit local reference to any
   allocated native client until ownership is safely represented by `runtime`
   and then the built map. On failure close that allocation exactly once,
   including the pre-runtime-assignment case. Keep chat/native cleanup in the
   existing concrete registry; no provider factory SPI or parallel lifecycle.
2. Attach the original RuntimeException as the contextual IllegalStateException
   cause. Preserve SafeAiConnectionConfigurationException identity and context.
3. Attach cleanup exceptions as suppressed evidence on the primary construction
   failure instead of discarding `destroyModels` results. Continue cleanup of
   all resources even after one close fails. Keep normal destroy idempotent.

Tests: add failing cause/suppressed-cleanup tests first; replace the obsolete
`hasNoCause` expectation directly. Prove native cleanup after a later connection
fails and no allocation survives a post-allocation construction failure.
Prefer existing Mockito support plus narrowly scoped reflective observation of
the actual Apache pool over a production test-only factory. Pure validation
before allocation is also executable assurance for that particular leak path.

### Automated Success Criteria

- Registry construction failures retain cause and cleanup errors, and all acquired
  chat/native resources close; normal repeated destroy still succeeds.
- Focused registry/client tests and `LoomspanPublicSurfaceArchitectureTest` pass.
