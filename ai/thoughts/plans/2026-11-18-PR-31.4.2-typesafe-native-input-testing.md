# PR 31.4.2 native TypeSafe input testing plan

## Change summary

Decisions receives a complete native request through the supported v1 invocation
input. A business-input leaf may use Framework's existing JSLT transform first.
TypeSafe leaf templates, mapping and connection overrides retire together.
Provider request validation, complete JSON responses and transport behavior remain
owned by the pack.

This is Step 3 of the approved `full` pipeline, continuing directly from Step 2.
The governing implementation plan is
`ai/thoughts/plans/2026-11-18-PR-31.4.2-typesafe-native-input.md`.
Planning performs no test execution or source edits.

## Impacted areas and risk assessment

| Area | Risk and required proof |
| --- | --- |
| Native request preparation | Old source ignores native input as a complete request. Prove input is the sole request source and validated before send. Preserve numbers, Unicode, null and native nested descriptions. |
| Retired leaf config | A stale key could silently affect the request or connection. Exercise each key with a valid native input and usable namespace settings, assert its exact config path and zero HTTP sends. |
| Executor settings | Removing precedence must preserve required credentials, URL validation/default/prefix, exact values, snapshot isolation and retry capture. |
| Recipe transform | Misplaced `.ticket`, invalid JSLT or changed question criteria could pass ordinary input validation yet send a wrong request. Capture real HTTP from the installed pack. |
| Parent composition | Existing fully bound children must retain receiving-input validation and result selection. Preserve missing and wrong-type answer rejection. |
| Shared fixtures | Lifecycle/accounting/diagnostic tests call the old config helper. Migrate their declarations and inputs while retaining their substantive assertions. |
| Documentation | TypeSafe snippets and qualification identities can drift. Check changed claims against production and tests, and identify current tested artifact provenance accurately. |

The compatibility classification in the implementation plan governs this matrix.
The existing closed Application API remains in use. The ticket authorizes the
TypeSafe Configuration and manifest contract break and removal of internal mapping
code. Existing current-run diagnostic fidelity and lifecycle obligations remain.
This work changes no Java-to-Go protocol or Console compatibility marker.

## Existing test coverage

- Pack `TypeSafeRequestTest` covers mixed native forms, finite/precise numbers,
  Resources, cycles, unsupported values, model/questions validation and old pointer
  behavior. Replace pointer-only expectations with input-source and obsolete-key
  checks. Keep applicable native validation coverage.
- `TypeSafeSettingsTest` covers present-value selection, URL validity, verbatim
  credentials, defaults and detached capture. Convert these to the sole executor
  map while keeping relevant value cases.
- Existing pack transport tests exercise request bodies, authentication, retries,
  redirects, decoding, timeouts, cancellation, response fidelity and diagnostic
  faults. Update invocation construction without weakening those checks.
- Installed-JAR `TypeSafeConsumerTest` covers discovery, native primitives,
  validation, responses, retry/redirect and trace evidence. It needs direct-native
  versus transformed recipe equivalence and explicit retired-key rejection.
- `CompositionConsumerTest` uses actual `triage`, `assess` and `parent` resources.
  It already exercises `/answers/repeat/noul` and invalid bound answers.
- `PublicationConsumerTest` exercises concurrent old/new endpoints, keys, retries
  and retained generations. Retain the executor-owned case as the current contract.
- `LifecycleConsumerTest`, `AccountingConsumerTest` and
  `DiagnosticFaultConsumerTest` provide regression coverage for migrated helpers.
- `ConsoleConsumerTest` is opt-in, currently guarded by its Console profile.
  Update its fixtures if affected. This ticket changes no Console protocol and
  ordinary acceptance does not require rebuilding or rerunning that separate
  qualification. Preserve its opt-in condition and executable declarations.
- Existing Framework `ExecutorInputTransformTest`,
  `ExecutorInputTransformIntegrationTest`, `ExecutorDeclarationTests` and
  `ExecutorConfigurationTests` protect the prerequisite and general config path.

## Tests to add or update

### 1. Native request source and provider validation

- Type is unit, in `TypeSafeRequestTest` in Extensions.
- Pass complete native input with `model`, state and Choice/Noul/Score questions.
  Assert exact serialized structure and detached copying. Include nested text,
  arrays, present nulls, escaped keys, BigDecimal/BigInteger and finite numbers.
- Preserve existing local Resource admission tests with Resources embedded in
  native input. Assert remote/unsupported Resources are rejected before opening
  them, URL strings remain text, cycles and nonfinite numbers fail, and the body
  limit remains in force.
- Missing/blank model, missing or invalid state, empty/malformed questions,
  unsupported type or provider field and invalid criteria fail at `input...`.
  Copy existing relevant invalid matrices instead of creating a second validator.
- Reject each of `request`, `bindings`, `api_key`, `base_url` and an arbitrary
  unknown leaf key. Include null and empty retired values, since their presence
  must be rejected. Assert field paths rather than exact whole messages.
- Reject unknown executor keys under `executorConfig`, preserving its supported
  two-field contract.
- Affected surfaces are Configuration and manifest contracts, native serialized
  request and internal implementation. Old mapping is intentionally removed.

### 2. Sole captured connection settings

- Type is unit, in `TypeSafeSettingsTest`, plus migrated transport tests.
- Supply only the captured executor settings. Assert default URL, path prefixes,
  slash handling, exact credentials and immutable captured result.
- Preserve invalid API-key and URL cases, including null, blank, non-string,
  control characters, user-info/query/fragment, bad scheme/host/port and invalid
  syntax. Errors identify `executorConfig.api_key` or `.base_url`.
- The original transport still captures once per send, uses the same body across
  retries and keeps its existing retry, timeout and cancellation assertions.
- Affected surfaces are Configuration and manifest contracts and internal
  settings selection. Leaf precedence expectations retire.

### 3. Installed recipe and direct native equivalence

- Type is installed-JAR integration, in `TypeSafeConsumerTest` or a focused peer
  beside it under `examples/support-triage/src/test/java/ai/loomspan/examples/triage/`.
- Publish the actual migrated triage resource with valid namespace settings and
  existing authorization. Invoke with its business ticket. Capture the local HTTP
  request and assert exact `/prefix/v1/systemone`, namespace Bearer key,
  `model: jev-latest`, ticket as state and exact team/repeat/impact questions and
  criteria from the recipe.
- Publish an ordinary native-input leaf with no `input_transform` or leaf config.
  Invoke with the equivalent expected native object. Assert parsed HTTP request
  equality with the transformed route. Retain installed JAR origin/discovery
  assertion so this proves the dependency path, without a test replacement pack.
- Return a complete fixture containing model, answers, usage and an unknown field
  for both calls. Assert complete business results. Preserve null/scalar/string
  and malformed-success response cases in existing tests.
- For each route, provide invalid provider input that passes any ordinary receiving
  schema. For the transformed route use a test leaf whose transform produces an
  invalid request. Assert invocation failure and zero provider sends. This proves
  both paths converge on pack validation after Framework handoff.
- Affected surfaces are supported Application API usage, manifest behavior,
  provider protocol and current diagnostics. Use real Boot and local HTTP stubs.

### 4. Retired config fails through installed invocation

- Type is installed-JAR integration in `TypeSafeConsumerTest`.
- Publish a valid native-input leaf with one retired leaf key at a time, valid
  captured connection settings and valid native request input. Include old-looking
  template/binding values and usable alternate key/endpoint values. Assert an
  explicit error naming the key and zero sends to both original and alternate
  endpoint. Repeat representative null/empty cases covered exhaustively by unit
  tests. A generic arbitrary key also fails.
- Test missing/invalid namespace credentials and endpoint with empty leaf config,
  asserting no send and the executor config error path.
- Affected surface is the intentional TypeSafe Configuration and manifest break.

### 5. Parent composition and captured publication

- Type is installed-JAR integration in existing `CompositionConsumerTest` and
  `PublicationConsumerTest`.
- Strengthen the successful composition case to inspect triage's full request
  rather than discard its capture. Assert its ticket/model/questions, then assert
  assess's native state contains the selected numeric probability and its declared
  followup question. Preserve full assess-result forwarding and missing/wrong-type
  answer rejection before a second HTTP send. Preserve planner request count.
- Keep the publication test's two distinct HTTP servers, captured old and new
  namespace endpoint/key, changed payload generation, exact old retry body,
  transport identity and retirement assertions. Remove the obsolete leaf-owned
  variation. The test should keep both invocations real through the supported
  facade and installed pack.
- Affected surfaces are manifest bindings, captured configuration and lifecycle.

### 6. Migrated regression fixtures and docs evidence

- Update fixture declarations and invocation values in lifecycle, accounting,
  diagnostic-fault, Console and pack transport suites. Tests continue delegating
  through the real installed pack. Keep existing lifecycle suppliers and accounting
  assertions substantive.
- Review changed docs against the tests above and the unchanged Framework source.
  Verify generic config remains supported and Framework `input_bindings` remains
  described as child input/result selection. Update coverage anchors.
- Classify final docs/source comparison as aligned, or explicitly record and
  resolve any remaining drift. Product docs describe current behavior. Keep test
  receipts, exact hashes and optional checks accurate for their producing run.

## How to run

All commands use local stubs and test credentials. Java 21 and Maven 3.9+ are
available. Run dependent artifact operations in order against the same Maven
repository. Quote comma-containing Maven properties in PowerShell.

From `C:/opendev/code/loomspan-framework`, refresh Framework while testing its
relevant generic boundaries and supported public surface.

```powershell
./mvnw.cmd "-Dtest=LoomspanPublicSurfaceArchitectureTest,ExecutorInputTransformTest,ExecutorInputTransformIntegrationTest,ExecutorDeclarationTests,ExecutorConfigurationTests" install
```

The installed starter POM must include
`ai.loomspan.thirdparty:jslt:0.1.15-jackson3-cf30e6d`. The pinned dependency is
already locally present. If dependency resolution disproves readiness, use the
repository-owned `ai/scripts/install-jslt.ps1` bootstrap and rerun the same install.

From `C:/opendev/code/loomspan-extensions`, execute the red test before production
edits, then the full pack suite and install the resulting JAR.

```powershell
mvn -B -f extensions/decisions/pom.xml "-Dtest=TypeSafeRequestTest#nativeInputIsTheCompleteRequest" test
mvn -B validate
mvn -B -f extensions/decisions/pom.xml install
mvn -B -f extensions/decisions/examples/support-triage/pom.xml verify
mvn -B -f extensions/decisions/examples/support-triage/pom.xml -DskipTests compile exec:java
git diff --check
```

Use the actual chosen red-test method name in the first command and record it.
`install` runs the complete pack tests and packages/installs the tested artifact.
Run the installed consumer only after that succeeds. Its default Console-only
skip is expected under the explicit opt-in condition and must be reported as such.
The demo must print the captured native request, complete stub response and its
existing illustrative policy. Run `git diff --check` in Framework as well.

Optional Console-profile execution is appropriate if a change affects Console
test behavior beyond mechanical fixture migration or independent review identifies
a protocol concern. Run the documented owning command with a matching executable
and record the exact identity, without assigning old executable receipts to a new
combination. A successful ordinary suite does not claim Console-profile execution.
