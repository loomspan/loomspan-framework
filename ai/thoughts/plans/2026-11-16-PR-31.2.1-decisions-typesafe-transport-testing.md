# Decisions TypeSafe transport testing plan

## Change summary and execution context

Pipeline Step 3 continues in the Step 2 context, selected profile **full**, approved
2026-11-16. Governing implementation plan:
`2026-11-16-PR-31.2.1-decisions-typesafe-transport.md` in this directory.
Ticket: `../tickets/loomspan-pr-31.2.1-decisions-typesafe-transport.md`.
Research: `../research/2026-11-16-PR-31.2.1-decisions-typesafe-transport.md`.

New behavior lives entirely in Extensions Decisions: captured credential/endpoint
selection, shared HTTP pool and shutdown, synchronous attempts with total deadlines,
bounded retries, complete JSON success and existing diagnostic calls. Framework
behavior and Console formats do not change.

## Existing coverage and risk

Framework `VersionedExecutorInvocationTest`, `ExecutorInvocationLifecycleIntegrationTest`
and `MissionLifecycleTest` establish private construction, captured business data,
live cancellation/original execution budgets, no-deadline/zero values, ancestry,
cleanup-grace separation and late-write fencing. `ExecutorDiagnosticsIntegrationTest`,
`DefaultExecutorDiagnosticsTest` and `BoundedExecutorDiagnosticCaptureTest` establish
real containment/snapshots/bounds. `LoomspanPublicSurfaceArchitectureTest` protects
the exact API. Native `TypeSafeClientTest` demonstrates protocol/header/error body
fixtures and why inactivity timeouts cannot enforce total deadlines; its internal
cancellation hooks are not an available pack contract.

Extensions currently has no tests or implementation. Key risks are presence-vs-null
fallback, credential/endpoint cross-contamination, total-vs-inactivity deadlines,
send-after-cancel/retry races, lost interruption, hidden SDK/client retries, entity
draining, timer leaks and successful-decoding errors accidentally entering retries.
Product docs must accurately state only the transport currently implemented.

## Red test approach

This is new behavior, not a bug fix against existing pack code. The first minimal
settings/transport tests initially fail compilation because the classes do not exist;
no artificial production bug or disabled test is needed. After implementing the
smallest settings surface, run its tests, then add real-stub deadline/retry tests
before the corresponding implementation. Record actual red evidence if observed;
do not claim a pre-fix run that was not executed.

## Test harness and locations

Use `../loomspan-extensions/extensions/decisions/src/test/java/ai/loomspan/decisions/`
with settings/transport tests in the matching internal package. Use JUnit 6,
AssertJ, MockWebServer 4.12.0, Mockito for the final invocation/diagnostics only,
and Boot `ApplicationContextRunner` or ordinary Spring context for bean lifetime.
No Framework internal constructors, reflective construction hacks or internal bean
replacement. This is transport-helper proof; actual supported Framework invocation
and packaged executor are expressly owned by 31.2.2.

All classes use `*Test` names and run under Surefire during `verify`. Use real
transport/client against local sockets, no mocked HTTP responses/client. Test-only
package-private timeout/backoff policy construction shortens waits without adding
user configuration. Every spawned test thread/executor/server/context must close
in finally/try-with-resources with bounded awaits. Prefer latches/request queues
and polling state to arbitrary sleeps. Clear only test-owned interruption in teardown.

## Tests to add

### 1. Captured setting selection

**Class:** `internal/typesafe/TypeSafeSettingsTest`. **Type:** unit.
**Surface:** pack Configuration and manifest contracts.

- Table-driven combinations prove skill presence wins executor presence independently
  for `api_key` and `base_url`; fallback only on absence; missing key fails and
  default base gives `https://api.typesafe.ai/v1/systemone`.
- Present null, empty, whitespace, non-string and invalid URI values fail at the
  selected config path even when a valid lower-priority value exists.
- Absolute HTTP/HTTPS prefixes with trailing separators/encoded paths are retained;
  userinfo, query, fragment, missing host, invalid port, surrounding whitespace and
  non-HTTP schemes fail. CR/LF/control-bearing header values fail without a send.
- Literal `${VALUE}` key content is not resolved. Exact valid credentials remain
  unchanged in the settings value; no environment/reference/registry lookup.
- A resolved old settings instance remains unchanged when test-owned source maps
  are changed and a later resolution sees new values. Actual Framework captured-map
  publication proof remains existing Framework tests and the later consumer ticket.

### 2. Real route, headers, bytes and concurrent isolation

**Class:** `internal/typesafe/TypeSafeTransportTest`. **Type:** local HTTP integration.
**Surface:** provider serialized contract / internal transport.

- Two stub servers receive concurrent calls through the same transport with distinct
  prefixes/keys. Barrier/latch overlap verifies each receives only its own auth,
  path and body. Retry calls retain original resolved settings if the invocation
  mock is configured to return changed config on a second lookup.
- Verify POST, JSON content type, exact body byte arrays and exact selected bearer
  header. Test meaningful internal/leading credential spaces and separate selected
  value equality from server-side trailing optional-whitespace normalization.
- Synthetic fixtures contain text and JSON state, mixed Choice/Noul/Score criteria,
  structured instructions, unknown response fields and OpenRouter envelope additions.
  These tests establish transport fidelity, not domain-binding/validation correctness.

### 3. Retry classification and cardinality

**Class:** `internal/typesafe/TypeSafeTransportTest`. **Type:** local HTTP integration.
**Surface:** external protocol and lifecycle behavior.

- Retry 408/429/500/502/503/504/529, including HTML and malformed JSON bodies; a
  transient error then success returns complete response with exactly two sends.
- Repeated eligible errors stop at exactly three physical sends. Compare all body
  bytes byte-for-byte. Multiple success responses enqueued after a permanent error
  must remain unused. Verify 400/401/403/404 and redirects do not retry.
- A disconnected connection/request timeout can retry while live budget permits;
  no underlying Apache retry layer adds a fourth physical send. Inspect builder
  configuration/source and exercise socket failure where feasible.
- Retry-After nonnegative seconds and HTTP date are respected within 5-second cap;
  invalid/overflow/negative values do not cause unbounded waits. Use shortened
  internal test policy and timing/latch evidence for delay instead of long sleeps.
- Classification is established from status before error capture. Slow/truncated/
  unreadable error-body evidence cannot turn a permanent status transient or remove
  eligibility from a transient status, unless live cancellation/exhaustion ends work.

### 4. Bounded error evidence and complete successful JSON

**Class:** `internal/typesafe/TypeSafeTransportTest`. **Type:** local HTTP integration.
**Surface:** serialized response/current-run diagnostic evidence.

- Oversized UTF-8 error captures <=64 KiB, has complete codepoints and explicit
  truncation. A slow remainder is not drained on entity close. A read failure
  records unavailable/incomplete body evidence while retaining known status.
- Success object preserves entire envelope, unknown fields, native refusals and
  usage. Test null, quoted string, array, numbers (large integers/high precision),
  booleans and bodies larger than error/diagnostic limits. No answer semantics/schema
  are enforced; diagnostics never truncate the business result.
- Empty/whitespace/malformed/trailing-token successful bodies fail after exactly one
  send. HTTP JSON `null` succeeds and is distinct from an empty response. Parsing
  failure stays outside the retry loop. Unknown answer kinds are data, not errors.

### 5. No redirects or credential forwarding

**Class:** `internal/typesafe/TypeSafeTransportTest`. **Type:** local HTTP integration.
**Surface:** external HTTP routing boundary.

For 302 and 307 responses, primary server points `Location` at a second server.
Call the real transport with fixture credentials. Assert ordinary HTTP failure,
exactly one primary request, zero target requests and thus no target auth. Wait a
bounded interval/use target queue rather than only an instantaneous counter.
Repeat this acceptance through the actual packaged executor in 31.2.2; helper
coverage here does not finish that later requirement.

### 6. Live lifecycle and interruption

**Class:** `internal/typesafe/TypeSafeTransportLifecycleTest`. **Type:** local HTTP integration.
**Surface:** lifecycle/internal transport.

- Already canceled, interrupted or zero remaining time causes no socket request.
  Interrupt flag remains set. Empty remaining time still allows ordinary requests.
- After first retryable response and during its wait, flip invocation cancellation
  or remaining time to zero; assert no second request. Separately interrupt waiting
  thread, assert preserved flag and no later retry. Use a diagnostic latch/first
  request observation to know retry wait has begun.
- Start with a shorter remaining execution budget than pack total and delay headers;
  completion fails within that budget plus generous scheduling slack. Budget suppliers
  use a monotonic original deadline, never a new duration per accessor call.
- Shorten remaining time while a body is active; verify watchdog sees the live cap.
  A cancellation during the physical attempt also causes bounded local cleanup.
- Send continuously progressing valid JSON chunks whose full duration far exceeds
  the total deadline but whose per-chunk delays stay under inactivity timeout. Assert
  deadline failure before body completion. This is the discriminating total-time test.
- Exhaustion before retry prevents another send rather than resetting original budget.
  A pack timeout with available execution budget remains eligible for bounded retry.
- Verify no timer tasks accumulate after completed sends, and a delayed/blocked
  socket does not leave an untracked transport I/O worker after return. Stub cleanup
  observes the bounded physical close; do not assert remote inference cancellation.

Existing Framework tests cover cleanup-grace distinction, parent/shutdown ownership
and late-write fencing. This pack neither reimplements those internals nor claims
advanced actual-consumer lifetime qualification (31.3.2).

### 7. Spring construction, shutdown and architecture

**Class:** `autoconfigure/DecisionsAutoConfigurationTest` and a focused architecture
test if useful. **Type:** Spring integration / boundary test.
**Surface:** internal integration machinery, no Supported SPI.

- Load auto-configuration from its packaged registration resource and verify exactly
  one shared transport bean. Repeated operations reuse the same pool/client rather
  than clients keyed by credentials/generation.
- Context close closes transport and watchdog; second close is safe; new sends fail.
  Close during a blocked local request terminates physical work in bounded time.
  Admission/close race cannot leak a watchdog task or request.
- Production dependencies/imports include only supported Framework API, never
  internal/autoconfigure. No manifest, new supported API, provider-accounting hook,
  generation retirement callback or conditional bean-replacement contract.
- Inspect JAR contents for auto-configuration imports; resource wiring is present
  in the artifact, not only explicit test imports.

### 8. Diagnostic containment and evidence

**Class:** `internal/typesafe/TypeSafeTransportDiagnosticsTest` (or coherent methods
in transport test). **Type:** real HTTP with diagnostic fake/mock.
**Surface:** ephemeral diagnostic formats, existing bounded facility.

- Capture request/response/caught failure/retry calls and assert JSON consists of
  allowed ordinary types; preserve authored body/response content. No provider DTO
  or JsonNode is passed to diagnostic capture.
- Have diagnostics.info/warn/error throw RuntimeException independently. Successful
  business output remains identical and original HTTP/transport failure remains
  the business failure with its status/cause, never the diagnostic failure.
- Response larger than Framework diagnostic limit is returned complete. Real
  capture validation/serialization/limit/notices/logging faults are established by
  the required existing Framework diagnostics tests, not a new fake guarantee.
- Usage stays part of returned/diagnostic JSON only; source/import boundary has no
  native accounting/attempt service calls. Existing Framework accounting tests own
  generic exclusion; actual consumer qualification remains later tickets.
- Caller expression/business preparation failures remain execution failures; do
  not use these tests to broaden automatic observation containment or catch Errors.
