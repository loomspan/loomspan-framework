# Explicit-Step Planner Inability Implementation Plan

## Overview

Allow an explicit-step model to report unsuccessful completion during assigned-task action generation and final synthesis. Required work can fail after a sibling or an earlier task has succeeded. The framework owns the resulting mission status, successful-result credit, and failure identity. A standard ancestor can continue through existing failed-call feedback within its authority. The Full 5-Step Pipeline was approved against the clean PR 29.1 baseline `e8de226`.

## Current State Analysis

- `StepLoopMissionExecutionEngine.java:856–1058` owns the action loop, one bounded malformed-action correction allowance, and final-output validation. `:1175–1232` parses ordinary actions with a tolerant action binding and accepts certain bare synthesis objects. `StepAction.java:13–36` ignores unknown properties. `StepActionValidator.java:34–84` distinguishes assignment and synthesis and checks that the assigned task is `IN_PROGRESS`.
- `StepLoopMissionExecutionEngine.java:417–488,644–811` admits groups, joins submitted futures, folds outcomes in task order, and selects the first failure. Ordinary worker exceptions already become future values. Owning timeout/cancellation, exceptional joins, and cutoff cleanup have separate existing paths.

- `DefaultCapabilityInvoker.java:216–227` already records failed calls without accepted output. The `SpringAiChatClientAssembler` feedback boundary recognizes the shared subtype. `ProviderAttemptCallAdvisor.java:102–112` captures responses and charges model usage before it returns them for action processing. `DefaultSessionUsageService.java:58–69` enforces the model call and usage quotas there.

## Desired End State

Assigned model workers may return `CALL_TOOL` or `{"stepAction":"CANNOT_COMPLETE","reason":"Required information is unavailable."}`. Synthesis accepts `FINAL_RESPONSE`, its existing bare-output form, or the same closed inability action. The declaration fails the active assignment or synthesis with the exact reason. It leaves earlier successes available for diagnostics and earns no output credit of its own. A joined parallel unit folds all ordinarily returned outcomes, then propagates the authoritative cancellation if present, the earliest terminal failure in accepted task order, or the earliest recoverable failure in that order. No later unit starts after a failed unit.

## Scope Boundaries

The existing standard control and callback behavior continue to own standard execution. This work covers the Framework producer and its Java/authoring guidance. PR 29.3 owns Browser/MCP consumption and coordinated cross-component fixtures. ## Implementation Approach

Extend the existing action, failure registry, and join owners. Prompts alone cannot ensure a failed mission or prevent a failed declaration from becoming successful application output. A global strict mapper or a new general result envelope would change successful inputs/results. A separate signal store or fail-fast scheduler would duplicate authority and introduce state and interruption behavior. The chosen design adds one action and one bounded source copy, retains the current scheduler, and accepts the time and resource cost of settling admitted work under the original deadlines.

### Phase 1 — Parse and validate the declaration

1. Add `CANNOT_COMPLETE` to `StepActionType` and a typed reason to the internal `StepAction` with a declaration factory. Keep that reason out of ordinary action binding (for example, `@JsonIgnore` on the dedicated component). An unrelated `reason` property of any shape on an ordinary action was previously ignored, and a reason-only bare synthesis object remains ordinary output. Update direct internal record constructor calls in tests without an overload.
2. In `StepLoopMissionExecutionEngine.parseStepAction`, inspect each original top-level `stepAction` before whole-action binding can discard duplicate values. If any value would bind to inability, read the same candidate with a locally strict tree reader enabling duplicate-key and trailing-token rejection. Require an object of exactly two fields, the exact textual `CANNOT_COMPLETE` value, and a textual nonblank `reason`. Preserve the decoded reason unchanged. Use the existing `ParsedStepAction`/`StepActionCorrection.Failure` path for any rejection. Keep the ordinary binding and bare final detection semantics intact. Leave the original model text untouched in the calling method for recording.
3. Update `StepActionValidator` so assigned declarations still pass through the trusted assignment status check before bypassing tool identity/argument validation. Preserve existing checks for ordinary calls. Synthesis still requires the completed task state, and a declaration needs no final output payload. A worker's rejection guidance offers its assigned call or the two-field declaration. Synthesis rejection guidance offers final output or the same declaration. Use the same choices in `StepPromptBuilder` and `StepActionCorrection`. Keep task/tool identity and argument language conditional on `CALL_TOOL` in the correction prompt.
