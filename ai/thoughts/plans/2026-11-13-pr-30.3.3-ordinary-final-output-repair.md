## Implementation Approach and settled decisions

1. Reuse Spring's single tool loop and immutable request/context maps. Allocate a holder for each non-planning interaction call. The ordinary validator chain activates final repair; production step execution filters those validators and retains its existing policy. Pass the same holder reference in advisor parameters and tool context. Do not put it on cached clients, managers, sessions or thread locals. Nested calls allocate independent holders, even on the same thread.
2. Holder stores completed appended Message objects in order, latest raw accepted AssistantMessage, and a terminal repair flag. Capture appended history only after successful manager delegate execution, using the input prompt's history prefix boundary. Accumulate appended exchanges across normal tool rounds, never baseline/candidate/feedback. Reject a nonconforming history boundary explicitly rather than summarizing/reconstructing protocol messages. Preserve returned object parts, metadata and tool/result associations.
3. Capture raw output at ProviderAttempt's successful returned-response boundary, after status acceptance and existing accounting; do not add attempts/accounting. Tool-call replies may be overwritten by subsequent final raw replies. Schema composition cannot overwrite this raw holder value. Error/retry paths keep existing owners.
4. Provide one internal final-repair request helper used by all three advisors. The helper requires the ordinary call's holder, sets terminal repair, and copies typed ToolCallingChatOptions to clear callbacks/names and any executable provider-native declaration surface while retaining native formatting/caps/effort, context and other settings. Establish exact SDK APIs/default override semantics with serialized tests; never assume null/empty means the same thing. Preserve tool context carrying the flag. Do not disable the tool-loop guard itself: a provider ignoring tool omission must still reach the canonical prohibition.
5. Track the inserted replay segment explicitly in each request's context, with holder ownership and a bounded start/count (or equally explicit immutable descriptor). The shared mutable holder does not own one global segment index: upstream/downstream advisors can hold different request versions. Before rebuilding, remove only that request's recorded replay span. Validate ownership/bounds; do not infer spans by message text or role. Replay is completed exchanges plus latest raw candidate. Keep correction feedback independently owned so existing advisor policies survive.
6. Schema rebuilds from its augmented entry baseline on every correction, strips inherited replay ownership, inserts current replay and one new UserMessage with its existing feedback. Repeated schema repairs discard their own stale candidate/feedback. Linter/evidence strip replay from their current request, append their existing system hint, then insert current replay; accumulated feedback remains. Propagate the new descriptor with the rebuilt request. Nested advisor chains therefore replace replay once without deleting baseline instructions/media or applicable outer feedback.
7. Canonical manager checks the call-local terminal flag before any delegate execution, including mixed/multi-call responses, defaults and planner control selections. Fail through existing runtime failure propagation; no special recovery loop. Preserve normal provider-status and canonical authorization/argument validation outside final repair.
8. Migrate direct ChatClient/mock-chain fixtures to explicitly supply state and raw-capture behavior. Do not add production fallback from composed text or a second loop merely to keep old internal tests unchanged. Unit fixtures may explicitly publish their raw scripted reply; real integration evidence must use ProviderAttempt.

Exact internal class/member names are ordinary implementation choices. The contract above, segment ownership and raw-versus-composed boundaries are fixed. No unresolved product question remains.
