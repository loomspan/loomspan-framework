## Desired behavior

For an `orders:lookup` catalog item, each summary and detail result contains the following values.

```json
{"registeredName":"orders:lookup","namespace":"orders","localName":"lookup"}
```

An `order-support:lookup` item has the same `localName` and its own `namespace` and `registeredName`. Exact catalog lookup, sorting, cursors and links distinguish the pair. Detail results expose components reusable by embedded Framework callers. `registeredName` remains the Console's documented qualified lookup key.

The Go validator accepts the same component and pair grammar as Framework. Captures require the entry identity's namespace to equal `entryNamespace`, the entry generation to agree with `namespaceGenerationIds`, and every captured namespace to satisfy component validation. A 64-character namespace may describe an installed empty namespace. A skill pair still satisfies `len(namespace) + 2 + len(localName) <= 64`.

Raw provider content retains `order-support--find-order` and the exact supplied arguments. Resolved tool metadata, `skillName`, catalog labels, plans and worker assignments use `order-support:find-order`. Trace correlations and display links use recorded resolved fields. Operation routes, task IDs, source labels, Java method strings and ordinary diagnostic data retain their own meaning.

## Design choices

### Catalog identity authority

Use the retained `CapabilityMetadata.identity()` components when constructing the registered catalog. Give internal `RegisteredSkillEntry` and its `Summary` validated `namespace` and `localName` components and derive `registeredName()` from them. Keep one internal identity authority. Update all direct constructors and consumers in place.

Serialized Java summary/detail records carry `registeredName`, `namespace` and `localName` explicitly. Validate the components using `SkillIdentity` and require exact agreement with `registeredName`. The mapper obtains every value from the same validated catalog entry. Continue validating source-specific provenance through the existing location rules. Executor-backed YAML still exposes its resolved, colon-qualified `executorName` and exact implementation/source fields.

Go observation DTOs, compact MCP DTOs and TypeScript contracts require all three identity fields. `validateSkillSummary` verifies the component grammar, pair length and exact qualified equality. `validateSkillDetail` carries those fields into summary validation and requires the returned name to equal the requested resource. MCP full schemas require the fields, and deterministic text fallback includes them. Source-specific optional/forbidden fields and nullable `outputSchema` retain their existing validation.

Keep catalog input and navigation based on the returned exact `registeredName`. Invalid or missing resource lookups terminate at the existing one lookup. The identity validation belongs to parsed catalog results and captured runtime facts. Opaque diagnostic text and trace filters retain exact-value semantics.

### Go identity validation

Replace the obsolete patterns in the existing `skillidentity` package with a shared exact component check. Enforce full lowercase ASCII grammar, 1–64 characters and reserved substrings for both components. Add the smallest shared pair validation needed by catalog and capture callers. For qualified parsing, require exactly one colon, valid nonempty components and the combined two-character provider limit. Capture validation compares the parsed namespace with the explicit entry owner and validates its entire captured generation map.

Keep `ValidNamespace` usable for publication/map owners and `ValidOwner` usable for optional executing-owner facts. Existing call sites should use those authorities directly. This package validates semantic identity fields. It must not interpret or rewrite raw provider names, model content, diagnostic JSON or source labels.
