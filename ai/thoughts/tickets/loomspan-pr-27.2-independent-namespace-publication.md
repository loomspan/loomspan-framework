# PR 27.2 — Publish and retire namespaces independently with concurrent preparation

## Outcome

Replace global publication with complete atomic namespace publication, preserving simple embedded startup and API-managed deployments while allowing detached candidates to prepare concurrently.

## Requirements

- Maintain one active immutable generation per canonical namespace, including complete supplied declarations, publishable execution configuration, fixed Java registrations assigned to it, and visibility. Every publication defaults to Private; Public must be explicit even on replacement. Visibility changes are ordinary publications.
- Namespace-targeted validation/preparation takes the namespace once, complete documents/configuration, and applicable existing credential inputs. Remove incomplete-publication overloads. Keep `publish(candidate)` with no separate target/revision arguments, `snapshot(namespace)`, and framework-wide `onGenerationRetired(...)`; removal takes namespace and expected active generation ID. Parameter order and visibility payload representation remain planning decisions, not reasons to add facades or a new revision type.
- Capture the target's base generation ID or strict absence exactly once under registry synchronization before expensive preparation, alongside a coherent external metadata view. The caller supplies no preparation revision. Candidate ID is a newly allocated, globally unique, never-reused opaque ID, including across removal/recreation. Null internal base means absent, never wildcard; add no public base accessor or tombstones.
- Prepare validates every candidate skill, all references/visibility, and applicable contracts against that coherent view. Resolve any reference into the candidate namespace against the candidate, including transitive return paths; never fall back to omitted skills in its old generation. Reuse contract resolution/validation. Preparation rejects detected errors rather than warning or deferring them all to admission. Do not scan incoming callers.
- Audit what validation reads. Immutable independently usable metadata needs no executable ownership; retirement-sensitive resources require existing temporary leases for their use. Release temporary ownership on all outcomes, without retaining dependencies through unrelated provider initialization or the candidate's wait for publication.
- Publication checks only target base/absence, framework ownership, candidate one-shot/closed state, and lifecycle, then atomically activates. External dependency revision changes, deletion, visibility changes, or recreation do not make a candidate stale. Do not revalidate dependencies, retry automatically, or maintain dependency revision preconditions at publication. Absence candidates may publish if the target is absent again; no history-of-absence contract.
- Remove the whole-preparation lock in `DefaultSkillReloader`; same-target and different-target preparations build detached candidates concurrently. No per-namespace preparation locks, queue, scheduler, throttling, fairness feature, or new transaction abstraction. Preserve narrow fixed-registration initialization, lifecycle, and candidate synchronization. Mutable catalogs, manifests, diagnostics, derived metadata, configuration, and credential inputs must be candidate-local.
- Registry capture, lease acquisition, publication, and removal share a synchronization boundary. Expensive validation/construction, resource closing, and retirement callbacks stay outside it. Preserve lifecycle checks before preparation, after construction, and at publication; cleanup a candidate rejected by the post-construction check. Do not promise forcible interruption of slow preparation.
- Reuse independent generation-owned runtimes and provider registries. Each candidate owns its resources until publication transfers ownership. Failure, abandonment, stale rejection, retirement, removal, and shutdown close only the appropriate resources once, respecting retained physical-work ownership. Preserve retirement callback isolation and existing delivery limitations, including no replay/order/retry guarantee and possible shutdown omission.
- Reuse strict `ExecutionConfigurationParser`: publish connections, models, session settings, and execution-trace persistence only. Reject host-only shutdown, startup locations, observability, other application settings, and unknown keys. A configuration document is required; supported omitted scalars use built-in defaults. No inheritance of previous/startup/other-namespace settings, models, or connections; retain explicit credential-reference resolution. Publications cannot change host configuration.
- Startup creates Private `default` containing startup declarations plus assigned Java methods, and Private namespaces for other Java assignments containing only their assigned methods. All use the same existing startup configuration values but separate runtimes. Same-namespace qualified startup composition works without publication; foreign Private targets fail ordinary validation. No visibility annotation, activation API, dependency-aware bootstrap coordinator, or per-namespace startup settings.
- Fixed Java registrations retain existing Spring lifecycle/binding/RBAC and are included in every generation of their assigned namespace. Publications cannot omit, override, relocate, copy, or reconfigure them; declaration collisions fail. Java bean state remains host-owned, not historically snapshotted. Managed hosts can publish Public shared Java capabilities then API-populate callers without local skill/configuration files. Departmental publication retains assigned fixed methods.
- Removal verifies expected active revision, withdraws atomically, and returns without drainage; retained work continues and cleanup occurs outside synchronization when eligible. Apply equally to `default` and Java namespaces, without destroying beans or implicit lookup-driven recreation. Explicit recreation retains fixed registrations and allocates a fresh ID. Restart rebuilds Private startup state; runtime publications/removals are not restored.
- Cyclic cross-namespace dependencies use valid staged complete publications (initial a, b referencing a, then replacement a referencing b), with Public targets and existing contract/cycle rules. No transactions, unresolved references, automatic stubs, cascading updates, or reverse-dependency subsystem.
- Complete replacement removes omitted supplied declarations; retaining fixed Java registrations is not merging prior supplied content. Empty supplied declarations are valid when existing validation permits them, including a self-identifying empty published namespace without assigned Java methods. No partial patching, unconditional create-or-replace, separate visibility-update operation, `SkillReloader.inNamespace(...)`, or separate revision counter/catalog revision. Each visibility change creates a new generation.
- The exact publishable keys are `loomspan.connections`, `loomspan.models`, `loomspan.session`, and `loomspan.execution-trace.persistence`. Preserve their existing nested fields and validation, including provider options, timeouts, retries, credentials, quotas, depth, mission timeouts, and attachments. Reject `loomspan.shutdown`, `loomspan.skills`, `loomspan.observability`, and other unsupported keys during validation/preparation rather than ignoring them. Reuse the existing `ExecutionConfiguration` document and parser; add no public configuration type, second parser, configurable boundary, or host fallback. For example, replacing a scalar value 100 with an omitted value whose built-in default is 64 yields 64.
- Namespaces are generic definition/configuration/visibility boundaries, not complete tenant isolation. Hosts authorize management/publication and external routing. No reserved shared/Public namespace, cross-namespace enablement switch, prescribed publisher role, namespace-specific Spring container, or separate embedded/managed runtime modes. Managed hosts own readiness and publication sequencing, including repeating publication after restart.
- Java discovery retains existing argument binding, result serialization, security-context propagation, and method RBAC. Annotation changes require rebuild/redeployment; publication does not load Java code or introduce a publisher-controlled binding manifest, per-namespace bean lifecycle, or inactive-registration state. Assigned Java methods are immediately available to host-authorized direct entry after startup; Public publication is needed for foreign callers, not activation. Startup foreign callers must be supplied later through publication, not deferred or exempted from Private validation.
- Generation IDs are process-local opaque revision strings, not durable restoration identifiers, and do not encode skill identity. Reuse the manager-prefix/counter approach or an equally unambiguous generator; allocation order need not match publication order. Retain callback concurrency and listener-failure isolation without a durable-delivery guarantee.
- Use a fresh mutable `YamlSkillCatalog` for every preparation, including internal suppliers and test fixtures. Reuse only safely initialized immutable fixed-registration metadata. Do not preserve old configuration inheritance by adding locks around legacy active-settings reads. The candidate overlay is one target-local resolution rule, not a staging registry or general multi-candidate overlay engine.
- Removal rejects missing targets or wrong expected active IDs, marks the withdrawn generation superseded for retirement, and invalidates candidates based on it. It does not cancel retained work, cascade into dependents, unload Java bindings/beans, or add a removal-specific shutdown/drain workflow. Public-to-Private changes are likewise prospective; dependent publications remain installed.
- In the staged cycle, initial a must already contain the skill/contract that b will call, without its reference to b. All intermediate versions are real, valid, callable publications; both cross-namespace targets must be Public. If valid intermediate versions cannot be supplied, the sequence is unsupported. Cycle traversal must not suppress edge validation or override existing schema-cycle, recursion, or execution limits.

## Acceptance criteria

- [ ] Replacement changes only its target; omission resets visibility to Private and supported settings to built-in defaults. Missing required models/connections and host/unknown configuration keys fail; host settings stay unchanged.
- [ ] Captured-base behavior distinguishes edits before versus after capture, candidate versus base IDs, competing creation/replacement, absence-again semantics, stale removal/recreation, foreign/closed/published candidates, and unrelated namespace changes. Dependency changes alone do not block publication.
- [ ] Candidate-local overlay covers changed local contracts, transitive return paths, omitted old skills, and a stable external view during concurrent publication; invalid outgoing dependencies still reject preparation. Temporary ownership is released safely.
- [ ] Latches/barriers with bounded waits prove another same-target and different-target preparation progresses while one is blocked, with snapshot reads and unrelated publication also progressing. Replace the old serialization test; do not use sleep/throughput assertions as the proof.
- [ ] Concurrent distinct candidates, including invalid and valid peers, isolate configuration, credentials, definitions, diagnostics, derived metadata, resources, and IDs. Same-base publication races have one winner; different namespaces both publish. Safe completed fixed Java/REST initialization is reused without invoking application skill implementations during preparation.
- [ ] Construction failure, abandonment, stale rejection, shutdown during blocked construction, and failed post-construction checks preserve one-shot cleanup and never close another candidate or active/retained generation. No candidate publishes after shutdown.
- [ ] Embedded, managed-without-local-files, departmental, and restart scenarios obey Private startup and fixed-registration rules; staged cycles work without relaxing existing contract validation. Removal/recreation of default and Java namespaces preserves the agreed availability/bean lifecycle.
- [ ] Namespace catalogs and management APIs implement PR 27.1 contracts; README examples and supported-surface tests cover the new API and `LoomspanPublicSurfaceArchitectureTest` is run.
- [ ] Omitted supplied skills disappear, fixed Java skills remain, and an empty namespace without fixed methods can publish and yield a self-identifying catalog. Management boundaries normalize namespace case and independently enforce 32/33-character limits. Required configuration cannot be omitted and complete replacement has no host fallback or second configuration system.
- [ ] A read of generation 1 followed by another publisher's generation 2 and then preparation captures 2 and can replace it; a change after capture fails without base refresh. Same-target creation and replacement races each have exactly one winner when the target stays present, the loser is stale, and loser cleanup preserves the winner. Absence-again behavior remains explicitly distinct.
- [ ] Metadata capture racing publication/removal yields a coherent view; any temporary validation leases survive retirement and are released after use. Shutdown between the final preparation check and publication rejects the candidate. Replace `SkillReloaderTest.preparationsSerializeWithoutBlockingSnapshots` with the specified deterministic concurrency coverage.
- [ ] Missing/wrong-revision removal fails, withdrawing default does not trigger lookup-based recreation, retained Java bindings/beans survive withdrawal, and explicit recreation includes the fixed methods. Startup direct Java entry needs no activation publication; foreign startup references fail even for Java targets. API/docs introduce none of the excluded management, registration, or startup mechanisms.

Do not postpone substantive preparation checks until runtime work or build three policy implementations.
