# Loomspan 1.0.0-beta.5-SNAPSHOT compatibility notes

This note describes the application-facing changes from beta 3 to beta 4. It
does not assert release readiness: the Sidecar SC5 snapshot-integration gate,
final release-commit checks, workflow validation, tagging, and publication are
tracked separately and remain required.

## Added supported surface

Beta 4 adds the public `SkillCatalog`, `SkillDescriptor`, and `SkillKind` API
types for an eager, immutable, exact-name-sorted, unfiltered startup catalog.
Descriptors expose the registered name, description, kind, and exact JSON input
schema. Catalog discovery is not authorization and is not a framework-bean
replacement contract.

Beta 4 also adds atomic external invocation handoff through the public
`SkillInvocationHandoff` and single-use `AdmittedSkillInvocation` types. A
handoff prepares input, captures authentication, and reserves one framework root
without starting execution. The handle may execute once on an application worker
or be released idempotently; framework cutoff invalidates abandoned pending
handles. Execution retains the existing authorization, result, exception,
observation, nested-work, and security-context-restoration behavior and uses the
same shutdown budget.

Beta 4 also adds application-handled REST leaf skills and the public
`RestSkillHandler` and `RestSkillInvocation` types. `RestSkillHandler` is the
only supported Loomspan SPI. The supported Java surface remains the closed
fifteen-type `ai.loomspan.api` allowlist enforced by
`LoomspanPublicSurfaceArchitectureTest`; public types under `internal` or
`autoconfigure` are not application extension API.

## Required application migration

`SkillTemplate` now declares both `validate(String, Map<String,Object>)` and
`validate(String, Object)`. This is an intentional source- and binary-sensitive
interface change. Custom implementations, fakes, and hand-written mocks must
implement both methods and applications must recompile. There is no default-
method shim or dual beta 3 mode.

Observers now receive at most one available completed public view after a
post-session failure as well as after success. Pre-session rejection produces
no callback. If execution fails, mapping or observer failures are suppressed
behind the original execution failure; an observer failure after successful
execution still propagates unchanged. Applications should make observer
handling idempotent and apply the same security and retention policy to success
and failure history. There is no success-only compatibility mode and no new
comprehensive sanitization guarantee for inputs, results, errors, or history.

Shutdown now rejects new roots as closing begins and applies one positive
`loomspan.shutdown.timeout` budget, defaulting to `30s`, across admitted root
execution, continuing nested work, trace finalization, available observation,
cutoff, and framework executor cleanup. Framework-owned resources remain alive
until completion or cutoff; uncooperative work is fenced and interrupted at
cutoff. Loomspan does not bound unrelated application hooks or halt the JVM,
and there is no old-admission compatibility mode.

## REST manifest and handler migration

A REST leaf requires nonblank `name`, nonblank `description`, and Boolean
`rest: true`; `input_schema` and `rbac_roles` are optional. With no schema, the
generic object contract applies. The following fields must be absent, including
null or empty presence: `model`, `prompt`, `thinking_level`, `allowed_skills`,
`planning_mode`, `concurrency`, `max_steps`, `linter`, `output_schema`, and
`output_schema_max_retries`.

REST skills share the exact-name registry, input/reference processing,
root/nested authorization, direct lifecycle, and success-only child credit.
When any REST manifest exists, startup requires exactly one application
`RestSkillHandler`; Loomspan provides no default. With no REST manifests,
handler beans are unused and do not trigger cardinality validation.

The handler owns routing, URLs, headers, credentials, retries, and response
mapping. It receives one `RestSkillInvocation` containing the exact skill name
and a recursively immutable map/list snapshot after validation and reference
resolution. Null values and non-container leaf identity, including Spring
`Resource` handles, are preserved; resource contents are outside the
immutability promise. Caller authentication is available through the scoped
`SecurityContextHolder`, not an identity or session SPI argument.

One handler call returns text unchanged. Empty text succeeds; null fails.
Authorization and existing `SkillException` boundaries are retained, other
runtime failures become safe facade failures, and JVM `Error` is not caught.
REST failures propagate through the facade rather than using the annotation-
defined Java skill exception-to-text adapter.

## Console diagnostic compatibility

REST is a semantic expansion of the framework-to-Console diagnostic protocol.
The coordinated framework/Console project version remains the compatibility
marker because the framework owns the complete diagnostic semantics. Resolved
releases require exact matching versions and reject missing or unequal markers.
Two `development` markers may attempt ordinary complete validation for local
development, without a compatibility promise.

Beta 4 introduces no separate schema counter, range negotiation, legacy reader,
version adapter, dual record format, or historical/cross-version readability
guarantee. Use matching beta 4 framework and Console versions for diagnostic
artifacts.
